마지막 갱신: 2026-09-05 (첫 세션 — 정적 분석만으로 문자표·글꼴·대본까지 확정).

## 한 줄 요약

**대본이 손에 들어왔고 되쓸 수도 있다.** 포인터 표 4벌(2,906 + 90 + 343 + 19건)이 가리키는 문안을 전부
덤프했고(main 글자 171,580B), 문자표는 코드→타일 표와 글꼴 시트에서 **읽어서** 확정했다. 본체
`$07:A721~$0B:FE75`(153,429B)를 **라벨로 풀어 오프셋을 다시 계산해 되쓰면 바이트가 같다**(`script.py`) —
옮겨 쓰는 재삽입의 첫 게이트가 서 있다.
**한자가 없는 가나 전용 8×16 글꼴**이라 한글을 어느 칸에 넣을지가 첫 설계 판단이다 — 예산은 쟀다
(6절): 고유 음절 수요 1,010 ↔ 고정 슬롯 207코드·480타일이라 **어느 칸이든 동적 글리프 적재가
필수**, 빈 공간 29KB 라 **롬 확장(2MB)이 필요**하다. 판단 요청은 7절. **디버거·에뮬이 이 머신에
없어**(Mesen2 미설치, mednafen 은 맥) 인게임 확인은 아직 하나도 못 했다.

## 확정된 것

### 1. 원본 — 8Mbit LoROM, 체크섬 정상

`originals/jp/sfc-ed1/*.zip` 안의 `.sfc` 1,048,576B(복사기 헤더 없음). 지문·상수는
[`tools/common.py`](../tools/common.py).

| 항목        | 값                                                  |
| ----------- | --------------------------------------------------- |
| 내부 헤더   | `$00:FFC0` 「DRAGON SLAYER LEGEND1」 map $20 type $02 |
| SRAM        | 2KB                                                 |
| 체크섬      | $E7B9 (보수 $1846) — 계산값과 일치                  |
| RESET       | `$00:8209`(에뮬 모드), NMI `$00:A9DC`                |

### 2. 코드 지도 — 롬에 RCS 태그가 박혀 있다

모듈마다 `$Header: <파일>.asm,v …$` 문자열이 남아 있다(1991-10 빌드, 저자 shino·yasu·abe).

`$18:E02C~` **글꼴** · `$1F` 그래픽.

### 3. 문자 체계 — 가나 전용 1바이트, 8×16 글꼴, 창 17칸×4줄

정본은 [`tools/text.py`](../tools/text.py) 의 `TABLE`. 근거는 `message.asm` 디스어셈블 +
글자→타일 표 + 글꼴 시트(코드 순서로 글리프를 늘어놓아 읽었다 — devlog).

- **글자 코드 `$00~$CE`**: `$00~$09` 숫자 · `$0B` ー · `$0C` ! · `$0F` ? · `$10` 공백 · `$11~$3E`
  あ~ん · `$3F~$6C` ア~ン · `$6D~$6F` ゃゅょ · `$71~$7F` 작은 가나 · `$83~$86` 。、「」 ·
  `$87~$8F` H M E P G O L D C(HP·MP·LV·GOLD 용) · `$90~$C2` 탁음·반탁음 · `$C3~$C4` A B ·
  `$CF` **개행**. ⚠ `$0E`·`$70`·`$7A`·`$8C`·`$C5~$CE` 는 타일이 시트 밖($1B9~$1BB·$1D6~$1DF)이라
  모양을 아직 못 봤다(`$8C` 는 GOLD 문맥으로 O).
- **글자 → VRAM 타일**: `$03:F3EC` 표(2B × $D0: 타일 번호 하위 + 속성|번호 상위 2비트).
  그리기(`window.asm $02:B07B`)는 위 타일 t · 아래 타일 t+$10 을 쓴다 ⇒ **글자 하나 = 8×16**.
  `$10` 만 위아래 같은 타일(=빈 칸). 속성 바이트 `$04`/`$0C` 가 색(팔레트)이다.
- **글꼴 시트**: `$18:E02C` 부터 1bpp 8×8 타일, 16타일/행(타일 t = 시트 + 8t). 타일 $001~$00A 가
  0~9, $040~ 부터 가나 윗부분·$050~ 아랫부분이 번갈아 온다. 시트 밖 타일(위)은 다른 자리다.
- **창**: 줄 버퍼 `$0305`(글자)·`$0349`(속성) 각 $44B = **17칸 × 4줄**, 개행은 다음 17 경계로,
  4줄이 차면 한 줄씩 밀어 올린다. 자동 줄바꿈은 없다(대본의 `$CF` 가 정한다).

### 4. 대본 — 평문, 3B 포인터 표 4벌, 사전 치환 + 스크립트 제어

- **포인터 표**(24비트 LoROM 주소, 어느 표를 쓰는지는 `$060C` 상위 비트): `$07:8000` main
  **2,906**건(뱅크 $05 71 · $07 296 · $08 797 · $09 646 · $0A 568 · $0B 498 · $1E 30) ·
  `$07:A20E` alt1 90 · `$07:A31C` alt2 343 · `$0B:E8AB` alt3 19. 세 표가 등을 맞대고 `$07:A721` 에서
  끝나며 **거기서 대본 본체가 시작**한다(첫 세션엔 스캔이 뒤 표까지 이어 읽어 3,339 로 잘못 쟀다).
  인덱스 = `$060B` + (`$060C` & $1F)<<8.
- **본체 구간 `$07:A721~$0B:FE75` = 153,429B, 항목 140,781개**가 빈틈없이 이어진다(글자 1B · 사전 2B ·
  제어 1B+인자). 참조 2,177건 중 2,170 이 항목 시작을 가리키고, 나머지는 구간 밖(`$1E` 절대 호출 2)과
  `$FD` 의 죽은 슬롯 5 다(`script.py --roundtrip`). 뱅크 `$05`(9,358B)·`$1E`(15,822B)는 코드와 섞여 있어
  포인터 목표에서 END 까지만 문안이다.
- **사전**(`$Dx idx`, 2B 포인터 표, 항목은 $FF 종료): `$D0` 인명 89 · `$D1` 지명 48 · `$D2` 아이템
  119 · `$D3` 몬스터 97 · `$D4` 마법 21 · `$D5` 시스템 문장 53. `$D0 8x` 는 항목 x&$F 를 강조색으로.
  `$D6~$DF` 는 인자 없이 런타임 값(파티원 이름 등)을 꽂는다 — 뜻은 인게임에서 못 박는다.
- **제어**(디스패치 표 `$02:E248` 로 핸들러를 맞췄고, 게임의 건너뛰기 표 `$02:E4E0` 과 인자 수가 전부
  일치한다): `$E0`·`$E4` 끝 · `$E1` 색 복원 · `$E2`/`$E3` 색 · `$E5 n` 효과음? · `$E6~$ED n` 플래그 set/clear ·
  `$EE addr24` **네이티브 코드 호출**(`jml`) · `$EF` 창 지움 · `$F0~$F3 flag` 플래그가 서 있으면 다음 항목
  하나 · `$F4~$F7 flag` 꺼져 있으면 다음 항목 · `$F8 n` 화자 슬롯 · `$F9 addr24` **절대 호출** ·
  `$FA rel16` **점프**(제어 바이트 기준, 뱅크 안 16비트) · `$FB o0..o4` 파티 인덱스로 고르는 8비트 점프 ·
  `$FC rel16` **호출**(복귀 +3) · `$FD o0..o4` 인덱스 호출(복귀 +6) · `$FE` 호출 복귀 · `$FF` 키 대기 + 페이지.
  ⚠ 「항목」= 글자 1B · 사전 2B · 제어 1B+인자. 조건이 가리키는 건 항목 하나뿐이다.
  ⚠ `$FB/$FD` 의 슬롯은 **고정 5개가 아니다** — 저작 시 필요한 만큼만 두고, 바로 다음 바이트가 다른
  항목(포인터 목표)일 수 있다(`$0A:80D0` 실측: 슬롯 0개). 파서는 앵커(포인터·분기 목표)에서 자르고
  앵커가 늘지 않을 때까지 되풀이한다(`script.py parse_region`).
- **덤프 실측**: main 2,906건 첫 조각 글자 171,580B(제어·사전 인자 제외).
  ⚠ 「포인터 구간 = 메시지 하나」가 아니다 — 분기 갈래가 같은 구간에 END 로 잘려 여럿 들어 있다.

### 5. 에뮬 — 실행은 되고 디버거는 없다

`sh scripts/emu.sh sfc-ed1` 은 mednafen snes 로 뜬다(zip 째). emucap 의 mednafen 빌드에는 SNES 가
없고(`--enable-snes` 없음, 있어도 디버거 없음), **Mesen2 어댑터는 .NET SDK 가 필요해 이 머신엔
못 깔았다.** 브레이크포인트·RAM 확인은 전부 미실시.

### 6. 예산 실측 — 한글 설계의 숫자 (정적, 2026-09-05)

| 항목 | 값 | 근거 |
| --- | --- | --- |
| 글자 셀 | **8×16**(위·아래 8×8 타일) | `window.asm $02:B07B`, 타일 표 `$03:F3EC` |
| 대사창 | 창 틀 19×10 타일(row 17, col 1) · 본문 **17칸 × 4줄** | 창 배치 표 `$03:BD54` 항목 $12 · 줄 버퍼 `$0305` $44B |
| 글꼴 적재 | `$00:91F5`: `$18:E02C+X` 에서 **512B(64타일)씩** WRAM `$7F:C78A` 로 펴서(1bpp→2bpp, 2번 평면은 미리 채운 $FF) DMA → VRAM 워드 `$1000 + 8·타일`. 호출은 `$00:9177~$00:9198` 의 **여섯 청크 = 타일 $000~$17F 뿐**. **한 번 올리고 끝** | sub.asm 디스어셈블 |
| 타일 공간 | 텍스트 타일은 $000~$17F(384). $180 이상은 다른 코드가 올리는 **2bpp 그래픽**(상태 라벨 한자 등, `$18:EC2C~`) — 시트 $18:E02C~$18:EC2C 는 1bpp 384타일이 전부 | 업로드 호출자 + 시트 렌더 |
| 코드 공간 | 1바이트 `$00~$CE` = **207** | 3절 |
| 상주 타일 | 시트 `$000~$1DF` = **480타일**(글자 240자분) + 시트 밖 소수 | 타일 표 최대값 |
| 활성 집합 상한 | 창 68칸 → 8×16 이면 **68자**, 16×16 이면 **34자** 동시 표시 | 17×4 |
| 한글 총 레퍼토리 수요 | **고유 음절 1,010**(ED1 번역본 145,431자 기준 — PS1 트랙 `script/ED1SCN*.json`) · 상위 800 = 99.6% | 실측 |
| 원문 분량 | 171,580 글자 바이트(main 표 첫 조각) · 본체 153,429B | 4절 |
| 롬 빈 공간 | **29.0KB**(256B 이상 $FF/$00 런 53개, 최대 2.2KB `$1A:F76E`) | 스캔 |
| 롬 확장 | LoROM 1MB → 2MB(뱅크 `$20~$3F`)는 매퍼 규격 안. 헤더 rom 바이트·체크섬 갱신 필요, 실기 배포 대상(플래시 카트)에서 확인 필요 | 플랫폼 규격 |

읽는 법:
- **고정 슬롯으로는 못 간다.** 207코드·480타일 대 수요 1,010이라 어느 칸을 골라도 **동적 글리프
  적재**(창에 나올 글자만 VRAM 에 올리는 코드)가 필요하다. 활성 상한(34/68)은 한 창 분량으로 넉넉하다 —
  병목은 활성 집합이 아니라 **총 레퍼토리 ↔ 코드 공간**이다 ⇒ 롬 안 문안은 **2바이트 코드**(또는
  사전+1바이트 혼합)가 된다.
- **2바이트가 되면 문안이 는다.** 171,580 가나 → 한글은 글자 수가 줄어도(대략 0.6~0.7배) 바이트는
  1.2~1.4배. 빈 공간 29KB 로는 어림없고 **포인터 표 4벌 + 분기 오프셋을 전부 다시 쓰는 재삽입**이
  전제다(스크립트 안 분기 `$F9/$FA/$FB/$FC` 재계산기 포함). 롬 확장이 거의 확실하다.
- 글꼴 적재가 「한 번」이라 동적 적재는 **새 코드**다 — 글자 놓기(`$02:DE85`)나 페이지 넘김(`$FF`)에
  훅을 걸어 WRAM 스테이징 → NMI DMA 큐(`$1022~$1028`, `jsl $00:95BB`)에 태우는 길이 보인다.
  ⚠ NMI 큐 용량·블랭크 예산은 실기/에뮬로 재야 한다(플랫폼 문서 4절).

### 7. 결정 D1 「한글 칸」 — A 채택 (2026-09-05)

| 필드 | 내용 |
| --- | --- |
| question | 8×16 반각 가나 창(17칸×4줄)에 한글을 **어느 칸**으로 넣나. 칸이 정해져야 글꼴 제작·동적 적재 설계·문안 압축률이 정해진다 |
| scope | sfc-ed1 대사창(`message.asm` 경로). 메뉴·전투·상태창의 8×8/8×16 라벨은 별도 경로라 이 결정 밖 |
| values | 가독성 vs 원문 정보량 보존 vs 구현·검증 비용(창 재설계는 mod 급) |
| A. 16×16 두 칸 | 줄당 **8자·4줄 32자**(원문 17가나 ≈ 한글 10~11자라 **줄이 모자란다** — 페이지 수가 1.5~2배). 글꼴은 기존 자산(Galmuri 계열 16×16) 재사용. 구현: 글자 놓기 훅 + 타일 4장/자 동적 적재. 창 코드는 그대로 |
| B. 8×16 반각 한글 | 17칸 유지 → 원문 분량 그대로 들어간다. 글꼴은 **새로 그려야** 한다(8px 폭 조합형 한글은 가독성 한계 — 초성·종성 두 줄 구조라 16px 높이에 8px 폭은 획이 뭉친다). 시각 판단이 필요해 **PoC 렌더 샘플을 먼저 봐야** 한다 |
| C. 창을 넓히는 mod | 12×12 또는 16×16 으로 25~30칸 창을 새로 만든다. 가독성·분량 다 잡지만 창 배치 표·타일맵·NMI 예산을 새로 쓰는 **mod 트랙** 작업이라 비용이 가장 크다 |
| recommendation | **A 를 기본으로 두되, B 의 8×16 한글 샘플을 PNG 로 먼저 보고 결정**한다(빌드 전 PNG 컨펌 원칙). A 는 기존 자산과 PS1 트랙의 조판기(`shared/text/krwrap`)를 그대로 쓰고, 분량 문제는 **페이지 수 증가로 흡수**한다(대사는 키 대기 `$FE/$FF` 로 넘기니 창 수 계약이 없다 — 단 `$FA/$FC` 분기 안의 문안은 길이 제약을 다시 봐야 한다) |
| effects (채택 시) | 글꼴 자산·코드 공간(2바이트)·재삽입기 설계·조판 폭(8자/줄) 이 이 결정에 묶인다 |
| reassessment | 인게임에서 대사창 BG 모드/비트 깊이가 2bpp 가 아니거나, NMI DMA 예산이 글자당 4타일 적재를 못 받으면 A 도 다시 본다 |

### 8. 재삽입 구조(A 기준) — 제안, 런타임 PoC 전

정적 근거만으로 세운 설계다. 인게임 확인(BG 비트 깊이·NMI DMA 예산)이 뒤집으면 여기부터 다시 쓴다.

1. **문안은 옮겨 쓴다** — 원본 스크립트 구조(조건·분기·호출)를 항목 열로 보존하고, 글자 런만 한글로
   바꾼 뒤 **전부 다시 배치**한다. 참조는 라벨에서 재계산(`script.py`): 포인터 표 4벌(addr24) · `$F9`
   addr24 · `$FA/$FC` rel16(같은 뱅크 안) · `$FB/$FD` 8비트×5. `$EE` 는 코드 주소라 그대로.
   ⚠ rel16 은 뱅크를 못 넘으니 **한 원본 뱅크의 문안은 한 새 뱅크에** 담는다(롬 2MB 확장 후 `$20~` 뱅크).
2. **한글 코드는 2바이트 — D3(구현 선택 2026-09-05, `tools/encode.py`)**: 선두 = **`$C5~$CE`**(원본이 시트 밖
   기호 타일에 쓰던 10코드), 색인 1B → 글리프 자리 2,544(+ 조사 코드 16). **가나 코드는 그대로 두므로** 번역
   안 된 조각(가나)과 번역된 조각이 한 롬에 섞인다(개발 빌드가 곧 된다). 반각 1칸: 공백 `$10` · 숫자 · `!?ー` ·
   **`.`→`$83`(。자리) `,`→`$84`(、자리)** 글리프만 교체 · `「」` · 영문은 원본에 있는 H M E P G O L D C A B 뿐.
   `…`·`~()` 등은 16×16 글리프로. 매핑 없는 글자는 **빌드 실패**(조용히 빼지 않는다).
   조사: 사전 토큰·글자 뒤는 빌드가 받침으로 확정, 런타임 치환 뒤는 **조사 코드 `[$CE][$F0+k]`** → 렌더러 훅.
   ⇒ 조건(`$F0~$F7`)이 「다음 항목 하나」를 건너뛰는 규칙은 2바이트 항목에 맞춰 건너뛰기 표·`$02:E49F` 를 고친다.
3. **글리프는 동적 적재** — 글자 놓기(`$02:DE85` 부근)에 훅: 글리프 번호 → 활성 슬롯(최대 34, 창 한 벌)
   배정 → 1bpp 16×16(32B, 확장 뱅크) → WRAM 스테이징 2bpp 타일 4장(t, t+1, t+$10, t+$11) → NMI DMA
   큐(`$1022~$1028`, `jsl $00:95BB`). 줄 버퍼 `$0305` 에는 슬롯의 좌·우 셀 코드를 넣고, 타일 표
   (`$03:F3EC`)의 그 코드 자리를 슬롯 타일로 둔다. 페이지 넘김(`$FF`)·창 지움(`$EF`)에서 슬롯 해제.
   글꼴 자산: **선택 가능**(D4 — 14절) `SFC_KR_FONT=neodgm|Galmuri14|Galmuri11`, 기본 Neo둥근모.
   1bpp 32KB / 2bpp 64KB.
4. **사전도 같은 인코딩** — 인명·지명·아이템·몬스터·마법·시스템 문장 427항목의 문자열을 한글로 바꿔
   확장 뱅크에 옮기고 6벌의 2B 포인터 표를 다시 쓴다. 조사는 **번역 시 확정**한다(9절 — 사전 이름은
   고정). 런타임 치환(`$D6~$DC`) 뒤 35 자리만 문장을 고치거나 최소 훅.
5. **롬 확장** — 1MB → 2MB LoROM, 헤더 rom 바이트 `$0A→$0B` · 체크섬 재계산. 원본 뱅크의 문안 자리는
   비우거나 그대로 둔다(무변경 구간 선언은 재삽입기가 만든다).

⚠ **타일 예산이 빡빡하다.** 텍스트 타일 384 중 가나가 $040~$16E(+아래 반쪽) 300 을 쓴다. 최종 설계에서 그 300 이
대사 동적 슬롯(창 한 벌 34자 × 4 = 136)과 **메뉴 상주 글리프**(라벨 44줄 고유 55음절 × 4 = 220)를 나눠 써야 한다 —
356 > 300. 남는 길: 메뉴 음절 줄이기(축약·중복 표기) · 2벌 버퍼 포기 · $180 이상 2bpp 그래픽 영역의 빈 타일 찾기
(런타임 VRAM 지도 필요). 결정은 인게임 지도 뒤.

**메뉴 한글 PoC(코드 수정 없음, 빌드에 들어 있다)** — 탁음·반탁음 가타카나 두 행(타일 $140/$160 행, 코드 $A4~$C2)을
빌려 한글 15자를 심고 커맨드 창(A01 + 부분 갱신 B0A/B0C/C0A) 라벨을 「주문·사용·장비·버린다·상태·그외·리더」로
다시 구웠다(`build.py menu_poc`). 시트 편집 → 기존 업로드 → 정적 타일맵의 경로가 코드 없이 사는지가 검증 대상.
⚠ PoC 롬의 일본어 대사에서 ガ~ポ 가 한글 조각으로 보이는 건 그 때문이다(빌린 자리).

**선례 — 우리 설계와 같은 길을 간 SFC 사례**(`docs/reference/worklog-sfc-gb.md`, 한식구 카페):

- **세일러문 어나더스토리**(HiROM, 1바이트 폰트 240자)가 우리와 같은 문제를 풀었다: 제어코드 **E5~EF 11개를
  2바이트 선두**로 쓰고(우리 `$C5~$CE` 10개와 같은 수법), 롬을 확장해 영역마다 폰트를 두고, **폰트 주소 계산
  루틴을 후킹**해 선두 바이트별로 「폰트 시작주소 + 뱅크」 두 값만 갈아 끼웠다. 우리 `$00:91F5`(적재)와
  `$02:B07B`(타일 배정)가 그 자리에 해당한다.
  🔴 **그쪽이 물린 함정**: 계산 뒤 원래 서브루틴으로 점프시켰더니 대사 포인터 증가(`INC`)를 안 거쳐 **같은
  글자를 무한 반복**했다. 원래 코드 일부를 훅 안에 복사해 넣고 **증가 루틴 직전으로** 복귀시켜 풀었다.
  ⇒ 우리 훅도 「어디로 복귀하나」를 먼저 정한다.
- **패트레이버**(LoROM 1.5MB)는 **일반 텍스트와 스토리 대사의 폰트 출력 루틴이 별개**여서 확장 루틴을 둘 써야
  했다. 우리도 경로가 둘이다(대사 `message.asm` ↔ 메뉴 정적 타일맵) — 같은 함정을 이미 11절에서 갈라 뒀다.
- **VRAM 타일 직접 쓰기 템플릿**(동적 글리프 적재에 그대로 쓴다): DMA 레지스터 `$4300`(모드 1)·`$4301`(=$18 →
  `$2118` VRAM)·`$4302/4304`(주소·뱅크)·`$4305`(길이) → `$420B` 로 기동. 목적지는 `$2116`(하위)·`$2117`(상위)에
  **나눠 넣는 게 안전**하다(한 번에 16비트로 넣으면 게임에 따라 오동작). ⚠ 타일 교체 루틴이 X/A 를 덮으면
  원래 값을 복원해야 화면이 안 깨진다(그쪽은 X 복원 누락으로 화면이 깨졌다).
- **재삽입 구조 계약**(`docs/reference/our-findings.md`): 「참조되지도 번역되지도 않는 블록은 이동 금지」와
  **「위치가 계약인 구간」**(구조가 다 맞아도 뒤가 당겨지면 이벤트가 깨진다). 우리는 본문을 통째로 옮기고
  참조를 전부 다시 잡았지만, **표에도 `$F9` 에도 안 잡히는 숨은 독자**(코드가 직접 상수로 읽는 자리)는 정적
  스캔으로 못 가린다 — 롱 주소 명령 스캔은 474건이 나왔는데 대부분 데이터가 명령으로 보인 가짜다.
  ⇒ **원문 자리를 `$FF` 로 비운 PoC 롬이 그 검출기**다(빌드에 이미 들어 있다).

### 10. 번역 정본 — `textmap/segments.json` (커밋, 조각 단위)

- **단위 = 조각**(END 사이, `units.py segments`) — PS1 번역본이 창 단위라 조각으로 맞추는 게 자연스럽고,
  번역자도 조각 하나를 통째로 본다. 키 = 조각 원문 바이트 sha1(12). 원문은 파일에 없다(work/derived).
- **토큰 계약**(`textmap.py --check` 가 게이트): **제어 토큰**(`<FF>`·`<E3>`·`<@>` …)은 전부 같은 순서로 있어야
  한다 — 빠지면 분기·페이지가 사라진다. **사전·치환 토큰**(`{D3:08}`·`{D6}`)은 글자만 찍으므로 빼거나 어순을
  바꿔도 된다(「キャリオンク{ロー}ラー」처럼 이름 조각을 재활용한 자리는 통째로 쓴다). 원문에 없는 토큰 추가는 불가.
- **라벨 토큰 `<@>`**: 분기 목표가 런 한복판에 떨어지는 자리(공유 꼬리 「…しますか?」, 실측 99+12건). 원문 덤프가
  그 자리에 `<@>` 를 두고, 번역문도 같은 뜻의 자리에 `<@>` 를 둔다 — 재삽입기가 분기 목표를 거기로 다시 잡는다.
- **조사 자리표시자** `{은/는}` `{이/가}` `{을/를}` `{와/과}` `{으로/로}` `{이라/라}` `{이다/다}`: 앞 토큰이 **사전**이면
  빌드가 표기의 받침으로 확정하고, **런타임 치환**(`{D6}` 파티원·`{D9}` 아이템 …)이면 조사 코드로 내려 훅이 고른다
  (전투 문안에 수백 건 — 9절의 「35」는 `<E1>` 을 사이에 둔 자리를 못 센 값이다).
- **상태**: `tm-draft`(PS1 에서 끌어옴, 토큰은 뒤에 붙어 있어 자리를 사람이 옮긴다) · `draft`(AI 1차, 사람 QA 대상) ·
  `reviewed`(빌드 입력 자격 — 릴리스 후보는 이것만).
- 현재 **1,375 항목**(조각 id 기준 — 같은 바이트의 조우 문안은 하나로 합쳐진다): tm-draft 988(대사, 유사도 ≥0.9) ·
  draft 387 = 전투 결과·시스템(alt1 84) + 조우·전투 행동(alt2, 215 패턴 템플릿) + 오프닝·엔딩(alt3 35, PS1 오프닝
  문안 기반) — 우선순위(11절) 대상은 초안이 다 있다.
  `dict.json` 427 도 전부 채워짐(glossary 308 · draft 119). 나머지 대사 ~2,200 조각은 PS1 확정 뒤.

### 12.1 챕터 제목 — 그래픽 텍스트다 (2026-09-06 실측)

`第1章 王子の旅立ち` 는 글꼴이 아니라 **그래픽 타일**이다. 실기 VRAM 으로 자리를 확정했다:

| 무엇 | 값 |
| --- | --- |
| 층 | **BG2**(타일맵 워드 1024 = 바이트 2048 · 문자 베이스 워드 4096 = 바이트 8192, BG 모드 0 = 2bpp) |

표기의 정본은 **PS1 트랙**이다(`patch_sys_ui.py` = 유저 확정 이력이 붙은 UI 표 · `shared/glossary`).

- 메뉴 라벨 **29종 전부** 대조 — 능력치 여섯 · 전투설정 여섯 · 설정 셋이 PS1 과 같다.
- 시스템 문장 **D5 53건** 대조 — 상점·주문가게·여관 문안이 PS1 ED1 대본과 같은 자리에 있다.
  일곱을 PS1 쪽으로 고쳤다(`어떤 볼일이신지요?` · 하게체 통일 · `정말 `+`감사합니다.` 의 빠진 공백).
- **전투 커맨드 여덟**을 새로 정본에 올렸다 — `textmap/battle_ui.json`. 창 배치 표가 아니라
  뱅크 $02 의 **13칸 고정 문자열 여덟**(포인터 표 `$02:A30A`)이고, 앞 셋이 커맨드 격자(칸 시작 0·5·10),
  뒤 다섯이 파티 이름 칸이다. 표기는 PS1 확정(`공격·주문·방어·사용·무기·자동·강함·도망`).
- 갈린 자리는 **편차 대장**(`docs/deviations.md`)에 이유·되돌릴 조건과 함께 적는다. 지금 셋 —
  `버린다`→`버림`(창 폭) · 상점 `사기/팔기`(원문이 다르고 칸이 좁다) · 전투 격자(13칸에 14칸이 필요).

### 13.3 🔴 글꼴을 줄여도 대사가 더 들어가지 않는다 (2026-09-06, 유저 물음)

대사창 안쪽은 **17칸 = 136px** 이다(원문 줄 길이 전수: **99%가 17칸 이하**, 창 기록 A0E `(10,1,19,12)`
= 열 1~19 중 틀 둘을 뺀 17).

| 규격 | 한 줄 |
| --- | --- |
| 일본어 반각 1칸 | **17자** |
| 한글 **16px 셀**(D1=A, 현행) | **8자** — 128px 쓰고 8px 남는다 |

🔴 **글꼴 크기는 이 숫자를 안 바꾼다.** 타일맵은 8px 눈금이고 한글 한 자가 **두 칸**을 먹는다 —
11px 글리프를 넣어도 여전히 두 칸이다. 셀 안 여백만 늘어난다(11px → 세로 5px 놀고, 14px → 2px).

⇒ 더 넣으려면 **셀 모델을 바꿔야 한다.** 두 갈래뿐이다:

| 갈래 | 한 줄 | 값 |
| --- | --- | --- |
| D1=B, 한 자 = **한 칸(8px)** | **17자** | 🟢 **된다 — `Galmuri11-Condensed`**(아래 13.4) |
| **줄 단위 렌더링** — 글리프가 아니라 **줄을 통째로 타일에 굽는다** | 12px 면 **11자** · 11px 면 12자 | 동적 적재를 어차피 만들 거라 가능하다. 한 창 = 17칸 × 4줄 × 2행 = **136타일**(지금 추정 128과 비슷) |

⚠ 줄 단위 렌더링의 값은 **타자 연출**이다 — 글자를 하나씩 드러내므로 한 자 늘 때마다 그 자리 칸
(최대 2칸 = 4타일)을 다시 올려야 한다. DMA 는 감당되지만 조판이 **픽셀 좌표**를 내야 한다.

### 13.4 🟢 **D1 = B 확정** — 한 자 = 한 칸(8×16) (유저 2026-09-06)

D1 을 정할 때 「8px 폭 한글은 읽기 어렵고 Galmuri 에 그 비율이 없다」며 B 안을 접었는데,
**틀렸다.** 글꼴 폭을 전수로 재니:

| 글꼴 | 가로 | 세로 | 8px 셀 |
| --- | --- | --- | --- |
| Galmuri7 | 6~7 | 7 | ○ (너무 작다) |
| Galmuri9 | 8~9 | 9 | ✗ |
| Galmuri11 | 10~11 | 11 | ✗ |
| **Galmuri11-Condensed** | **7 (전부)** | 11 | 🟢 **○** |
| Galmuri14 | 12~14 | 14 | ✗ |

**`Galmuri11-Condensed` 는 완성형 11,172자가 전부 폭 7px 다**(빈 글리프 0 · 8px 초과 0 ·
숫자·영문·부호도 전부 있다). 8×16 반각 셀에 **그대로** 들어간다 — 우겨넣는 게 아니라 설계가 그렇다.

| | 한 자 | 한 줄 | 화면(4줄) | 글리프 타일/자 | 글리프 뱅크 |
| --- | --- | --- | --- | --- | --- |
| 현행 Galmuri14 | 2칸 | 8자 | 32자 | 4 | 27.5KB |
| **Condensed** | **1칸** | **17자** | **68자** | **2** | **13.75KB** |

⇒ **일본어와 같은 밀도**가 된다(원문도 반각 17자/줄). 실측 예: 한 문장이 Galmuri14 로 **9줄**
(= 3페이지)인데 Condensed 로는 **4줄**(= 1페이지)이다. 타일 예산·롬 용량도 절반이다.
⚠ 값은 **글자 크기** — 세로 11px 로 원본 가나(13px)보다 2px 작다. 가로도 7px 로 가나(5~8px)와 같다.

🟢 **적용 완료**(2026-09-06, 실기 확인). `hangul_font.CELL_W` 가 8이면 한 칸으로 굽는다:

| 딸려 온 것 | |
| --- | --- |
| **D2(창 넓히기) 철회** | `WIDEN = {}`. 커맨드 창 4칸에 `버린다`(PS1 정본)가 들고, 시스템 창 4칸에 `시스템` 이 든다 ⇒ **창을 하나도 안 건드린다.** 13.1 의 커서 결함도 우회가 아니라 **안 건드려서** 사라졌다 |
| **전투 격자** | 13칸에 `공격·주문·방어`(끝칸 12) — 칸 시작 0·5·10 그대로라 커서도 그대로다 |
| 편차 대장 | 셋 중 둘이 지워졌다(`버림`·전투 격자). 남은 하나는 제약이 아니라 **원문이 다른** 자리다 |
| 타일 예산 | 한 자 4타일 → **2타일**. 「메뉴 상주 220 + 대사 128 = 348 > 324」 벽이 사라졌다 |
| 글리프 뱅크 | 27.5KB → **13.75KB** |
| 대사 조판 | 한 줄 8자 → **17자** · 화면 32자 → **68자** |

### 12.2 챕터 제목에 한글을 얹으면 (실측 목업 2026-09-06)

자리는 128px. `제1장 왕자의 여행` 을 자간 1px 로 재면:

| 글꼴 | 폭 | |
| --- | --- | --- |
| (원본 일본어 12px 비례) | 101px | |
| **Galmuri11** | **103px** | 원본과 거의 같다 |
| **Galmuri14** | **127px** | 🔴 한계 128px 에 **1px** 남는다 — 제목이 길어지면 바로 넘친다 |

🔴 **제목은 글자만이 아니다 — 밑줄과 테두리가 같은 타일 안에 있다**(유저 지적 2026-09-06):

| 요소 | 어디에 |
| --- | --- |
| **밑줄 2px** — 화면 행 14(색 1 어두움) · 행 15(색 3 밝음), 폭 전체 | **아래 타일 16장 전부가 같은 꼬리를 갖는다**(실측). 우리 타일로 갈아치우면 **그 구간만 밑줄이 끊긴다** ⇒ 반드시 같이 그린다 |
| **1px 테두리** — 흰 획 둘레를 어두운 색(1)으로 두른다 | 어두운 점 500개가 **100% 흰 획의 8방향 이웃**이다(그림자가 아니라 외곽선). 한글도 같이 둘러야 원본과 같은 톤이 된다 |
| 색 | 2 = 바탕 · 3 = 흰 획 · 1 = 테두리·밑줄 (2bpp 4색) |

**세로 자리**(유저 요청 「위로 좀 올려서 글자가 온전히 나오게」):

| dy | 흰 획 | 테두리 |
| --- | --- | --- |
| −3 | 행 0~10 | 위 테두리가 **행 −1 이라 잘린다**(원본도 그렇다 — 원본 흰 획이 행 0~11) |
| **−2** | 행 1~11 | **행 0~12 로 온전하다** · 아랫줄이 원본 기준선(11)과 같다 |

⇒ **dy −2 확정**(유저 2026-09-06). 테두리까지 온전하고 아랫줄이 원본 기준선과 같다. 폭 103/128px.
16행 창에서 잉크가 **행 0~10** 으로 원본 일본어(행 0~11)의 **윗줄에 맞는다**. dy −2 면 행 1~11 로
원본 기준선에 맞지만 한 줄 내려앉는다.

🔴 **첫 목업은 받침이 잘려 있었다** — 11px 글꼴이라고 **창을 11행으로 잡은 것**이 원인이다.
Galmuri11 의 잉크는 dy 0 에서 **행 3~13**(=11행이지만 3행부터 시작)이라, 11행 창에 넣으면
아래 세 행이 사라진다(`왕` 의 `ㅇ` 받침이 통째로 날아갔다). BDF 는 **셀 밖 잉크를 조용히 자른다** —
이 레포에서 두 번째로 밟았다(첫 번째는 인게임 글꼴 dy 검증). **항상 넉넉한 창에 떠서 확인한다.**

⇒ 챕터 제목은 **Galmuri11** 이 맞다. 대사(16칸)와 제목(비례 12px)은 **규격이 다른 자리**라
글꼴이 달라도 된다 — 원본도 대사 가나 13px · 제목 12px 로 갈려 있다.

### 13.5 🟢 렌더러 훅 설계 — 그리기 루프는 **안 고쳐도 된다** (2026-09-06 실기 특정)

읽기 브레이크포인트로 글자→타일 표(`$03:F3EC`)를 읽는 자리를 잡고 둘레를 뜯었다.

**칸 배열과 변환 루프** — `$02:B07E`:

```
B07E  LDX $1713            ; 칸 색인(0~$43 = 68칸 = 17칸 × 4줄)
B081  LDA $0305,X          ; ← 칸마다 **글자 코드 1바이트**
B08F  ASL/ROL              ; ×2
B099  ADC #$EC / #$F3      ; $06/$07/$08 = $03:F3EC + code*2
B0A6  LDA $0305,X / CMP #$10   ; 공백이면 위·아래 같은 타일
B0AF  LDA [$06],Y          ; 타일 번호 하위 → $1734
B0B5  ADC #$10             ; 🔴 **아래 타일 = 위 타일 + $10** (하드코딩)
B0C7  LDA [$06],Y / ORA $0349,X ; 속성|상위 → $1735/$1737
B0DA  STA $038D,X / $038E,X    ; 위 워드
B0E6  STA $0415,X / $0416,X    ; 아래 워드
B0EF  INC $1713 / CMP #$44     ; 68칸까지
```

**글자를 칸에 넣는 자리** — `$02:DE73`(메시지 엔진):

```
DE4C  LDA $173A / CMP #$CF   ; $173A = 방금 읽은 글자 코드 · $CF = 개행
DE73  INC $173B              ; 칸 커서
DE7D  JSR $DE23              ; 줄이 차면 스크롤(0305·0349 를 한 줄 당긴다)
DE80  LDX $173B / LDA $173A
      STA $0305,X            ; ← **여기가 훅 자리**
      LDA $176C / STA $0349,X ; 칸 속성
DE94  STA $1713 / JSL $02B07B ; 그 칸만 변환
```

🟢 **그래서 변환 루프를 안 고쳐도 된다.** 한글 한 자가 **한 칸**(D1=B)이고 아래 타일이
**위+$10** 인데 우리 글리프 규약이 정확히 그것이다 ⇒ **코드 하나가 타일 하나를 가리키게만
해 주면 기존 경로가 그대로 그린다.**

**동적 슬롯 방식**(코드를 빌린다):

| | |
| --- | --- |
| 슬롯 | 표에서 **타일이 유일하고 업로드 범위($000~$17F) 안**인 코드 = **177개**(실측) |
| 필요분 | 한 창 68칸이 전부 다른 글자여도 68 · 메뉴 상주 ~55 ⇒ **여유가 2배 넘는다** |
| 훅 | `$02:DE80` 앞에서 코드가 `$C5~$CE`(한글 선두)면 **다음 바이트까지 읽어** 글리프 색인을 만들고, 캐시에 없으면 슬롯 하나를 잡아 **글리프를 그 슬롯의 타일 자리에 DMA** 한 뒤 그 **슬롯 코드**를 `$173A` 에 넣는다 |
| 그 뒤 | 기존 코드가 `$0305,X` 에 넣고 `JSL $02B07B` 로 변환한다 — **손 안 댐** |

⇒ 고칠 곳은 **글자 소비 지점 하나**다. 건너뛰기 표(`$02:E4E0`)에 `$C5~$CE` = 2바이트를 더하고,
슬롯 캐시(칸 배열이 스크롤될 때 함께 늙는다)와 DMA 큐만 얹으면 된다.
⚠ 아직 안 본 것: 스크롤(`$DE23`)이 슬롯 참조를 옮길 때 캐시 수명 · NMI DMA 예산 · 오프닝 경로
(`$1E`)가 같은 루프를 쓰는지.

### 14. 결정 D4 「글꼴」 — 인게임 = Galmuri14 · 오프닝/엔딩 = Neo둥근모 (유저 확정 2026-09-05)

유저: 「다른 게임들도 오프닝/엔딩은 네오둥근모, 인게임은 갈무리로 거의 결정되어 있어.」 ⚠ **Galmuri16 은 없다** —
상류(quiple/galmuri v2.40.4)는 7·9·11·14 뿐이라 **16셀에는 Galmuri14** 가 맞는 크기다.
셀이 16×16(D1=A)이라 후보 셋 다 **축소 없이** 든다(도트 무손실 · 실측 1,009 음절 전부 셀 안).

**원본 글꼴의 실측 치수**(2026-09-06, 유저 「갈무리14가 좀 큰 느낌」 확인 요청). 칸은 8×16 이지만
**잉크는 그보다 작다** — 시트 $18:E02C 의 글리프를 전수로 재면:

| 잰 것 | 값 |
| --- | --- |
| 가나 158자 잉크 **아랫줄** | **13** (155자) · 12·15 가 각 1 |
| 가나 잉크 **윗줄** | 1(41자) · 4(60자) · 5(30자) — 큰 가나가 1 |
| ⇒ 원본 글자 크기 | **세로 13px**(행 1~13) · 가로 5~8px |
| 메뉴 라벨에 실제로 쓰인 61자 | 아랫줄 13 이 60자 — 기준선이 하나다 |

⇒ **원본은 16px 이 아니라 13px 글꼴**이고, 칸 16 중 위 1 · 아래 2 가 여백이다.

| 후보 | 설계 | 16셀에서 | 원본(가나 1~13)과 | 성격 |
| --- | --- | --- | --- | --- |
| **Neo둥근모 16** | 16×16 TTF | 잉크 y1~13(dy 0) · **x0~15(꽉)** | 세로 같다 · **가로가 꽉 찬다** | 획이 굵어 멀리서도 읽힌다. 새턴 트랙 확정 글꼴 |
| **Galmuri14** | 14×14 BDF | 잉크 y0~13(dy −4) · x1~14 | 세로 1px 크다 | 1px 획 — 원본 가나와 같은 톤. PS1 트랙과 집안이 맞는다 |
| Galmuri11 | 11×11 BDF | 잉크 y3~13(dy 0) · x1~11 | 세로 2px 작다 | 작아서 여백이 넉넉하다. 획이 가늘어 별 배경에서 묻힌다 |

🔴 **dy 는 눈이 아니라 기준선으로 맞춘다**(2026-09-06 수정). 예전 값(Galmuri14 −3 · Galmuri11 −1)은 Neo둥근모의
겉모습에 맞춘 것이라 각각 **한 줄씩 어긋나** 있었다. 원본 기준선(행 13)에 맞추면 셋 다 같은 줄에 앉는다 —
전수 확인: 잘리는 글자 0(BDF 는 셀 밖 잉크를 조용히 자르므로 넉넉한 창에 따로 떠서 셌다).

⚠ **「16px 글꼴」은 칸 이름이지 글자 크기가 아니다** — Neo둥근모 한글의 세로 잉크는 완성형 11,172자 전수로
재도 **13px**(행 1~13, 11,115자)이다. 대신 **가로는 x0~15 로 칸을 꽉 채운다**(Galmuri14 는 x1~14). 세로가
원본과 같은데도 빽빽해 보이는 건 이 가로 때문이다. 영문·숫자는 Neo둥근모 y2~14 · Galmuri14 y1~15 로
Galmuri 쪽이 칸 아래끝까지 닿는다(넘치지는 않는다).

🔴 **「Galmuri14 가 커 보인다」는 착시가 아니다** — 완성형 11,172자 중 11,115자가 **행 14** 에서 끝나
원본 가나 기준선(13)보다 한 줄 아래로 앉는다. 줄일 방법은 둘뿐이다: **dy 를 −4 로** 내려 아랫줄을 13 에
맞추거나(윗여백이 0 이 된다), Galmuri11(11px, 2px 작다)로 내려간다. Galmuri 에 13px 은 없다.
