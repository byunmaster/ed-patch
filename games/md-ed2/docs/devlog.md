## 2026-10-12 — 엔진 대응·빌드 뼈대

- ED1 바이트 16B 창을 ED2 에서 찾는 앵커 맞춤으로 엔진 대응을 얻었다 — 구간마다 이동량이 다르다(0x9xxx 대는 +0x1FAC~0x1FB8,
  필드 HUD 는 +0x4378). **대응이 틀리면 조용히 엉뚱한 자리를 쓴다** → 각 자리를 디스어셈블로 명령 일치까지 보고
  sha1 지문으로 고정(`engine.py --check`).
- 에뮬 검증을 하려다 **같은 입력을 원본·재빌드 롬에 넣고 화면 해시를 대조**하는 쪽이 맞다고 정했다(빨간 화면이 떴을 때
  「깨졌나」를 원본과 같은 해시로 바로 갈랐다 — 원본도 같았다). 입력 재생은 `start_frozen` + 프레임 수가 고정된 `tap`
  만 쓴다(`resume` 후 실시간 대기는 재현이 안 된다).
- 모든 아카이브(그래픽 포함)가 최적 파싱으로 원본보다 작아진다(−5.7K·−1.1K·−1.6K·−0.9K·−11.5K·−0.5K·−14.2K).

## 2026-10-12 — 코드 영역의 대사 · 고아 스트림 · 빨간 화면

- ED1 의 `sysmsg` 방법(코드의 lea/pea 참조 → 스트림)을 ED2 에 그대로 돌리니 스트림이 167 뿐이고 **0x37000~0x39FFF 의
  이벤트 대사가 통째로 빠졌다.** 원인은 ED1 에서 가져온 필터 `스트림 길이 ≤ 400B` — ED2 의 이벤트 대사는 05(페이지)로
  이어진 수 KB 짜리다. 필터를 풀자 화자 태그 스트림이 46 → 74. 「ED1 에서 가져온 상수는 ED2 의 분포가 아니다」.
- 씬 모듈 화자 태그 74 건은 참조(lea·표·goto)가 안 닿는다. 사슬 앞뒤로 05/00 이 붙어 있어 죽은 문안이거나 런타임 계산으로
  닿는다 — 못 밝혔다. 번역 때 빠지지 않게 **태그에서 시작하는 고아 스트림**으로 따로 모았다(재조립은 안 옮긴다).
- 새 게임 직후 빨간 화면: 실은 **어트랙트 데모 루프**였다. 같은 입력을 원본에 넣어도 같은 해시. 「깨졌나」를 원본 대조로
  갈랐다 — 에뮬 입력 타이밍(메뉴는 start 를 로고 뒤 일정 창 안에 눌러야 뜬다)이 원인이지 롬 문제가 아니다.

- 아카이브 재배치가 안전한지 **정적으로** 확인했다: 코드에서 대본 아카이브·분할표 안 주소를 직접 쓰는 명령(lea/jsr/
  move.l #abs)은 0x1A426·0x1A470(색인) · 0x1A490(분할표) · 0x24BEC(색인) 넷뿐이다. 블록 위치는 색인만 따라가므로 다시 깔아도
  된다 — `build.verify_archive_refs` 가 게이트로 지킨다. ⚠ 화면(필드·대사 씬)으로는 아직 못 봤다.

## 2026-10-12 — 타이틀 셀 · 새 게임 진입 · 필드 씬 확인

- 시작 메뉴는 ED1 과 같은 **16×16 셀 그림**이고 셀 폰트(롬 0xEB3A0, 셀 0~69)가 ED1 것과 **바이트까지 같다**. 처음엔 기준 주소를
  0xEB340 으로 잘못 잡아(셀 10 = 0xEB9E0 에서 10×160 을 빼야 하는데 산수 실수) 「반만 일치」로 보였다 — **타일 단위로 VRAM↔롬을
  맞춰 보고서야** 기준이 0xEB3A0 인 걸 알았다. 에뮬 덤프(플레인 B 행 10~15·열 15~24)로 배치 확인, 시험 낱말(번역 아님)로
  셀을 바꿔 구운 롬이 메뉴에 그대로 뜬다(`inbox/md-ed2/title-menu-test.png`).
- 새 게임 진입: 「빨간 화면」은 어트랙트가 아니라 **c 를 너무 많이 눌러 오프닝이 어긋난** 것이었다. 정답은 **입력 없이 기다리기** —
  로고 후 `mode`+1000f · `start`+300f(메뉴) · `c`+300f · 이후 입력 없이 3000f×4 = 첫 필드 씬(「アトラス … おはよう」). 앞서
  「어트랙트 루프」라고 쓴 진단은 **틀렸다**(원본·재빌드가 같게 어긋났을 뿐이라 같은 해시로 보였다) — 같은 해시는 「같은 상태」이지
  「맞는 상태」가 아니다.
- 재압축 대본 롬의 첫 필드 씬이 원본과 **82픽셀만 다르다**(▼ 깜빡이는 위치 153~167,182~190 — 애니메이션 위상). 대사 글자는 같다.

## 2026-10-12 — P0 기반: 첫 대사가 한글로 뜬다(시험 번역)

- ED1 의 글꼴(`font.py`·`hangul.py`)을 ED2 주소로 옮겼다 — 글꼴 구역(0xF41C2~0x10B37E, 0x171BC B)이 ED1 것과 **바이트 전체가 같아서**
  주소 이동량 하나(`hangul.SHIFT`)로 상수 여섯이 다 옮겨진다. 텍스트맵은 씬 모듈 단위(`script/BBB-K.json`).
- 첫 필드 씬의 첫 대사(블록 46-3 스트림 0xFD0)를 시험 번역해 굽자 대사 줄은 한글로 뜬다. ⚠ 첫 판은 **이름 행에 대사가 붙어**
  나왔다 — 원문의 `<0900>`(파티원 이름) 뒤 `01`(개행)이 `<0900> 안녕` 의 공백으로 들어가 조판기가 지웠다. 개행은 `<01>` 태그로
  명시해야 한다(ED1 은 화자 머리가 별도 스트림이라 안 드러난 함정).
- **이름 행이 비었다** — 파티원 이름 「アトラス」는 대본이 아니라 램 파티 레코드의 가나라 표 0 에 가나가 없어 빈칸으로 그려진다.
  이름 표(P1 시스템·고유명사)에서 풀 일이다. 「대사가 한글로 뜬다」와 「이름까지 맞다」는 다른 눈금이다.
- 디코드 블록 크기 상한을 **원본 최대(23,124B)로 못 박았다**(`build.MAX_BLOCK`) — 로더가 블록 통째를 FF6650 에 푸는데 그보다 큰 블록이
  램의 뒤 칸을 덮는지 아직 분석 전이다.

## 2026-10-12 — P1 표 · 조판기가 먹는 공백

- ED2 표의 위치는 ED1 표의 **바이트열을 ED2 롬에서 찾아** 잡았다: 메뉴·설정·상태·상점·패배 메뉴 등 ZGROUPS 열한 곳이 내용까지 같다
  (주소만 다름). 아이템은 139(ED1 118)·주문 33, 지명은 **ED1 의 12B 고정 폭이 아니라 앞 5칸만 9B 고정이고 그 뒤는 폭이 제각각인
  06 종결 문자열**이다(미이식). 「하나만 같으면 표가 다 같다」가 아니다 — 표마다 주소·개수·꼴을 다시 재야 한다.
- 조판기(`krwrap`)는 덩이의 **앞뒤 공백을 지운다.** 첫 대사 「이런 <이름>님」의 「이런 」 뒤 공백이 사라져 화면에 「이런아트라스님」이
  떴다. 검사기는 통과했다(공백 하나는 글자 수에 안 잡힌다) — **화면에서만 보였다.** 태그가 이어지는 덩이는 뒤 공백을 되살린다.
- 마스터가 시험 캡처에서 「안녕, 라우엘」이 PS1 정본(「여어, 라우엘. 좋은 아침～」 ED2SCN1 #15)과 어긋난 것을 짚었다 — **시험 문안도
  원문이 PS1 과 같으면 PS1 문안을 쓴다**(이름은 정본에서). 물결은 전각 「～」(반각 `~` 글리프는 반각 표에 없다).
- 필드 메뉴에 들어가는 입력: 대사를 `c` 로 모두 넘기면(번역 안 된 대사는 빈 상자로 나온다) 조작권이 돌아오고, `b` = 커맨드 메뉴,
  `down`·`c` 로 항목 선택.

## 2026-10-12 — 시스템 메시지: 채우기 · 정본 대조 · 묶음 넘침

- ED1 문안을 **원문 내용 키**(참조 오프셋을 뺀 토큰열)로 물려받는다 — ED1·ED2 에서 같은 문장이라도 `0f hh ll` 상대 오프셋이 달라 스트림 해시가
  안 맞는다. 191 중 82 가 같았고, **정본 ed2 와 12곳이 갈렸다**(ED1 문안은 PS1 ED1 기반 — 「더는 못 가집니다」 vs 정본 「하지만 더는 지닐 수
  없습니다」). 갈린 곳은 정본으로 덮었다. 「같은 원문이면 같은 문안」이어도 **어느 작품 정본이냐**가 있다.
- ED1 의 `PINNED`·`RELOCATE` 주소는 ED2 에서 쓸 수 없는데, **같은 내용 키로 대응을 뽑아** 옮겼다(RELOCATE 7 전부, PINNED 둘; 나머지 PINNED 는
  ED2 에 같은 원문 스트림이 없거나 갈려 있다). 흐름 게이트는 그대로 일한다.
- 잠복 둘: 짧은 가나 조각(`_short_kana`)·묶음 안 참조 스트림 블록을 처음 이식에서 빠뜨려, 재삽입기가 「안 옮겨지는 참조」로 막아 줬다.
- 정본 문안(PS1 기반 14칸 창)은 MD 칸에선 길어 **원문 길이 묶음을 넘기는** 곳이 있다 — 보류 다섯(status).

## 2026-10-12 — 칸이 모자라 보이던 것의 절반은 스트림을 덜 찾은 탓이었다

- 「문안을 줄여야 들어가는 칸」 다섯 중 둘(0x47F8·0x82F8)은 **스트림 목록이 불완전**해서였다: ① `06` 으로 끝나는 스트림 뒤 **흐름 꼬리**(참조 없이
  물리적으로 이어지는 「ポイント あがった」)를 못 찾아 그 17B 가 묶음 칸으로 안 잡혔고 ② **워드 오프셋 표**(0x8150, 33항목 — 첫 셋이 같은 항목인 꼴까지
  ED1 0x73BC 와 같다)가 가리키는 주문·아이템 효과 메시지(`のＭＰを` 따위)가 통째로 빠져 있어 인접 12B 가 못 쓰는 칸처럼 보였다. 칸이 모자라 보이면
  **먼저 목록이 맞는지** 의심한다 — ED1 도 같은 자리에서 같은 순서로 걸렸다.
- ED1 의 `PINNED` 대응은 **내용이 같은 스트림이 둘이면 키가 모호**하다(HP 꼬리·MP 꼬리 둘 다 「ﾎﾟｲﾝﾄ あがった。」) — 잘못된 쪽(MP 꼬리)을 고정해 칸이
  어긋났다. 수작업 대응표 대신 **규칙(흐름 꼬리 자동 검출)** 이 맞았다.
- 정본 문안 vs ED1 문안: ED1 문안을 채우는 도구가 정본이 이미 정한 자리를 다시 덮었다(어긋남 3) — `held`·`src` 로 정본 값을 지켜 두고 도구가 건드리지 않게 했다.

## 2026-10-12 — 「여유」라고 본 718B 가 살아 있는 표였다

  맞대야 한다 — 후보 문자열 변형(끝 개행 유무·줄바꿈 공백·공백 제거)을 모두 해시해 맞는 것을 취한다.

- 0x31026 은 본문을 `01`(줄바꿈) 앞뒤로 쪼개 앞(30B)은 제자리, 뒤(15B)는 근처 비워진 묶음에 앉히고 goto 로 이었다(`sysmsg.TAIL_SPLIT`). 「조용히 어긋나도 빌드는
  통과한다」가 이 레포의 단골이라 **구운 이미지에서 되읽는 게이트**를 같이 넣었다 — 참조를 따라 goto 를 펴 읽은 바이트가 정본 바이트와 같아야 한다(세 곳 OK).
