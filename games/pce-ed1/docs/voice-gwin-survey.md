# 음성 씬 전수 표 — 비모달 자막 안 B 를 넓히기 전에 (11-01, 관리자 지시)

음성(ADPCM `JSR $5815`) 호출이 있는 씬 **29 · 호출 39**(블록 덤프 전수, `narration_gates.VOICE_AT` + 인라인 섹터로 거름). 안 B 가 붙은 씬은 6 · 98 · 18@1268(gon e0ec6b62).
수치는 지금 소스로 센 값이다 — 번역 블록 크기는 `translate.translate_block`(빌드와 같은 경로), 컨테이너 데이터는 제품 롬 패킹 합(나눈 컨테이너는 원래 칸의 값 — ±1KB).

## 넓히기를 막는 한계 넷 (기술 선택은 관리자)

1. **시각표** — 안 B 는 `script/voice_sched.json` 의 씬 항목(메시지 열쇠 + 쪽 끝 시각)을 읽는다(`gwin_rt.on_flow_spec`). 정식 = 6·18·98 뿐, 초안 = 32·41·151(인게임 검수 전), 나머지 23씬은 게이트 토막(타이머)뿐이라 **시각표부터 만들어야** 붙는다(상태 문서 「음성 자막 22토막 채우기 — 다음 라운드」와 같은 일).
2. **코드 영역은 컨테이너마다 하나** — `build._gwin_tail` 이 한 컨테이너에 안 B 씬이 둘이면 실패시킨다. 1252 = 씬 6 → 2·32·34·40·41 막힘, 1268 = 씬 18 → 17·20 막힘, 1396 = 씬 98 → 100 막힘. 풀려면 코드 영역을 씬별이 아니라 컨테이너별 공용(쪽 자료만 블록에)으로 바꿔야 한다.
3. **짝 표** — 나눈 컨테이너 넷(1348·1396·1252·1268) = 8항목, `MAX_PAIRS` 10 → **나눌 수 있는 컨테이너는 하나 더**. ⚠ 11-01 정정: 「안 나누고 붙는 넷」은 틀렸다 — 1380·1508·1588·1620 은 **10섹터(3뱅크)** 컨테이너라 4번째 뱅크를 더하면 캐시 점유가 원판보다 늘어 빌드 게이트가 막는다(「15섹터 = 4뱅크 > 원판 3뱅크」). 코드 영역은 컨테이너의 **마지막 뱅크**(`gwin_rt.code_sector`: 16섹터 → 12, 10섹터 → 8)에 두고, 데이터가 그 앞(2뱅크 = 16KB)에 안 들면(넷 다 19~20KB) **나눠야** 한다 → 새 씬마다 짝 표 +2. 짝 표 루틴 자리 169B 중 127B 가 코드, 표 30B(10항목) → 12B 남아 **`MAX_PAIRS` 14 까지(두 컨테이너 더)** 는 자리 안에서 된다 — 관리자 판단.
4. **블록 한계 0x1A00** — 안 B 몸체는 ≈1.85~1.96KB(실측: 씬 6 +1,962 · 98 +1,962 · 18 +1,845, 쪽 수와 거의 무관). 번역 블록 여유 − 2.0KB 가 300B 아래면 🔴(없음), 700B 아래면 🟡(쪽이 많으면 걸릴 수 있다 — 20·46·100·203·6·204·50).

## 짝 표를 영구로 둘 큰 자리 — 설계안 (11-01, 관리자 지시 1)

지금: `splitload` 의 `check` 루틴(127B) + 짝 표(3B × `MAX_PAIRS` 14 = 42B) = 169B 가 **글리프 뱅크 0(0x86) 꼬리 `$9F57~$9FFF`** 에 산다. 씬 열기 사이트(뱅크 0x6A `$6E1C`, 21B)가 MPR4 에 0x86 을 잠깐 걸고 `JSR check` 한 뒤 MPR4 를 복원한다. 루틴이 도는 순간의 매핑: MPR4 = 0x86(우리), MPR5 = 씬 뱅크 0x76(새 블록을 풀기 **전** — 사이트는 디렉터리 탐색 루프 안), 나머지는 엔진 그대로. 음성 씬 29 가 전부 나뉘면 항목 ≤ 29 × 2 = 58 → 174B(+끝 표시 없음, 항목 수 즉치).

⚠ **정정(11-01 오후)**: A 의 「992B」는 빌드 시점 0 바이트였을 뿐 — 제품 롬을 다시 재니 그 구간은 동적 글리프 칸(블록이 열릴 때 런타임에 채움, 288B)과 코드 칸이고, 뱅크 1 의 실제 빈 꼬리는 풀기 루틴 뒤 **76B** 다(뱅크 0 꼬리 169B 는 지금 루틴+표로 꽉 참). **관리자 판정(11-01)**: **㉠만**. 단 뱅크 1 꼬리 76B 는 빌드 산출물의 0 런이 아니라 **실행 중 쓰기 BP**(블록 열기·글리프 적재·씬 6/98/18·전투·메뉴·세이브/로드)로 비어 있음을 확인한 뒤에만 쓴다 · SEI 구간과 MPR5 복원은 디스어셈블로 검산 · 기존 나눔(1348·1396·1252·1268·1620·1540) 회귀 실측 · 시험 빌드에서만, 제품 반영은 마스터 확인 뒤. 

⚠ **정정 둘(11-01 저녁) — ㉠ 도 무효.** 뱅크 1 꼬리의 「0 런 76B」(0x1F66~)는 **반각 영숫자 표**(`hook.HALF_TAB` 130B, 0x1F57~0x1FD9 — 비트맵이라 0 바이트가 105개) 한가운데다. 꼬리 배치를 **소유자별로** 세면 풀기 루틴 103 · 반각 표 130 · 조사 선처리 37 → 남는 건 **2B**. 글리프 뱅크 전체의 빈 바이트: 뱅크 0 꼬리 0(루틴+표 169/169) · 뱅크 1 꼬리 2 · 코드 칸(어절·반 칸) 여유 19 · 디버그 키 자리 1 · 상주 글리프 816/816 꽉 참. 10-24 디버그 키 ②(「0 이 이어진 곳은 반각 표였다」)와 같은 함정을 세 번째로 밟았다 — 🔑 빈자리는 0 런이 아니라 **「누가 쓰나」(정적 소유) → 실행 중 쓰기 BP** 순서로 잰다.

남은 후보(목표 30항목 = 음성 컨테이너 15): **㉤ 표 둘 — 뱅크 0 꼬리 + 상주 RAM `$3E46~$3E90`(75B = 25항목)**. 이 RAM 은 11-01 아침 래스터 핸들러 자리 고를 때 같은 쓰기 BP 전수(부팅·타이틀·이어하기 ×3·씬 6·마을·동굴 LZ·메뉴·SAVE·LOAD·전투·씬 98 1만 프레임·씬 18 걷기)에서 히트 0 이었고(「`$3B00~$3DFF` 가 튀는 구역과 LZ 링 사이」라 안 골랐을 뿐), 늘 매핑이라 MPR·SEI 가 필요 없다. 표는 부팅 때 후킹 페이로드를 `$2300` 에 올리는 스텁이 같은 섹터의 0 꼬리(1,280B)에서 TII 로 같이 올린다(빌드가 채운다). 루틴에 둘째 표 훑기 ≈ +15B 가 필요한데 뱅크 0 자리가 꽉이라 표 0 을 14 → 8 항목으로 줄여 코드 자리를 낸다 → 8 + 25 = **33항목 = 16컨테이너**. ㉢(항목 2B, 짝 섹터수 16 고정)를 겹치면 21 + 37 = 58 이지만 트랙 끝 반쪽을 16섹터로 읽는 전제가 더 필요하다. 관리자 판단 대기 — 판단 전에 `$3E46~$3E90` 쓰기 BP(마을 **재진입** 포함)를 다시 돈다.
