# 한글 글리프 뱅크가 캐시 2칸을 먹는 구조 — 근본안 조사(11-22 밤, 마스터 「근본해결이 되어야 앞으로 손이 덜 갈 것 같아」)

조사만이다. 구현은 마스터 판정 뒤. 값은 `tools/` 의 정본 함수(`glyphdyn.forced_chars` · `translate.body_chars` · `font.py` 상수)로 이번에 센 것이다.

## ① 실제 값

| 무엇 | 값 |
| --- | --- |
| 글리프 한 자 | 12×12 1bpp, **18B 묶음 저장**(`font.PACKED_BYTES`) — 이미 1bpp 라 비트 깊이로는 줄일 게 없다 |
| 쓰는 글자(전수) | **1,027자** = 한글 975 + 그 밖(부호·숫자·영문) 52 |
| 늘 상주해야 하는 글자(`forced_chars`: 이름·UI·시스템·전투·조사·숫자·합자 + 입장 배너) | **612자**(한글 581) = 11,016B = **1.34칸**(8,192B/칸) |
| 지금 | 2칸 16KB 에 상주 816 + 동적 24(씬마다 ≤16) = 840자 칸, 14.9KB. 코드 자리 504B 포함 |
| 씬 본문 글자 수 | 평균 152 · 중앙 156 · 최대 304. 그중 forced 밖 평균 17 · 최대 57 |
| 사용 빈도 | 출현 기준 90% = 244자 · 95% = 354자 · 99% = 599자 · 99.9% = 844자 |
| 1칸에 드는 글자 수 | 8,192 ÷ 18 = **455자**(코드 자리 빼면 더 적다) |
| 한글 자모(쓰는 것만) | 초성 19 · 중성 21 · 종성 24 |

**결론 ①**: forced 612 가 이미 1칸(455)을 넘는다 — **씬 단위 동적 적재를 아무리 늘려도 1칸이 안 된다**(K=600 이하로 줄이면 씬 91개가 동적 한도 16 을 넘고 최대 57자, 이름·시스템·전투 글자를 맥락별로 따로 올리는 구조가 별도로 필요하다). 상주를 840→700으로 줄이는 건 8곳이 한도를 넘고 칸 절감은 0(1.54칸이라 여전히 2칸).

| 안 | 칸 절감 | 값(근거) | 위험 | 규모 |

## ② 실측 지도(안 쓰이는 RAM)에 대해 — ⚠ 아래 「2차 실측」 으로 대체(1차 때는 못 쟀다)

1차 때는 **못 쟀다.** emucap 으로 CD RAM 256KB 를 파일로 덤프하는 도구가 없고(`read_memory` 는 값을 인라인으로만 돌려준다 — 64KB 가 13만 자), 쓰기 덫은 범위 하나씩이라 전 장 대표 장면(장 5 × 필드·전투·메뉴·상점)을 돌며 256KB 전체를 덮으려면 별도 하네스가 필요하다. 하려면: 헤드리스 코어에서 장면마다 CD RAM 전체를 파일로 내보내는 하네스 → 장면 간 변한 바이트의 합집합을 비트맵으로 → 연속 8KB 이상 안 변하고(0 또는 FF) 로드 이후 쓰기 덫 0회인 구간만 후보. 후보가 나와도 15KB(1.8칸)가 한 덩이일 가능성은 낮다(10-07 전례).

## ④ 디스크 지연 읽기 속도

CD-ROM² 1배속 = 초당 150KB(≈ 73섹터). 글리프 한 칸(8KB) = 4섹터 ≈ 55ms + 탐색 0.2~0.5초. 씬 하나에 필요한 글자(평균 152자 = 2.7KB)는 2섹터라 전송 자체는 문제가 안 된다 — **병목은 탐색**이다(지금도 씬 진입마다 컨테이너 읽기 한 번 + 동적 글리프를 블록에 싣는 방식이라 탐색은 늘지 않는다). 그래서 C(블록에 싣기)가 속도로는 싸지만 위 표대로 칸 절감이 0 이다. D(맥락 교체)는 전투 진입마다 추가 탐색이 든다.

## 정리

- **칸을 정말 줄이는 건 A(자모 조합)뿐**이고 대가는 글자꼴·도트 작업이다. 마스터 판정이 필요한 갈림: 「글자꼴을 지키고 2칸 유지」 vs 「자모 조합으로 1칸」.
- E·F 는 측정 하네스를 먼저 만들어야 한다 — 하네스 규모는 중(하루), 결과가 비어 있을 가능성이 높다.
- 지금 구조는 이미 동적 24칸 + 상주 816 으로 **한계에 있다**(씬 최대 동적 15자 / 한도 16). 글자가 더 늘면 빌드가 멈추므로 번역 추가가 이 한도에 걸린다는 점이 「앞으로 손이 가는」 부분이다 — 동적 한도 여유는 1자뿐.

## 2차 실측(11-22 밤 — 마스터 「pce1 2칸은 아직 진행 안했어?」) — F(안 쓰는 RAM)·E(VRAM) 결과: **둘 다 불가**

**방법**: emucap `save_state` 가 낸 mednafen 상태 파일(`SysCardRAM` 192KB = 뱅크 0x68~0x7F · `CDRAM` 64KB = 0x80~0x87 · 기본 RAM 8KB · VRAM 64KB 가 이름표 뒤 그대로 들어 있다)을 파이썬(`docs/ram-survey-an.py`)으로 읽어 **장면 간 비교**한다 — 덫(쓰기 BP)은 범위 하나씩이라 256KB 전체를 못 덮고 `read_memory` 는 인라인뿐이라 덤프가 안 되지만, 상태 파일이 곧 전체 덤프다. 기준: **모든 스냅샷에서 값이 같고 00/FF 인 바이트** = 「한 번도 안 쓰였을 후보」(거기서 값이 한 번이라도 바뀌면 쓰인 것). 후보도 쓰기 값이 우연히 같거나 스냅 사이의 임시 사용은 못 잡으므로 **후보 수는 상한**이다.

**장면(게임 중 19 + 타이틀·오프닝·파일 선택 3)**: 4장 바즈눈 마을 · 시스템 메뉴 · 부 메뉴 · 디버그 W 목록 · W 곶의동굴 · 2장 유혈의동굴(가르고 이벤트 직전·음성 자막·이어짐) · 1장 필드 · 필드 전투(슬라임)·승리 창 · 시스템 메뉴·아이템 메뉴 · 5장 필드 · 5장 W 목적지 · 종장 바니스성 + **엔딩 쪽·최종 보스 전투(패배)**. (엔딩 크레딧·장 제목 띠 자체는 못 돌렸다 — 종장 바니스성 걸어 들어가 최종 보스까지.)

| | 값 |
| --- | --- |
| CD RAM 256KB 중 **한 번이라도 값이 바뀐 바이트**(게임 중 19장면) | 40.7% (고정 코드·표 59% — 쓰이는 데이터) |
| 전 장면 00/FF 상시인 바이트 | **23,059B**(8.8%) — 뱅크 0x68~0x7A 코드 뱅크의 **정렬 패딩 · 함수 사이 틈**(뱅크마다 수백 B~3KB, 우리 패치가 이미 쓴 자리는 FF 가 아니라 안 센다) |
| 그중 **연속 64B↑** 구간 | 합 **6,256B**, 가장 큰 것 **1,992B**(뱅크 0x85 +0x1838 — 리소스 캐시 맨 끝, 어느 장면에선 캐시 자료가 들어온다) · 768B · 512B · 456B · 423B … |
| 연속 **4KB↑ / 8KB↑ / 16KB↑** | **0 / 0 / 0** |
| 기본 RAM 8KB | 전 장면 00 바이트 3.5KB · 연속 64B↑ 합 1.8KB · 최대 364B(`$3C36`) — 인터프리터·엔진 스택·워크가 쓰는 자리라 상한 |
| **VRAM 64KB** | 전 장면 00 바이트 22,850B 중 **연속 64B↑ 합 8,689B · 가장 큰 3,072B(= `sprmask` 풀 셀 0xA0~0xBF, 워드 0x2800~ — 이미 우리 것)**. 워드 0x5400~0x6FFF(14KB)는 10~14/19 장면에서 00 이지만 나머지 장면(전투 몬스터 등)에서 쓰인다 → 상시 빈 자리 아님 |

**결론(F·E)**: 연속 **8KB 는커녕 4KB 도 없다**(최대 2KB). 스트라이프로 흩어진 23KB 는 15~18KB 글리프 묶음(조각 없이 한 덩이로 `$6000` 창에 걸어 읽는 구조)에 못 쓴다 — 조각마다 먼 호출·창 전환이 들어 풀기 사이클·흔들림이 늘고, 대부분 엔진 패딩이라 다른 패치와 부딪힌다(10-07 「빈 자리는 다 쓰이고 있었다」를 실측으로 확인). VRAM 도 상시 빈 자리는 이미 쓰는 4KB 풀뿐이라 불가. **그러므로 칸 절감은 A(자모 조합)뿐 — 마스터 판정 대기.**
