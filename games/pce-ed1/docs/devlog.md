# pce-ed1 devlog — 경위·삽질·오진

## 2026-09-05 — 첫 세션: 대본·코덱·폰트 소재

- **정적 분류로는 대본이 안 보였다.** 섹터별 엔트로피·SJIS 밀도로 트랙을 훑으니 SJIS 는 시스템
  문구 9섹터뿐이고 나머지가 「MID」로 뭉개졌다. 1bpp 비트맵 탐지는 0xFF 채움 섹터에 속았다(같은
  바이트끼리 XOR 이 0 이라 「상관 높음」으로 읽혔다). ADPCM 은 니블 크기 분포로만 갈라졌다.
  ⇒ 결국 **에뮬로 첫 대사까지 가서 RAM 을 뒤진** 게 빨랐다(SJIS 평문이 뱅크 0x76 에 있었다).
- **BP 는 두 번 헛돌았다.** 뱅크 0x76 의 대사 자리에 쓰기 BP 를 걸었더니 (1) BIOS 의 CD 전송
  루프가 그 자리에 **다른 데이터**(그래픽 스테이징, $C400 에 0x1C00B)를 쓰는 걸 먼저 잡았고,
  (2) 그걸 읽는 디코더($4837)를 대본 디코더로 오해할 뻔했다 — 뱅크 0x68 은 RAM 이라 **오버레이가
  갈리면 같은 논리 주소에 다른 코드**가 온다. 실제 대본 쓰기는 $6E55 였고 값(0x82 = お 의
  상위 바이트)으로 가렸다.
- **스테이트 로드 직후 `tap` 이 씹혔다.** 타이틀 스테이트를 올리고 run 을 눌렀는데 오프닝을
  한 바퀴 돌고 타이틀로 돌아왔다. 두 번째 탭은 먹었다.
- **LZ 는 첫 바이트 하나가 함정이었다.** 디렉터리 src 가 가리키는 첫 바이트는 헤더(모드 변형,
  0)였고 스트림은 그 다음부터다. 링 초기 커서 0xEF 는 초기화 루틴($45A9)에서 읽었다 — 그걸
  0 이나 0xF0 으로 두면 31바이트째부터 갈린다.
- **컨테이너 스캔의 가짜 양성 둘**(rel 1,249 · 1,475) — 디렉터리 모양은 맞는데 블록 헤더가
  쓰레기였다. 헤더 검사를 넣으니 걸러졌다. 「디렉터리로 읽힌다」는 계약이 아니다(체크리스트 10).
- **cue 의 대문자 파일명**: redump cue 가 `.ISO` 로 적어 리눅스 emucap 이 못 열었다. 심볼릭
  링크는 emucap 이 「too many levels of symbolic links」로 거부해 **하드링크**로 뒀다 — 원본과
  같은 inode 라 거기 쓰면 원본이 망가진다.
- **syscard3.pce 가 393,728B** — 표준 256KB 가 아니라 384KB+512 헤더 덤프인데 부팅은 됐다.
  BIOS 안 12×12 글꼴 시트가 파일 0x10000~0x28000 부근에 있다(24B 로 그려 보면 가나·1수준 한자가
  보인다 — 실제 저장은 18B 패킹이라 시트 정렬이 어긋난 채로도 눈엔 들어왔다).

## 2026-09-05 (3) — 제어코드·후킹 PoC

- **읽기 BP 로 인터프리터를 잡는 데 두 번 헛돌았다.** (1) 대사 첫 글자 자리(0xEC42A)에 읽기 BP 를
  걸고 타이틀부터 돌리니 **그래픽 스테이징이 같은 주소를 먼저 읽어** 엉뚱한 PC 에서 섰다 — 뱅크 0x76 은
  씬 블록이 오기 전엔 다른 용도다. (2) 첫 대사 스테이트에선 그 문장이 이미 그려진 뒤라 안 걸렸다.
  범위 BP(0xEC42A~0xEDFFF)를 걸고 **다음 대사(병사)까지 걸어가서** 잡았다. 잡힌 PC 는 렌더러가 아니라
  **인터프리터의 바이트 페치**(`$6712`)였고, 그게 오히려 옵코드 표를 통째로 줬다.
- **`[10][1E]ｨ` 는 토큰이 아니었다.** 덤프에서 제어코드처럼 보이던 `10 1E A8` 은 「서브루틴 호출 +
  2바이트 주소」다. 덤프 필터가 `1E` 를 제어코드로 세던 건 오진 — 옵코드 표를 보고 나서야 갈렸다.
  ⇒ 대본 덤프는 **옵코드 길이를 알고** 걸어야 한다(지금 `text_runs` 는 정규식이라 아직 그 전이다).
- **ADPCM 재생 중 스테이트는 로드하면 멎는다.** `field1.mcs` 를 올리자 화면이 그대로 서서 「게임이
  이벤트에서 기다리는가」로 한참 봤다. CD 상태 그룹의 `Playing=1` 에 `Length` 가 1KB/s 로 줄고 있었다 —
  스테이트가 ADPCM 타이밍을 되살리지 못한 것. 타이틀부터 다시 갔고, 스테이트는 지웠다.
- **PoC 는 링 버퍼에 얹었다.** 루틴·글리프를 `$3F00~$3F5F`(LZ 이력 버퍼)에 뒀는데 씬 로드가 없는 동안만
  안전하다. 제품 자리는 아니다 — 워크 RAM 사용 지도가 먼저다.
- 캐시 피크 측정에서 **`run`·`select` 는 필드에서 아무 것도 안 한다**. 메뉴는 `ii`. 세 번 눌러 보고 알았다.

## 2026-09-05 (4) — 워크 RAM 빈 자리: 정적 스캔은 버렸다

- **명령 길이표로 모듈 코드를 선형 스윕해 `$2000~$3FFF` 참조를 세는 방법은 못 쓴다.** 페이지별 참조
  횟수가 주소에 비례해 단조 증가했다 — 압축 데이터·그래픽을 코드로 읽으면 쓰레기 참조가 고르게 깔려
  진짜 참조가 묻힌다. 코드/데이터 경계를 모르는 채로는 상한도 못 준다. 표(`huc6280.py`)는 지웠다.
- 대신 **덤프 겹치기 + 쓰기 BP** 로 갔다. 두 덤프에서 0 인 768B 구간 둘에 쓰기 BP(pause 없음)를 걸고
  타이틀부터 첫 전투까지 한 바퀴 — 이벤트 0. 30분 걸렸고 정적 스캔보다 믿을 만하다.
- **전투 문구도 대사와 같은 인터프리터를 탄다.** 전투 중 `$E060` 에 exec BP 를 걸어 트레이스를 보니
  `$6712 → $7047 → $7044` 그대로였다. 「전투 모듈은 따로」라는 추정(모듈 450/898)은 적어도 문구 경로엔
  해당 없다 — 모듈들은 오프닝·타이틀·(아마) 엔딩이다.

## 2026-09-05 (6) — 제품 폰트 경로

- **할당기 초기화 패치 좌표를 2바이트 틀렸다.** `STA $375C` 검색 결과의 오프셋(0x14FD)이 STA 자리인데
  `LDA #$90` 자리(0x14FB)로 적었다. `expect` 사전조건이 그 자리에서 잡았다 — 사전조건 없는 쓰기였으면
  `8D 5C 37` 의 앞 두 바이트를 `A9 8D` 로 덮어 조용히 망가졌다.
- **BCC 로 BIOS 폴백까지 131B — 분기 범위 초과.** 미니 어셈블러의 assert 가 잡았다. 폴백 `JMP $E060` 을
  검사 직후로 올려 해결. 손으로 썼으면 오프셋 하나가 틀린 채 굽혔을 것.
- **반각 공백을 게이트가 막았다** — `font.encode` 가 전각만 받는다. 공백은 전각(`81 40`)으로 매핑.
- **「화자 이름이 두 칸 밀렸다」를 코드 패치 탓으로 봤다.** 이분(패치 그룹 `--only`)으로 셋을 굽고 나서야
  문안만 바꾼 빌드에서도 밀리는 걸 봤다 — 첫 줄 길이(10칸 초과분)만큼 밀린다. 원인 후보를 하나씩 빼는 데
  이미지 넷·부팅 넷(각 1분)이 들었다. 다음엔 **패치 없는 대조군을 먼저** 굽는다(디버깅 문서 §2.2 그대로).
- 캐시 13슬롯으로 줄여도 대사까지 멀쩡했다(슬롯 13~15 가 표에서 사라진 걸 `$375C` 로 확인).

## 2026-09-05 (7) — 번역 정본 형식

- **16비트 값 전부를 참조로 보면 메시지의 44%가 pinned 였다**(1,604/3,676). 실제 포인터 꼴을 scn 2 에서 보니
  `LDA #lo; STA $10; LDA #hi; STA $11` 분할 즉치였고, 그 사이 바이트가 우연히 주소처럼 읽혔던 것. 머리 표·분할
  즉치·JMP/JSR 로 좁히니 33건(0.8%). 스크립트 옵코드 피연산자(`10 lo hi`)는 `STA $10` 의 `10` 과 겹쳐 소음이라
  뺐다 — 못 보는 참조가 남는다는 걸 status 에 적었다.
- **`09 nn` 는 6502 `ORA #` 이기도 하다.** 열개 후보로 `09` 를 그냥 잡으니 코드 안에서 쓰레기 메시지가 쏟아졌다.
  `nn < 0x40` + 뒤에 `01`/대본 런 조건으로 좁혔다. 화자 이름은 한두 글자 한자라 「대본 런 ≥3 자」 필터에 걸려
  화자를 잃었다 — `1F` 후보는 길이 불문으로.
- **첫 대사의 화자 「侍女」는 메시지 안에 없다.** `10 lo hi` 호출이 이름만 있는 메시지(`1F 侍女 04 07`)를 부른다.
  그래서 speakers.json 으로 이름만 있는 메시지를 자동 번역하게 했다.
- **라이아스 4페이지 대사가 화면에 안 뜬다.** 스플라이스가 틀렸나 해서 RAM 을 봤더니 바이트는 제자리에 있었다.
  원본 스테이트로 같은 구간을 프레임마다 찍어 보니 원본도 창이 안 뜬다 — 음성 전용 컷신. 「내 패치가 깨뜨렸다」로
  단정하기 전에 **원본에서 같은 자리를 본다**(디버깅 문서 §2.2, 오늘 두 번째다).
- 초기 어림으로는 반각 `?` `!` 를 그대로 넣으려다 게이트에 막혔다. 이 창에 반각이 없으니 ASCII 부호·숫자도 우리
  글리프(Galmuri)로 낸다 — 셀 12px 왼쪽 정렬이라 `요?` 가 자연스럽다. 공백은 전각 한 칸이라 좀 넓다.
- **화자 전환 앞 `05` 를 빼먹어 세리오스 이름이 병사 창에 이어 붙었다.** 조각(종료 없는 메시지)을 합성할 때
  종료 바이트만 다시 붙이고 꼬리 옵코드(페이지)를 버린 탓. 원문 흐름의 옵코드는 **문안이 아니라 구조**다 —
  합성이 보존한다(테스트 추가).

## 2026-09-05 (8) — 시스템 문구

- **64B 「화자 슬롯」은 캐릭터 레코드였다.** 이름 뒤 48B 를 0 으로 밀었더니 HUD 에 파티원 넷(Lv 0 HP 0)이
  떴다. 장 제목 32B 쓰기도 뒤 7B(0)를 공백으로 덮었었다. **필드 폭은 「문자열이 차지한 길이」로 재야지 「눈에
  보이는 여백까지」로 재면 이웃 데이터를 밟는다.** 둘 다 원본 바이트를 다시 보고 잡았다.
- **라벨을 00 으로 채우면 다음 라벨이 사라진다.** 상태 화면이 라벨 목록을 00 개수로 세어 n 번째를 찾는다 —
  짧아진 라벨 뒤의 00 이 빈 항목이 돼 지혜 다음이 전부 비었다. 전각 공백 패딩으로.
- **시스템 메시지 경계는 「참조」가 정한다.** SJIS 런으로 자르면 「運悪」「く」 같은 공유 조각을 못 보고, 16비트 값
  전부를 참조로 보면 BIOS 인자(`$FA`)까지 포인터로 읽어 글자 중간(9D46)을 경계로 삼는다. 분할 즉치(zp `$FA` 제외) +
  조각 안 `0F/10` 피연산자로 좁혔다.
- 초벌 94건 중 18건이 자리를 넘어 게이트에 걸렸다. 한 번에 다 보이게 오류를 모아서 내니 두 바퀴로 끝났다.
- 오버월드 스테이트(`overworld1.mcs`)는 **RAM 에 옛 본 프로그램**을 품고 있어 시스템 문구 확인엔 못 쓴다 —
  타이틀 스테이트에서 다시 가야 한다(적재 이후 스테이트는 옛 문안을 되살린다, PS1 함정 재현).

## 2026-09-06 (3) — 기반 다지기: HUD 지명 · 부팅 화면 · 몬스터 이름

유저 방침 「씬보다 시스템 문구·타이틀·오프닝/엔딩 등 기반부터」. 셋을 끝내고 남은 것의 좌표를 세웠다.

- 🔴 **ruff 가 내 편집을 조용히 무효로 만들었다.** HUD 지명(`places`)이 화면에 안 나와서 빌드한
  이미지를 뜯어 보니 `06` 이 **왼쪽 패딩**으로 들어가 있었다. 원인은 코드가 아니라 편집 —
  문자열 치환으로 삼항식을 고쳤는데 그 사이 `ruff format` 이 그 삼항식을 다시 줄바꿈해서
  **패턴이 안 맞았고**, 치환은 예외 없이 「안 바뀐 채로」 지나갔다. 교훈은 둘이다:
  치환은 **성공을 확인**한다(`assert old in s`), 그리고 **포매터를 돌린 뒤엔 소스를 다시 읽는다**.
- **`06` 은 종결이지 패딩이 아니다.** 지명 렌더러(`$92A0`)는 「이름 06」을 읽고 뒤를 안 본다 —
  오른쪽 정렬로 `06 06 06 … 이름` 을 쓰면 **첫 바이트에서 끝나 이름칸이 빈다.** 아이템·주문이
  0x20 오른쪽 정렬이라 같은 규칙일 거라 넘겨짚은 게 화근이었다. 가족마다 패딩 규칙이 다르다.
- **스테이트로는 시스템 문구를 못 본다.** 확인하려고 `overworld1.mcs` 를 로드했더니 메뉴가 통째로
  일본어였다 — 시스템 문구는 CD RAM(뱅크 0x74·0x78)에 **부팅 때** 올라오므로 스테이트가 곧 옛
  빌드다. PS1 이 오버레이로 물린 것과 같은 함정인데 **자리가 다르다**(저기는 워크 RAM, 여기는 CD RAM).
  `write_memory` 로 그 자리를 덮어 봤지만 HUD 이름칸은 **맵이 바뀔 때만** 다시 그려서 그것도 안 됐다.
- **부팅·파일 선택 화면은 「화면」 단위로 길이를 지킨다.** `col row <SJIS> 00` 레코드가 이어지고
  `FF` 가 끝인데, 코드가 가리키는 건 **화면 머리**뿐이라 안에서는 줄끼리 길이를 옮겨도 된다.
  실제로 「출력할 수 없습니다」 계열은 줄 나눔을 새로 잡아야 들어갔다(한국어가 짧아 앞줄이 남는다).
- **몬스터 이름이 어디 있나를 두 번 틀렸다.** 09-05 에는 「rel 162 는 우리 컨테이너 형식이 아니다
  (디렉터리 없음)」로 닫았었다. 다시 보니 **디렉터리가 있는데 항목이 4B**였다(씬은 5B + `FF` 끝).
  단서는 엉뚱한 데서 왔다 — 트랙 전체를 SJIS 로 훑었더니 텍스트가 **8바이트씩 토막나** 보였고,
  그게 곧 LZ 플래그 바이트 사이의 리터럴 8개다. 즉 「토막난 일본어 = 압축된 텍스트」다.
- 🔴 **긴 이름은 간접 참조다.** 이름칸이 16B 라 「キャリオンクロ－ラ－Ａ」가 안 들어간다 —
  원본은 `23 주소(2)` 로 블록 안 다른 자리를 가리키고 꼬리 `Ａ` 를 뒤에 붙인다. 처음엔 전부

- ⚠ **긴 이름 저장소를 레코드로 오독했다.** rel 186 blk9 의 「B\nダークリッチ」는 몬스터가 아니라
  앞 레코드 셋이 가리키는 저장 칸이다. 표 끝 판정을 `FF FF FF FF` 하나에만 맡긴 게 문제였고,

    고친 화자표의 진짜 소비자는 **대사 이름창**이다. 소비자를 세운 셈이라 헛걸음은 아니었다.

- **음성 조사(유저 요청).** 먼저 **디스크 구성부터 틀려 있었다** — 도구가 훑던 `rel 0~1,760` 은
  데이터 트랙의 일부고, 트랙 2 는 **10,297섹터**다. 그리고 **BGM 은 CD-DA 19트랙**(약 58분)이라
  우리 작업 대상이 아니다. 음성만 데이터 트랙 안 ADPCM 이다.
- **적재 경로를 살아 있는 화면에서 확인했다** — `CD_READ`($E009)에 BP 를 걸고 제로페이지를 읽으니
  `_al`($F8)=섹터 수 · `_dh`($FF)=0xFF 면 ADPCM 이었다. 오프닝 모듈 119섹터(rel 514 와 일치)와
  프롤로그 음성 32섹터가 문서의 값과 맞아떨어졌다. QA 가 그대로 쓸 수 있는 탐침이다.
- 🔴 **오프닝엔 자막이 없다.** 끝까지 돌렸는데 글자 창이 한 번도 안 떴다 — 음성만 나간다.
  ⇒ **kr 범위 밖**이고, 자막을 넣는 건 mod 다. 「엔딩은 씬 안이라 할 일 없다」와 같은 종류의
  **범위를 줄이는 결론**이라 값이 있다.
- ⚠ **정적으로 음성 색인표를 찾으려던 시도는 접었다.** 4B 로드 레코드 꼴로 트랙을 훑으니 후보가
  162개인데 대부분 같은 값이 반복되는 압축 데이터였다. 압축 자료가 깔린 디스크에서 「표처럼 보이는
  바이트」는 신호가 아니다 — 런타임 탐침으로 간다.
- **엔딩 스태프롤을 찾았다**(rel 909, 2,241B, `0x1A` 종단). 09-06 낮에 「엔딩은 씬 컨테이너 안이라
  할 일 없다」고 적은 건 **타이틀 카드 얘기였고**, 성우·제작진 명단은 따로 있다. 탭·CRLF·강조
  코드(`1B`/`1D`)가 섞인 평문이라 형식이 다르다. 렌더러는 엔딩 모듈(rel 898)의 `EX_GETFNT`
  호출 두 곳(+0x56B3 · +0x57CC)이다.
