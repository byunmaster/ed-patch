# ED1 오프닝 한글 폰트 작업일지

영웅전설 1(PS1) 오프닝 내레이션(OPEN1.EXE, LBA 69)을 한글화하는 과정 기록.
코드에는 최종 결과만 남지만, 여기엔 **왜 그렇게 했는지·무엇을 시도하다 막혔는지**를 남긴다.

관련: 메모리 `ed1-opening-font`, 도구 `tools/patch_opening_font.py`.

---

## 목표

오프닝은 세계 지도 위로 내레이션(26문장, ~49 표시줄)이 스크롤된다. 텍스트 번역은
정발(만트라) 기반으로 완료(온리크/라누라 지명 통일 포함). **폰트만 남았다.**

인게임(ED.EXE)은 자체 12×12 비트맵 폰트를 임베드해서, 한자 슬롯을 한글 글리프로
덮어쓰는 방식으로 이미 해결됐다. 오프닝도 같은 줄 알았으나 — 아니었다.

## 1. 폰트 출처 규명 (에뮬레이터 디버깅)

DuckStation 스크린샷으로는 오프닝에 우리 한글 슬롯이 **깨진 한자(亜·室·域…)**로 나왔다.
OPEN1.EXE에 ED.EXE 폰트가 없고 글자가 커서 다른 폰트로 추정 → 확정을 위해
mednafen(디버거 포함)을 빌드해 라이브 분석.

- 정적 분석 착각들: START.DAT·파일 스캔에서 "폰트 비슷한" 밀집데이터가 계속 오검출.
  히라가나 순서 매칭(ヒラギノ 템플릿)도 이미지 데이터에 낚임. **정적 접근은 한계.**
- 라이브 브레이크포인트로 확정:
  - 내레이션 렌더 진입은 파서 `0x800132B0`(문자열 @0x80010198 읽음).
  - 문자 그리기: `0x800136EC jal 0x8001BE24`(a0=SJIS) → 글리프주소 v0 → `0x80013104`로 그림.
  - 글리프주소 함수 `0x8001BE24`: `s0(폰트베이스) + index×30`. **30바이트 = 16×15**.
  - 폰트베이스 s0은 `0x80016CE8` = `addiu t2,0xB0; jr t2; addiu t1,0x51` → **BIOS 콜 B(0x51)**.
  - 실측 s0=**0xBFC66000** (BIOS ROM). 글리프 읽어보니 진짜 한자 도트.

**결론: 오프닝 폰트 = PS1 BIOS 일본어 한자 폰트.** 게임 파일이 아니라 콘솔 펌웨어.
BIOS는 수정·배포 불가 → ED.EXE식 슬롯 덮어쓰기 불가. **OPEN1을 패치해 BIOS 대신
임베드 한글폰트를 쓰게** 해야 한다.

## 2. 막다른 길들

### (a) 제자리 임베드 → OPEN1이 폰트를 지움
OPEN1 이미지(0x80010000~0x80027000)는 코드·데이터로 꽉 찼고, 유일한 여유는 tail의
0영역. 거기 폰트를 넣으니 **오프닝이 검은화면**. 격리 결과: tail(0x8002546C~)은
**OPEN1의 힙/작업구조체**(setjmp 컨텍스트 포함, 시작 시 0으로 초기화)라 폰트가 로드
직후 지워졌다(RAM 실측 0).

### (b) 힙 재배치 → 참조가 너무 많음
"힙을 자유 RAM으로 옮기면?" 좋은 발상이었으나, 작업구조체 필드를 **코드 38곳 이상이
하드코딩 절대주소로** 접근(렌더 코드 포함). 단일 베이스가 아니라 흩어져 있어, 하나라도
놓치면 크래시. 비실용적.

### (c) ISO 확장 → 배포 패치가 커짐
폰트를 이미지 밖(0x80027000+)에 로드하려면 OPEN1.EXE를 키워야 하고, 그러면 ISO의
후속 파일(OPEN2 LBA116~)이 전부 밀린다(ISO 리빌드). 배포는 xdelta로 가능하나 패치가
커지고 리스크↑. 유저가 원치 않음.

## 3. 돌파구 — PC0 후킹 memcpy (제자리, ISO 안 건드림)

핵심 관찰:
- PS-EXE 헤더 `b_size=0` → **로더는 아무것도 0으로 지우지 않는다**. 폰트는 파일에서
  로드된 그대로 **PC0(진입점) 시점엔 온전**하다. 지우는 건 그 뒤 게임코드(힙 init).
- 자유 RAM이 **1.27MB**(0x8007317F~0x801B0000, 오프닝 내내 0 유지) 남아있다.

⇒ **진입점을 후킹해, 힙이 지우기 전에 폰트를 자유 RAM으로 대피시킨다.**

1. 폰트를 파일에 임베드(로드시 RAM 0x800254E0으로 옴).
2. 저작권 문자열 자리(0x80025414, 힙 밖·미사용)에 **memcpy 스텁**을 넣는다.
3. 헤더 PC0(파일 0x10)를 스텁 주소로 바꾼다.
4. 스텁: 폰트를 0x800254E0 → **0x80080000(자유RAM)** 워드복사 후 원래 PC0(0x80021D50) 점프.
5. 렌더 폰트베이스를 0x80080000대로 리다이렉트(`0x8001BE84` jal 자리에 lui/addiu s0).

`tools/patch_opening_font.py`가 이 5단계 + 내레이션 재인코딩을 자동화.

## 4. 그 과정에서 잡은 버그들

- **인덱스 공식 착각**: 처음엔 표준 JIS 선형인덱스(0x889F=1410)로 base를 잡았는데
  틀렸다. 게임 index함수(`0x8001BED4`)는 첫바이트≥0x88(한자)에서 `0x8001C338` 경로로
  **테이블 룩업**(`index = SJIS − table[k].base + table[k].offset`, 테이블 @0x80024E60).
  `table[0]=(0x889F, 0)` → **index(0x889F)=0, 0-기반·연속**. 그래서 base=폰트시작(오프셋
  없음). 에뮬 실측(카타카나 0x8340→292, jis_index 376과 차이 84)으로 발견.
- **복사 +4 밀림**: memcpy 결과가 일정하게 첫 워드에 쓰레기가 붙어 폰트가 +4 밀림
  (`mem[FONT_LOAD]` 첫워드가 쓰레기; 원인 미규명). 렌더 base=0x80080004로 보정하니
  글리프 정렬 5/5. (내일 근본원인 재확인 여지.)
- 스텁 위치 함정: 0x80025410을 OPEN1이 변수로 써서 스텁 첫 워드가 오염 → 스텁을
  0x80025414(+4)로. 폰트 소스도 setjmp(0x800254A4~DC) 뒤 0x800254E0으로.

## 5. 현재 상태 (2026-07-11 밤)

**오프닝이 한글로 렌더되고 끝까지 정상 재생.** 글리프 정렬·가독 확인(9행).

### 잔여 폴리시 (내일)
1. **글자 아래 그림자 점 행** — 그리기 루틴이 content 뒤에 shadow 4행을 쓰는데
   (`0x80013258 addiu t4,r0,3`), 15→9행 축소 탓에 글자 바로 밑에 노출된다.
   스프라이트 그리기(`0x80017BD4`)의 텍스처 높이도 관련.
2. **글자 크기** — 현재 9행(작음). 더 크게 원함.

### 권장 해법
**네이티브 15행(30B)으로 전환** — 행수/stride 패치를 제거(원본 렌더 그대로)하면
그림자 문제가 자동 소멸하고 풀 품질이 된다. RAM 대피 방식이라 크기 제약은 없어졌으나,
**소스(파일 내 폰트 원본) 공간**이 걸린다:

| 파일 0영역 | 크기 |
|---|---|
| 0x15C69~0x16CD4 | 4203B |
| 0x16E30~0x17239 | 1033B |
| 0x17729~0x17800 | 215B |
| **합** | **5451B** |

30B×191자 = 5730B → **279B 부족**. 대응: (i) 음절 ~10개 감축(재작문) + 멀티블록
memcpy 스텁(저작권 88B 공간이라 2블록까지), 또는 (ii) 축소행 유지 시 shadow·스프라이트
높이(`0x80017BD4` 파라미터)를 패치.

## 6. 폰트 완성 — 네이티브 15행 압축 디코더 (2026-07-12~13)

9행 축소의 그림자·크기 문제를 **네이티브 15행(30B) 전환**으로 근본해결. raw 30B×191=5730B는
안전영역 초과라 **행-마스크 압축**(글리프당 2B 마스크+비영행) → 3620B로 넣고, **memcpy 스텁을
행-마스크 디코더로 교체**해 자유 RAM에 전개.

### 디코더 손인코딩 함정 2개 (반나절 디버깅)

- **andi rs 필드 오타**: `andi t5,t3,1`을 `0x306D0001`로 썼는데 이건 `andi t5,**v1**,1`. rs를
  t3(11) 아닌 v1(3)로 인코딩 → 마스크가 v1(비트0=0)로 읽혀 **모든 행이 빈 행 처리 → 폰트 전부 0**.
  정답 `0x316D0001`. **교훈: 스텁을 `disasm.py`로 역어셈블 + Python으로 로직 시뮬 필수.**
- **load-delay 슬롯**: memcpy에서 `lw t3; sw t3`면 sw가 stale t3 → **+4 밀림**(어제 "복사 +4"의 정체!).
  사이에 `addiu`를 넣어 지연 채우면 해결. (폰트 디코더는 lhu/sh 사이 지연이 이미 채워져 무탈)

### 폰트 크기·품질 결정

- 잘림 원인: dy=2면 잉크가 5~14행(아래여백0)이라 받침이 맨끝행에서 컷. → dy로 중앙정렬.
- 11px(Galmuri11)는 무잘림 시 압축 4338B > 안전 4084B(불가). 9px(Galmuri9)는 3584B로 여유.
- neodgm(16px TTF)은 10~12px까지 들어가나 축소렌더라 획이 거침(유저 확인). **→ Galmuri9 채택**(또렷·전체음절·무잘림, 유저 확정).

### 내레이션 표시 버그 = 렌더가 2바이트 전용

폰트가 뜨자 **중간단어 누락·부호 깨짐**이 드러남. 원인: 표시 루프(`0x800136CC`)가 **항상 2바이트씩**
읽어 1바이트 문자 미지원 → 한글 사이 `\x20` 공백이 다음 글자 첫바이트를 삼켜 **줄 전체 어긋남**.
(폭측정 루프 `0x800132D4`는 1바이트를 폭0으로 건너뛰어 측정≠표시 불일치도 유발.) JP 원문은 전부
2바이트 SJIS + `\n`(0x0A)만 1바이트 특수처리.
**해결: 모든 문자(한글·부호·숫자·공백)를 2바이트 폰트 슬롯으로 통일(196글리프).** → 제자리 줄 온전 렌더.

### 초과줄 재배치 — 미해결(검은화면)

공백 2바이트화로 **17줄이 JP 바이트예산 초과**. 자유 RAM(`0x80082000`) 재배치 시도:

- 포인터테이블(파일 0x145A0~, 줄 RAM주소 1:1) 갱신 + 디코더가 줄 블록도 자유RAM 복사.
- **크래시 → 블록이 안전영역(0x16CD4) 28B 침범 = OPEN1 테이블 손상**(스캔이 못 잡은 참조). 유저요청대로
  "이셀하사의 거의 중앙에"→"중앙에" 한 줄 축약(28B 확보)해 블록이 안전영역 내에 들어가게 함 → 크래시 해소.
- **하지만 재배치 켜면 오프닝이 검은화면**(크래시X, PC정상, VRAM 0). 원인 미규명 → 내일. 지금은
  `RELOCATE_OVERFLOW=False`(초과 16줄 스킵, 제자리 33줄 정상)로 커밋. 이어작업: `docs/HANDOFF.md`.

## 에뮬레이터 세팅 메모

- mednafen 빌드: `vendor/emucap/adapters/mednafen/build.sh`. deps: brew `flac sdl2 libsndfile`(+cmake 소스빌드).
- BIOS: `~/.mednafen/firmware/scph5500.bin`(일본판) — DuckStation bios에서 복사.
- read/write BP는 **pause 후 step**에서만 작동(run_frames free-run은 무시). PSX는 exec/read/write 모두 `cpu` 메모리타입(가상주소).
- 프로세스 종료: `pkill -9 -f "emucap/mednafen/47800/mednafen"`(광역 kill 금지).
- 오프닝까지: 부팅 후 start → circle(ED1 선택, 일본판이라 ○=확인) → ~900프레임.

# 2026-07-13 (회사): 텍스트 완성 — 재packing·0x0A 필드클리어·advance 축소·정발 원문

## 검은화면의 진짜 원인과 재packing (재배치 문제 종결)

재배치 검은화면의 원인은 **스크립트(0x145A0)가 포인터 "값"의 주소 범위로 text/command를 구분**하기
때문이었다: text_ptr=0x8001xxxx, command_ptr=0x80026Dxx. 줄을 자유RAM(0x80082000)으로 옮기면
command로 오인 → 검은화면. 해결은 재배치가 아니라 **저주소 텍스트 영역(파일 0x974~0xEEE, 1402B) 내
재packing**: 50줄을 영역 상단부터 아래로 촘촘히 다시 깔고 포인터테이블만 갱신. 전 줄 저주소 유지.

## "세리오스→리오스" 글자 잘림과 딸림("파렌, 온리크, 는")의 규명

표시 루프는 **널 검사 없이 X좌표(s3)가 960(필드 우변)에 닿을 때까지** 그린다. 필드는 [896,960]=64유닛.
- 긴 줄(>필드): 중앙정렬 시작점이 화면 밖 → 앞뒤 글자 잘림("세리오스"→"리오스").
- 짧은 줄: 자기 글자를 다 그려도 널에서 멈추지 않고… 인 줄 알았으나, 실은 **0x800136B4에 널 종료가
  이미 있었다**. 진짜 원인은 **잔상**: 원본 JP 각 줄은 `…0A 00`으로 끝나고, **0x0A(개행) 핸들러
  (0x8001366C)가 960까지 빈 글리프16으로 필드를 채워 이전 줄 픽셀을 지운다**. 우리 줄엔 0x0A가 없어
  이전(더 긴) 줄 잔상이 남았던 것. RAM 라이브 패치 대조실험으로 확정(0x0A 주입한 파렌 줄만 깨끗).
  → enc()가 각 줄 끝에 0x0A 자동 부가.

## 글자 간격(가독성)과 줄당 한계 확대

전각 1글자 advance는 4유닛(=16px 셀)인데 Galmuri9 잉크는 ~9px라 성김. 폭측정(0x13370)·표시(0x13750)의
`addiu ,4`를 **3(12px)으로 패치**(둘 다 바꿔야 중앙정렬 일치). 2(8px)는 넓은 받침 겹침 — 라이브 패치로
2/3/4 비교 후 3 채택. 부수효과: **줄당 한계가 16→21전각슬롯**(64÷3)으로 늘어 정발 장문 수용 가능해짐.

## 정발 원문 적용 (유저: "정발판에 이렇게 오프닝이 있어")

정발 오프닝은 SINDLL이 아니라 **`originals/kr/ED1/OPENING.EXE`**(OPEN.EXE도 동일)에 CP949 평문으로
있다(0x5E07B~, 26문장). 이를 우선 적용, JP에만 있는 부분(다섯 나라·몬스터 습격 확장)은 정발 어투 신규
번역. 표기 규칙(유저 확정): **쉼표 뒤 공백 없음**(쉼표도 전각 슬롯이라 여백 과대), **문장 끝 마침표
일관**, 따옴표 미사용. 예산이 빠듯할 땐 **어색한 한국어(겹말 등) 수정으로 공간 확보** — 45/47행의
"왕위계승때까지" 중복 제거로 8슬롯 확보한 것이 대표 사례. 문안 변경은 반드시 사전 보고.

## 50번째 줄 누락 발견 (전수 캡처의 소득)

전체 캡처 검수 중 마지막 화면에 깨진 글자 발견 → 포인터 0x147B8의 50번째 줄
`それから約１０年の歳月が流れた…`(파일 0x974)이 LINES에 누락돼 JP 원문이 한글 폰트로 깨져 표시되고
있었다(작업 초기부터). 정발 "그리고, 10여년의 세월이 흘렀다."로 추가. 영역 경계도 0x998→0x974로 확장.
영역 앞(0x938~ 포인터 배열)·뒤(0xEF0~ TIM 파일명, 0x14824~가 참조)는 확장 불가 확인 — **예산 1402B 고정**.
