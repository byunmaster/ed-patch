### 2. LZ 코덱 — 디컴프레서 `$0C9E~$0DEE` 이식, 왕복 검증

블록 = `[LE16 길이-1][00][플래그8][스트림]`. 플래그 워드(LE16, LSB 부터)와 데이터가 섞인 LZSS —
리터럴 / 거리 8비트 / 거리 13비트, 길이 부호 2~269(단항+3비트+바이트), 거리 1 = RLE(14~4,109),
거리 0 = 끝. 정본은 [`tools/lz.py`](../tools/lz.py) 머리말. 색인 접근은 `$0C60`(a1=색인, d0=번호).
`archives.py --check` 가 225+110+… 블록의 **디코더 끝 == 헤더 길이**를 매번 확인하고, 실물 블록
재압축 왕복도 본다. ⚠ 인코더는 탐욕 매칭이라 원본보다 **~3.5% 크다**(script 35: 2,492 → 2,579B) —
자리가 빠듯해지면 최적 파싱으로 바꾼다.

### 4b-2. BDF 는 **BBX 의 y 오프셋을 써야 한다** (2026-09-06, pce 발 지적)

`_load_bdf` 가 BBX 의 `by` 를 버리고 모든 글리프를 같은 행에 붙이고 있었다. 한글은 `by=0·bh=11`
이라 우연히 맞았지만 **키 작은 글자가 셀 꼭대기에 붙는다** — MD 에서 해당하는 건 **「…」**
하나다(`BBX 9 1 1 5` → 밑에서 5행 떠야 한다). 문안엔 전투 26곳에 있다.

- 고친 식: `행 = top + (ref − (by + bh))`, **`ref` 는 한글 한 글자(가)의 `by+bh`**(=11).
  ⚠ `FONT_ASCENT`(14)를 쓰면 한글이 3행 내려가 **HUD 장 제목 바에서 받침이 잘린다** — 그래서
  「위쪽 정렬」이라는 우리 사정은 `top` 으로 유지하고 글자 간 높이 차이만 `by` 로 맞춘다.
- 확인: 빌드 롬에서 「…」 잉크 행 **6~6**(가운데), 「가」는 **1~11**(그대로).
- 반각(마침표·쉼표)은 이 경로가 아니다 — 원본 리소스 1 글리프 + 우리가 그린 것이라 영향 없다.
  자막(리소스 5 네오둥근모)은 PIL 렌더라 원래 정상이었다(`work/emu/qa_opening.png` 의 「옛날…」).

### 4b. 한글 코드는 정본에 고정한다 (2026-09-05)

`textmap/hangul_codes.json` = {글자: 코드}. **쓰는 글자를 유니코드 순으로 매번 매기면 문안이 늘 때마다 코드가
밀린다** — 세이브에 든 장 제목·파티 이름과 스테이트의 글자가 다른 글자로 뜬다(실측: 옛 스테이트의 「제1장 왕자의
여행길」이 「로1됐 렇렁뎐 랑받고」로). 새 글자는 `python3 tools/hangul.py --freeze` 로 **뒤에 붙이고** 커밋한다.
빌드는 정본에 없는 글자를 실패로 친다. 배포 버전 사이에서도 세이브 호환이 유지되는 유일한 길이다.

🔴 **빌드만으로는 절반이다** — 「없는 글자」는 잡지만 **재생성**(코드표를 다시 매기는 것)은 못 잡는다.
그 경우 빌드는 그대로 통과하고 **옛 세이브의 이름·장 제목만 딴 글자로 뜬다**(pce-ed1 이 실제로 겪었다 —
그쪽은 세이브 +0x244 에 파티 이름이 우리 코드로 박힌다). MD 도 **파티 이름은 레코드
(`$FF1DBC+n*0x40+0x30`)에 우리 코드로 들어가고**(인게임 실측: 슬러그A = `8bca 8aeb 8a6f 41 06`)
그 레코드가 세이브에 실린다. ⇒ `tools/hangul.py --check` 가 **커밋본과 대조**해 이미 있던 글자의
코드가 바뀌면 게이트가 운다(P5 축 「세이브 호환: 글리프 배정 고정」).

### 4d-2. ⚠ 미번역 대사는 **일본어가 아니라 빈칸**으로 뜬다 (2026-09-06)

글리프 방침 (b) 로 표 0 의 **가나·한자 자리를 전부 한글로 갈아 끼웠다** — 남긴 원본 글자는
기호·전각 영숫자 87뿐이다(`hangul.KEEP_MAX = 0x829a`). 그래서 아직 정본을 안 채운 대사는
화면에서 **글자가 하나도 안 보이고**, 숫자·부호만 남는다(실측: 라이아스의 첫 대사가 「2」와 마침표만).

🔴 **인게임 QA 에서 「안 나온다」와 「깨졌다」가 구별되지 않는다** — 원본 롬을 같은 지점까지
돌려 보면 갈린다(2026-09-06 실제로 이렇게 갈랐다: 원본은 화자 이름(라이아스) 뒤에 호칭이 붙은 줄이 뜬다).
정본은 지금 **스트림 12/2,750**(블록 104 의 첫 대사와 장 카드 여섯)뿐이다.

### 4e. 장 카드·HUD 제목 — 한 스트림에 계약이 둘 (2026-09-06)

장이 바뀔 때 뜨는 카드(「제2장 침묵의 주문 / 끝」)와 **HUD 왼쪽 위의 장 제목**은 **같은 스트림**에 들어 있다.
자리는 여섯(블록 20 · 34 · 41 · 75 · 82 · 15).

- 머리 스트림 = **앞 30바이트가 HUD 제목**이다. 모듈 코드가 `moveq #$f,d4` + `move.b (a1)+,(a2)+` ×2 로
  **정확히 30바이트**를 `$FF1B3C` 로 복사한다(capstone 확인). **그 뒤 +30 부터가 카드 문안**으로,
  메시지 함수(`movea.w #$85e2,a5`)가 그린다. 즉 한 스트림이 「고정폭 30B 표」와 「자유 문안」을 겸한다.
- ⇒ 정본은 30바이트를 **공백으로 채워** 맞춘다. 모자라면 뒤 스트림의 바이트가 HUD 에 딸려 올라온다
  (실측: `제3장 국왕의 증표\x00제2장 침묵의`).
- 🔴 **조판기를 태우면 이 계약이 조용히 깨진다** — `typeset()` 이 줄을 strip 하고 다시 감아 우리가 센
  여백을 지운다. 그래서 정본 항목에 **`"raw": true`** 를 두었다(`build.build_stream(raw_text=...)`) —
  여백까지 우리가 정한 자리는 조판을 건너뛰고 `\n` 만 `01` 로 바꾼다.
- **중앙 정렬은 원본에서 재서 맞춘다** — 반각 6px · 전각 12px 로 재면 원본 카드 다섯 장이 전부
  **중심 102px**, HUD 제목 넷이 전부 **중심 90px** 이다(원본이 반각 공백으로 들여쓰고 「完」 줄만 전각
  공백을 쓴 이유가 이 계산으로 설명된다). 우리 문안도 같은 중심에 놓았다.
- 문안은 PS1 정본(`patch_gfx_cards.CARDS`)과 같다. 「完」 자리는 「끝」.

### 4f. 메뉴·설정·시스템 메시지를 PS1 표기로 (2026-09-06)

`patch_sys_ui.UI` 를 기준으로 표와 시스템 메시지를 훑었다. **칸이 표기를 이기는 자리**가 또 나왔다.

- 표(`names.json`): `민첩`→**민첩성** · `레벨 업`→**레벨업** · `전투/회복 주문`→**전투의/회복의 주문** ·
  `안 씀`→**미사용** · `빠름/느림`→**빠르게/천천히**. 인게임 확인(`work/emu/sys_config.png` ·
  `sys_battlecfg.png` · `sys_status.png`).
- 🔴 **폭은 곧 픽셀이다** — 반각 1B=6px · 전각 2B=12px 이라 **슬롯 바이트 × 6 = 픽셀 폭**이다. 값 열이
  고정 열에 겹쳐 찍히므로 라벨+여백의 **바이트 수**를 원문과 맞춰야 값이 안 밀린다(설정 A 는 15B,
  설정 B 는 13B 자리에서 값이 시작한다).
- 🔴 **값 문자열은 슬롯 폭까지 공백으로 채워져 지우개 노릇을 한다** — 원문이 `ＯＮ  `·`速い  ` 처럼
  전부 같은 폭인 이유다. 우리 값도 표 기록기가 폭까지 채우므로 `천천히`→`보통` 으로 되돌려도 꼬리가
  안 남는다(인게임 확인).
- 시스템 메시지(`sysmsg.json`): 원문이 존댓말인 자리는 존댓말로 되돌렸다(`얻었습니다`·`포기했습니다`·
  `찾았습니다`), 전투 문구는 PS1 표기로(`전투에서 승리/패했습니다` · `해치웠다` · `회심의/통한의 일격` ·
  `혼란에 빠졌다` · `마비되고 말았다` · `정신을 차렸다`).
  ⚠ **묶음이 제자리라 못 맞춘 자리 다섯**: `아무 일도 없다`(PS1 「없었다」) · `에겐`(PS1 「에게는」) ·
  `전원 설정을`(PS1 「전원의 설정을」 — 값 열과 붙는다) · `<0e>을(를) 가졌다`(PS1 「갖고 있었다」) ·
  `더는 못 가집니다`(PS1 「그러나 더는 가질 수 없습니다」). 0x24b1b 묶음은 **73/73B 로 꽉 차 있다.**
  ⇒ 넓히려면 **꼬리 재배치**가 필요한데, 참조 105 중 55 가 `lea x(pc)` 라 ±32KB 밖인 꼬리로는 못 간다.
  절대 참조(50)만 옮기는 길은 열려 있다(아직 안 한다 — 아카이브가 이미 꼬리를 쓴다).

### 4g. 「참조로 찾는다」는 샌다 — 화면 바이트를 직접 센다 (2026-09-06)

시스템 문안은 `lea/pea` 참조로 찾아 왔는데, **참조가 없는 자리가 이만큼 있었다**:

| 어떻게 가리키나 | 무엇이 걸렸나 |
| --- | --- |
| **워드 오프셋 표** `0x73bc`(33항목, `lea $73bc,a3` + `move.w (a3,d0.w),d0`) | 주문·아이템 효과 메시지 30 (MP 부족·주문 봉인·독 상태 따위) |
| **`06` 뒤로 물리적으로 이어지는 꼬리말** | 오름·늘어남·내려감·빼앗음·획득·회복의 과거형 꼬리 따위 |
| **다른 스트림의 `0f` goto 대상** | 오델로 승패 대사 둘 |
| 00 종결 문자열 묶음(표) | 패배 메뉴 3 · 예/아니오 · 삽니다/팝니다 · 전투 하위 메뉴 · 미니게임 라벨 5·이름 2 · `menu_cmd` 22→25 |
| **전투 아카이브도 같다** | 06 뒤 꼬리말 · 레코드 영역의 보스 등장 문구 — `battle.chain()` 으로 39 (스트림 281→320) |

⇒ **`tools/jp_left.py`** 가 원본 코드 영역(0~0x40000)과 **전투 아카이브**에서 **가나가 든 일본어 런**을 세고 정본이 덮는
구간을 뺀다. 남은 자리는 `textmap/jp_left.json` 에 굳혀 두고, **늘면 게이트가 운다**(`--check`).
지금 남은 7 은 전부 코드·그림이 우연히 cp932 로 풀린 것이다.

⚠ 이 기전들 때문에 재삽입기에 둘이 붙었다 —
- **`sysmsg.PINNED`**: 소비자를 못 찾은 스트림은 **제자리에, 원본 길이 안에서만** 다시 쓴다(각자 자기 묶음).
- **`sysmsg.plan` 은 두 패스**: 자리를 **전 묶음** 다 잡은 뒤에 바이트를 만든다. 🔴 안 그러면 묶음을
  넘는 goto 가 옛 자리를 가리킨다 — 실제로 **오델로 승패 대사가 깨져 있었다**(꼬리 공유 스트림
  `0x31154`·`0x31169` 를 우리 문안으로 옮겨 놓고, 그걸 가리키는 goto 는 안 고쳤다).

### 4h. 반각 글리프가 없으면 화면에서 조용히 빈칸이 된다 (2026-09-06)

리소스 1(반각 8×14)의 원본 표는 ` !"-.0-9?A-Za-z` 뿐이다. 쉼표는 이미 끼워 넣었는데 **괄호가 없어
병기 「을(를)」이 화면에서 「을 를」로** 떴다(인게임 실측 — 39자리 전부). `hangul.EXTRA_R1` 에
`(`·`)`·`,` 를 두고 리소스 1 을 다시 만든다. **인코더가 게이트**다 — 표에 없는 반각을 만나면
빌드가 실패한다(이 게이트가 곧바로 `[RETURN]` 의 대괄호를 잡았다).

### 5. 창 규격 (PoC 롬 실측 + 창 서술자 2026-09-05)

메시지 함수 넷(85DC/E2/E3/E4 → `$60A0`, d0 = 0~3)은 같은 창 서술자(`$63FC`, 0x30B → `$FFFE52`)를
쓴다: `00 00 | 00 90 | 00 E0 | 00 50 | 02 00 | 08 08 | 01 01 01` = y 144 · **폭 224px** · 높이 80 ….
`$FF2020` 비트7 이 서면 `$642C`(y 184 · 224 × 40 = 2줄 창), `$FF1853` 비트6(전투?)이면 `$2165A`
(y 176 · **312 × 48**). 뜻은 폭·높이만 확정, 나머지 필드는 미해석.

대사창: **화자 줄 + 본문 3줄**, 본문 한 줄 **210px(전각 17.5칸)** — 옛 값 18칸(안쪽 218px ÷ 피치 12px — `$9802` 가 창 종류에

### 6b. 세이브 물리기 — `tools/import_save.py` (2026-09-07)

`python3 tools/import_save.py` 하나면 유저 세이브가 지금 빌드에 물린다. 두 번 헛돈 자리라 적어 둔다:

- **이름은 롬 md5** — mednafen 은 `<롬 이름>.<롬 md5>.sav` 를 읽는다. **빌드를 다시 하면 md5 가
  바뀌어** 전에 넣어 둔 세이브가 조용히 안 읽힌다(빈 슬롯 셋으로 보인다).
- **크기는 16,384B 그대로.** SRAM 은 `0x200001~0x203fff` **홀수 바이트**지만 mednafen 은 범위를
  통째로 담는다. 홀수만 뽑아 8,192B 로 주면 `Unexpected EOF` 로 **에뮬레이터가 뜨지도 않는다.**
- 🔴 **빈 세이브를 고르지 말 것.** 유저 폴더의 셋 중 둘은 설정만 든 빈 파일이다(비-FF 14B).
  알맹이가 있는 건 하나(2,042B)뿐인데 빈 것을 넣어 놓고 「형식이 다른가」를 한참 뒤졌다.
  스크립트가 **비-FF 바이트 수로 고른다**(`--list` 로 확인).
- 세이브는 **띄울 때** 읽힌다 — 이미 떠 있으면 다시 `launch`.

### D3 엔딩 — 확정된 사실 (2026-09-26 닫힘)

**세이브(SRAM)** — 홀수 바이트 8KB, 1,024B 레코드 8개, 슬롯 하나 = 레코드 둘(A/B). 레코드 = 16B 머리 + **상태 블록
`$FF1ABC` 미러**(레코드 오프셋 = RAM + 0x10). 체크섬이 있어 **오프라인 패치는 슬롯이 무효** → **라이브 RAM 수정 →
게임 안 SAVE → SRAM 을 스테이트(.mcs)에서 인터리브 패턴으로 잘라 낸다**(mednafen 은 kill 해도 .sav 에 안 쓴다).
**위치** — 씬 로더 `$18460` 이 맵 id(`$FF1AC5/6`)를 표 0x134DDC 에서 찾아 씬 번호(`$FF343C`)로 삼는다. 그러나
**서 있는 자리는 34B 워프 서술자**(좌표·방향·카메라·지역 바이트·맵 id) — 서비스 0x836F → `$FF208C` → 전환 루틴
`$17C30` 이 상태 블록 0x00~0x1E 로 옮긴다. 맵 id 만 바꾸면 그림과 스크립트가 섞인다(1차 배달 오진).
