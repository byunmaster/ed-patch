## 2026-09-05: 첫 세션 — 인터리브 오판에서 글꼴·코덱까지

- **ports-survey 의 판정이 통째로 틀려 있었다.** 「.SMD 인터리브 · 커스텀 문자 테이블 · SJIS 0」
  — 소장본은 확장자만 `.SMD` 이고 **plain BIN** 이라(0x100 에 `SEGA MEGA DRIVE`, 벡터가 0 에)
  디인터리브하면 바이트가 섞여 SJIS 가 0 이 된다. 그대로 읽으니 시스템 문구 2,700자 · 오프닝
  자막이 평문으로 나왔고, 대본은 LZ 안에 SJIS 로 있었다. 파일 지문부터 보지 않은 대가다.
  ⇒ `ports-survey.md` 의 MD ED1 행을 고쳤다.
- **폰트는 정적 렌더로 못 찾았다.** 16×16·8×8 1bpp 로 엔트로피 낮은 구간을 그려 봤지만 전부
  4bpp 타일이었다. 결국 **글꼴 표(0x1A551A, SJIS 코드가 순서대로 나열된 1,459자)에 읽기 BP** 를
  걸어 조회 루틴(`$9C36`)을 잡고 그 구조체(`$FF1A68`)에서 글리프 시작을 읽었다. 14×14 에
  **두 면**(채움 + 테두리)이라 스트라이드가 56 — 16×16 으로 그리면 절대 안 보이는 형상이었다.
- **레지스터를 16진으로 잘못 옮겨 RAM 을 엉뚱한 데서 읽었다.** `A4=16718440` 을 0xFF1668 로
  읽고 「구조체가 비었다」고 30분을 헤맸다. 0xFF1A68 이다. emucap 상태값은 십진이다.
- **LZ 는 단항 길이 부호의 극성을 반대로 읽었다.** `bne $dcc`(비트 1 이면 멈춤)를 0 으로 읽어
  첫 블록 셋째 바이트부터 갈렸다. 6블록의 「디코더 끝 == 헤더 길이」 대조로 잡았다 — 코덱은
  **실물 블록 여러 개로 경계까지** 맞춰야 안심이다.
- **인코더는 플래그 워드 자리를 한 번 틀렸다.** 그룹이 차는 순간 내보내면, 그 마지막 비트에 딸린
  데이터 바이트가 다음 그룹으로 밀린다. 디코더는 비트 직후 바이트를 읽고 **다음 비트가 필요할 때**
  워드를 읽으므로 내보내기를 미뤄야 한다. 합성 왕복 테스트가 바로 잡았다.
- **대본 자리 찾기는 세 번 헛돌았다.** (1) `1E 侍女 04` 가 롬 0x158BAD 에 평문으로 보여 읽기 BP 를
  걸었더니 부팅 체크섬만 걸리고 대사 때는 안 걸렸다 — LZ 스트림 안의 **리터럴 조각**이었다.
  (2) RAM 대본 자리(`$FF6E62`)에 쓰기 BP 를 걸자 그래픽 스테이징(`$FF5650`~)이 같은 자리를 먼저
  덮었다(PCE 와 똑같은 함정). 값 필터를 걸어도 **모듈 로드 주소가 회차마다 달랐는지** 안 걸렸다.
  (3) 결국 **헤더 길이로 이어지는 블록 체인을 롬 전체에서 정적으로 스캔**하는 게 답이었다 —
  0x135324 부터 225블록이 한 줄로 이어졌고, `lea $134FA0` 이 그 색인이었다.
- **아카이브 색인의 「다음 항목」 읽기는 +2 다.** `$0C74` 가 `move.l 2(a1,d0.l)` 로 다음
  오프셋을 읽는데 항목은 4B 라 **반 어긋난 값**이다 — 게임은 그걸 크기 검사(0·음수 배제)에만 쓴다.
  우리가 흉내 낼 필요는 없지만 「색인이 왜 저렇게 생겼나」로 헤매지 말 것.
- **모듈 안에 68000 코드가 있다.** 블록 0 머리가 `movem.l` 이라 처음엔 「텍스트가 아닌가」 했다.
  씬 = 코드 + 이벤트 + 문안 한 덩이다(PCE 와 같은 계열이지만 저쪽은 코드가 아니라 이벤트 바이트코드).
  문안 참조가 pc 상대라 재삽입은 「문안 교체」가 아니라 **모듈 재조립**이다.

## 2026-09-05(3): 재조립기와 길이 변경 PoC — 종결 코드·특수값·뿌리 규칙이 세 번 바뀌었다

- **PoC 의 블록을 잘못 골랐었다.** 「侍女」 가 있는 블록이 9개인데 그중 35 를 옮기고 「재압축·재배치
  통과」로 적었다. 대사 때 RAM 0xFF6650 을 블록 225개와 맞대 보니 침실은 **104** — 35 는 로드조차 안
  됐다. 판정 문장을 지우고 104 로 다시 쟀다(원본 자리를 FF 로 지워 옛 자리를 안 읽는 것까지).
  「화면에 떴다」는 「내가 바꾼 것을 읽었다」가 아니다 — 바꾼 자리를 지워야 증명이 된다.
- **06·07 이 스트림의 끝이었다.** 처음엔 00 만 끝으로 봐서 파서가 07 뒤의 **코드**를 문안으로
  삼켰고(블록 141), 그 안의 진짜 `lea` 가 「문안 안의 뿌리」로 잡혀 재조립이 거부됐다. 메시지 함수
  `$60A0` 이 렌더러를 한 번만 부른다는 걸 읽고서야 06/07 = 반환 = 끝으로 못 박았다. 05 만 이어진다.
- **`10 8644` 는 오프셋이 아니다.** 상대 오프셋으로 풀면 −0x6EEC 라 재조립이 16비트를 넘겼다.
  핸들러 `$A2AE` 가 그 값을 `$FF3644`(동적 문자열)로 바꿔치는 특수 케이스였다 — 15 와 같이 상위비트로 가른다.
- **뿌리 규칙은 세 번 바뀌었다.** 「lea a1 전부」 → 글자 수로 거르기(분기 허브 142건을 버림) →
  「바로 뒤 movea.w a5 의 함수 ID」(54건 놓침 — `46DF` 가 끼어든다) → **ID 또는 내용(화자 태그·SJIS 3자↑)**.
  `46DF` 만 따르는 529건은 자료 포인터라, 내용 규칙이 없으면 재배치가 코드를 깨뜨렸을 것이다.
- **대사창 피치는 12px 다.** 글리프가 14px 라 14 로 잡았다가, 늘린 대사의 「。」 이 잘린 자리를 재니
  18칸 × 12px 였다(`$9802` 의 `$FF2014 = 0x0C`). 오프닝만 14px. **자동 줄바꿈이 없다** — 조판기가 갈라야 한다.
- `$200.w` 는 RAM 이 아니라 **롬 0x000200** 의 포인터다(절대 단축 주소는 부호 확장). 디스패처 `$634`,
  ID 표 `$68C`(163개), 함수 표 `$7D4`. 덤프의 RAM 0x200 을 읽고 한 번 헤맸다.
- **표 참조는 블록 둘뿐이었고, 진짜 함정은 음수 오프셋이었다.** 표 뿌리를 넣어도 화자 태그가 안 늘어
  보니 `10 FFF6`(−10) 을 「상위비트 = 엔진 특수」로 버리고 있었다. 핸들러를 다시 읽으니 15 는 상위
  니블이 정확히 8, 10 은 정확히 8644 만 특수다. 「비트 하나로 가르는」 지름길이 두 번째로 물었다.
- **그래픽 문자는 없었다.** 타이틀 VRAM 을 8×8 시트로 펴 봤지만 눈으로 못 갈랐고, 대신 「はじめから」
  를 롬에서 찾으니 대본 블록 0 의 스트림(`FE 10 … FE 0C`)이었다. 가타카나 12×12 리소스(#4)는
  타이틀용이 아니라 이름 입력용이다(히라가나가 없다). 「그림인가」는 VRAM 보다 **문자열 검색이 먼저**다.
- **덤프 함수 교체를 두 번 헛쳤다.** `str.replace` 로 본문을 바꾸는데 ruff 가 이미 줄을 다시 접어
  옛 문자열이 없었다 — 조용히 안 바뀐다. 함수 머리~다음 정의 사이를 **잘라 갈아 끼우는** 쪽이 안전하다.
- **게이트 결과를 `| tail` 로 보면 종료 코드가 사라진다.** 빨간불인 채 `&&` 가 커밋을 통과시켰다.
  파일로 받아 종료 코드를 따로 본다.
- **4MB 확장은 헤더만 늘려선 안 된다.** 검은 화면에서 PC 를 두 번 찍으니 SRAM 초기화(`$1116A`,
  0x200401 부터 홀수 바이트 FF 채우기)를 **계속 다시** 돌고 있었다 — `$11188` 이 SRAM 에 서명을 쓰고
  되읽는데 4MB 롬이 0x200000 을 덮어 롬 바이트가 되읽혀서다. 플랫폼 문서 §2 가 말한 「SRAM·주변장치
  매핑 검증」이 이것이다. 매퍼(`$A130F1`) 토글 없이는 2MB 가 상한이다.
- **체크섬 불일치는 선다.** 4MB 를 재면서 `$11302` 를 읽었다 — 헤더 ROM end 까지 워드 합을 `$18E` 와
  비교하고 틀리면 `$11330` 무한 루프(VDP 배경만 바꾼다). 「늘 맞춘다」의 근거가 생겼다.

## 2026-09-05(4): 방침 (b) — 한국어 첫 대사까지, 14px 글꼴이 12px 피치에 부딪혔다

유저가 글리프 자리를 (b)(한자 슬롯에 쓰는 한글만)로 정했다. 정본 형식(`script/NNN.json`, 원문은
해시만) · 인코딩(0x8A40~ 유니코드 순) · 글꼴 리소스 0 재구성 · 허용 구간 밖 쓰기를 거부하는 빌드를
한 번에 세우고 첫 대사 두 스트림을 한국어로 넣어 인게임까지 갔다.

- **한계 1 — 14px 글꼴은 12px 피치에서 옆 글자를 갉는다.** 첫 빌드(Galmuri14)는 화면에 떴지만
  「왕자님」이 깨져 보였다. 글리프가 14 폭인데 12 마다 찍으니 다음 글자의 **테두리 면(검정)**이 앞
  글자의 오른쪽 2px 를 덮는다. 앞선 PoC 의 「한」 도 같은 이유로 찌그러져 보였던 것이지 BDF 파싱
  문제가 아니었다(BBX 14×14 정상). **극복**: 후보 넷을 12px 피치로 합성해 비교(`font_cmp.png`) →
  Galmuri11(11×11)이 1px 여유로 깨끗. 원본 굵기(2px 획)에 가까운 Bold 는 글자끼리 닿아 보류.
  피치를 14 로 올리는 길(`FE 0E`)도 있지만 한 줄이 18칸 → 15칸으로 준다.
- **한계 2 — 획이 얇다.** 원본 일본어 글꼴은 2px 획이라 흰 몸통이 두껍고, Galmuri 는 1px 라 같은
  창에서 가늘어 보인다. 검은 테두리는 어두운 창 배경에서 안 보이니 굵기 차이가 그대로 드러난다.
  결정은 유저 몫으로 두고 상수 한 줄(`hangul.BDF`)로 바꿀 수 있게 했다.
