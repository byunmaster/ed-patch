https://github.com/nleseul/ds6_pc98_trans — Python, **Unlicense(퍼블릭 도메인)**.

🔴 **문안은 안 본다.** 우리 방침은 JP 원문 직역이고(루트 ROADMAP 「기본 방침」), 남의 번역을
저본으로 삼으면 그 해석의 오류까지 물려받는다. 저자 본인이 _"My Japanese is still fairly
mediocre"_ 라고 적어 뒀다. 가져오는 건 **구조 지식과 하네스 설계**뿐이다.

## 🔴 갈리는 자리 — 폰트

그쪽은 **영문이라 반각 ANK 로 끝난다.** CGROM 글리프를 읽어 오는 헬퍼(`0x8a49`, 0x50B)를
NASM 으로 다시 써서 **반각 폭으로 접어 넣는 것**이 전부다.

우리는 한글 2,350자를 **디스크에서 싣어야** 한다 — 같은 루틴을 후킹하지만 「ROM 에서
읽기」를 「우리 표에서 읽기」로 바꾸는 것이라 **작업이 그쪽보다 크다.** 그쪽 코드가 답을
주는 게 아니라 **후킹이 성립한다는 증거**를 준다.

## ⚠ 컨테이너가 다르다 — 지문이 안 맞는다

그쪽 원본은 **NFD** 덤프이고 우리 소장본은 **d88** 이다. README 의 sha1 세 개는 우리
`tools/common.py` 의 것과 **당연히 다르다**(같은 디스크의 다른 담는 그릇).
그쪽 파일 오프셋 산식(`addr - 0x4000 + 0x13e10`)도 NFD 레이아웃의 것이라 **그대로 못 쓴다** —
우리 좌표는 `common.read_d88()` 의 평면 이미지 기준이다.

## 아직 안 본 것

`ds6_util.py`(1,597줄) · `build_patch.py`(1,339줄) 전문. 재삽입 설계에 들어갈 때 읽는다 —
지금 통째로 옮겨 적으면 **우리 이미지에서 검증 안 된 상수**가 문서에 박힌다.

## 2026-09-08 — 그쪽 제어코드 표가 우리 구멍을 짚어 줬다

막힌 자리(왕가 장비가 두 번 나온다 · 아크담 루프) 때문에 `ds6_util.py` 의 `EVENT_CODE_INFO`
를 처음으로 열었다. 우리 `walk_scn.CODE_LEN` 과 **길이는 다 같았다.** 새로 얻은 것은 **뜻**이다:

    0x09  길이 2   **파티 이름 주입**       ← 우리 표엔 뜻이 없었다
    0x0F  길이 3   점프
    0x10  길이 3   서브루틴 호출
    0x11~0x14 길이 3  조건 분기 계열
    0x15  길이 3   **어셈블리 호출**
    0x16  길이 **11**  선두에 따른 다중 호출로 보인다

🔴 **그리고 우리 가드가 좁았다는 게 드러났다.** 우리는 「길이 3짜리 옵코드 + 목적지가
창(`0xExxx`)인가」로만 인자를 지켰다. 그래서 **`0x09`(2) · `0x0C`(3, 주소 아님) · `0x16`(11)**
의 인자를 통째로 놓치고 있었다.

**실측: 런 머리가 옵코드 인자에 걸친 정본 블록이 61.** 그중 **`0x16` 이 22 · `0x0C` 가 18**이다.
⇒ 가드를 **길이 표 전체**로 넓혔다(`MULTI_OPS`). `0x16` 은 **인자가 열 바이트**라 한 자리에서
열 바이트를 덮었을 수 있다 — 「다중 호출」을 뭉개면 **이벤트가 다시 돌 만하다.**

⚠ 대신 **뒤로 훑기에 멈춤 조건**이 필요했다 — 종결자(`00/06/07/0A/0D`)나 화자 여는 `1E` 를
만나면 멈춘다. 안 그러면 **데이터 속의 `0x16` 을 옵코드로 읽어 오탐**한다(실측: 화자 런
`頑固そうな老人` 앞 아홉 바이트에 `0x16` 이 있는데 사이에 `1E` 가 있다).

💡 **교훈 — 남의 표에서 가져올 것은 「길이」가 아니라 「뜻」이었다.** 길이는 우리도 갖고
있었는데, **`0x16` 이 열 바이트라는 사실을 우리 가드가 안 쓰고 있었다.** 표를 갖고도
**끝까지 안 쓴 것**이 구멍이었다.
⚠ 그쪽 결론을 값으로 검산한다는 원칙대로, **뜻은 아직 가설**이다. 우리가 확인한 것은
**길이가 우리 표와 같다**는 것과 **인자를 덮으면 안 된다**는 것뿐이다.
