## 확정된 것

### 1. 원본 — 2HD 3장, FAT 없는 자체 레이아웃, **디스크마다 섹터 ID 가 다르다**

`originals/jp/pc98-ed1/` — d88 각 1,281,968B, 섹터를 이으면 **1,261,568B**
(= 1232KB 2HD: 77트랙 × 2면 × 8섹터 × 1024B). 지문 정본은
[`tools/common.py`](../tools/common.py) 이고 `python3 tools/common.py` 가 확인한다.

| 장       | 무엇                       | 마커  |
| -------- | -------------------------- | ----- |
| Event    | 오프닝·데모·유틸리티 메뉴  | 78    |
| Program  | 본체(엔진·전투·메뉴)       | 24    |
| Scenario | 시나리오 + **세이브 매체** | 3,694 |

- **FAT 도 파일 시스템도 없다** — `IPL`·`FAT`·`.EXE` 어느 문자열도 0건이고, 부트 섹터부터
  바로 8086 코드다. 로더가 **섹터 번호로 직접 읽는다** ⇒ 파일 단위 교체가 아니라
  **섹터 단위 패치**가 된다.
- 프로그램 디스크 부트 섹터의 서명:
  `The Legend of Heroes for PC-386,286 & PC-9801  Copy rights 1989,90 Nihon Falcom LTD.`
- ⚠ **시나리오 디스크는 게임이 쓰는 매체다**(세이브). 소장본에 세이브가 남아 있으면 지문이
  갈린다 — 영문 패치 레포도 같은 경고를 달았다([prior-art](prior-art.md)).
- 🔴 **섹터 ID 가 1 부터가 아니고, 세 장이 서로 다른 대역을 쓴다** —
  event `0x30~0x37` · program `0x10~0x17` · scenario `0x20~0x27`, 그리고 **부트만 `R=0x01`**.
  로더가 이걸로 「지금 꽂힌 게 어느 장인가」를 가리는 것으로 본다(가설).
  ⇒ 다시 쓰는 날에도 **섹터 ID 를 보존**한다. 정규화하면 디스크가 안 읽힐 수 있다.
- 🔴 **시나리오 디스크는 3:1 인터리브로 물리 배치**돼 있다(`20 23 26 21 24 27 22 25`).
  d88 트랙표 순서 ≠ 게임이 읽는 순서라, 그냥 이어 붙이면 **문자열이 조각난다**
  (실측: 그 상태로는 마커가 3,694, 논리 순서로 세우니 3,704). event·program 은 논리 순서다.
  ⇒ `common.read_sectors()` 는 **트랙 안 R 순위**를 논리 번호로 쓴다(base 상수를 안 둔다).

### 2. 폰트 — 🔴 레트로 PC 의 관문이 여기서 풀렸다

글꼴은 **디스크에 없다.** 본체 CGROM 이다. 그런데 이 게임은 텍스트 VRAM 에 맡기지 않고
**CG 윈도우로 도트를 읽어 자기가 그린다** — 후킹할 자리가 있다는 뜻이다.

```
0x0269  cmp ax, 0x3021      ; JIS 제1수준 경계로 한자/비한자 분기
0x026e  sub ah, 0x20        ; JIS → CG 코드
0x0271  out 0xA1, al        ; ten (코드 하위)
0x0275  out 0xA3, al        ; ku  (코드 상위)
0x027f  out 0xA5, al / in 0xA9   ; 16행 × 좌·우 = 16×16 글리프
0x0291~ (비트 조작)         ; 굵게/윤곽 처리
0x02a6  stosw es:[di]       ; RAM 버퍼로
```

측정 정본은 [`tools/probe_font.py`](../tools/probe_font.py) — **CG 루틴 9곳**
(Event 6 · Program 3 · Scenario 0). 판정이 뒤집히면 이 스크립트가 먼저 운다.

- **후킹이 성립한다는 증거**는 영문 패치가 이미 준다 — 같은 헬퍼를 NASM 으로 다시 썼다
  ([prior-art](prior-art.md)). 다만 그쪽은 반각 ANK 로 끝나고 **우리는 한글 2,350자를
  디스크에서 실어야 한다**(× 32B = 75,200B).
  **실을 자리는 있다 — 다만 디스크마다 다르다.** 지도는 [`tools/free_map.py`](../tools/free_map.py).
  🔴 **0xFF 런은 미포맷이 아니었다** — 세 장 다 섹터 1,232장이 전부 정상 CHRN·1024B 이고,
  그중 일부가 0xFF 로 채워져 있을 뿐이다. 즉 **주소를 매길 수 있는 빈 섹터**다.

| 장       | 빈 섹터  | 제일 큰 연속                                                         |
| -------- | -------- | -------------------------------------------------------------------- |
| event    | 601,088B | 852~1231 = 389,120B                                                  |
| scenario | 462,848B | 1006~~1231 = 231,424B · **809~~895 = 89,088B**(시나리오와 전투 사이) |
| program  | 21,504B  | 1216~1231 = 16,384B                                                  |

~~🔴 program 디스크가 병목이다~~ **아니었다**(2026-08-30 해결, 12절). 로더가 **두 드라이브를
다 읽으므로**(`AL=0x90` 드라이브1 · `AL=0x91` 드라이브2) 폰트가 program 에 있을 이유가 없다.
자리 문제는 디스크가 아니라 **RAM** 이었고, 그쪽도 자리가 있다.

⚠ **「비었으니 써도 된다」가 아니다.** 여기서 「비었다」는 섹터가 한 값으로 채워졌다는
뜻이고, **로더가 그 섹터를 안 읽는다는 증명이 아니다.** 쓰기 전에 확인한다 — 이 레포는
같은 판단으로 사운드 뱅크를 깨뜨린 적이 있다(`our-findings.md` 「빈 공간의 VAB 함정」).

### 3. 시나리오 디렉터리 — 파일이 없으니 「몇 번째 섹터부터 몇 장」이 전부다

정본은 [`tools/scn.py`](../tools/scn.py) (우리 이미지에서 재확인).

```
시나리오 = 논리 섹터 256~808 · 각 시나리오 = 머리 1장 + 머리[6] 장   → 224 건 (553섹터를 정확히 채운다)
전투     = 논리 섹터 896~1005 · 한 장에 하나                          → 110 건
머리 0x00 `e9 xx xx` = 진입점 0xe000 · 0x03 `e9 xx xx` = 0xe003
```

- ⚠ **머리[6] 을 못 믿는 자리가 둘 있다**(`20.00.20` → 2, `26.01.22` → 3). 선행 영문
  패치도 같은 자리에 같은 예외를 박았다 — 서로 독립으로 같은 값에 걸렸으니 데이터의 성질로 본다.
- **꼬리 빈칸이 시나리오 104,462B · 전투 48,068B** 있다. 🔴 0xFF 미포맷 런과 달리 이건
  **로더가 실제로 읽는 자리**라 값이 다르다.

### 4. 텍스트 — 생 SJIS, 제어코드가 **만트라 정발과 같은 집안**

시나리오 디스크 마커 3,694. 실측한 블록 문법:

```
1E <화자 SJIS> 04    화자 헤더        01  개행        00  종료
10 xx xx             블록 머리(2바이트, 미규명)      20  공백
```

정발 DOS ED1(`SINDLL/*.DLL`)의 `1E 화자 04` / `01` / `00` 과 **같다**
(루트 ROADMAP 「DOS 정발판 대사 추출」). 만트라가 PC-98 판을 이식했다는 문서상의 판단이
**제어코드로도 받쳐졌다** ⇒ `ps1-ed1+2/tools/extract_dos_kr.py` 의 문법 지식이 붙는다.

- ⚠ **저본은 아니다.** 문안은 JP 원문에서 직접 번역한다(루트 ROADMAP 「기본 방침」).
  정발은 **고유명사 표기 대조용**으로만 링크했다(`originals.txt`).
- 우리 `script/`(ED1 여섯 씬 완주분)의 **재사용률 90.7%**(정찰표) — PS1 리메이크와 원작
  사이라 그대로는 안 붙고, JP 원문 해시로 붙일 층이 필요하다(「남은 일」 4).

### 6. 시나리오 한 장 = **8086 코드 + 이벤트 스크립트**

🔴 시나리오는 「스크립트 파일」이 아니다. 머리 세 바이트가 `e9 xx xx`(JMP rel16)이고
**이벤트 스크립트는 그 코드가 가리켜서** 들어간다. 스크립트 옵코드만 진입점(`0xe000`·
`0xe003`)부터 따라가면 **0.8% 밖에 안 닿는다**(실측 — 처음에 이렇게 짰다가 걸렸다).

측정 정본은 [`tools/walk_scn.py`](../tools/walk_scn.py). 층을 셋으로 갈라 잰다:

| 층            | 무엇을 더하나                                    | 텍스트 377,474B 중  |
| ------------- | ------------------------------------------------ | ------------------- |
| 진입점        | x86 흐름을 따라가며 만난 즉치값                  | 126,596 = **33.5%** |
| + 포인터 훑기 | 데이터 어디든 **범위 안 워드**면 진입점으로 본다 | 315,154 = **83.5%** |
| + 이어짐      | 닿은 종료코드 **바로 다음**이 텍스트면 잇는다    | 341,097 = **90.4%** |

⇒ **「포인터를 전부 찾아 고친다」가 성립한다**(9할). 남은 1할이 선행 패치의 per-scenario
코드 훅에 해당하는 몫이다 — 실제로 우리가 꼽은 최악 `10.01.20` 은 그쪽에도 전용 훅
(`PointerTableHook(..., 0xe019, 63, 4, 2, table_addr=0xe027)`)이 박혀 있다. 서로 독립으로
같은 시나리오를 지목했다.

⚠ **훑기는 과대추정이다** — 우연히 범위 안 값인 바이트쌍이 진입점으로 잡힌다.
재삽입에 쓰려면 후보마다 **검증**(그 자리가 정말 블록 머리인가)이 붙어야 한다.

### 8. 한글 글리프 표 — 16×16 · 75,200B · 결정적

한글도 같은 기하(32B)로 만들면 후킹한 자리에 그대로 흘려 넣을 수 있다.

- 완성형 **2,350자 · 표 75,200B · sha1 `516e5a8f…`** · 빈 글리프 0.
  ⚠ 2,350자는 KS X 1001 이지 현대 한글 전부가 아니다 — `힣` 은 없다.
- 🔴 **결정성 확인됨** — `--check` 가 두 번 그려 대조한다(제1 원칙). 표 지문은 얼려 뒀고
  `--freeze` 로만 갱신한다.
- 미리보기: `python3 tools/font.py --preview` → `work/review/font_preview.png`.
  받침 있는 글자(`값`·`많`·`읽`·`웅`)까지 안 뭉갠다.

### 9. 한글을 앉힐 코드 자리 — **있다**

[`tools/census_sjis.py`](../tools/census_sjis.py). 글꼴이 ROM 이라 「폰트 표의 빈 슬롯」이란
게 없다. 대신 후킹한 CG 루틴이 **어떤 코드를 가로챌지**를 정해야 하고, 그러려면 원본이
안 쓰는 코드를 알아야 한다 — 쓰는 자리를 뺏으면 그 글자가 화면에서 사라진다.

**화면에 나가는 문자 2,724종**(덤프 기준, 등장 148,572회). JIS 자리로 환산하면:

| 대역               | 전체  | 쓰임  | 빈 자리   |
| ------------------ | ----- | ----- | --------- |
| 한자 1급 (ku16~47) | 3,008 | 1,349 | 1,659     |
| 한자 2급 (ku48~84) | 3,478 | 1,095 | **2,383** |
| 비한자 (ku1~8)     | 752   | 280   | 472       |

⇒ **한자 1·2급 빈 자리 4,042 — 한글 2,350자가 들어간다.** 한 번도 안 쓰인 구도 17개 있다
(9~~15 · 85~~94).

🔴 **생 디스크를 훑으면 안 된다** — 코드·그래픽이 우연히 SJIS 로 읽혀 6,333종으로 부푼다
(실측). 그 값으로는 판단이 안 선다. **덤프한 문안에서만** 센다.
⚠ ku·ten 환산은 **codecs 를 정답으로** 회귀 테스트에 묶었다 — 손으로 적은 기대값이 실제로
틀려서 멀쩡한 코드를 고칠 뻔했다.

⚠ **아직 「어느 자리에 어느 음절」은 안 정했다** — 자리가 있다는 것까지다. 배정은 후킹
설계와 같이 정한다(「남은 일」 3).

### 10. 이름 표 — 순수 한자 이름의 회수 경로

[`tools/tables.py`](../tools/tables.py). 7절의 가나 필터가 「大根」·「金塊」 류를 버리는데,
이름은 대개 **고정 폭 레코드**에 들어 있어 표를 찾으면 필터 없이 통째로 회수된다.

| 자리(program) | stride | 레코드 | 무엇                                   |
| ------------- | ------ | ------ | -------------------------------------- |
| `0x3f09`      | `0x14` | 106    | **아이템** — 이름 14B 우측정렬 + 값 6B |
| `0x4779`      | `0x14` | 9      | 아이템 이어지는 묶음                   |
| `0x485c`      | `0x0b` | 26     | **마법**(ハイパー·オビス·サクタス…)    |
| `0xa7f1`      | `0x07` | 10     | 메뉴(ＯＦＦ·ＯＮ·ＥＰ…)                |

⚠ **후보다** — 「진짜 표인가」는 사람이 본다. 한 글자 이름은 섬으로 안 잡혀 거기서 끊긴다
(아이템이 106 + 9 로 갈린 이유).
🔴 **섬의 시작만 보면 못 찾는다** — 이름이 우측정렬이라 시작이 들쭉날쭉하다. **끝** 간격으로
묶어야 잡힌다(실측: 시작만 보면 후보 1건).

### 11. 🔴 이미 번역한 문안은 **거의 안 붙는다** — 정찰표 90.7% 는 다른 자다

[`tools/reuse.py`](../tools/reuse.py). 새턴 ED1+2 는 PS1 과 **블록이 축자 동일**이라 문안이
그대로 넘어갔다. PC-98 은 **1989 원작 vs 1998 리메이크**라 사정이 다르다.

| 자                                  | 결과                                        |
| ----------------------------------- | ------------------------------------------- |
| 블록 단위 — 사전 열쇠가 그대로 맞나 | 706 / 10,354 = **6.8%** (글자 13.1%)        |
| 문장 단위 — 문장 부호로 잘라 겹치나 | 글자 71,470 / 157,292 = **45.4%**           |
| (참고) 정찰표의 「재사용률」        | 90.7% — **부분문자열 포함**이라 자가 다르다 |

⇒ **번역량을 「거의 다 돼 있다」로 잡으면 안 된다.** 새 번역이 본진이다(문장 절반쯤은
낯익겠지만 손은 다시 간다). ⚠ 정찰표도 그 값을 「타이틀 간 비교용이지 절대값이 아니다」라고
적어 뒀다 — 어긋난 게 아니라 **자가 다른 것**이다.

🔴 **여기까지 오는 데 표기 함정 둘을 밟았다**(devlog):
**(1)** PS1 블록은 `{c}화자{c}{n}본문{c}` 로 **화자가 본문에 붙어** 있다. 화자를 버린 덤프로
재면 붙는 줄이 0.2% 로 보인다. ⇒ 덤퍼가 `1E <화자> 04` 를 살리게 고쳤다.
**(2)** **꼬리 `{c}` 하나**를 빠뜨리면 중립꼴이 한 글자 달라 열쇠가 통째로 안 맞는다.
회귀 테스트에 「PS1 과 같은 열쇠가 나오나」를 박아 뒀다.

### 12. 폰트를 어디에 얹나 — **풀렸다** (RAM 세그먼트 0x4000)

측정 정본은 [`tools/memmap.py`](../tools/memmap.py). program 디스크 `0x5a48` 이 답이다:

```
mov al,[0x501] / and ax,7 / dec ax     ; BIOS 워크 = 128KB 단위 메모리 크기
mov cl,[0x40ac] / and cx,3             ; 유틸리티 메뉴 설정(뱅크 수 0~3)
mov ah,0x40 / mov al,0 / mov es,ax     ; 세그먼트 0x4000 = **선형 256KB**
mov es:[0],0x96d8 / cmp                ; 써 보고 되읽어 RAM 이 있나 검사(두 값으로 두 번)
mov cx,0x10 / call 0x5b9b              ; 그 뱅크를 **8KB 페이지 16장**으로 등록
add ah,0x20 / loop                     ; 다음 뱅크 = +128KB
test [0x40ac],4 / mov ax,0xe000        ; 안 쓰는 VRAM 4번째 면도 페이지로
```

⇒ **게임 자신은 0~256KB 를 쓰고, 256KB 위는 「캐시 페이지 풀」이다.** 게임이 이미
**8KB 페이지 할당기를 갖고 있다.**

| 층        | 자리                                                          |
| --------- | ------------------------------------------------------------- |
| 글리프    | **RAM 세그먼트 0x4000**(=256KB), 풀에서 **10장**(80KB)을 뗀다 |
| 디스크    | scenario 809~895(89,088B 연속) · event 에도 사본(오프닝용)    |
| 후킹 코드 | program (21.5KB 로 충분하다 — 코드만 들어간다)                |

- **완성형 2,350자를 통째로 싣는다.** 서브셋(우리 번역 61만 자의 고유 음절 **1,342**,
  완성형 밖 0개)도 검토했는데 **뗄 필요가 없다** — 페이지 열 장이면 전부 들어간다.
  ⚠ 서브셋은 「번역이 늘면 없는 글자가 생기는」 사고를 부른다. 안 한다.
- ⚠ **384KB 이상을 요구하게 된다**(세그먼트 0x4000 뱅크가 있어야 한다). 배포에 명시한다.
  대신 유틸리티 메뉴의 캐시 설정을 한 칸 줄이는 셈이라 **동작에는 영향이 적다**.
- 🔴 **여기까지는 정적 판독이다.** 그 자리가 실제로 비는지는 **에뮬로 확인**해야 한다
  (`mame-pc98` 어댑터가 이미 있다 — 「남은 일」 6).

### 14. 🎉 사슬 전체가 섰다 — **디스크 → RAM → 후킹 → 화면**

    ⑴ 로더  IPL 이 로드된 코드로 뛰기 직전(`0x13b`)에 끼어들어 글리프 표를 **RAM 0x4000** 으로 읽는다
    ⑵ 후킹  루틴 A 를 가로채 **우리 대역(JIS ku 0x40)** 이면 RAM 표에서 32B 를 버퍼에 복사
    ⑶ 표시  원본 블릿이 그 버퍼를 VRAM 세 면에 뿌린다 (손 안 댄다)

**완성형 2,350자 전부**가 JIS ku `0x40~0x58`(25구)에 올라간다. 오프닝의 그 대역 한자가
전부 한글로 나오고, 검사한 열 자가 **모두 256/256 픽셀 일치**다(ku +0 … +13).

| 무엇    | 값                                                           |
| ------- | ------------------------------------------------------------ |
| 디스크  | event 논리 섹터 **856~955**(트랙 107부터 13트랙) · 102,400B  |
| RAM     | `0x4000` 부터 ku 당 `0x100` 파라그래프씩 (`0x4000`~`0x5800`) |
| 배치    | **ku 당 128칸**(앞 94칸만 글자)                              |
| 짚는 법 | `seg = 0x4000 + ku색인 × 0x100` · `off = ten색인 × 32`       |

🔴 **94칸이 아니라 128칸으로 깐 게 핵심**이다. 128×32 = 4,096B = `0x100` 파라그래프라
**곱셈도 64KB 넘김도 없어진다** — 94칸이면 `mul` 과 17비트 오프셋이 들어가 48바이트에 안 들어간다.
⚠ 대가: 25 × 34칸(27,200B)이 빈다. RAM 도 디스크도 그만큼 여유가 있다.

🔴 **게임의 캐시 뱅크를 껐다** — program 디스크 `0x5a56` 의 `and cx,3` 을 `xor cx,cx` 로
바꾸면 바로 뒤 `je` 가 항상 걸려 **선형 256KB 위 등록을 통째로 건너뛴다.** 우리 표가 거기
있기 때문이다. 패치 후에도 program 디스크가 **정상 부팅**하는 걸 확인했다(세이브 선택 화면).
⚠ 대가: 디스크 캐시가 없어져 로딩이 느려진다.

🔴 **표를 시나리오 디스크에 둔 이유** — 부팅 경로가 둘인데(event 로 새로 시작 · program 으로
이어하기) **양쪽 다 드라이브 2 에 시나리오를 꽂는다.** event 에 두면 이어하기 때 못 읽는다.
로더는 두 경로 모두 `AL=0x91`(드라이브 2)로 읽는다.

🔴 **두 디스크의 글자 루틴이 바이트까지 같은 꼴**이다 — 갈림길 다섯 바이트도, 없앨 비한자
경로 48바이트도, `je` 거리(0x3f)도 같다. **버퍼 주소만 다르다**(event `0x4070` ·
program `0x4076`). 그래서 같은 패치를 사이트 표(`SITES`)로 양쪽에 건다.

| 디스크  | IPL 훅  | 로더    | 갈림길   | 우리 코드 | 버퍼     |
| ------- | ------- | ------- | -------- | --------- | -------- |
| event   | `0x13b` | `0x302` | `0x8fb6` | `0x8ffa`  | `0x4070` |
| program | `0x116` | `0x1c0` | `0x7dce` | `0x7e12`  | `0x4076` |

- 로더는 게임 규약 그대로 — `INT 1Bh` / `AH=0x56` / `AL=0x91` / `ES:BP`, **트랙 통째로**
  13번 읽으며 ES 를 `0x200` 씩 민다. 밀어낸 원래 명령(`mov al,[…]`)은 로더가 대신 한다.
- ⚠ **읽기가 실패해도 그냥 진행한다**(시나리오가 없을 때) — 한글이 안 나올 뿐 게임은 돈다.
- ✅ program 디스크로 부팅해도 **정상**이다(세이브 선택 화면). 그 화면의 가나가 멀쩡한 건
  의미가 있다 — 비한자 경로를 없앴으니 **가나도 반드시 우리 코드를 지난다.**
- ✅ **인게임 한글을 화면으로 봤다**(2026-09-03) — 엘아스타 성 안 라이아스,
  「왕자님, 의자에 얌전히 앉아 기다리고 / 계시옵소서. 곧 돌아오겠사옵니다…」.
  정본 문안 그대로, 창 안에서 접히고 ▽ 도 정상이며 대화를 닫고 나서도 게임이 그대로 돈다.
  막고 있던 **디스크 교체**의 원인은 둘이었고 둘 다 우리 쪽이다(자세한 건 devlog):
  ⑴ 드라이브마다 이미지를 **하나씩** 물려 스왑 목록이 비어 있었다
  (`imgmount 0 event.d88 program.d88` 처럼 **둘을 물려야** 한다)
  ⑵ 핫키가 `Ctrl+F4` 가 아니라 **호스트키+`O`** 다(DOSBox-X 는 호스트키 조합을 쓴다).
  📌 호스트키는 `scripts/emu/pc98.sh` 가 정한다 — 지금 main 은 `hostkey=ctrlalt` 라 **⌃⌥+O**,
  맨 `\` 에도 같은 걸 걸어 뒀다. 그 파일이 정본이고 여기 적힌 건 경위다.
  `Drive → A: → Swap disk` 가 회색인 건 맞다 — `-fs none` 번호 마운트는 드라이브 문자에 안 붙는다.
- ⚠ **화면으로 본 건 「틈 건너뜀」 전략 하나**다(972 중 688). 나머지 셋은 **바이트까지만**
  확인됐다 — `patch_scn.py --verify` 가 구운 이미지를 되읽어 정본과 글자로 대조한다(972/972).
  즉 **「제대로 써졌나」는 증명됐고 「인터프리터가 그렇게 실행하나」는 밖으로(126)·공백
  메움(132)·제자리(26)에 대해 아직 화면으로 못 봤다.**
  🔴 셋 중 위험한 건 **밖으로**뿐이다 — 런 머리에서 꼬리 빈자리로 뛰고 되돌아온다.
  나머지 둘은 점프를 안 쓴다(제자리는 덮어쓰기, 공백 메움은 뒤에 공백을 채운다).
  📌 확인법: 아무 「밖으로」 대사나 인게임에서 한 번 보면 닫힌다. 유저 QA 1회차에서
  자연히 잡힌다 — 굳이 따로 몰지 않는다.
- ✅ **유저 세이브로 인게임 진입이 30초**가 됐다(2026-09-03). 세이브는 **시나리오 디스크의
  논리 섹터 0~127 한 덩이**(파일 `0x0002B0`~`0x00020AB0`, 133,120B)라
  **아무 빌드에나 이식**할 수 있다 — 우리 패치는 1008~1107 이라 안 겹친다 —
  새 이미지의 같은 두 섹터에 덮어쓰면 그 빌드로 이어하기가 된다.

  세이브 둘을 받았다 — 우리 빌드용(`pc98-ed1-<sha1>.d88`)과 **원본용**(`orig-<sha1>.d88`).

  **원본 디스크 + 원본 세이브**로도 똑같이 멈춘다 ⇒ **우리 패치와 무관하다.**
  한 라운드는 돌고 다음 라운드에서 멈추며, 무입력 25초에도 진행이 없고 에뮬은 살아 있다.
  클럭(8000→30000) · FM 보드(auto/26k/off) · `timer always cycles` 를 바꿔도 그대로다.
  ⇒ 남은 후보는 **DOSBox-X 의 PC-98 에뮬레이션**. 다른 에뮬(emucap `mame-pc98` ·
  Neko Project II)에서 재현되는지가 다음 갈림길이다. 자세한 건 devlog.
  🔴 **이게 안 풀리면 인게임 QA 가 첫 전투에서 막힌다** — 지금 최우선 미해결이다.
- ⚠ **화자 이름은 아직 일본어**다(`ライアス`) — 이름은 `1E <이름> 04` 로 본문과 다른 자리에 산다.
- ⚠ 정본이 없는 줄은 일본어 그대로고, 그 안의 **대역 한자가 한글 글리프로 나온다**
  (「第1章」→「剞1章」). 우리가 그 구를 뺏었으니 **정상**이다 — 번역이 덮이면 사라진다.

### 15. 폰트 후킹의 자리 — **루틴 안에서 만들었다**

`tools/patch_font_hook.py`. 오프닝 첫 줄의 `昔` 이 **`가`** 로 나온다. 픽셀로 대조해
**256/256 픽셀 완전 일치**. 나머지 화면은 그대로다.

무엇이 성립했나 — **CGROM 에 없는 글자를, 디스크에서 올린 표로 화면에 낼 수 있다.**
한글화의 관문이 열렸다.

**자리를 어떻게 냈나** — 트랙(8KB)은 꽉 찼고 이미지의 0 런은 런타임 변수 영역이라 못 쓴다.
그래서 **루틴 안에서 만들었다**: 비한자 경로(48B)를 한자 경로와 합치고, 원래 갈림길
(`cmp ax,0x3021`/`jb`)을 **우리 판정**(`cmp ax,대상`/`je`)으로 바꿨다. 비는 48바이트에
**글리프 32B + 코드 16B 가 딱 맞는다.**

```
0x8fb6  cmp ax,0x404e / je short  ← 원래 갈림길 자리(다섯 바이트)
0x8ffa  글리프 32B                ← 없앤 비한자 경로
0x901a  mov di,0x4070 / mov cx,16 / call·pop·sub si / rep movsw / nop
0x902a  (흘러 나가 원본 에필로그)
```

🔴 **적재 주소를 가정하지 않는다** — `call`/`pop` 으로 자기 주소를 얻어 글리프를 **상대로**
가리킨다. 절대 오프셋으로 짰을 땐 **잡음이 그려졌다**(글리프 바이트는 이미지에 정확히
들어갔으니 틀린 건 오프셋 가정이었다).
⚠ 한때 「좌우를 뒤집어 담아야 한다」·「한 행 내려야 한다」로 봤는데 **둘 다 오진**이었다 —
원인은 `sub si, N` 의 **손계산 오프바이원** 하나였다. 고치니 그대로 담아도 맞는다.
⚠ **대가**: 가나가 한자 쪽 「굵게」 공식으로 그려진다. 화면으로 보면 멀쩡하지만 획이 조금
굵어질 수 있다. 되돌리기는 쉽다.
🔴 **손계산을 없앴다** — 글리프를 asm 소스에 같이 넣고 `sub si, .here - glyph` 로 **nasm 이
라벨 뺄셈**을 하게 했다. 오프셋을 손으로 세면 또 틀린다.

### `program` 로드 베이스 확정 — 파일 오프셋 ↔ 실행 주소 변환 (2026-09-15 재료로 올림)

`memmap.py`·`common.py` 어디에도 **`program` 디스크가 실행 시 어느 세그먼트에 실리는지**가

중 `program:0xd93`(HUD 장 제목 슬롯) 을 **어느 코드가 쓰는지** 추적하려다, 파일 오프셋을
실행 주소로 바꿀 좌표계가 없어 시한 안에 못 갈랐다. ⚠ **급하지 않다** — 코드 참조 추적이

INT 1Bh 버퍼 주소 · 디스어셈블 시작점 확정이 한 벌).

🎉 **✅ 확정됨(2026-09-27, 디버거 라이브 추적으로) — `runtime = file_offset + 0x0C00`
(세그먼트 고정 `0000`).** 조사 훅 ⓑ 작업 중 주문 시전 메시지가 뜬 순간을 헤드리스
디버거(아래 「반각 조사 훅」항목)로 멈춰서 데이터 뷰로 직접 확인했다 — 원문 미번역
`は`(`program:0x4be2`)가 실행 주소 `0000:57E2`에 그대로 있었고, 뒤이은 `に`(0x4be6→
0x57E6)·`の`(0x4bea→0x57Ea)·우리 번역 `자신에게`(0x4bee→0x57EE, 바이트까지 정확히
일치)로 **네 자리 전부 +0xC00 하나로** 맞았다(바이트 직접 대조 — 디코더 출력으로
어림잡았을 땐 `+0xC0A`로 어긋나 헷갈렸었다, 직접 대조가 이겼다).

### 반각(8px) 한글 — 재 봤고, **지금은 안 간다** (2026-09-06)

sfc-ed1 이 `Galmuri11-Condensed` 로 8×16 한 칸에 한 글자를 넣었다는 소식을 받고 pc98 에도
되는지 쟀다. 폰트 쪽은 사실이다 — **한글 음절 11,172자 전부 DWIDTH 8**(직접 확인).

**얻는 것**: 줄 폭 여유. 우리 줄 2,335 중 36칸(창 폭) 초과가 **592(25.4%)** 인데 8px 이면
**83** 으로 준다. 글리프 표도 75,200B → 절반이 된다.

🔴 **그런데 pc98 은 SFC 와 처지가 다르다.**

1. **코드 자리가 없다.** 우리 한글은 **JIS 구 0x40~0x58**, 곧 **2바이트 전각 코드**에 앉아
   있다. 반각은 **1바이트 코드**인데 빈 자리가 100 남짓이라 2,350자를 못 담는다.
   ⇒ 2바이트 코드를 유지한 채 **그리는 폭만 8px 로** 바꿔야 하고, 그건 글꼴 교체가 아니라
   **렌더러의 전진폭 로직을 고치는 일**이다.
2. **고정 칸이 바이트로 잡혀 있다.** 아이템 14B·지명 12B/14B 는 **바이트 예산**이라 8px 이
   돼도 **안 늘어난다**(코드가 여전히 2바이트다). 오히려 칸의 시각 폭이 반이 되어
   **정렬이 깨진다** — 방금 96칸을 가운데 정렬로 맞춰 놓은 자리다.
3. 지금 밀도는 **원문과 같다** — 전각 1자 = 2바이트 = 16px 로 원문 한자·가나와 동일하다.
   SFC 는 8px 눈금에 한글이 두 칸을 먹어 밀도가 절반이었다(그래서 이득이 컸다).

⇒ **얻는 것은 「줄 폭 여유」 하나**고, 치르는 것은 렌더러 수술 + 고정 칸 재정렬이다.
지금은 창 넘침이 실질 문제가 아니다(엔진이 공백에서 자동으로 접고, 페이지 넘침은 4건).
📌 **문안이 굳고 인게임 QA 에서 「줄이 모자라다」가 실제로 나오면** 그때 다시 꺼낸다.

| `program:0x5fb6`·`0xa80e` | `あと` | 남은 | **남다** | 5·6B — 4B |

· `その他` 는 **메뉴 항목**이라 「그 밖」이 자연스럽고, 「기타」는 표 층 말투다.
⇒ **화면을 보고 판정한다.** 하네스로 그 창들을 이미 찍을 수 있으니 다음 회차 첫 자리다.

### `サクサク` 창은 **메시지 속도가 아니라 난이도**다 (2026-09-08)

sfc 실측 중계로 확인했고, **PC-98 에도 같은 설정이 있다.** 네 단계다 —
**`ジ ゴ ク`(지 옥) · `ツ ラ イ`(힘 듦) · `普 通`(보 통) · `サクサク`(술술)**,
`event`·`program` 두 자리씩. 부팅 화면의 `LOAD` 아래 버튼이 그것이다.

🔴 **그중 `普通` 두 자리가 안 옮겨져 있었다** — 순한자라 덤퍼가 버리던 그 부류다
(같은 자로 오늘만 여섯 자리를 더 찾았다). 넣었다.
⚠ **`普通` 은 두 곳에 있다** — 여기(난이도)와 `program:0xa81c`(메시지 속도). 이름이 같아도
**다른 설정**이다.

⚠ **SFC 에서는 이 설정이 「저장 가능한 맵」을 제한했다** — 「저장이 안 된다」를 버그로 잡으면
안 되는 자리다. **PC-98 에서도 그런지는 아직 안 봤다**(`⬜ 미탐색`) — 세이브 구조 조사와
이어지는 자리다.

### 화면 QA 하네스 — 조작 (`tools/qa_shot.py`)

`windowfocus` + 포인터를 창 안으로 옮겨야 한다. 이걸 안 하면 **화면이 하나도 안 바뀌어서**
「키가 안 먹는다」와 「게임이 그 키를 안 받는다」가 구분이 안 된다(반나절 태울 자리다).

🔑 **`セリオス` 는 program 표 탓이 아니다** — `program:0xf30`·`0x77fc` 둘 다 **이미 한글**이고
event 쪽 넷도 다 한글이다. **전투가 읽는 이름은 세이브에 있다**(세이브 파일 `0x1220` 이하).
그리고 **우리 빌드로 새 게임을 해도 세이브엔 `セリオス` 가 적힌다.**

⚠ **초기 파티 표를 무늬로 찾아봤고, 값이 나왔는데 그게 답을 지웠다**(2026-09-08).
세이브의 이름 자리가 **stride 0x40** 이니 디스크에도 같은 무늬가 있으리라 보고,
**「`セリオス` 뒤 0x40 마다 `リュナン`·`ロー`·`ゲイル`」**로 세 디스크를 통째로 훑었다:

    event     없음
    program   **`0xf30` 하나** ← 그런데 이건 `08b66fd3` 에서 **이미 한글로 옮겼다**
    scenario  없음 (원본·빌드 둘 다. 세이브 구역은 새 게임 전엔 `0xFF` 다)

⇒ **가설이 값으로 무너졌다** — 표는 하나뿐이고 이미 한글인데도 세이브엔 원문이 적힌다.
초기값은 **stride 0x40 짜리 텍스트 표에서 오지 않는다.**

**남은 갈래 둘** — ⑴ 세이브가 이름을 **다른 표현**으로 들고 있다(우리 표를 안 탄다)
· ⑵ 🔴 **`0x1220` 이 파티 이름이 아닐 수도 있다** — 세이브 구조는 **이미 두 번 틀렸다**
(「두 장」→「세 장」→「논리 0~127 한 덩이」). 원본 세이브와 우리 세이브를 **바이트로 대 보는 것**이
다음 수다. ⇒ `⬜ 미탐색`, **다음 라운드 첫 자리.**
⚠ 찾아 고쳐도 **이미 만든 세이브는 안 고쳐진다** — 값이 세이브에 박혀 있다.
`pc98.sh` 의 가져오기에 이름 변환을 붙일지 같이 본다(md 가 같은 것을 겪었다).

⚠ **전투 문안 손질은 유저가 다음 라운드로 미뤘다**(2026-09-08). 여기는 기록이다.

않았다.」·「회심의 일격 / 슬러그A 96의 대미지!!」. 새로 짓지 말고 거기서 가져온다.

    **x86 코드 자체**(머리의 `e9`·`eb` 점프들, `ASM_CALL` 대상)를 디스어셈블해야 하고,

    ✅ **ⓑ 라이브까지 완료 — 주입 지점은 확정, 다만 찾은 분기는 「은/는」이
    아니라 다른 문제(자신에게/에게) 것이었다.** 로드 베이스로 즉시값
    `E2 57`(=`0x57E2`)을 검색해 `file 0x9bb3`(`mov si,0x57e2`)를 찾은 뒤,
    관리자 지시대로 `0000:A7C1` 에 실행 BP 를 걸고 세리오스로 레스 1 을
    **실제로 시전**해 걸리는 순간을 라이브로 잡았다:

    ```
    EBX=00000B00  EDI=00000B00   ← bx 와 di 가 같은 주소를 가리킨다(항상 같음)
    A7C1: mov bx,[40D1]   bx=[0x40D1]=0x0B00
    A7C5: mov al,[bx]     al=[0x0B00]=0x00
    A7C7: cmp al,[di]     [0x0B00] vs [di=0x0B00] → 자기 참조라 늘 같다(Z=1)
    A7C9: mov si,57ED     먼저 "자신에게" 표지를 무조건 넣고
    A7CC: je A7D1         같으면(자기 타깃) 그대로
    A7CE: mov si,57E5     다르면(남 타깃) "~에게" 표지로 교체
    ```

    🔑 **이 분기는 は(주어 조사)가 아니라 "자신에게" vs "○○에게"(대상 표현)를
    가르는 분기였다** — 은/는 문제와는 다른 자리다. 다행히 한국어 "~에게"는
    받침 무관 고정형이라 **이 축은 애초에 걱정할 게 없었다**(값으로 확인하며
    하나 던 셈).

    **は 자체는 여전히 무조건이다.** `0000:A7B3`(=`mov si,0x57e2`, 위 분기보다
    훨씬 앞자리)에 실행 BP 를 걸고 다시 시전해 **정확히 거기서 멈추는 것까지
    값으로 확인**했다 — 이게 **주입 지점**이다. 다만 그 순간 레지스터
    (`EAX=B00·EBX=601·ECX=700·EDX=C96·ESI=B27·EDI=B00`) 어디에도 "지금
    시전자가 누구인지" 바로 알려주는 작은 인덱스가 안 보였다(전부 워크램
    포인터로 보이는 큰 값). 이 세이브는 파티원이 세리오스 하나뿐이라 다른
    이름으로 비교도 못 했다 — **캐스터 식별값이 어디 있는지는 이번 회차
    예산 안에 못 좁혔다.**

    **ⓒ(분기 설계)로 넘길 것**: ✅ 주입 지점 확정(`runtime 0000:A7B3` = 파일
    `0x9bb3`, `mov si,0x57e2` 그 자리) — 여기를 "캐스터 받침 검사 → si 를
    그대로 두거나 새 은-버전 문자열로" 분기로 바꾸면 된다. ⬜ 아직 없는 것 —
    그 조건을 읽을 메모리 자리. 다음 회차 후보 둘: ① 파티원이 늘어난(류난·
    게일 등 받침 있는 이름 포함) 세이브로 같은 지점을 다시 걸어 레지스터가
    이름별로 달라지는지 대조 ② `call 0x8dba`(미확인, `si` 를 실제로 쓰는
    자리로 추정) 안쪽을 봐서 "누구 이름을 찍는지" 결정하는 값을 거슬러 찾기.

   흔들려** 이미 붙인 정본 1,800여 줄의 열쇠가 갈린다. ⇒ 지금 할지, ED1 문안이 굳은 뒤에 할지.

   **여기서 나온 것 — 장 카드(P3 연출) 여섯을 다 넣었다.** 머리 잡음은 정본이 `head` 로
   그 바이트를 적어 두면 패처가 **그만큼 건너뛰고 뒤부터** 쓴다(사전조건: 바이트가 다르면
   그 자리에서 죽는다).

   | 장 | 원문 | 우리 | 자리 |
   | --- | --- | --- | --- |
   | 1 | `第１章　王子の旅立ち` | `제1장 왕자의 여행길` | 제자리 (시나리오 + 세이브 라벨) |
   | 2 | `第２章　沈黙の呪文` | `제2장 침묵의 주문` | 제자리 |
   | 3 | `第３章　国王のあかし` | `제3장 국왕의 증표` | 밖으로(`head` 4B) |
   | 4 | `第４章　魅せられた国王` | `제4장 매혹된 국왕` | 밖으로(`head` 4B) |
   | 5 | `第５章　妖しき光の塔` | `제5장 요사한 빛의 탑` | 밖으로(`head` 6B) |
   | 종 | `終章　そして英雄たちの伝説` | `종장 그리고 영웅들의 전설` | 밖으로(`head` 1B) |

   ⚠ 3~종장은 **한 블록에 두 장씩** 들어 있고(이번 장 + 지난 장) 여백으로 자리를 잡으므로,
   **원문 제목이 차지하던 칸 안에 가운데 정렬**로 넣어 바이트 수를 정확히 맞췄다.
   ⚠ `제N장` 뒤는 **반각 공백**으로 통일했다 — 전각으로 두면 5장이 칸을 넘는다.

   **얼마나 손해인가 — 실측 2026-09-06.** 미번역 블록 전량을 훑어 「런 머리에 **글이 아닌
   바이트**가 붙은」 것을 셌더니 **10건**이고, 그 열은 전부 **글이 아예 아닌 잡음 덩이**다
   (번역할 것이 없다). 우리가 건너뛰던 나머지 40여 건은 잡음이 아니라 **글자 한둘이 앞
   런으로 넘어간 것**이라(`んたがた 旅人のようじゃな` 처럼) 바이트로는 멀쩡하고, 대개
   **깨끗한 사본이 다른 자리에 하나 더 있다.**
   ⇒ 덤퍼를 다시 쓰는 값은 **장 카드 넷**이었고 그건 `head` 로 풀었다. 남은 값은 「앞 글자
   하나」뿐이니 **ED1 문안이 굳은 뒤로 미뤄도 된다.**

   🔴 **여기는 인게임 확인이 필요하다** — 넷 다 런 안으로 **점프가 들어온다**(오프셋 6·12·
   16·22·30·32). 「밖으로」는 머리 3바이트만 바꾸므로, **런 머리로 들어오면 한글**이 나오고
   **중간으로 뛰어들면 그 뒤는 원문 그대로** 나온다. 지금보다 나빠지진 않지만, 한 화면에
   한글과 일본어가 섞여 보일 수 있다. `[P6]` 에서 눈으로 본다.
4. `[P3]` ⚠ **엔딩·장 카드를 화면으로 못 봤다** — 문안은 다 들어갔고 되읽기도 맞지만,
   거기까지 가려면 전투를 지나야 한다(위 1번). ⇒ 프리즈가 풀릴 때까지 미룰지, 세이브를
   받아 그 지점부터 볼지.
5. ✅ **옛 세이브의 HUD 문제는 끝났다**(2026-09-07). 공용 실행기가 세이브를 가져올 때
   **이름 넷과 장 이름을 이 빌드 문안으로 바꿔 준다**(`scripts/emu/pc98.sh`, main `d49283b8`).
   ⇒ 유저는 **옛 세이브를 가져와도 이름·장 제목이 한글로** 뜬다. 아래는 그때 찾은 자리다.
   유저가 본 「빈칸」의 한 갈래다. 화면: `.local/inbox/pc98-ed1/p1-hud-oldsave.png`.

   | 화면 자리 | 옛 세이브로 | 왜 |
   | --- | --- | --- |
   | 장 이름 바 | `쮁1章  王子の씁씀ち` (깨짐) | **세이브에 글자로 박혀 있다**(파일 `0x1083`, 30바이트) |
   | 파티 이름 | `セリオス` (일본어) | **세이브에 박혀 있다**(파일 `0x1220`·`0x1260`·`0x12a0`·`0x12e0`, stride 0x40, 종결자 `06`) — 파티는 **넷**이다 |
   | 지명 | `엘아스타` ✅ | 실행 파일 표에서 읽는다 |
   | `Gold`·`L`·`HP`·`MP` | ✅ | 실행 파일 |

   ⚠ **우리 정본에는 다 들어 있다** — `program:0xf30` = 세리오스 · `0xf70` = 류난 ·
   `0xff0` = 게일. 즉 **패치가 빠진 게 아니라 세이브가 옛 바이트를 들고 있는 것**이다.
   ⇒ **공용 실행기가 가져올 때 바꿔 준다**(main `d49283b8`) — 세이브에서 읽은 값을 원본
   `program.d88` 에서 찾아 **빌드 `program.d88` 의 같은 자리 값**으로 바꾸는 식이라,
   빌드가 바뀌면 저절로 따라오고 이미 우리 문안이면 그냥 넘어간다(멱등).

6. `[P5]` ℹ **세이브 호환은 「우리 빌드끼리」만이다** — 장 제목이 세이브 안에 **글자
   그대로** 복사된다(scenario 논리 섹터 0~2 중 `0x59d`, 30바이트). 그래서 **원판으로 만든
   세이브를 우리 빌드에서 열면 슬롯 이름이 깨져 보인다**(`第`·`旅`·`立` 이 뺏은 구
   0x40~0x58 안이다 — 실측). 반대도 같다. **세이브 데이터 자체는 멀쩡하고** 슬롯 이름만
   그렇다. ⇒ 배포 안내에 적을지, 아니면 그대로 둘지.
   🔴 pce 가 물린 「배정이 문안을 타는」 사고는 **우리에겐 없다** — 우리 한글 코드는
   KS X 1001 완성형 **코드 순서 2,350자 통째**라 문안이 바뀌어도 자리가 안 움직인다
   (`font.TABLE_SHA1` 이 못 박는다).
7. `[P1]` ℹ **부팅 경고 셋은 일본어로 둔다** — `GDCが5MHzモードに…`·`ディップスイッチ…`·
   `リセットボタンを…`. 이건 **폰트를 RAM 0x4000 에 올리기 전**에 본체 ROM 폰트로 찍는
   자리라, 한글로 바꾸면 화면에 엉뚱한 한자가 뜬다. 되돌릴 이유가 생기면 알려 달라.

### np2kai 를 dev 에 세웠다 — 굽는 건 됐고 **ROM 이 없다** (2026-09-08)

⇒ **유저 맥에서 그 폴더의 `*.rom` 을 올려 주면** dev 에서 원본·우리 빌드를 **내가 몇 번이고**

## 🔴 머지 시점에 열려 있는 결함 (2026-09-08)

**묶음 ⑤(타이틀)는 칸으로 닫혔지만 게임은 아직 못 돈다.** 유저 확정으로 조건 ⑷ 를 이 건에
한해 유예하고 올린다 — **막는 결함이 그 묶음이 만든 게 아니기** 때문이다(문안 재삽입 축이다).

| 무엇 | 상태 |
| --- | --- |
| **왕가 장비 메시지가 두 번 나온다** | 🔴 열림 — 엘아스타 탈출 때. 「끝난 이벤트가 다시 실행된다」 |
| **아크담 이벤트 대사 무한루프** | 🔴 열림 — 같은 꼴일 수 있다 |

**어디까지 좁혔나**
· **원판은 한 번만 나온다** ⇒ 우리 버그다.
· **`only-font`(문안 0)도 한 번만** ⇒ **폰트 후킹은 무죄**, 범인은 **문안 재삽입**이다.
· `known-good` 에서도 난다 ⇒ **오늘 넣은 대사·화자 탓이 아니다**(그 빌드는 그 전이다).
· 아이템 지급은 **8086 코드**(`11.01.20 +0xe5`, `mov al,ID; call` 셋)고 **우리가 덮은 적이 없다.**
· 원판↔`known-good` 전 구간 diff — 바뀐 바이트가 **전부 「글자 자리」**(텍스트 런 · 꼬리 빈자리)다.

⚠ **「지금 빌드가 슬라임 전투에서 멈춘다」는 내 오독이었다**(2026-09-08, 같은 날 정정).
하네스로 전투에서 확인키를 서른 번 넣어도 프레임이 안 바뀌길래 「굳었다」고 적었는데,
**유저가 전투 정상으로 확인해 준 `known-good`(88761bc5)에서도 똑같이 안 넘어간다.**
⇒ **빌드 결함이 아니라 내 하네스가 전투 커맨드를 못 고르는 것**이다(필드는 `Escape`,
전투는 다른 키다). 🔑 **「멈춤」과 「입력 대기」를 헷갈린 것**이고, 오늘 관리자가
「멈춤과 재출력을 가르라」고 경고한 그 부류의 셋째 얼굴이다.

**그래서 ⓐⓑⓒ 를 다 갈랐고 셋 다 무죄다** — 유저 확인 빌드(`b3605db1`) 뒤에 들어온 셋
(ⓐ 등장 문구 일곱 · ⓑ `<WAIT>` 하나 · ⓒ 옵코드 인자 가드 43자리)을 하나씩 되돌려 구웠는데
**넷 다 같은 자리에서 같은 화면**이었다(`no-a` `d44990fd` · `no-c` `869c19f0` · `opargs`

## ⚠ 「검수를 돌렸다」가 「말투를 다 봤다」가 아니다 (2026-09-12)

ps1 의 09-06 말투 회차는 **종결 어미의 등급 한 축**이었다 — **호칭 · 감탄사 · 대답어 ·
1인칭 · 지시사는 처음부터 안 봤다.** 그래서 「영감/할아범」(호칭)도 「예이」(대답어)도
안 걸렸고, 마스터 QA 에서야 나왔다.

🔑 **다음 라운드 첫 숙제 — 우리 회차가 어느 축을 봤는지 센다.** 「`rpg-translate` 돌렸다」로
닫으면 같은 데서 샌다.

**ps1 에 있고 우리에게 없는 검사기 일곱**(관리자 집계: ps1 40 · pc98 5):

| 검사기 | 무엇을 |
| --- | --- |
| `check_speaker_register` | 인물별 말투가 **대장과 맞는가**(기계 대조) |
| `check_speech_level` | 한 사람이 한 호흡에 존대·반말을 섞는가 |
| `check_name_echo` | **이름이 두 번 나가는가** |
| `check_window_nl` | 창 앞 개행 — 2인 대사가 한 줄에 붙는 부류 |
| `check_block_join` | 앞 블록 꼬리에 뒷 블록 머리가 붙는 자리 |
| `check_onomatopoeia` | 의성어가 원문 꼴을 지키는가 |
| `check_register_vs_jp` | 원문 표지 대비 우리 등급 |

💡 **우리 다섯은 다 게이트에 물려 있다**(관리자 실측 — ps1 은 40 중 17 이 안 물렸고 그중
`check_speaker_register` 가 있다). **있는 검사기를 손으로만 돌리면 돌린 회차에만 초록**인데,
우리 쪽엔 그 함정이 없다. 새로 만드는 것도 **만들면 게이트에 문다.**

🔴 **그런데 「물려 있다」도 「본다」가 아니다.** ps1 이 초록이던 셋을 캐 보니 **원인이 셋 다
달랐다**(2026-09-12) — 우리 숙제의 잣대가 여기 있다:

| 초록의 이유 | 실측 |
| --- | --- |
| **분모가 좁다** | `check_window_nl` — 게이트가 **인자 없이** 불러 ED1 여섯 씬만 봤다 |
| **정규식이 대상을 제외** | `check_name_echo` — 진짜 이름창 꼴(`{c}이름{c}{n}`)을 **일부러** 뺐다 |
| **소관이 아니었다** | `check_block_join` — 분모는 멀쩡했고, 그 결함은 **원문의 구분 공백을 우리가 지운 것** |

⇒ 숙제는 **「검사기가 있나 · 게이트가 부르나」에서 끝나지 않는다.** 셋을 더 센다 —
**분모가 전량인가 · 무엇을 제외하나 · 그 결함이 이 검사기 소관인가.**
🔑 한 줄로 — **「가지고 있다」와 「쓰고 있다」를 가른다**(md 의 말).
