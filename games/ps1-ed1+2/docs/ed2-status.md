## 한 일 (2026-08-11)

### 1. 씬↔정발 표 매칭 규칙을 새로 도출했다

옛 규칙은 **정발 파일명 셋째 글자(그룹) = 씬번호 − 1** 이었다. ED1 실측 규칙인데
ED2 에는 안 맞는다:

- **정발 그룹 9개(0~8) ↔ PS1 씬 13개.** 한 자리 전제라 씬 10~13 은 늘 0건이었고
  (빌드가 `⚠ ED2 씬10~12 — 대응 KR 테이블 0건` 을 계속 찍었다), 씬 1~9 도 한 칸씩
  어긋난 그룹을 보고 있었다.
- 진짜 구조: **정발은 ED1 의 지역 묶음을 물려받았고**(그룹0 = ED1SCN1 지역 =
  엘아스타·루디아·크루즈·베르가·네리아 …) **PS1 은 그걸 진행 순서로 다시 갈랐다**
  (그룹0 → 씬1+2, 그룹2 → 씬4+5+13).

판정 근거는 **원본 맵 세그먼트의 지명 헤더 전수 스캔**이다. ED1 은 `patch_sys_ui.PLACES`
사전으로 찾지만 ED2 는 사전이 없어 **구조로만** 긁었다(포인터 꼬리 `0x80`/널 뒤의 널종단
SJIS). 씬이 덮는 맵이 그대로 나오고, 정발 `F_000`(워프 목적지 30곳)과 **깨끗이 맞물린다.**

정본: [`../ed2_scene_tables.json`](../ed2_scene_tables.json) · 지도:
[ed2-scene-map.md](ed2-scene-map.md).

⚠ **기계 판정만으로는 안 됐다.** 고유명 다리 사전(JP 가타카나 247종 → 정발 표기 음차
퍼지 매칭 162개)으로 표별 점수를 매겨 봤지만 `T_04`(네리아)가 씬5·7 로, `T_20`(요르도)이
씬5 로 갔다 — **상점·잡담이 많은 표는 고유명이 안 나와 판정이 안 선다.** 계열별로
내용을 읽어 확정했다(`tables_hint`).

### 2. 옛 규칙으로 만든 배정 568건을 폐기했다

`align_map.json` 의 `ED2SCN1~9` 는 **어긋난 그룹에서 뽑은 것**이다 — 예컨대 `ED2SCN1`
(엘아스타·크루스·베르가·네리아)이 `T_04x`(네리아)뿐 아니라 엉뚱한 표를 물고 있었고,
`ED2SCN2`(루디아)는 그룹1(론도·랄파·리젤)을 보고 있었다. **재삽입 체인에 안 올라와
있어 이미지에는 영향이 없었지만**, 정본 파일에 남겨 두면 「사람이 검토한 배정」과
구분되지 않아 첫 ED2 빌드를 조용히 오염시킨다. 지워서 0 에서 시작한다.

### 3. 정발 교정 규칙을 게임별로 갈랐다

`dos_spelling_fixes.json`(공용) + **`dos_spelling_fixes_ED2.json`(ED2 전용, 신규)**.
`spell_fix(t, game)` 으로 게임이 흐르고, `kr_entry` 가 표 이름(`ED2/C_000`)에서 떼어
엔트리에 stamp 한다. 문제가 둘이었는데 파일을 가르니 한꺼번에 풀렸다:

- **오염** — ED2 겨냥 규칙이 ED1 문안을 조용히 바꿨다(`한 가운데에` 사고). ED1 은 QA 를
  끝낸 층이라 이 방향이 제일 비싸다.
- **머지 충돌** — 양쪽 브랜치가 3,000쌍짜리 `replace` 배열 같은 자리에 append 했다.

⚠ 보호는 **한 방향**이다(공용 규칙은 ED2 에도 걸린다 — 의도한 설계, 파일 `_doc` 참조).
`check_spell_rules.py` 도 게임별로 세도록 고쳤다(사문 판정이 코퍼스를 가려야 맞는다).
**수용 기준이던 이미지 sha1 `8d368c90…` 동일** — 순수 리팩터링임을 확인했다.

#### 제안이 얼마나 맞나 — ED1 로 실측한 77.4%

같은 도구를 ED1 에 돌려 **손으로 다듬은 정본과 대조**했다. 이게 ED2 수작업 분량의 실측
근거다:

| | 일치 | 좌표 다름 | 정본에만 | 제안에만 |
| --- | ---: | ---: | ---: | ---: |
| ED1 6씬 | 1,284 | 314 | 61 | 126 |

**정본 대비 재현율 77.4%** — 문서에 적힌 「유사도 배정 정밀도 79%」와 사실상 같은 수다.
즉 **제안의 5분의 1은 좌표가 틀린다.** 눈으로 확인한 것도 같다(`work/review/ED2_SCN1.md`) —
`시녀 저녁식사 ↔ 비프 스튜` 처럼 정확한 쌍이 있는가 하면, 무기점 대사가 한 블록씩 밀리거나
(`T_001#1` 이 jp13 에 붙고 jp12 는 엉뚱한 `T_010#27`) 본문이 빈 엔트리를 무는 것도 있다.

#### ⚠ ED2 에만 있는 실패 방식 — 씬끼리 같은 정발 엔트리를 문다

ED1 은 씬↔그룹이 1:1이라 후보가 안 겹쳤다. ED2 는 겹치고, 헝가리안은 씬마다 따로 풀려
서로를 모른다. **738건 / 청구 3,556건(21%)** 이 두 씬 이상에 물렸다:

```
씬4↔씬5 266 · 씬1↔씬2 210 · 씬8↔씬9 157 · 씬8↔씬11 57 · 씬9↔씬11 50 …
```

⚠ **겹침 자체는 오류가 아니다**(정발 한 엔트리를 PS1 이 여러 번 쓰는 건 일상이다).
판정에 쓰는 건 **점수차** — 새 검출기 `tools/check_scene_overlap.py` 가 점수차 순으로 낸다.
0.15 이상 벌어진 **325건**이 의심이고, 실제로 씬1 이 루디아 성 표(`C_00x`)를 0.5 대로 물고
같은 엔트리를 씬2 가 0.9 대로 물고 있었다.

#### 🌱 `ED2SCN1` 정본 씨앗 229건 — **미검토다**

`align_map.py --update ED2SCN1` 로 넣었다(399 매칭 중 `accept_pair` 가 229건만 통과 —
게이트는 ED2 에서도 제대로 돈다). **사람이 읽고 확정한 게 아니라 작업 바닥재**다.
위 77.4% 대로면 이 중 50건 안팎이 좌표가 틀렸다. 검토 전에 다른 씬을 `--update` 로
더 넣지 말 것 — 정본이 「검토된 것」이라는 뜻을 잃는다(그래서 옛 568건을 지웠다).

### 5. 🔴 ED2 오버레이는 ED1 과 **다른 주소에 로드된다**

`reinsert_kr_pilot.OVERLAY_RAM_BASE = 0x8016A000` 은 「ED1 전 씬 공통」으로 검증된 값인데,
**ED2 는 `0x80165000`** 이다(0x5000 = 20,480B 차이).

추측이 아니라 **도출**했다 — 오버레이 안의 `lui+addiu/ori` 가 만드는 주소마다
`base = addr − 블록오프셋` 후보를 세어 최빈값을 취한다. ED1 은 이 방법이 알려진 값을
92~97% 적중으로 재현하고, **ED2 는 13씬이 만장일치**다. 검사기: `tools/check_overlay_base.py`.

⚠ **이 상태로 ED2 를 체인에 올렸으면 모든 포인터가 20,480B 씩 어긋나 확정 소프트락이었다.**
지금은 정본 표(`reinsert_kr_pilot.OVERLAY_BASE`)만 두고 코드는 안 고쳤다 — `OVERLAY_RAM_BASE`
를 그대로 쓰는 자리가 열댓 곳이고 전부 ED1 값이라, **ED2 를 체인에 올릴 때 그 표를 타게
고치는 게 필수 작업**이다.

### 6. ED2 오프닝 — 위치·정발 문안 확보 (배치는 미착수)

⚠ **동영상 EXE 는 넷이고 전부 같은 문자열 테이블을 통째로 들고 있다** — `OPEN1`(69) ·
`OPEN2`(116) · `END1`(163) · `END2`(210), 넷 다 96,256B 에 226포인터다. 같은 프로그램에
데이터만 얹은 꼴이라 **어느 파일을 고치는지가 곧 어느 화면을 고치는지**다. 처음엔 OPEN1
안에서 ED2 오프닝·엔딩·크레딧을 다 찾고 「OPEN1 하나에 셋이 들어 있다」고 적었는데,
**OPEN1 의 엔딩 텍스트를 고쳐 봐야 화면엔 안 나온다**(엔딩은 END1 이 돌린다).

| 파일        | 화면                | ED2 몫 | 상태                          |
| ----------- | ------------------- | :----: | ----------------------------- |
| `OPEN1.EXE` | ED1 오프닝          |        | ✅ 한국어(폰트 임베드 + 50줄) |
| `OPEN2.EXE` | **ED2 오프닝**      |   ●    | 🔴 일본어                     |
| `END1.EXE`  | ED1 엔딩·크레딧     |        | 🔴 일본어 (ED1 몫)            |
| `END2.EXE`  | **ED2 엔딩·크레딧** |   ●    | 🔴 일본어                     |

파일 안 구획(OPEN1 기준 — 파일마다 조금씩 밀려 있다): ED1 오프닝 `0x145A0~` ·
**ED2 오프닝 26줄 `0x148A0~0x149EC`** · 엔딩 내레이션 `0x14ABC~0x14D88` · 크레딧 `0x14DE4~`.
텍스트 본문은 `0xEF0~0x1B14`(build.py `IMMUTABLE` 에 「OPEN1 ED2 오프닝 내레이션」으로
등록돼 원본과 byte 대조 중 — **손대려면 그 항목부터 풀어야 하고 이름도 고쳐야 한다**).

⚠ **OPEN2·END1·END2 엔 한글 폰트가 안 들어가 있다** — `patch_opening_font` 가 OPEN1 에만
임베드한다. 문안만 넣으면 글자가 안 나온다.

**정발 문안은 찾아 뒀다:**

- ED2 오프닝 → `originals/kr/dos-ed2/OPENING.EXE` **0x99102~0x99640**, cp949, **26줄**
  (공백이 `_` 로, 선두 공백은 가운데 정렬용).
- ED1 엔딩 → `originals/kr/dos-ed1/ENDING.EXE` **0x1973A~**, cp949.
- ⚠ **크레딧은 사람 이름이라 번역하지 않는다**(유저 판단 2026-08-11).

⚠ **줄 수가 26으로 같은 건 우연이다.** PS1 리메이크가 문장을 다시 썼다 — PS1 은 영웅 넷을
이름으로 부르며 시작하고(`伝説の英雄達セリオス、リュナン、`) 정발 DOS 는 `악신 아그니쟈가
쓰러져` 로 시작한다. 대응은 **문장 단위**지 줄 단위가 아니다. ED1 오프닝에서 굳은 원칙이
그대로 적용된다 — **PS1 줄·블록 구조를 저본으로 삼고 정발 문장을 그 위에 배치한다**
(구조와 싸우려다 세 번 깨졌다. 루트 `CLAUDE.md` KISS 절).

### 7. 🔴 **ED2 는 자기 실행파일이 따로 있다** — ED1 의 UI·아이템 작업이 하나도 안 걸린다

디스크 파일 목록을 뜨고 알았다(2026-08-11). `ED.EXE`(LBA 257) 는 **ED1 전용**이고
**`ED2.EXE`(LBA 756, 872,448B)** 가 따로 있다. `patch_sys_ui`·`patch_items`·`battle_text`
는 전부 `ED.EXE` 오프셋을 직접 물고 있으므로 **ED2 화면엔 아무 효과가 없다.**
몬스터 데이터도 갈려 있다 — `BIN/ED2MON0~5.BIN` · `DATA/ED2MON.DAT`.

`ED2.EXE` 안을 SJIS 밀집도로 훑은 결과(ED1 구조와 나란히 두면 읽힌다):

| 영역               | 내용                                             | ED1 대응            |
| ------------------ | ------------------------------------------------ | ------------------- |
| `0x800~`           | **캐릭터명 4**(아트라스·란도·플로라·신디) + 장비 | `0x828~0xE73`       |
| `0x830~0xC000`     | 무기·방어구·아이템·마법 이름 블롭                | 〃                  |
| `0x6000~0xA400`    | **EXE 안에 박힌 이벤트 대사** — 프롤로그(황제·플래드·레이시아)·지나 관광투어 | ED1 엔 없던 층 |
| **`0x99C84~0x99F80`** | **UI 라벨 전체** — 메뉴·전투커맨드·전투설정   | `0xBE290~0xBE5C6`   |

UI 라벨은 고정 슬롯이라 ED1 처럼 오프셋별 직접 매핑이 가능하다(실측 목록):
`呪文·使う·装備·捨てる·強さ·その他` / `リーダー·戦う·呪文·守る·使う·武器·オート·強さ·逃げる` /
`最後に出た町に戻る·戦いの直前に戻る·冒険の続きをする·ＳＡＶＥ·ＬＯＡＤ·システム·戦闘設定` /
`強さ·かしこさ·すばやさ·運の良さ·攻撃力·防御力·呪文能力` /
`オートバトル·オート回復·戦いの呪文·回復の呪文·回復アイテム·全員の設定を` /
`ＯＮ·ＯＦＦ·使う·使わない·同じに·別々に·オート移動·レベルアップ·ＥＰ·ＢＧＭ·移動·メッセージ·オート·ﾏﾆｭｱﾙ`

⚠ **`0x6000~0xA400` 은 예상 못 한 층이다** — ED1 은 대사가 전부 SCN 오버레이에 있었는데
ED2 는 프롤로그·특수 이벤트를 EXE 안에 들고 있다. **`todo_untranslated`·`check_scn_jp_left`
어느 것도 여기를 안 본다.** 정발 대응은 찾아 뒀다(관광투어 = `F_501`).

### 8. 오프닝 폰트 장치는 나머지 셋에 **기계적으로 이식된다** (2026-08-11 확인)

오프닝은 **BIOS 일본어 폰트**(`0xBFC66000`, 16×15/30B)를 렌더러 `0x8001BE24` 로 그린다.
BIOS 는 수정 불가라 ED1 은 이렇게 우회했다(`patch_opening_font`):

1. 압축 Galmuri9 한글 폰트를 파일 `0x15CE0`(RAM `0x800254E0`, 안전 0영역)에 임베드
2. **PC0 훅 스텁**(`0x15C14`, 저작권 문자열 자리)이 **게임 힙클리어보다 먼저** 자유 RAM
   `0x80080000` 에 전개한 뒤 원 PC0 로 점프
3. 폰트베이스 획득부(`0x8001BE84` = `jal`+`nop`+`move s0,v0`)를 **`lui/addiu s0 =
   0x80080000`** 으로 덮는다. 렌더 코드는 원본 그대로(glyph = base + index×30)

**나머지 셋(OPEN2·END1·END2)에도 같은 코드가 있다** — 주소만 밀려 있다. 하드코딩된 값을
**도출**로 바꾸면 그대로 이식된다:

| 앵커                 | 도출 방법                                        | OPEN1 / OPEN2 / END1 / END2                 |
| -------------------- | ------------------------------------------------ | ------------------------------------------- |
| 원 PC0               | PS-EXE 헤더 `0x10`                               | `21D50` / `21BAC` / `21D4C` / `21BA4`       |
| 폰트베이스 획득부    | `ori a0,zero,0x889F` + `jal` + `nop` + `move s0,v0` | RAM `1BE84` / `1BCE0` / `1BE80` / `1BCD8` |
| 안전 0영역(폰트·스텁)| 최장 0런                                         | 넷 다 **4,203B** (f0x15C69 / 15AC5 / 15C65 / 15ABD) |

⚠ 패턴 탐색이 **OPEN1 에서 하드코딩 값(`0x8001BE84`)을 정확히 재현**했다 — 그래서 나머지
셋의 도출값도 믿을 수 있다(오버레이 base 를 도출할 때와 같은 논법). 넷 다 taddr `0x80010000`
· tsize `0x17000` · bss 0 · sp `0x801FFFF0` 로 동일하다.

⚠ **텍스트 예산은 파일마다 다시 재야 한다** — ED1 오프닝은 저주소 텍스트 영역
`0x974~0xEEE`(1,402B) 안에서 재packing 했고, **고주소 재배치는 금지**다(스크립트가 주소
범위로 text/command 를 구분해서 옮기면 검은 화면이 된다).

**패치 앵커도 넷 다 도출했다** — `tools/check_movie_anchors.py`. 여섯 앵커 전부 OPEN1 의

⚠ 두 앵커는 **패턴을 처음에 잘못 짚었다** — 반각 비교 체인의 즉시값 순서가
`8140·8289·8286·828A·828C`(내 가정과 8289/8286 이 뒤바뀌어 있었다)이고, advance 상수는
같은 워드가 체인 **앞에도** 있어 「체인 뒤 첫 것」으로 갈라야 한다. 검사기가 OPEN1 을
재현하는지 보지 않았으면 둘 다 조용히 틀린 자리를 팼을 것이다.

#### 🔴 폰트는 **파일마다 자기 구획만** 담아야 한다

| 구획       | 고유 문자 | 압축 추정 |
| ---------- | --------: | --------: |
| ED1 오프닝 |       214 | 3,988B(실측) |
| ED2 오프닝 |       140 |  ~2,610B  |
| ED1 엔딩   |       160 |  ~2,980B  |
| ED2 엔딩   |       137 |  ~2,550B  |
| **합집합** |   **337** | **~6,280B** |

**안전 0영역은 4,203B** — 합집합은 안 들어간다. 파일마다 자기 구획만 담으면 넉넉하다.
그래서 **각 EXE 에는 자기 화면 몫만 한국어로 넣는다**(OPEN2=ED2 오프닝, END1=ED1 엔딩,
END2=ED2 엔딩). 나머지 구획은 일본어로 남긴다 — 어차피 그 파일이 안 그리고, **가정이
틀렸을 때 깨진 글자가 아니라 일본어가 나오는 쪽이 안전하다.**

#### 남은 일 — 여기부터 이미지가 바뀐다

1. `patch_opening_font` 를 **타깃 구동**으로 넓힌다(앵커는 하드코딩 대신 도출).
   ⚠ 수용 기준: **OPEN1 결과가 바이트 동일**(지금 sha1 `8d368c90…`).
2. 줄머리 `!`·`＿`·`*`·`~`·`「」` 는 **스크립트 표식**이라 2바이트 슬롯으로 바꾸면 안 된다.
   textmap 에서 `parts` 로 문안과 갈라 뒀다 — 패처가 이걸 지켜야 한다.
3. `build.py` `IMMUTABLE` 의 「OPEN1 ED2 오프닝 내레이션」 항목을 풀고 이름을 고친다.
4. ⚠ **보조 풀(`POOLS`)은 OPEN1 전용이다** — CD 오류문 자리를 본문으로 돌려쓰는 건 그
   경로가 죽은 뒤라는 근거가 OPEN1 에서만 확인됐다. 다른 파일엔 쓰지 않는다.
5. **인게임 확인 필수** — 이 머신엔 에뮬레이터가 없다. 앵커는 정적으로 검증했지만
   틀리면 증상이 검은 화면·소프트락이다.
