⇒ **더 두드리지 않는다.** 시간을 두고 다시 본다.

**도구 쪽에 고칠 것 둘**(둘 다 `shared/text/spellcheck.py` — main 몫이라 여기선 못 고친다):
1. **기본값이 체험 엔드포인트에 너무 세다** — `--jobs 4` 로 130요청을 연달아 쏜다.
   요청 간 간격이나 백오프가 없다.

   ⇒ **청크별로 실패를 견디고 끝에 「몇 개 실패」로 보고**해야 한다.

제자리엔 안 들어가는데(786B/684B), 줄마다 포인터가 따로 있어 **블록을 통째로 재packing**

⚠ **파일마다 스태프롤 블록이 둘이다** — END1·END2 가 서로의 스크립트를 사본으로 들고 있다.
판별은 **포인터가 어느 표에 놓였는가**로 선다:

| 파일 | 내레이션 표   | 살아있는 스태프 블록 | 상대편(=보조 풀로 씀) |
| ---- | ------------- | -------------------- | --------------------- |
| END1 | 0x14AB8~14D84 | **0x1260~0x150C**    | 0x1B84~0x1E84         |
| END2 | 0x14EF4~15184 | **0x1B80~0x1E80**    | 0x125C~0x1508         |

라벨 넷(`*原作`·`*発売`·`*開発`·`*協力`)은 스태프 문자열과 **떨어진 자리**에 있다

`~`·`#1`·`%<` 대역은 **제어 스트림이라 손대면 안 된다.**

⚠ **본영역(`min~~max` 스팬)에서 블록을 도려내야 한다.** END2 는 내레이션 줄 둘이 블록
뒤쪽에 있어 스팬이 0x1B80~~0x1E80 을 삼켰고, 내레이션 packer 와 블록 packer 가 같은
바이트를 서로 덮어썼다 — `＊발매` 아래 「..」가 떴다(2026-08-16 인게임 실측). END1 은

⚠ **폰트 예산이 곧 어휘 예산이다.** END1 은 여유가 26B(≈글리프 0개)뿐이라

### ⚠ 넘침 50건의 원인은 하나다 — 조사 병기

원문 `は` 는 2바이트인데 우리 `은(는)` 은 **6바이트**다. 넘치는 자리를 늘어놓으면 부족분이
대부분 +1~+3바이트라 **병기가 곧 원인**이다:

```
は目がさめた。      14B → `은(는) 깨어났다.` 18B   슬롯 16B
```

~~ED1 은 동적 조사 훅으로 이 4바이트를 회수한다. ED2 에는 없다.~~

⚠ **이 진단은 틀렸다**(2026-08-16 실측). 훅은 **표시할 때** 병기를 고르는 장치라 저장된

| ✅ **즉치 자리는 루프다** | 세레 마을 실측: `ra 0x80074D08 · a2=0`(목록 비우기) → `ra 0x8006CFD0 · a2=2, a0=1` → **같은 자리 · a2=2, a0=3**. 즉 「일반 마을사람(조형 2)을 여러 명 놓는다」는 루프다. 조형이 일곱 종뿐인 것과 앞뒤가 맞고, **고칠 자리는 데이터가 아니라 명령**이라는 그림이 굳는다 |
| ⚠ **막힌 자리** | 슬롯6(마을)에서 위로 올라가 **`camY`=0(맵 위쪽 끝)** 까지 갔지만 좌·우로 훑어도 **BP 무반응 = 전환 없음**. **입구 칸을 못 짚었다** |
| ✅ **닫혔다 — 고칠 자리는 바이트 하나** | 마을 밖으로 나온 **그 자리에서 곧바로 `up`** 으로 재진입해 설치를 잡았다. 슬롯9 id 바이트(`0x8013D94D`)에 write BP + **PC 필터 `pc_min=pc_max=0x8002E73C`** ⇒ 설치 한 번만 잡힌다. 프레임(`fp 0x801FFF70`): `+0x01`=id **0x04** · `+0x10`=슬롯 **9**. 호출자 `ra 0x801888A0` ⇒ jal 은 `0x80188898` |
| ✅ **고칠 자리** | 오버레이 `0x80188880` 의 **`addiu a2, r0, 0x0004`**(조형 id 즉치). 바로 뒤 블록이 「슬롯10·id 7」인데 실제 배열의 idx10 이 `0x07` 이라 **독립 교차검증**이 됐다 |
| ✅ **파일 자리** | 서명 `09 00 04 24 80 00 05 24 04 00 06 24 0e 00 07 24` 가 **원본·빌드 각 1곳**(모호함 없음) — raw **`0x004645B0`**(lba 1958 · 섹터 안 `+0x78`). **조형 id 바이트 = raw `0x004645B8`, 값 `0x04`**. 검산: 슬롯10 의 id 는 raw `0x004645E0` = `0x07` ✓ |
| ✅ **넣을 값 = `6`** | **정적으로 결정된다.** `jal 0x8002E610` 을 오버레이 전수로 뜨고 인자를 역디코드하면 **같은 NPC 명단의 사본이 다섯 벌**(lba 1958·1959·1961·1964·1965) 나온다. 슬롯 1~8·127 은 다섯 벌 **전부 일치**하는데 **슬롯 9 만 갈린다** — 038 자리(1958)만 `id 4`, 나머지 넷은 `id 6`. **`a3` 는 다섯 벌 모두 `0x0e`** ⇒ **같은 NPC 자리, 조형만 다르다.** 한 칸만 튀는 건 설계가 아니라 한 글자 실수의 모양이다 |
| ⬜ 남은 것 | **인게임 한 장.** 잰 것은 「같은 자리의 다른 넷이 6 이다」까지다 — 굽고 나서 세레 그 자리에서 제니가 마스터 캡처(붉은빛 갈색 머리)와 맞는지 보면 닫힌다. 그 전엔 「id 6 이 제니 조형이다」라고 적지 않는다 |
| 🔑 왜 낫슈가 필요 없었나 | 비교가 **같은 오버레이·같은 맵 명단 안**에서 끝나 **맵을 건너는 가정이 없다.** 「조형 id 가 맵 공통인가」를 잴 필요도 사라졌다(참고로 `tpage` 는 낫슈도 세레와 같은 `0x01E2`). ⚠ 앞서 낫슈 로드로 간 회차는 **정적으로 끝나는지를 먼저 안 물어서** 생긴 우회다 — devlog 참조 |
| ⚠ 참고 | 제니 후보의 조형 id 는 **세이브 블록7 `+0x422`**(카드 파일 `0xE422`)에도 있지만 **세이브를 고치면 그 세이브만 고쳐진다** — 배포용 수정이 아니다. 실험은 전부 RAM 이고 **마스터 카드는 전후 sha1 무변경** 확인 |
| ⚠ 함정 | **NPC 인접 재현이 잘 안 된다**(30회 넘게 스쳐 BP 가 한 번도 안 걸렸다). 원인 모름 — devlog 「조작 함정 여섯째」 |

⚠ ED1 에서도 NPC 배치 구조체를 정적으로 못 찾아 라이브 BP 로 갔던 전례(devlog "NPC 바인딩"
절)가 있다 — 이번에도 결국 라이브 조사가 필요할 공산이 크다. 경위는 `devlog.md` 「038」 절 셋.

## 16. `042` 전투 각성 메시지 조사 훅 — BP 기준선 확정, 재현 막힘 (2026-09-13 밤, RE 세션)

**증상**: 전투 종료 후 "X가 깨어났다"(수면 각성) 메시지가 "아트라스은⁝⁝"처럼 조사 미해결 +
글리프 없는 `(`·`)` 원문자로 깨져 나온다. 자리: `textmap/battle_ed2.json`
k=1c451b86b3 "은(는) 깨어났다.\n".

정적 추적으로 이 메시지가 독·마비·혼란과 **같은 디스패처·버퍼·훅 경로**를 탄다는 것,
패턴 매칭 자체는 문제가 없다는 것(`fix_buffer` 모델 확인)까지는 확정했다. 남은 물음은
**워크슬롯(`0x800F1718`) write 와 훅① 진입(`0x80089A8C`) 중 어느 게 먼저인가** — 이번
회차에 실전 BP 로 이 순서를 재려 했으나 **수면 상태 자체를 재현하지 못해 막혔다**.

🔴 **재현 실패 경위**: 카드2 슬롯8 "라누라"에서 아시카사고A·B+익룡 조합 3전 — **셋 다
사이레스만 걸렸고 수면은 0건**. 익룡이 매번 1턴째에 죽어(란도 불꽃의 창 프록 선공킬)
행동할 기회가 없었던 것이 유력한 원인 — **수면 시전자가 아시카사고가 아니라 익룡일
가능성**을 배제하지 못한다. 전투가 자동 진행(수동 커맨드 개입 불가, 이번 관찰상)이라
익룡을 먼저 안 죽이는 식의 개입도 못 했다. 다음 사람은 이 세 조합을 또 반복하지 말 것.

**대신 파티 구조체 위치는 확보**(스냅샷 diff로 확정, 스트라이드 0x6C):

    아트라스  flags/Lv @0x13D670 · HP(i32) @0x13D674 · MaxHP(i32) @0x13D678
    란도      flags/Lv @0x13D6DC · HP(i32) @0x13D6E0 · MaxHP(i32) @0x13D6E4

사고전에서 재현률 높음)을 먼저 걸고 이 8바이트를 전/후 diff** 하는 것. 경위는 `devlog.md`
