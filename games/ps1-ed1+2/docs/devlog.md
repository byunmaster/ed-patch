## 오프닝 한글 폰트

> 원 제목: ED1 오프닝 한글 폰트 작업일지

영웅전설 1(PS1) 오프닝 내레이션(OPEN1.EXE, LBA 69)을 한글화하는 과정 기록.
코드에는 최종 결과만 남지만, 여기엔 **왜 그렇게 했는지·무엇을 시도하다 막혔는지**를 남긴다.

관련: 메모리 `ed1-opening-font`, 도구 `tools/patch_opening_font.py`.

---

### 목표

오프닝은 세계 지도 위로 내레이션(26문장, ~49 표시줄)이 스크롤된다. 텍스트 번역은
정발(만트라) 기반으로 완료(온리크/라누라 지명 통일 포함). **폰트만 남았다.**

인게임(ED.EXE)은 자체 12×12 비트맵 폰트를 임베드해서, 한자 슬롯을 한글 글리프로
덮어쓰는 방식으로 이미 해결됐다. 오프닝도 같은 줄 알았으나 — 아니었다.

### 1. 폰트 출처 규명 (에뮬레이터 디버깅)

DuckStation 스크린샷으로는 오프닝에 우리 한글 슬롯이 **깨진 한자(亜·室·域…)**로 나왔다.
OPEN1.EXE에 ED.EXE 폰트가 없고 글자가 커서 다른 폰트로 추정 → 확정을 위해
mednafen(디버거 포함)을 빌드해 라이브 분석.

- 정적 분석 착각들: START.DAT·파일 스캔에서 "폰트 비슷한" 밀집데이터가 계속 오검출.
  히라가나 순서 매칭(ヒラギノ 템플릿)도 이미지 데이터에 낚임. **정적 접근은 한계.**
- 라이브 브레이크포인트로 확정:
  - 내레이션 렌더 진입은 파서 `0x800132B0`(문자열 @0x80010198 읽음).
  - 문자 그리기: `0x800136EC jal 0x8001BE24`(a0=SJIS) → 글리프주소 v0 → `0x80013104`로 그림.
  - 글리프주소 함수 `0x8001BE24`: `s0(폰트베이스) + index×30`. **30바이트 = 16×15**.
  - 폰트베이스 s0은 `0x80016CE8` = `addiu t2,0xB0; jr t2; addiu t1,0x51` → **BIOS 콜 B(0x51)**.
  - 실측 s0=**0xBFC66000** (BIOS ROM). 글리프 읽어보니 진짜 한자 도트.

**결론: 오프닝 폰트 = PS1 BIOS 일본어 한자 폰트.** 게임 파일이 아니라 콘솔 펌웨어.
BIOS는 수정·배포 불가 → ED.EXE식 슬롯 덮어쓰기 불가. **OPEN1을 패치해 BIOS 대신
임베드 한글폰트를 쓰게** 해야 한다.

### 2. 막다른 길들

#### (a) 제자리 임베드 → OPEN1이 폰트를 지움

OPEN1 이미지(0x80010000~~0x80027000)는 코드·데이터로 꽉 찼고, 유일한 여유는 tail의
0영역. 거기 폰트를 넣으니 **오프닝이 검은화면**. 격리 결과: tail(0x8002546C~~)은
**OPEN1의 힙/작업구조체**(setjmp 컨텍스트 포함, 시작 시 0으로 초기화)라 폰트가 로드
직후 지워졌다(RAM 실측 0).

#### (b) 힙 재배치 → 참조가 너무 많음

"힙을 자유 RAM으로 옮기면?" 좋은 발상이었으나, 작업구조체 필드를 **코드 38곳 이상이
하드코딩 절대주소로** 접근(렌더 코드 포함). 단일 베이스가 아니라 흩어져 있어, 하나라도
놓치면 크래시. 비실용적.

#### (c) ISO 확장 → 배포 패치가 커짐

폰트를 이미지 밖(0x80027000+)에 로드하려면 OPEN1.EXE를 키워야 하고, 그러면 ISO의
후속 파일(OPEN2 LBA116~)이 전부 밀린다(ISO 리빌드). 배포는 xdelta로 가능하나 패치가
커지고 리스크↑. 유저가 원치 않음.

### 3. 돌파구 — PC0 후킹 memcpy (제자리, ISO 안 건드림)

핵심 관찰:

- PS-EXE 헤더 `b_size=0` → **로더는 아무것도 0으로 지우지 않는다**. 폰트는 파일에서
  로드된 그대로 **PC0(진입점) 시점엔 온전**하다. 지우는 건 그 뒤 게임코드(힙 init).
- 자유 RAM이 **1.27MB**(0x8007317F~0x801B0000, 오프닝 내내 0 유지) 남아있다.

⇒ **진입점을 후킹해, 힙이 지우기 전에 폰트를 자유 RAM으로 대피시킨다.**

1. 폰트를 파일에 임베드(로드시 RAM 0x800254E0으로 옴).
2. 저작권 문자열 자리(0x80025414, 힙 밖·미사용)에 **memcpy 스텁**을 넣는다.
3. 헤더 PC0(파일 0x10)를 스텁 주소로 바꾼다.
4. 스텁: 폰트를 0x800254E0 → **0x80080000(자유RAM)** 워드복사 후 원래 PC0(0x80021D50) 점프.
5. 렌더 폰트베이스를 0x80080000대로 리다이렉트(`0x8001BE84` jal 자리에 lui/addiu s0).

`tools/patch_opening_font.py`가 이 5단계 + 내레이션 재인코딩을 자동화.

### 4. 그 과정에서 잡은 버그들

- **인덱스 공식 착각**: 처음엔 표준 JIS 선형인덱스(0x889F=1410)로 base를 잡았는데
  틀렸다. 게임 index함수(`0x8001BED4`)는 첫바이트≥0x88(한자)에서 `0x8001C338` 경로로
  **테이블 룩업**(`index = SJIS − table[k].base + table[k].offset`, 테이블 @0x80024E60).
  `table[0]=(0x889F, 0)` → **index(0x889F)=0, 0-기반·연속**. 그래서 base=폰트시작(오프셋
  없음). 에뮬 실측(카타카나 0x8340→292, jis_index 376과 차이 84)으로 발견.
- **복사 +4 밀림**: memcpy 결과가 일정하게 첫 워드에 쓰레기가 붙어 폰트가 +4 밀림
  (`mem[FONT_LOAD]` 첫워드가 쓰레기; 원인 미규명). 렌더 base=0x80080004로 보정하니
  글리프 정렬 5/5. (내일 근본원인 재확인 여지.)
- 스텁 위치 함정: 0x80025410을 OPEN1이 변수로 써서 스텁 첫 워드가 오염 → 스텁을
  0x80025414(+4)로. 폰트 소스도 setjmp(0x800254A4~DC) 뒤 0x800254E0으로.

### 6. 폰트 완성 — 네이티브 15행 압축 디코더 (2026-07-12~13)

9행 축소의 그림자·크기 문제를 **네이티브 15행(30B) 전환**으로 근본해결. raw 30B×191=5730B는
안전영역 초과라 **행-마스크 압축**(글리프당 2B 마스크+비영행) → 3620B로 넣고, **memcpy 스텁을
행-마스크 디코더로 교체**해 자유 RAM에 전개.

#### 디코더 손인코딩 함정 2개 (반나절 디버깅)

- **andi rs 필드 오타**: `andi t5,t3,1`을 `0x306D0001`로 썼는데 이건 `andi t5,**v1**,1`. rs를
  t3(11) 아닌 v1(3)로 인코딩 → 마스크가 v1(비트0=0)로 읽혀 **모든 행이 빈 행 처리 → 폰트 전부 0**.
  정답 `0x316D0001`. **교훈: 스텁을 `disasm.py`로 역어셈블 + Python으로 로직 시뮬 필수.**
- **load-delay 슬롯**: memcpy에서 `lw t3; sw t3`면 sw가 stale t3 → **+4 밀림**(어제 "복사 +4"의 정체!).
  사이에 `addiu`를 넣어 지연 채우면 해결. (폰트 디코더는 lhu/sh 사이 지연이 이미 채워져 무탈)

#### 폰트 크기·품질 결정

- 잘림 원인: dy=2면 잉크가 5~14행(아래여백0)이라 받침이 맨끝행에서 컷. → dy로 중앙정렬.
- 11px(Galmuri11)는 무잘림 시 압축 4338B > 안전 4084B(불가). 9px(Galmuri9)는 3584B로 여유.
- neodgm(16px TTF)은 10~12px까지 들어가나 축소렌더라 획이 거침(유저 확인). **→ Galmuri9 채택**(또렷·전체음절·무잘림, 유저 확정).

#### 내레이션 표시 버그 = 렌더가 2바이트 전용

폰트가 뜨자 **중간단어 누락·부호 깨짐**이 드러남. 원인: 표시 루프(`0x800136CC`)가 **항상 2바이트씩**
읽어 1바이트 문자 미지원 → 한글 사이 `\x20` 공백이 다음 글자 첫바이트를 삼켜 **줄 전체 어긋남**.
(폭측정 루프 `0x800132D4`는 1바이트를 폭0으로 건너뛰어 측정≠표시 불일치도 유발.) JP 원문은 전부
2바이트 SJIS + `\n`(0x0A)만 1바이트 특수처리.
**해결: 모든 문자(한글·부호·숫자·공백)를 2바이트 폰트 슬롯으로 통일(196글리프).** → 제자리 줄 온전 렌더.

#### 초과줄 재배치 — 미해결(검은화면)

공백 2바이트화로 **17줄이 JP 바이트예산 초과**. 자유 RAM(`0x80082000`) 재배치 시도:

- 포인터테이블(파일 0x145A0~, 줄 RAM주소 1:1) 갱신 + 디코더가 줄 블록도 자유RAM 복사.
- **크래시 → 블록이 안전영역(0x16CD4) 28B 침범 = OPEN1 테이블 손상**(스캔이 못 잡은 참조). 유저요청대로
  "이셀하사의 거의 중앙에"→"중앙에" 한 줄 축약(28B 확보)해 블록이 안전영역 내에 들어가게 함 → 크래시 해소.
- **하지만 재배치 켜면 오프닝이 검은화면**(크래시X, PC정상, VRAM 0). 원인 미규명 → 내일. 지금은
  `RELOCATE_OVERFLOW=False`(초과 16줄 스킵, 제자리 33줄 정상)로 커밋. 이어작업: `docs/HANDOFF.md`.

## 2026-07-13 (회사): 텍스트 완성 — 재packing·0x0A 필드클리어·advance 축소·정발 원문

### 검은화면의 진짜 원인과 재packing (재배치 문제 종결)

재배치 검은화면의 원인은 **스크립트(0x145A0)가 포인터 "값"의 주소 범위로 text/command를 구분**하기
때문이었다: text_ptr=0x8001xxxx, command_ptr=0x80026Dxx. 줄을 자유RAM(0x80082000)으로 옮기면
command로 오인 → 검은화면. 해결은 재배치가 아니라 **저주소 텍스트 영역(파일 0x974~0xEEE, 1402B) 내
재packing**: 50줄을 영역 상단부터 아래로 촘촘히 다시 깔고 포인터테이블만 갱신. 전 줄 저주소 유지.

### "세리오스→리오스" 글자 잘림과 딸림("파렌, 온리크, 는")의 규명

표시 루프는 **널 검사 없이 X좌표(s3)가 960(필드 우변)에 닿을 때까지** 그린다. 필드는 [896,960]=64유닛.

- 긴 줄(>필드): 중앙정렬 시작점이 화면 밖 → 앞뒤 글자 잘림("세리오스"→"리오스").
- 짧은 줄: 자기 글자를 다 그려도 널에서 멈추지 않고… 인 줄 알았으나, 실은 **0x800136B4에 널 종료가
  이미 있었다**. 진짜 원인은 **잔상**: 원본 JP 각 줄은 `…0A 00`으로 끝나고, **0x0A(개행) 핸들러
  (0x8001366C)가 960까지 빈 글리프16으로 필드를 채워 이전 줄 픽셀을 지운다**. 우리 줄엔 0x0A가 없어
  이전(더 긴) 줄 잔상이 남았던 것. RAM 라이브 패치 대조실험으로 확정(0x0A 주입한 파렌 줄만 깨끗).
  → enc()가 각 줄 끝에 0x0A 자동 부가.

### 글자 간격(가독성)과 줄당 한계 확대

전각 1글자 advance는 4유닛(=16px 셀)인데 Galmuri9 잉크는 ~9px라 성김. 폭측정(0x13370)·표시(0x13750)의
`addiu ,4`를 **3(12px)으로 패치**(둘 다 바꿔야 중앙정렬 일치). 2(8px)는 넓은 받침 겹침 — 라이브 패치로
2/3/4 비교 후 3 채택. 부수효과: **줄당 한계가 16→21전각슬롯**(64÷3)으로 늘어 정발 장문 수용 가능해짐.

### 정발 원문 적용 (유저: "정발판에 이렇게 오프닝이 있어")

정발 오프닝은 SINDLL이 아니라 **`originals/kr/dos-ed1/OPENING.EXE`**(OPEN.EXE도 동일)에 CP949 평문으로
있다(0x5E07B~, 26문장). 이를 우선 적용, JP에만 있는 부분(다섯 나라·몬스터 습격 확장)은 정발 어투 신규
번역. 표기 규칙(유저 확정): **쉼표 뒤 공백 없음**(쉼표도 전각 슬롯이라 여백 과대), **문장 끝 마침표
일관**, 따옴표 미사용. 예산이 빠듯할 땐 **어색한 한국어(겹말 등) 수정으로 공간 확보** — 45/47행의
"왕위계승때까지" 중복 제거로 8슬롯 확보한 것이 대표 사례. 문안 변경은 반드시 사전 보고.

### 50번째 줄 누락 발견 (전수 캡처의 소득)

전체 캡처 검수 중 마지막 화면에 깨진 글자 발견 → 포인터 0x147B8의 50번째 줄
`それから約１０年の歳月が流れた…`(파일 0x974)이 LINES에 누락돼 JP 원문이 한글 폰트로 깨져 표시되고
있었다(작업 초기부터). 정발 "그리고, 10여년의 세월이 흘렀다."로 추가. 영역 경계도 0x998→0x974로 확장.
영역 앞(0x938~ 포인터 배열)·뒤(0xEF0~ TIM 파일명, 0x14824~가 참조)는 확장 불가 확인 — **예산 1402B 고정**.

  (구 이미지인 줄 모르고 "패치가 안 먹었다"고 오판할 뻔 — find_pattern으로 RAM에 신규 슬롯 부재 확인이 결정타)

## 2026-08-02: 바이트 예산 확장 — JP CD 오류문 자리 회수

정발 표기(인명+직함 띄어쓰기 7건 + 절 경계 쉼표)를 넣자 **영역(0x974~0xEEE, 1402B)이 10B
모자랐다.** 유저가 "공백·온점·쉼표를 반각처리하면 공간이 생기지 않나"라고 물어 그 길을
파다가, **더 크고 코드 수정이 없는 자리**를 찾았다.

### 반각화는 왜 막혔나 (조사 결과)

- **폭측정 루프는 한 줄이면 된다** — `0x80013310 beqz $v0, 0x80013374` 가 1바이트 문자를
  advance 누적 없이 건너뛴다(폭 0). 바이트 소비는 이미 1바이트로 올바르다.
- **표시 루프가 문제** — `0x800136CC` 가 **무조건 2바이트를 읽는다**(1바이트 분기 부재).
  1바이트를 지원하려면 새 코드가 필요한데 `0x8001xxxx` 에 32B 이상 빈 자리가 **0개**라
  자유 RAM 트램폴린(`jal`)이 필요하다. 이득은 145B(공백 115·온점 14·쉼표 12·기타 4).
- **덤**: 렌더러에 이미 비례폭이 있다 — advance 2(`0x8140` 전각공백, `0x8286/89/8A/8C`
  = ｆｉｊｌ) · 3(`0x8281~0x829A` = ａ~ｚ) · 4(그 외, 우리가 3으로 패치). 공백·부호를
  advance 2 코드에 매핑하면 **코드 수정 없이 표시 폭**이 준다(바이트는 그대로).

### 실제 해법 — JP CD 오류문 204B (코드 수정 0)

영역 **바로 아래** 0x864~0x937 에 JP CD 오류문 2개가 있다.

```
0x80010064  CD-ROMからのファイルサーチに失敗しました。…   (104B)
0x800100CC  CD-ROMからのファイル読み込みに失敗しました。… (104B)
```

전 명령 lui/addiu 쌍 스캔으로 참조를 전수 확인했다 — **CD 실패 경로
(0x80012D08 · 0x80012DC0 · 0x80012DFC)에서만 참조**되고 그 안을 가리키는 다른 참조는 없다
(대조군 `cdrom:\ED.EXE` 6건 · `OPENEND` 1건은 정상 검출돼 스캐너 신뢰성 확인). 그 시점엔
게임이 이미 죽으므로 문안을 비우고 본문 공간으로 돌렸다.

- 각 문자열 **선두 4B 를 0으로** 남겨 오류 경로가 **빈 문자열**을 읽게 한다. 안 그러면
  오류창에 내레이션이 뜬다.
- 풀 2개(`0x868~0x8CC`, `0x8D0~0x938`, 204B). 줄마다 포인터가 따로 있어 **연속일 필요가
  없다** — 스크립트는 값의 주소 대역(0x8001xxxx)만 본다.

#### ⚠ 클리어 범위 함정 (실측으로 깨짐)

`for k in range(0x864, region_hi)` 로 한 번에 지웠더니 **사이의 0x938~0x973 포인터 테이블이
통째로 0이 됐다**(0x80014xxx 를 가리키는 표). 두 범위를 **따로** 지워야 한다.

### 곁가지 발견 — OPEN1.EXE 안에 ED2 오프닝이 있다

포인터 191개를 전수 분류하니 우리 슬롯 63 · **JP 잔존 128개(2,808B)** 였다. 정체는
**ED2 오프닝 내레이션 100줄**이다(`伝説の英雄達セリオス、リュナン、ゲイル、ソニア` …
`セリオスはディーナ姫と結婚し、ファーレーンの王となった。`). 포인터 테이블에서도
0x14528~~0x1476C(우리 ED1 50줄)과 0x14780~~(ED2 블록)로 **깨끗이 갈린다.**

→ ED1 오프닝에는 일본어가 안 나온다(유저 확인 완료). **ED2 트랙의 번역 대상**이지
회수 가능한 빈 공간이 아니다. 정발 ED2 오프닝 문안은 `originals/kr/dos-ed2` 에서 찾으면 된다.

## 2026-08-02(2): 정발 전문 이식 — 블록 구조 · 반각화

축약했던 정발 문장을 되살리려다 **두 개의 숨은 제약**을 찾았다.

### 제약 1 — 50줄은 균일 간격이 아니다 (블록)

스크립트(0x145A0)는 줄 넘김 커맨드 `0x80026DEC` 를 **3개 연속** 놓아 빈 줄(문단 간격)을
만들고, 장면 전환 때는 다른 커맨드를 무더기로 넣는다. 그래서 50줄이 **11개 블록**으로
갈린다 — `[2,5,6,6,4,2,11,1,3,9,1]`.

**문장이 블록을 걸치면 화면에서 문장 한가운데에 큰 여백이 생긴다**(유저 지적: "생활하는
사람들이 살고 ⟨여백⟩ 있다는 것뿐이었다"). 그래서 배치는 블록 단위여야 하고, 한 줄은
반드시 한 문장에서만 나와야 한다(두 문장을 한 줄에 이으면 원문 슬라이스가 문장 경계를
넘어 사이의 제어 바이트를 문다).

블록 구조는 `gen_opening_textmap.script_blocks()` 가 **원본에서 직접 읽는다**(스크립트는
우리가 안 건드리므로 원본이 정본).

### 제약 2 — 블록 7이 1줄이다

그 자리에 오는 정발 문장 `이때,후계자인 세리오스 왕자는 겨우 6살.` 이 23슬롯 = 69유닛
이라 필드(64유닛)를 넘겼다. **전문 이식이 여기서 막혔다.**

### 해법 — 반각화, 그런데 트램폴린 없이

처음엔 1바이트 인코딩(=바이트 절약)을 파려 했는데 방향이 틀렸다. **막고 있던 건 바이트가
아니라 표시 폭**이었다(바이트는 716/753슬롯으로 여유가 있었다).

렌더러에는 **이미 비례폭이 있다**:

```
advance 2 : 0x8140(전각공백) 0x8286 0x8289 0x828A 0x828C  (ｆｉｊｌ — 좁은 라틴)
advance 3 : 0x8281~0x829A (ａ~ｚ)
advance 4 : 그 외 전각   ← 우리가 3으로 패치한 것
```

이 다섯 상수는 폭측정(0x800132E0~)·표시(0x80013704~)에 `ori` 즉치값으로 박혀 있다.
**그 즉치값을 우리 공백·온점·쉼표의 슬롯 SJIS 로 바꿔치면 코드 한 줄 안 늘리고 반각이
된다.** 트램폴린·자유 RAM·1바이트 분기 전부 불필요.

```
' ' → 0x889F   '.' → 0x88A1   ',' → 0x88A0     (남는 두 자리는 공백 코드로 채움)
```

- ⚠ **폭측정·표시 양쪽을 반드시 같이** 바꾼다. 한쪽만 바꾸면 측정≠표시라 중앙정렬이
  밀려 글자가 화면 밖으로 잘린다(advance 4→3 때 겪은 함정과 같다).
- ⚠ 자리가 **다섯 개뿐**이다. 더 필요하면 비교 체인을 새로 짜야 한다.

결과: `이때,후계자인 세리오스 왕자는 겨우 6살.` 63유닛 → 블록 7에 들어간다.
`생활하는 사람들이 살고 있다는 것뿐이었다.` 64유닛 → 한 줄.

### 그 밖에

- **1바이트 인코딩은 여전히 불가** — 표시 루프(0x800136CC)가 무조건 2바이트를 읽고,
  `0x8001xxxx`(텍스트 허용 대역, 파일 0x800~0x10800)에 코드 넣을 24B 이상 빈틈이 **0개**다.
  필요해지면 자유 RAM 트램폴린을 짜야 한다. 폭측정 쪽은 `0x80013310 beqz` 한 줄이면 된다.
- **재배치도 불가** — 스크립트가 포인터 값의 주소 대역으로 text/command 를 가른다.
  대사(SCN) 트랙과 달리 오프닝은 첫 64KB 안에 묶여 있다.
- **따옴표 제거** — `'이셀하사' 라고` 는 정발 표기지만 오프닝은 모든 글자가 전각 슬롯이라
  따옴표 한 짝이 두 칸을 먹어 여백이 뜬다(유저 인게임 확인). `이셀하사라고` 로.
- **블록 배치 알고리즘** — 문장별 최소 줄 수를 구해 블록에 담고, 남는 줄은 가장 빡빡한
  문장에 준다(여백 제곱합 최소화 DP). 그래도 남으면 블록 끝을 빈 줄로 채운다.
- ⚠ **FIX 구절은 자동으로 분리 금지 등록**한다. 구절 중간에서 줄이 갈리면 그 줄의 원문
  슬라이스에 패턴이 반쪽만 들어가 fix 가 안 걸리고 파생이 어긋난다(`왕위 계승` 실측).
- ⚠ CP949 오프셋은 **바이트로** 센다 — 한글 2B·공백/숫자/부호 1B 라 문자 인덱스×2 로
  잡으면 어긋나 파생이 euc-kr 디코드에서 죽는다.

### 방침 전환 — 정발 따라가기(A) → 원본 형식 + 정발 어투(B)

정발 26문장을 PS1 구조에 우겨넣는 A안을 끝까지 밀어봤고, **되돌렸다.** 경위를 남긴다.

#### A안이 실패한 이유

PS1 스크립트의 **50줄·11블록·장면 전환 위치는 JP 문장 길이에 맞춰 설계된 것**이다.
정발 문장은 길이도 문단 경계도 달라서, 넣으려면 구조를 비틀어야 했다.

- 정발에 없는 **PS1 전용 연출 103슬롯을 버려야** 했다(다섯 나라 나열·바다 묘사·태양 비유).
- 그러고도 블록 7(1줄)에 안 들어가 **반각화가 필수**가 됐다.
- 문단 경계가 정발과 어긋나 **스크립트 배열을 다시 써야** 했고, 그 과정에서 세 번 깨졌다.

**정발도 온전히 못 살리고 PS1 연출도 잃는 자리**였다. 유저 판단으로 B로 전환.

#### B안 — PS1 50줄을 저본으로

줄 구조·문단·장면 전환은 **손대지 않는다.** 각 줄을 정발 어투로 채우되, 정발 문안이 그 줄에
맞으면 그대로 쓴다(`tools/set_opening_lines.py`). 결과: **정발 포인터 24줄 · 우리 문안 26줄.**

- 목표 문자열이 `OPENING.EXE` 에 그대로 있으면 **자동으로 (오프셋,길이) 포인터**가 된다 —
  문안이 리포에 안 남는다. 표기 교정만 `fix` 로 병기(정발은 `아스엘왕` 처럼 붙여 쓴다).
- 정발이 4문장으로 쓰는 대목(몬스터 습격)은 PS1 줄이 셋뿐이라 **정발 어투로 압축**했다
  (기습·성문 이상·병사 혼란 세 beat 유지, 마지막 줄은 정발 원문 그대로).
- 쉼표 뒤 공백을 **복원**했다 — 쉼표가 전각 슬롯이라 여백이 과대했던 게 이유였는데
  반각화로 근거가 사라졌다.

#### A안에서 건진 것 (전부 유지)

- **CD 오류문 자리 204B 회수** · **반각 렌더** · **first-fit 패킹** → 여유 4B → **136B**
- 폭 여유가 생겨 축약했던 문안을 복원하고 정발 문안(`이렇다 할 특산물도`,
  `예기치 않은 사건이`, `것뿐이었다`)을 넣을 수 있었다.

#### 스크립트 배열은 다시 쓸 수 있다 (조사 완료, 미사용)

`0x145A0~0x147B8` 은 32비트 포인터 **135워드**(텍스트 50 · `DEC` 68 · 그 밖 17)의 평평한
배열이고 `DEC` 는 인자가 없다. **총 워드 수만 지키면 슬롯 배치가 자유**라 문단 간격을 옮길 수
있다. 다만 B안에선 쓸 일이 없다. 나중에 필요하면 아래 함정을 기억할 것 — 전부 실측이다:

1. **커맨드를 앞으로 몰면 안 된다.** 원본은 `DEC×3 → 배경로드 dc4 → DEC×4` 로 섞여 있다.
   모아 놓으니 배경 전환이 **네 줄 일찍** 터졌다. 장면 나열은 순서까지 통째로 보존한다.
2. **`DD0`·`DC8` 도 줄을 넘긴다.** 원본에서 그 줄들엔 DEC 가 없다.
3. **장면 나열은 셋이다**(초기 배경 · 배경 교체 dc8 · 화면 전환). 둘로 세다가 dc8 이 전환
   자리로 끌려갔다.
4. **자기 출력을 다시 읽으면 비멱등**이다 — 스크립트는 원본에서 읽어야 한다.
5. 검증은 **원본과 워드 나열을 나란히 덤프해 대조**하는 게 제일 빠르다.

## 동적 조사 훅

> 원 제목: 동적 조사 훅 (은/는·이/가·을/를) — 트랙 devlog

> **이 문서는 조사 훅 조사·구현의 시간순 일지다.** "지금 무엇을 어떻게 쓰나"는
> **`text-pipeline.md`**(대사 텍스트 처리 장치 레퍼런스) 5절에 정리돼 있다.

전투 메시지의 런타임 `%s` 치환 자리 조사 병기("세리오스은(는)")를 정확 조사로 바꾸는 ASM 훅.
HANDOFF 항목 5의 실행 트랙. 정적 조립엔 `shared/text/josa.py`(완성) — 여기는 런타임 쪽.

### 조사 결과 (2026-07-19, 정적 분석)

- **0x800CC680 = BIOS A(0x15) strcat 썽크** (게임 함수 아님). 옆에 나란히:
  0x800CC690=A(0x17) strcmp · 0x800CC6A0=A(0x18) strncmp · **0x800CC6B0=A(0x19) strcpy**
  (아이템 초기화가 쓰는 그 strcpy) · 0x800CC6C0=A(0x1A) strncpy · 0x800CC6D0=A(0x1B) strlen.
  전형적 `li $t2,0xA0; jr $t2; li $t1,N` 패턴.
- **병기 실측** (battle 499 + items_battle 82 파생 테이블): 은(는) 134 · 을(를) 21 · 이(가) 5 =
  총 160곳. 이 중 **문자열 선두 128곳**(strcat 조각 — "은(는) 도망쳤다" 류),
  **중간 31곳**("%c%s%c을(를) 입수했습니다" — 포맷 문자열 안 %s 뒤).
- 결론: strcat 훅만으론 중간 31곳을 못 잡음 → **렌더 직전 최종 버퍼 스캔-재작성 훅**이 정답.
  한 훅으로 두 조성 경로(strcat 체인 + %s 포맷터) 모두 커버, 데이터 무변경, 멱등(재스캔 무해),
  대사·시스템에 병기가 생겨도 자동 처리.

### 설계

1. **종성 비트테이블**: 완성형 2,350음절 순서(hangul_map 슬롯 배치 순) → 받침 유무 1bit,
   294B. 생성은 `shared/text/josa.batchim()` 재사용. 배치: ED.EXE 빈 영역(주의 —
   0x15CE0~0x16CC0은 오프닝 폰트가 사용 중. 다른 제로런 필요, 빌드 후 이미지에서 스캔).
2. **훅 루틴**(대략 40~60 instr): 렌더러 진입 시 문자열 버퍼를 1패스 스캔 —
   `[음절 2B][은/이/을 2B][( ][는/가/를 2B][) ]` 패턴(괄호는 전각 0x81 0x69/0x6A)을 찾아
   앞 음절 SJIS→음절 인덱스 역산(hangul_map 슬롯 산식의 역함수) → 비트테이블 조회 →
   받침이면 앞 조사, 없으면 뒤 조사 채택. 나머지 6B(2글자+괄호)는 memmove로 당김(널 종단 유지).
   앞 글자가 한글 슬롯 밖(라틴·숫자 등)이면 병기 유지(현행 폴백과 동일).
3. **훅 지점**: 전투/대사 공용 텍스트 렌더러 진입점 — **미규명, 라이브 필요**.
   찾는 법: emucap(mednafen)으로 전투 진입 세이브스테이트 → RAM에서 조립된 메시지 버퍼를
   find_pattern → 그 주소 read watch → 렌더러의 fetch 루프/진입점 특정.
4. **통합**: `tools/patch_josa_hook.py` — 비트테이블 생성·루틴 어셈블(파이썬 수조립)·
   썽크/렌더러 패치, build.py 체인 마지막 단계. 검증: 세이브스테이트 회귀(횃불 사용 메시지 =
   "세리오스는 횃불을 사용했다" 기대) + 병기 없는 메시지 바이트 불변 확인.

### 라이브 2차 (2026-07-20) — 훅 지점 특정 도구 한계에 막힘

emucap+mednafen 도구 조합 실측:

- **read/write watch 미작동**(cpu·ram, read·write 전부). pause_on_hit여도 안 멈춤 —
  대기루프 PC만 반환. **execute BP는 정상**(reason:breakpoint, interrupted 확인).
- **렌더러 컨텍스트 분리 확정**: 오프닝 렌더러 0x8001BE24에 execute BP → 도망 메시지
  표시돼도 **미히트**. 전투/대사는 오프닝과 다른 렌더러를 쓴다.
- **조립 버퍼 0x800011B0은 ED.EXE 코드가 직접 참조 안 함**(iter_lui 0건) — 전투 로직이
  전투 오버레이(별도 로드 코드)에 있을 강한 정황. 병기 문자열(은(는) 도망쳤다=0x80014856
  등 123개)은 각 이벤트 코드가 직접 렌더 큐에 넣음(참조 157곳 분산) → 공용 조립함수 없음.
- **렌더러는 1회성**: 메시지 표시 후 매 프레임 재렌더 안 함(버퍼 read 미발생). VRAM에
  한 번 그리고 유지 → 훅은 "조립 완료 후 최초 표시 직전" 1회.
- **trace(set_trace)는 PC-only**(실효주소 없음) + vsync 대기루프(0x800C1E00~0x800C1E9C)가
  프레임당 수천회 돌아 실질 로직을 덮음 → 조립·렌더 순간 포착 실패.

### 라이브 3차 (2026-07-20, DuckStation) — 조립본 구조 규명

DuckStation CPU Debugger(Debug 메뉴, macOS 네이티브)로 전환 — memory search 정상 동작.
mednafen과 달리 실기 디버깅 가능. "무찔렀다"(8D4A91EF8C558AD7) 검색으로 6곳 분류:

- **코퍼스 원본**(RAM 로드된 배틀 텍스트): 0x14A00 `%s을(를) 무찔렀다`(25 63 90 B9 28 8C A4
  29 20 …), 0x17BC0대 `%c%s%c…` 헤더형. %s(25 63)에 이름 치환.
- **조립본**(이름 채워진 완성형): **0x1190B0**(워크램), **0x1FFD90**(스택). 형태:
  `02 [이름 슬라임=8F5C8BF190D1] 01 [을=90B9] 28 [를=8CA4] 29 20 [무찔렀다] 2E`
  → **이름과 조사 사이에 01 제어코드**(추정: 02=이름색 시작 마커, 01=이름 끝/색복귀).
  괄호는 반각(28/29) — patch_items.enc 확인과 일치.

#### 훅 루틴 수정 필요 (중대)

기존 patch_josa_hook 패턴은 `[음절][조사A][(][조사B][)]` — 실제는 **`[음절][01][조사A][(][조사B][)]`**.
스캔 시 조사 후보 앞의 01(및 02 마커)을 건너뛰고 **직전 실제 음절**을 봐야 한다.
prev 추적에서 01/02(제어코드)는 prev 갱신하지 않고 skip. fix_buffer/asm 양쪽 반영 필요.

#### 다음: 조립 루틴 PC

0x801190B0(실제 조립본)에 write BP → 재조립 시 조립 루틴 PC 확보 → return 직전이 훅 지점.
조립본이 2곳(워크램+스택)이라, 어느 쪽이 렌더 소스인지도 확인(스택은 임시일 가능성).

### 조립 함수 규명 (2026-07-20, DuckStation write BP + mednafen 정적/execute)

**write BP는 DuckStation에서 정상 작동**(mednafen만 미작동). 0x801190B0 write BP → 조립 순간
히트 → Step Out → **호출자 ra=0x800B1EB4**. 그 함수(**0x800B1E58~0x800B1E54**) 정적 분석:

- 프롤로그: `sw a0, 0x28(fp)`(a0=렌더할 문자열 포인터), `jal 0x800CC6D0`(BIOS strlen)→0x16(fp).
- `0x800B1EAC: jal 0x800CC700`(a0=0x1190B0+idx*64, a1=0, a2=0x40) = **memset**(워크슬롯 클리어).
  → 우리 write BP는 이 memset 첫 바이트에서 걸린 것(다음 메시지 준비). \**0x1190B0 = 0x80120000
  − 0x6F50, idx*64 stride 워크버퍼.**
- `0x800B1EB4~`: fp+0x28 문자열을 문자별로 읽어(`lbu`, 0xA=개행 체크) 워크슬롯에 조립하며
  렌더하는 **복합 루프**(0x800B1EB4~0x800B2050, 각 문자 0x800B1EBC 재진입). 조립·렌더 혼재.

**미해결 — 훅 지점 정밀화**: 이 함수는 **모든 전투 텍스트에 공용**이고 조립·렌더가 한 루프에
섞여 있어, "병기 메시지 조립 완료 직후" 한 줄을 아직 못 집었다. mednafen execute BP로 함수
진입은 잡히나(execute 정상), a0가 스크래치/빈인 진입도 많아 병기 메시지만 필터링 필요.

### 조립 함수 정적 분석 (2026-07-20) + mednafen 불안정

mednafen이 이 세션에서 execute BP/step 부하로 **반복 크래시**(연결 끊김 3회) → 자율 라이브
분석 불가. DuckStation은 안정적이고 write BP도 작동하나 GUI 수동. 에뮬 없이 정적 분석으로 전환.

**함수 0x800B1E58 (712B, ~0x800B2120 jr ra) 흐름**:

- 프롤로그: `sw a0,0x28(fp)`(입력 문자열) → `jal 0x800CC6D0`(strlen) → `jal 0x800CC700`
  (memset 워크 0x1190B0+idx*64, 64B 클리어).
- **루프A 0x800B1EB4~0x800B2050**: 입력(fp+0x28) 문자별 `lbu`(0x800B1EEC), 처리
  `jal 0x800ACC5C`(문자→폰트?), **`sb`(0x800B2020) 워크에 쓰기**(조립), `jal 0x800B2128`
  (0x800B1F8C, 글리프 렌더 추정). 0xA(개행)에서 `j 0x800B2054`.
- **루프B 0x800B2054~0x800B2118**: 유사 구조, `jal 0x800ACC5C`·`jal 0x800B2128`.
- 서브함수: **0x800ACC5C**(문자 변환/폭?), **0x800B2128**(글리프→GPU 렌더 추정).

#### 미해결 핵심 질문 (라이브 1회로 판별 가능)

조립(sb→워크)과 렌더(jal 0x800B2128)가 **문자별로 섞였나, 통짜 조립 후 렌더인가**:

- **통짜면**(DuckStation에서 0x1190B0에 완성 조립본 "02슬라임01을(를)…" 관측된 것이 근거)
  → 조립 완료 지점(루프 후 or memset 다음)에 우리 스캔 훅 삽입 가능. **훅 후보: 0x800B2054**.
- **문자별이면** → 버퍼 통짜 스캔 불가. 대안: 0x800B2128(글리프 렌더) 진입 시 직전 렌더
  글자를 추적해 병기 조사 결정(렌더러 상태 기반, 더 복잡).

DuckStation 관측(0x1190B0 통짜 조립본)은 **통짜 가설**을 지지 → 0x800B2054 훅이 유력.

#### 다음 세션 재개 (DuckStation 권장 — 안정적)

1. DuckStation execute BP 0x800B2054 → 병기 메시지(무찔렀다) 유발 → 그 시점 0x1190B0+idx*64

3. patch_josa_hook: 훅 stub(0x800B2054 → josa 루틴, 워크 스캔, 원명령 복귀) + 01/02 제어코드

### 훅 구현·통합 + 인게임 크래시로 보류 (2026-07-20)

훅 지점 확정(0x800B2054) 후 완전 구현:

- **josa_fix asm**(892B): 제어코드 01/02 skip(조립본 02[이름]01[조사]) + 스캔 상한 128B(무한
  루프 방지). MIPS 미니 인터프리터로 조사 정확 선택 + 널없는 버퍼 상한 종료 검증 PASS.
- **훅 stub**: 0x800B2054를 `j stub`으로 교체, stub이 워크(0x801190B0) → josa_fix →
  원명령(lh v0,0x16(fp)) → `j 0x800B2058` 복귀. 배치 0x801059A0(ED.EXE 0런, 참조 회피).
- build.py 통합(patch_josa_hook.main = 최종 디스크 ED.EXE 제자리 패치, write_user_data).

**인게임 결과: 크래시.**

- 1차: PC=0x000000A0(BIOS 예외벡터), a0=0xF0000010 → 워크주소 `idx*66` 동적계산 폭주
  (진입 시 gp+0x440 미세팅 추정). **→ 워크 0x801190B0 고정으로 수정.**
- 2차: 워크 고정 + 스캔 상한 후에도 **여전히 크래시**(PC 미확인). stub 진입 자체 or
  훅 지점 다중진입(0x800B1ED4 `j 0x800b2054` 재진입 타겟이기도 함) 부작용 의심.
- **결정: 병기(은(는)) 유지로 롤백**(build.py에서 훅 호출 주석 처리). 투자 대비 리스크 과다.

#### 재개 시 (크래시 원인 좁히기)

1. **no-op stub 먼저**: stub을 josa_fix 호출 없이 원명령+복귀만(`lh v0,0x16(fp); j 0x800B2058`)
   으로 만들어 훅 지점 자체가 안전한지 확인. 크래시나면 훅 지점/재진입이 문제, 정상이면 josa_fix가 문제.
2. 0x800B2054가 **루프 재진입 타겟**(0x800B1ED4 j 0x800b2054)임에 유의 — 우리 j-훅이 그 경로도
   가로챈다. 두 진입 경로(정상 + 재진입)에서 stub이 안전한지, 특히 delay slot 처리 확인.
3. DuckStation execute BP를 stub_addr(0x80105E42)에 걸어 stub 진입 시 레지스터/워크 내용 직접 관찰.
4. 대안: 훅 지점을 0x800B2054(재진입 타겟) 대신, 렌더 루프가 워크를 처음 읽는 지점(단일 진입)으로.

**병기 유지가 현 상태.** 훅 코드·유틸·조립함수 규명은 전부 보존 — 크래시 원인만 잡으면 재활성.

### 재도전 — 크래시 원인 규명 + 재설계 (2026-07-27, 인게임 검증 대기)

**크래시의 진짜 원인 = 배치 주소였다.** 구판이 코드·테이블을 실은 `0x801059A0`은 ED.EXE 파일에서
0런처럼 보였지만 **런타임 워크램**이다 — 07-26 도너 공간 작업의 3중 검증(필드·전투 세이브스테이트
RAM 덤프) 과정에서 이 구간에 `+0x3~+0x101A` 범위로 런타임 데이터가 기록되는 것이 실측됐다.
즉 스텁이 진입할 때쯤 우리 명령어가 이미 게임 데이터로 덮여 있었다. 훅 로직이 아니라 **부지 선정**이
문제였고, 그래서 "워크주소 고정 + 스캔 상한"으로도 2차 크래시가 재현됐던 것.

#### 재설계 내용 (patch_josa_hook.py)

1. **배치 = 도너 검증 통과 클린 0런 2개**(원본·현빌드 0 / 참조 0건 / 런타임 덤프 0 유지):
   - `0x0BF5DC~0x0BF7E8`(524B) → josa 루틴
   - `0x0C105C~0x0C1268`(524B) → 비트테이블 294B + 쌍 데이터 12B + 훅 스텁 96B
   - reinsert `DONOR_RUNS`에서 **주석으로 예약 제외**(대사 도너가 먹지 않게).
2. **루틴 압축 456B**: 클린 런이 최대 524B라 구판 3쌍 언롤(~860B)이 들어가지 않는다 →
   **데이터 구동 쌍 루프**로 재작성(쌍 데이터 `[A hi lo B hi lo]×3` 빅엔디언, t7=쌍 ptr·v1=남은 수).
   부수 압축: `0x01/0x02` 제어코드 스킵을 `sltiu t3,t2,3` 한 번으로, `lui+ori` 즉치를 `ori`로.
3. **워크 인덱스 동적 계산 제거**: `gp+0x440`(1차 크래시 원인 — 진입 시점 미세팅)을 쓰지 않고
   **워크 6줄(`0x801190B0 + k*66`)을 전부 스캔**한다. 훅은 줄 조립마다 재진입하고 치환은
   멱등(병기 패턴이 없으면 무동작)이라 다중 스캔이 안전하다.
4. **훅을 2워드로**: `0x800B2054 = j stub`, `+4 = nop`. 구판 1워드 훅은 다음 명령
   (`lw v1,0x28(fp)`)이 `j`의 지연 슬롯으로 선실행되고 복귀 후 또 실행됐다(load라 무해했지만
   계약이 불명확). 원명령 2개를 스텁 끝에서 재현하고 `0x800B205C`로 복귀.
   스텁은 `ra/s0/s1`을 sp에 저장·복원(16B 프레임), `a0`는 훅 지점에서 죽은 레지스터.
5. **가드 추가**: 훅 지점 원명령 2워드 일치 assert / 배치 영역 전 구간 0 assert / 런 크기 초과
   assert / 테이블 4바이트 정렬 패딩(`j` 인코딩이 하위 2비트를 버리므로 스텁 비정렬 금지).

#### 검증 현황

- ✅ 셀프테스트(`--selftest`): 테이블 294B + 쌍 12B + josa 456B + 스텁 96B, 두 런(각 524B) 안에
  들어간다. capstone 디코드 josa 114/114 · 스텁 24/24 명령.
- ⬜ **build.py 통합·인게임 검증 미실시** — 훅 호출은 여전히 주석, 기본 빌드는 **병기 유지**로 무변화.
- ⚠ **스테일 빌드 함정**: 현 `work/*.bin`(07-26 23:52)은 런 예약 **이전** 빌드라 두 구간에 대사
  도너 텍스트가 들어 있고(nonzero 513/498), `patch_josa_hook.py` main()이 0 assert로 정지한다.
  원본 ED.EXE는 두 구간 모두 nonzero 0 확인 → **재빌드하면 해소**. (assert가 제 일을 한 것.)

#### 재개 절차

1. `python3 tools/build.py`로 재빌드(예약 반영 = 두 런이 0으로 남는지 확인).
2. **no-op 스텁 A/B 먼저**: josa 호출 없이 원명령 2개 + 복귀만 하는 스텁으로 훅 지점 자체의
   안전성을 확인한다. ⚠ `0x800B2054`는 `0x800B1ED4`의 `j` 재진입 타겟이기도 해서 **두 진입
   경로 모두** 스텁을 지난다 — 이 A/B가 통과하면 훅 지점·지연 슬롯 처리는 무혐의.
3. josa 활성 후 전투에서 `슬라임을 무찔렀다`(받침 O) / 무받침 몬스터(`~를`) 양쪽 확인.
4. 실패 시 스텁 진입 BP(`stub_addr` = 데이터 런 + 306)로 레지스터·워크 내용 직접 관찰.

**QA 재판단 포인트는 유효**: 전투 `%s`가 세리오스 고정이면 `%s은(는)` → `세리오스는` 정적 치환이
훅보다 싸다. 훅의 값은 **몬스터명 조사**(가변 208종)에 있다.

### 메시지 박스 파이프라인 전모 + 훅 2(prewrap early-resolve) (2026-07-28)

capstone 정적 RE로 **개행이 어디서 결정되는지**를 끝까지 따라가 HANDOFF #2/#3(단어 중간
분할·불필요 개행)의 원인을 확정하고 훅 2를 구현했다. 라이브 확인은 필요 없었다.

#### 파이프라인 (호출 순서 = 데이터 흐름)

```
0x800B1D50  jal 0x800CC6B0  strcpy(fp+0x18, msg)   ← 호출자 스택 128B 사본(fp+0x18~0x98)
0x800B1D60  jal 0x800ACE18  prewrap(fp+0x18)       ← ★자동 개행 삽입기(글자단위·29열)
0x800B1D7C  jal 0x800B1E58  assemble(fp+0x18)      ← 0x0A로만 분할 → 워크슬롯(0x801190B0+k*66)
                                                     ↳ 훅 1(0x800B2054)이 여기 끝에서 병기 해결
0x800B1DF0  jal 0x800B2410  drawline(work+k*66, y) ← 줄마다 반복(k < gp+0x440)
0x800B245C   jal 0x800AD3A8 layout/draw            ← 그리면서 남은 초과분만 재차 개행
```

- **`0x800ACE18`(prewrap)이 개행의 주범**: strlen → 글자단위로 폭 누적(`0x800AE430`이 글자 폭
  반환), 29열(`s5`) 넘으면 끊을 인덱스를 `sp+0x10` 배열(최대 8개)에 기록 → 2패스에서 `sp+0x20`
  스크래치(0x80B)에 `0x0A`를 끼워 재조립 → **`strcpy`로 원 버퍼에 제자리 복귀**(0x800AD158).
  구두점·공백에 걸리면 끊기를 1~2글자 당기는 보정만 있고 **단어 인식은 없다**(=#2).
- **호출자는 단 하나**(전수 `jal` 스캔) — `0x800B1D60`.
- `0x800B1E58`은 **폭 개행을 하지 않는다** — `0x0A`만 보고 워크슬롯을 넘긴다(0x800B1EF4).
- ⚠ **이전 HANDOFF의 RE 오류 정정**: `0x800B245C`는 `0x800B1E58` *내부*가 아니라 별개 함수
  `0x800B2410`(0x800B240C에서 앞 함수 종료). 그리고 `0x800AD3A8`에 넘어가는 `a2`는 원문이
  아니라 **워크슬롯 줄**이다 — 즉 "a2에 미해결 병기가 있나"라는 라이브 확인 항목 자체가
  잘못된 질문이었다. 병기는 그보다 **한 단계 앞(prewrap)**에서 이미 폭을 부풀리고 있었다.

#### 원인 확정 (유저 재현과 산술이 일치)

훅 1은 assemble **뒤**라 개행이 이미 결정된 다음 병기를 줄인다. 그래서 폭 계산만 미해결
병기로 이뤄졌다 — `세리오스은(는) 횃불을(를) 사용했다` = 10+4+1+6+4+1+8 = **34열 > 29** →
28열에서 끊겨 "…사 / 용했다". 해결 후는 `세리오스는 횃불을 사용했다` = **28열 ≤ 29** → 무개행.
유저 재현 스크린샷의 끊김 위치와 정확히 맞는다.

#### 훅 2 구현 (patch_josa_hook.py)

- **`0x800B1D60`의 `jal` 타깃 1워드만** 우리 스텁으로 교체 → 스텁이 `josa_fix(a0, 128, guard)`
  후 `j 0x800ACE18` **꼬리호출**(ra 유지 → prewrap이 호출자에게 직접 복귀). 원명령 재현·지연
  슬롯 처리가 아예 필요 없어 훅 1보다 훨씬 단순하다(지연 슬롯은 원래 nop).
- **안전 근거**: 대상은 호출자 전용 스택 사본이고, 치환은 **항상 4B씩 짧아지므로** 오버플로가
  없다. prewrap·assemble 모두 자체적으로 `strlen`을 다시 재므로 길이 불일치도 생기지 않는다.
- **josa_fix 파라미터화**: `a1`=스캔 길이, `a2`=cross-line 후보 ptr. josa 런이 524B로 꽉 차
  사본을 둘 수 없어 한 루틴을 공유한다. cross 비활성은 분기 대신 **zero guard 주소**(상수 0
  4바이트)를 `a2`로 넘겨 푼다 — 명령 추가 0개(런 여유 8B 보존), 0은 `(`가 아니라 판정이
  자연히 실패한다.
- 훅 1·2는 **멱등**이라 중복 무해: 훅 2가 먼저 지우면 훅 1은 무동작이 된다.
- 크기: josa 516B(여유 8B) · 데이터 런 = 테이블 296 + guard 4 + 쌍 12 + 스텁1 104 +
  스텁2 52 = **468B(여유 56B)**.

#### 검증

- **MIPS 미니 인터프리터 셀프테스트 신설**(`--selftest`) — 파이썬 시뮬만 맞고 인코딩이 틀리면
  통과해버리던 구멍을 막는다. 어셈블된 **바이트를 실제로 실행**해 시뮬과 바이트 단위 비교:
  같은 줄 받침 O/X · 이름색 제어코드 · 영문 식별자 무받침 · cross-line · prewrap 평문 2치환 ·
  zero guard 비활성 · capstone 전량 디코드.
- 빌드 후 **디스크에서 다시 꺼낸 바이트**로 재실행해 배치·정렬까지 확인:
  `세리오스은(는) 횃불을(를) 사용했다` → `세리오스는 횃불을 사용했다`(34→26B),
  `슬라임을(를)무찔렀다` → `슬라임을무찔렀다`.
- ⚠ HANDOFF의 "capstone 미설치"는 **스테일** — 5.0.7 설치돼 있고 셀프테스트가 쓴다.
- ✅ **인게임 검증 완료**(유저, 07-28): 횃불·요슈아의 눈 도구사용 — **조사·개행 모두 정상**.
  회귀 시 `JOSA_NOPREWRAP=1`(훅 2만 제외) / `JOSA_NOOP=1`(훅 1 무력화)로 계층을 가른다.

#### 훅 2가 커버하지 않는 것 — 그리고 왜 문제되지 않는가

- **상점(도구점) 프롬프트는 이 체인(`0x800B1D40` 부모)을 안 탄다** — 유저 QA 07-27에 훅 1이
  `해독초은 (는)`을 못 잡은 것이 근거. 훅 2는 같은 체인의 **한 단계 앞**일 뿐이라 마찬가지.
  ⇒ 상점은 훅에 기대지 않고 **문안 자체를 조사가 필요 없게** 짰다(유저 설계):
  - **살 때**: 아이템명 뒤에 서술을 바로 붙인다 — `…이군요`.
  - **팔 때**: 조사를 **고정 명사 '값'**에 붙인다 — `… 값은 %d Gold가 되는데…`
    (`shop_price_build`. 받침 있는 '값'에 은 고정이라 아이템명과 무관).

  즉 **런타임 이름 뒤에 조사가 오지 않게 어순을 잡는 것**이 훅보다 싸고 확실한 해법이다.
  훅이 생겼다고 되돌리지 말 것.

- `0x800A9A60`(단문 직접 그리기, 호출자 ~45곳 = 메뉴·상태창 라벨)도 prewrap을 안 탄다.
  여기 병기가 생기면 위와 같은 문안 설계나 별도 대응이 필요하다(현재 발견된 건 없음).

## NPC 대사 바인딩

> 원 제목: NPC ↔ 대사 바인딩 역분석 devlog

**목적**: 정발 대사를 남김없이 자동 매핑하려면 "같은 NPC의 대사끼리 묶기"가 필요하다.
의미 유사도만으로는 한 맵 안의 동명이인(크루즈 마을 남자 2명·여자 2명)을 못 가른다 —
「어서 오십시오, 왕자님」이 여러 NPC에 걸쳐 존재하기 때문이다. 통계 신호를 네 번 바꿔 봤지만
정밀도가 83~88%에서 천장을 쳤다(경위는 `HANDOFF.md`). NPC 바인딩은 통계가 아니라 게임
데이터라 그 천장이 없다.

### 확정된 구조 (2026-07-30)

#### SCN 오버레이 좌표

```
file = RAM − 0x8016A000        (reinsert_kr_pilot.OVERLAY_RAM_BASE)
검증: 0x80186030 − 0x8016A000 = 0x1C030 = SCN_ARG_PATCHES[("ED1SCN1", 287)] 좌표
텍스트 영역 = 0 ~ text_end(SCN1은 0x13208), 그 뒤가 코드
```

#### 맵 세그먼트와 인스턴스

세그먼트 구조는 `[지명][대사 블록들][메시지 점프테이블]`의 반복이고 **점프테이블이 꼬리**다.
테이블 시작 = 다음 세그먼트 시작 − 테이블 크기가 **바이트까지 일치**한다.

- 지명 헤더는 바이트 검색으로 찾는다(`patch_sys_ui.patch_scn_headers`와 같은 판별).
- 점프테이블 위치가 **맵 인스턴스(방·구역)** 경계를 준다 — 지명보다 12배 세밀.
  루디아는 지명으론 440블록 한 덩어리인데 인스턴스로는 9개(각 ~36블록).
- 정발 테이블이 엔트리 10~~20개씩이라 인스턴스 하나가 테이블 1~~3개 = **거의 NPC 단위**.
- 구현: `tools/scn_maps.py` (`segments` / `instances` / `block_instances`).

#### 메시지 점프테이블

엘아스타(테이블 0x000B88, 117엔트리) 실측:

```
[0]  ----- -----  0x01369c 0x0136b4     ← msg 0·1 미사용, 2부터 핸들러
[16..116]  0x0139f8 × 87                ← 미사용 ID의 공용 no-op 핸들러
핸들러 간격 24B(6 MIPS 명령) = 인자 세팅 + jal sprintf + 공용 꼬리 점프
고유 핸들러 28개 = 이 맵의 실제 메시지 수
```

**메시지 ID → 블록**은 핸들러 24B 창 안의 `lui/addiu` 텍스트 참조를
`reinsert_kr_pilot.find_refs`로 뽑아 블록 경계와 대조하면 나온다. SCN1에서 **548건 확정**
(서로 다른 블록 400개, 한 블록에 ID 2개 이상 걸린 것 78개 = 같은 대사의 상황별 재사용).

⚠ 창을 200B로 잡으면 이웃 핸들러 참조까지 긁혀 블록이 7~8개로 뭉개진다. 24B로 좁힐 것.

#### 디스패처 (`msg_build`)

루디아#2 실측 — 이 관용구가 정본이다:

```
0x801810c8  addiu $sp,-0x538            ← 진입점
0x801810d4  sltiu $v0,$a0,0xe5          ← 경계 검사: 메시지 ID < 229
0x801810ec  beqz  $v0, <기본>
0x801810f4  sll   $v0,$a0,2             ← id*4
0x801810f8  lui   $at,0x8017
0x801810fc  addu  $at,$at,$v0
0x80181100  lw    $v0,-0x3050($at)      ← table[id]  (0x8016CFB0 = file 0x2FB0)
0x80181108  jr    $v0                   ← 핸들러로 점프
```

`lw rX,imm(base)` → (nop) → `jr rX` 관용구를 스캔하고 앞쪽 `lui`로 테이블 주소를 복원하면
**디스패처 53개**가 나온다(내 휴리스틱 런 탐색은 21개만 찾았다 — **디스패처가 정본**).
맵마다 주 디스패처(경계 109·209·229·306)와 보조 디스패처(경계 5·6·8·21·53)가 있다.

### ⛔ 여기서 막혔다 — NPC → 메시지 ID는 오버레이 밖

- 오버레이 안의 `jal <디스패처>` 호출부가 **7건뿐**이다. 즉 **엔진(ED.EXE)이 함수 포인터로
  디스패처를 부르고**, 메시지 ID는 엔진이 NPC 데이터를 보고 결정한다.
- ED1에는 **이벤트 데이터 파일이 없다**. 디스크 구성: `BIN/ED1SCN1~6.BIN` +
  `DATA/ED1{BGD,CEL,CHR,MON,PARTS,SE,TIM}.DAT`. (ED2는 `ED2EVT.DAT` 296,960B가 별도로 있다.)
  ⇒ ED1의 NPC 배치는 `ED1BGD.DAT` 안이나 `ED.EXE`에 묻혀 있을 가능성이 크다.
- **정적 경로는 소진됐다.** 오버레이 안에서 즉치를 긁어 NPC→ID를 얻을 수는 없다.

### ▶ 다음 절차 — 라이브 조사 한 번이면 이후는 정적

구조를 한 번 찾으면 그 뒤 전 맵 추출은 정적·자동이다.

1. **emucap 재연결** 후 게임 기동 → 메모리카드 세이브 로드(이미 맵 안이다).
   절차는 `HANDOFF.md` "메모리카드 로드 워크플로" 참조(9세이브, 슬롯1).
2. **디스패처 진입점에 BP** — 예: SCN1 루디아#2는 RAM `0x801810c8`. NPC에게 말을 걸면
   `$a0` = 그 NPC가 요청한 **메시지 ID**다. 몇 명만 찍어도 대응이 보인다.
3. BP 시점의 **호출 스택/`$ra`** 로 엔진 쪽 호출자를 얻고, 그 함수가 읽는 **NPC 구조체**를
   찾는다(`$s0`/`$a2` 등에 실린 포인터). 워크램에서 그 배열을 덤프해 stride·필드 배치 확정.
4. 배열을 채우는 소스를 역추적 — 맵 로드 루틴이 어느 파일/오프셋에서 읽는지.
5. 그 뒤로는 전 맵 정적 파싱 → NPC → {메시지 ID} → 블록 집합.

**기대 효과**: 정발 테이블이 이미 NPC 단위이므로 양쪽이 NPC 단위로 만나면 동명이인이
원리적으로 사라지고, 한 NPC의 3~~5줄 대 정발 엔트리 3~~5개의 소규모 배정만 남는다.
앵커 노이즈에 의존하지 않는 유일한 길이다.

⛔ **버전 간 NPC 좌표 대조는 안 된다** — PS1은 리메이크라 맵 레이아웃이 다르다.
정발 DOS `MAP/`에도 위치 데이터가 있지만 대조 대상이 못 된다.

### 진행 중 틀렸던 추정 (반복 방지)

- "맵 제약만으로 동명이인이 상당히 풀린다" → 아니다. 83% 천장이 그 답이었다.
- "인스턴스 제약으로 97.7%" → **잘못된 측정**. 홀드아웃 블록을 학습에서 빼서 마스크가 우연히
  촘촘해진 것이었다. 실제 도구로는 88.2%.
- "NPC 바인딩은 반나절" → 점프테이블까지는 순조로웠지만 그 다음 고리가 오버레이 밖에 있다.
- 순서(단조성) 제약은 **역효과**다 — 테이블 내 단조도가 71.6%뿐이라(리메이크가 대사 순서를
  재배치) 가산점이 맞는 매칭을 밀어낸다.

#### ⭐⭐⭐ 최종 해법 — 버튼 원본 유지, 내부 텍스트만 교체 (2026-07-15, 유저 아이디어)

버튼을 **다시 그리는 접근을 모두 폐기**. 이전의 절차적 드로잉/인페인트/윈도우채움은
전부 위치·크기·테두리·배경 문제를 반복 유발. 근본 해결:

- **원본 버튼(프레임·베벨·선택/비선택 상태색·크기·위치)을 100% 그대로 둔다.** 렌더 함수는
  각 버튼 **내부(프레임 안쪽) rect만** 손댄다 → 지오메트리를 안 건드리므로 이동·크기변화·
  테두리 위화감이 원천적으로 불가능하고 "원본 느낌"이 그대로 유지됨.
- **내부 일본어 텍스트만** 행별 배경색으로 덮고(일본어 가림) 그 위에 한글을 얹는다.
  배경색 = 그 행의 밝은 픽셀(상위 ~32%) 평균 → **알약 금색 세로 그라디언트·박스 상태별
  밝기(선택 흰/비선택 맵투과)가 자동 보존**된다. (`overwrite_text()`)
- rect 좌표 = 원본 각 버튼 **일본어 텍스트 bbox 실측**(PILL_TEXT/COLL_TEXT). 좁으면 첫 글자
  좌측이 남으니(유저 QA) bbox+1px로. 알약은 세로를 텍스트 행 안에 둬 둥근 캡·아웃라인 보존.
- **컬렉션은 로마숫자 Ⅰ/Ⅱ(x403+)를 원본 유지**하고 英雄伝説(4자, x324-401)만 "영웅전설"로
  덮는다(유저: 내가 그린 Ⅱ가 어색 + 원본 Ⅰ/Ⅱ의 초록 엠보싱 살림). 패치 폭도 4자만이라 좁다.
- 글자 크기는 overwrite_text(wfrac,hfrac)로 조절 — 박스 hfrac 0.58, 알약 hfrac 0.48(더 작게,
  둥근 알약 안 여백 확보). 버튼 뚫지 않게(유저 QA).
- emucap 검증: 박스·알약 모두 프레임 불변(상태 간 diff는 내부만), 원본 베벨/맵투과/금색 유지.

#### ⭐⭐⭐ emucap 캘리브레이션 확정 (2026-07-16) — 컬렉션 버튼 blit 규명

유저 QA: 커서 이동 시 폰트 위치·크기가 셀마다 달라 보임. 요구 = 버튼/폰트 크기·위치 고정,
**배경 밝기만** 선택=밝음/비선택=짙음. emucap로 직접 규명(캘리브레이션 = 각 셀에 고유색+
가로 눈금선 심어 디스크 write 후 화면 실측, `_calib_title.py` 임시):

- **엔진은 각 셀을 1:1(스케일 없음)로 화면 고정 슬롯에 blit한다** — TIM 눈금 10px가 화면
  10px로 나옴(scale=1.00). 즉 **화면 폰트 크기·위치 = TIM 폰트 크기·위치 그대로**.

### 2. ⚠ 소프트락 — 게이트가 한쪽만 보고 있었다

유저가 **진행 불가**(대사가 안 넘어감 + 쓰레기 글자)를 보고했다. 원인:

`build_block` 의 구조 계약 게이트 둘이 오래도록 **`<`(원본보다 적을 때)만** 검사했다 —
`window_deficit`(`%c`)·`fmt_drop`(`%s`/`%d`). **넘치는 건 안 봤다.**

`jp245` 는 원본 `%s` 가 0개인데 정발의 `\x09`(이름 주입)가 `%s` 를 만들어 1개가 됐다. 원본은
그 자리에 **리터럴 인라인 헤더**(`%c<이름>%c`)를 쓴다. 엔진이 **없는 인자를 소비**하며 인자열이
통째로 밀려 쓰레기 글자가 뜨고 흐름이 멈췄다.

대칭 게이트 `fmt_excess` 를 넣으니 **전 씬 14블록**이 걸렸다 — 전부 같은 지뢰:
`SCN1 245·548·699·701 / SCN2 402·521·614·617·622 / SCN3 247 / SCN4 568 / SCN5 1117·1149 /
SCN6 54·124`.

| 장치                    | 용도                                                                                                                                          |
| ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `subs: [["\\x09", ""]]` | 정발 이름 주입이 원본의 **리터럴** 헤더 자리에 올 때 **제거**. 이름은 템플릿의 인라인 헤더가 채운다 — 리터럴로 *치환*하면 이름이 두 번 나온다 |
| `speaker`               | `\x09` 를 지우면 화자 해석이 실패하므로 명시                                                                                                  |
| `nl_after`              | 원본이 인라인 이름 창 **앞**에 두는 개행 복원                                                                                                 |

결과 `%c`=5·`%s`=0 으로 원본과 정확히 일치. 나머지 13블록도 같은 조합으로 살릴 수 있을 것이다.

⚠ `nl_after` 의 창 인덱스는 **눈으로 세면 안 된다**(템플릿 토큰 기준이라 어긋난다).
`build_from_template` 를 직접 호출해 인덱스를 훑어 찾는다.

사령관 이벤트를 낀 구간 전체를 스크린샷으로 훑었다. 개별 오타보다 **장치가 없어서 못 고치던

#### 7-1. `subs` 는 페이지를 만들지 못한다 → `pre_subs`

치환은 **슬라이스 뒤에** 돈다. 그래서 `subs` 로 `{p}` 를 넣어 페이지를 쪼개려 하면 이미 늦었고,
`#1` 이 빈 문자열이 돼 `본문 없음` 으로 조용히 탈락한다. 슬라이스 **전에** 도는 `pre_subs` 를
새로 팠다(13건). ⚠ 경고는 찍히고 있었는데 내가 grep 을 안 했다 — 침묵이 아니라 내가 안 본 것.

#### 7-2. 인라인 이름 헤더 — 지울 것이냐 채울 것이냐

정발은 이름을 `\x09`(이름 주입)로 넣는데 PS1 은 블록에 따라 둘로 갈린다. **반대로 하면 이름이
두 번 나오거나 아예 빠진다.**

- **템플릿이 이미 이름 창을 채우는 블록**(`jp245`) → `\x09` 를 **지운다**. 안 지우면 중복.
- **이름이 본문 텍스트인 블록**(`jp548`) → `\x09` 를 **이름으로 치환**한다.
- ⚠ 이때 뒤따르는 `\x03` 까지 **같이** 소비해야 한다. 남기면 그 자리가 공백으로 렌더돼
  조사가 떨어진다(`게일 이라고` → `게일이라고`).

#### 7-3. 게일 동료 문구가 일본어였던 이유 — 이스케이프 오타

`ED1SCN1.559` 의 `subs` 가 `\x09\x02` 를 지우려 했는데 정발 `T_031` 의 실제 바이트는 `\x09\x03`
이었다. 매칭이 조용히 실패 → `\x09` 잔존 → **창 수 계약 불일치(1≠2)로 템플릿 경로가 탈락** →
원본 일본어가 그대로 나갔다. 로우(`jp317`)와 동형으로 맞춰 회수.

**교훈: 오버라이드를 복붙할 때 제어 바이트는 표마다 다르다.** 치환이 안 먹으면 조용히 원문이
나가므로, `subs` 를 쓸 땐 대상 문자열이 실제로 존재하는지 먼저 확인한다.

#### 7-4. 강제 개행은 조판이 아니라 데이터로

`모두들, 크루즈 마을이 안전해.` 는 **14.5슬롯**이라 14슬롯 한계를 넘는다(정발은 온점이 없어
딱 14.0 이었다). 온점을 빼는 대신 `dos_break_fixes.json` 의 `line_overrides` 로 하드개행을
넣어 3줄로 잡았다 — `HARD_NL` 은 `protect_hard` 를 켜 문장 리플로우가 못 지운다.

#### 7-5. 인라인 이름 색상은 현재 불가

`#126`(본문 중간 이름에 주황). 정발에는 색 제어가 없고 우리 파이프라인에도 **강제 색상 장치가
없다**. 유저 판단으로 보류 — 장치를 만들면 같이 적용한다.

#### 7-6. 반각 부호 함정 (2건)

SJIS 반각(JIS X 0201) 은 ASCII 가 아니다. `~`(0x7E)는 `‾`(윗줄)로, `-` 도 일자 대시로 렌더된다.
`HALF_PUNCT` 에 넣기 전에 **실제 글리프를 확인**한다. 현재 안전 집합은 `.,!?()` 뿐.

#### 7-7. 사령관 이벤트 후 메뉴 불가 — **원판 버그**(우리 것 아님)

베르가 사령관을 쓰러뜨리고 게일이 합류한 뒤, 필드에서 `✕` 를 눌러도 메뉴가 안 열린다.
이동은 정상이라 "이벤트가 건 메뉴 잠금이 안 풀린" 모양새 — 재삽입이 이벤트 종료 경로를
끊었나 의심할 만하다. **차분 빌드 대신 JP 원판으로 같은 지점을 재현했더니 원판도 똑같이
막혔다**(2026-08-02, mednafen). 확인한 것:

- 화면 sha 완전 동일 → 입력이 아예 안 먹음. 방향키 이동·카메라 스크롤은 정상.
- 같은 맵 안에서는 12칸 이상 걸어 나가도 동일. `✕` 뿐 아니라 `△` 도 무반응.
- 이벤트 전에는 `✕` 로 메뉴가 열린다(양쪽 다) → 버튼 매핑 문제가 아니다.
- **맵을 넘어가면 풀린다** — 한 화면 아래 「베르가 광산남서」로 나가면 `✕` 정상(KR 확인).

즉 팔콤 PS1판 자체의 결함이고, **그 맵 한정 · 맵 로드가 잠금을 대신 푼다**. 진행 차단이
아니라 원판도 이대로 출시된 흠집이다.

**고치려다 접은 기록(유저 판단: 간단하면 고치고 복잡하면 넘어간다)** — 잠김 2표본 ×
풀림 3표본(같은 맵 1 + 다른 맵 2)으로 5중 RAM diff 를 걸었다. `L1==L2 && A==B==E &&
L1!=A` 조건이라 위치·HP·골드·파티구성·맵데이터가 전부 상쇄되는데도 후보가 **4,692B /
2,177구간**에서 안 줄었다. 플래그다운 단일바이트 33개 중 유력 후보(`0x80112E45`)를
직접 써 봐도 안 열렸고, 포인터형 후보는 전부 스택(`0x801FFxxx`)이었다.

⇒ **"메뉴 금지 플래그 한 개"가 아니다.** 차이가 넓게 퍼져 있고 맵 로드로만 풀린다는 건
**이벤트 스크립트 VM 이 그 이벤트를 아직 물고 있는 상태**(정상 종료를 못 하고 이동만
양보)에 가깝다. 맵 로드가 VM 을 초기화하니 그때 풀린다. 고치려면 SCN 옵코드 레벨에서
종료 경로를 손봐야 하고 실패 증상이 소프트락이라 위험 대비 이득이 나쁘다 — [mod] 트랙
과제로 미룬다. **다음에 붙는다면 데이터 플래그 탐색이 아니라 필드 상태머신부터.**

재현이 애매한 인게임 이상은 **차분 빌드보다 원판 대조가 먼저다** — 여기서는
`PILOT_TEXT_IDENTITY` 한 판(빌드 2분 + 재플레이)을 통째로 아꼈다.

### 10. 빌드가 머신을 타던 문제 (2026-08-04)

회사에서 만든 락이 집에서 **24건 위반**으로 빌드를 세웠다. 파생물을 전부 재생성해도
**똑같은 24건이 해시까지 동일하게** 재현됐다 — "묵어서"가 아니었다.

원인은 **원작의 완전 중복 블록**이다. 루디아 병사 여럿이 글자까지 같은 JP 대사를 하고
(`jp1116` ≡ `jp1261`), 정발도 같은 대사를 세 벌(`C_001#13`·`C_009#5`·`C_00E#5`) 조금씩 다르게
옮겨놨다. 동일 텍스트 → 동일 임베딩 → **정확한 동점** → 승자는 부동소수 잡음이 정한다.
점수 문턱으로 못 막고(양쪽 0.97/0.94) 재계산으로 복원도 안 된다. **대개 양쪽 다 옳다** —
오역이 아니라 **재현 불가**가 문제였다.

해결은 배정을 파생물에서 **소스로 올린 것**(`align_map.json` — 좌표·화자만, 문장 없음).
정렬 파일을 전부 지우고 빌드해 **바이트 동일**(sha1 일치)을 확인했다. 상세는
`our-findings.md` 와 게임 `CLAUDE.md`.

⚠ 이 과정에서 **내가 두 번 헛짚었다.** ① 머신을 옮기자마자 `--freeze` 를 눌러 회사 값을 덮을
뻔했다(diff 에서 출처 테이블이 갈린 걸 보고 되돌렸다). ② `align_map.py` 가 모듈 최상단에서
`LOCK_BYPASS` 를 걸어, `reinsert` 가 import 하는 것만으로 **빌드 전체의 락 검증이 꺼졌다** —
"빌드 통과"가 실은 검증을 안 한 것이었다. 우회는 `main()` 안에서만 건다.

- ~~"접미표는 stride 8B"~~ → 원본은 그렇지만 **빌드본은 촘촘히 재packing 된다**(`patch_items`).
  참조 immediate 를 같이 고치므로 동작은 맞는데, **원본 stride 로 오프셋을 계산하면 엉뚱한
  바이트를 읽게 된다.** 실제로 빌드본을 그 가정으로 덤프하다 "부근이 깨져야 하는데 멀쩡하네?"
  로 한참 헤맸다. ⚠ **패치된 이미지를 읽을 땐 그 표를 누가 다시 쓰는지부터 확인한다.**

⚠ **교훈: `our-findings` 의 항목도 가설이다.** 세 줄 다 "실측"이라 적혀 있었는데 셋 다 반증됐다.
근거가 되는 코드 위치(주소)가 안 적힌 항목은 특히 의심한다 — 이번에 고친 것들엔 전부 RAM
주소를 박아 뒀다.

**그리고 그 자리에서 나도 한 번 더 틀렸다.** "좌표가 정확히 일치하는 건 실내뿐"이라고 단정하고
`入口` 분기를 죽였는데, **월드맵에서 마을 타일에 올라선 것도 같은 분기**였다. 유저 스샷으로
바로 반증돼 되돌렸다. 좌표만 보는 루틴 안에서는 실내/실외가 원리적으로 안 갈린다 —
**갈라야 할 곳은 호출처**(6곳, 전부 `j 0x800856BC`)다. 그건 런타임 플래그를 알아야 하고
정적으로는 후보 둘(`0x80108B2C`·`0x80108AD5`)까지만 좁혔다.
⚠ **교훈: "이 분기는 A 상황에서만 걸린다"는 추론은 B 를 안 세어 본 것이다.** 분기를 죽이기 전에
그 분기에 도달하는 경로를 전부 나열한다.

### 실내 `입구` — 원본 대조가 세 번의 오판을 끊었다

유저가 **원본 디스크로 같은 자리를 찍어 보내주면서** 끝났다. 그전까지 내 판단은 이랬다.

1. ~~"실내에서도 `입구` 가 붙는 건 원판 사양"~~ → 유저 원본 스샷: 실내는 `クルスの村` 뿐. **버그였다.**
2. ~~"좌표가 정확히 일치하는 건 실내뿐이니 `入口` 분기를 죽이면 된다"~~ → 월드맵에서 마을 타일에
   올라선 것도 같은 분기. 죽였더니 거기까지 사라졌다. 되돌림.
3. ~~"반각 공백이 홀수를 만든다는 기록은 틀렸다"~~ → 월드맵에서 멀쩡하길래 반증 처리했는데,
   **실내 경로에서는 그 기록이 옳았다.** 되살렸다.

**진짜 원인.** 실내 HUD 는 SCN 헤더의 지명을 같은 버퍼에 덮어쓰면서 **종단을 2바이트 단위로**
본다. 반각 공백이 낀 홀수 길이 지명은 널이 홀수 자리라 종단을 놓치고 앞 문자열 꼬리가 비친다.
**원본 지명 48개가 예외 없이 짝수**(SJIS 2B/글자)라 원작에선 성립할 수 없던 버그다.

- 결정적이었던 건 **재빌드 없는 대조**였다 — 짝수 지명 `루디아`(6B)는 같은 빌드에서 멀쩡했다.
  지명을 길이 패리티로 갈라 놓고 "짝수 하나만 들어가 봐 달라"고 한 게 한 판에 끝냈다.
- 그 앞의 진단 빌드(ED.EXE 지명표만 일본어)도 값을 했다 — 실내가 **한글**로 뜨는 걸 보고
  이름 출처가 SCN 헤더임을 확정했고, 꼬리에 낀 쓰레기 글자가 "종단 실패"를 가리켰다.
- ⚠ **교훈 셋.** ①"원판 사양"이라는 결론은 원판을 켜 보기 전엔 가설이다.
  ②분기를 죽이기 전에 그 분기에 도달하는 경로를 전부 센다.
  ③**원본 데이터가 예외 없이 지키는 성질은 엔진의 암묵적 불변식일 수 있다** — 번역문이 깨면
  엉뚱한 화면에서 터진다. 원본 테이블을 전수로 재 보는 습관.
