# NPC ↔ 대사 바인딩 역분석 devlog

**목적**: 정발 대사를 남김없이 자동 매핑하려면 "같은 NPC의 대사끼리 묶기"가 필요하다.
의미 유사도만으로는 한 맵 안의 동명이인(크루즈 마을 남자 2명·여자 2명)을 못 가른다 —
「어서 오십시오, 왕자님」이 여러 NPC에 걸쳐 존재하기 때문이다. 통계 신호를 네 번 바꿔 봤지만
정밀도가 83~88%에서 천장을 쳤다(경위는 `HANDOFF.md`). NPC 바인딩은 통계가 아니라 게임
데이터라 그 천장이 없다.

## 확정된 구조 (2026-07-30)

### SCN 오버레이 좌표

```
file = RAM − 0x8016A000        (reinsert_kr_pilot.OVERLAY_RAM_BASE)
검증: 0x80186030 − 0x8016A000 = 0x1C030 = SCN_ARG_PATCHES[("ED1SCN1", 287)] 좌표
텍스트 영역 = 0 ~ text_end(SCN1은 0x13208), 그 뒤가 코드
```

### 맵 세그먼트와 인스턴스

세그먼트 구조는 `[지명][대사 블록들][메시지 점프테이블]`의 반복이고 **점프테이블이 꼬리**다.
테이블 시작 = 다음 세그먼트 시작 − 테이블 크기가 **바이트까지 일치**한다.

- 지명 헤더는 바이트 검색으로 찾는다(`patch_sys_ui.patch_scn_headers`와 같은 판별).
- 점프테이블 위치가 **맵 인스턴스(방·구역)** 경계를 준다 — 지명보다 12배 세밀.
  루디아는 지명으론 440블록 한 덩어리인데 인스턴스로는 9개(각 ~36블록).
- 정발 테이블이 엔트리 10~~20개씩이라 인스턴스 하나가 테이블 1~~3개 = **거의 NPC 단위**.
- 구현: `tools/scn_maps.py` (`segments` / `instances` / `block_instances`).

### 메시지 점프테이블

엘아스타(테이블 0x000B88, 117엔트리) 실측:

```
[0]  ----- -----  0x01369c 0x0136b4     ← msg 0·1 미사용, 2부터 핸들러
[16..116]  0x0139f8 × 87                ← 미사용 ID의 공용 no-op 핸들러
핸들러 간격 24B(6 MIPS 명령) = 인자 세팅 + jal sprintf + 공용 꼬리 점프
고유 핸들러 28개 = 이 맵의 실제 메시지 수
```

**메시지 ID → 블록**은 핸들러 24B 창 안의 `lui/addiu` 텍스트 참조를
`reinsert_kr_pilot.find_refs`로 뽑아 블록 경계와 대조하면 나온다. SCN1에서 **548건 확정**
(서로 다른 블록 400개, 한 블록에 ID 2개 이상 걸린 것 78개 = 같은 대사의 상황별 재사용).

⚠ 창을 200B로 잡으면 이웃 핸들러 참조까지 긁혀 블록이 7~8개로 뭉개진다. 24B로 좁힐 것.

### 디스패처 (`msg_build`)

루디아#2 실측 — 이 관용구가 정본이다:

```
0x801810c8  addiu $sp,-0x538            ← 진입점
0x801810d4  sltiu $v0,$a0,0xe5          ← 경계 검사: 메시지 ID < 229
0x801810ec  beqz  $v0, <기본>
0x801810f4  sll   $v0,$a0,2             ← id*4
0x801810f8  lui   $at,0x8017
0x801810fc  addu  $at,$at,$v0
0x80181100  lw    $v0,-0x3050($at)      ← table[id]  (0x8016CFB0 = file 0x2FB0)
0x80181108  jr    $v0                   ← 핸들러로 점프
```

`lw rX,imm(base)` → (nop) → `jr rX` 관용구를 스캔하고 앞쪽 `lui`로 테이블 주소를 복원하면
**디스패처 53개**가 나온다(내 휴리스틱 런 탐색은 21개만 찾았다 — **디스패처가 정본**).
맵마다 주 디스패처(경계 109·209·229·306)와 보조 디스패처(경계 5·6·8·21·53)가 있다.

## ⛔ 여기서 막혔다 — NPC → 메시지 ID는 오버레이 밖

- 오버레이 안의 `jal <디스패처>` 호출부가 **7건뿐**이다. 즉 **엔진(ED.EXE)이 함수 포인터로
  디스패처를 부르고**, 메시지 ID는 엔진이 NPC 데이터를 보고 결정한다.
- ED1에는 **이벤트 데이터 파일이 없다**. 디스크 구성: `BIN/ED1SCN1~6.BIN` +
  `DATA/ED1{BGD,CEL,CHR,MON,PARTS,SE,TIM}.DAT`. (ED2는 `ED2EVT.DAT` 296,960B가 별도로 있다.)
  ⇒ ED1의 NPC 배치는 `ED1BGD.DAT` 안이나 `ED.EXE`에 묻혀 있을 가능성이 크다.
- **정적 경로는 소진됐다.** 오버레이 안에서 즉치를 긁어 NPC→ID를 얻을 수는 없다.

## ▶ 다음 절차 — 라이브 조사 한 번이면 이후는 정적

구조를 한 번 찾으면 그 뒤 전 맵 추출은 정적·자동이다.

1. **emucap 재연결** 후 게임 기동 → 메모리카드 세이브 로드(이미 맵 안이다).
   절차는 `HANDOFF.md` "메모리카드 로드 워크플로" 참조(9세이브, 슬롯1).
2. **디스패처 진입점에 BP** — 예: SCN1 루디아#2는 RAM `0x801810c8`. NPC에게 말을 걸면
   `$a0` = 그 NPC가 요청한 **메시지 ID**다. 몇 명만 찍어도 대응이 보인다.
3. BP 시점의 **호출 스택/`$ra`** 로 엔진 쪽 호출자를 얻고, 그 함수가 읽는 **NPC 구조체**를
   찾는다(`$s0`/`$a2` 등에 실린 포인터). 워크램에서 그 배열을 덤프해 stride·필드 배치 확정.
4. 배열을 채우는 소스를 역추적 — 맵 로드 루틴이 어느 파일/오프셋에서 읽는지.
5. 그 뒤로는 전 맵 정적 파싱 → NPC → {메시지 ID} → 블록 집합.

**기대 효과**: 정발 테이블이 이미 NPC 단위이므로 양쪽이 NPC 단위로 만나면 동명이인이
원리적으로 사라지고, 한 NPC의 3~~5줄 대 정발 엔트리 3~~5개의 소규모 배정만 남는다.
앵커 노이즈에 의존하지 않는 유일한 길이다.

⛔ **버전 간 NPC 좌표 대조는 안 된다** — PS1은 리메이크라 맵 레이아웃이 다르다.
정발 DOS `MAP/`에도 위치 데이터가 있지만 대조 대상이 못 된다.

## 진행 중 틀렸던 추정 (반복 방지)

- "맵 제약만으로 동명이인이 상당히 풀린다" → 아니다. 83% 천장이 그 답이었다.
- "인스턴스 제약으로 97.7%" → **잘못된 측정**. 홀드아웃 블록을 학습에서 빼서 마스크가 우연히
  촘촘해진 것이었다. 실제 도구로는 88.2%.
- "NPC 바인딩은 반나절" → 점프테이블까지는 순조로웠지만 그 다음 고리가 오버레이 밖에 있다.
- 순서(단조성) 제약은 **역효과**다 — 테이블 내 단조도가 71.6%뿐이라(리메이크가 대사 순서를
  재배치) 가산점이 맞는 매칭을 밀어낸다.
