# 관리자 세션 — 규약 (유저 확정 2026-09-06)

게임 워크트리마다 세션이 하나씩 여덟이 돈다. 사람이 탭을 넘나들며 상태를 모을 수 없어
**관리자 세션 하나**를 main 본 트리에 둔다. 회차 기록은 [`manager-log.md`](manager-log.md).

## 관리자가 하는 일 넷 + 🔴 1차 검토

0. 🔴 **바이패스가 아니다 — 이슈를 들고, 1차로 검토한다**(마스터 확정 2026-09-27).
   「이슈를 파악해두고 세션이 고치면 1차적으로 너가 검토하라고 매니저를 만든거야. 바이패스 할거면
   내가 직접 얘기하지.」 — 마스터 지적마다 **증상(마스터 표현 그대로)·캡처·재현 조건·기대 결과**를
   관리자가 들고 있고, 세션 보고는 **그 기록과 대조해 통과한 것만** 「확인 대기」로 올린다.
   ⚠ 세션은 재현이 안 되면 **자기가 재현한 증상으로 문제를 바꿔** 닫으려 한다(실측 09-27: 「글자 이탈」을
   「원판 잔상」으로 두 번). 「원판도 같다」·「없다」·「해당 없음」은 근거가 **화면**인지 **코드 검색**인지
   가리고, 캡처는 직접 열어 본다. 안 맞으면 마스터께 올리지 말고 세션에 되돌린다.
1. **전 작업을 꿰뚫는다.** 세션 시작 시 여덟 상태 문서(`games/<게임>/docs/*status*.md`)를 다
   읽고, 회차마다 `sh scripts/dashboard.sh` 로 갱신한다. 세션의 busy/idle 은 세션 목록으로 겹친다.
2. **브릿지.** 유저 지시를 해당 세션에 세션 간 메시지로 전달하고, 워커가 올린
   「유저 판정 대기」를 모아 유저에게 한 목록으로 올린다. 답이 오면 다시 뿌린다.
3. **main 관리.** 공용(`shared/`·`scripts/`·`docs/`) 손질, `sh scripts/check-updates.sh` 로
   emucap·스킬·패치 템플릿 갱신 확인. 워커가 낸 공용 문제(문서 오류·정본 불일치)를 main 에서 고친다.
4. **rebase 요청.** main 에 커밋이 쌓이면(dashboard 「뒤 N」≠0) 각 세션에 `git rebase main` 을
   요청한다. 더티면 먼저 커밋하라고 같이 보낸다. 되머지는 아니다(루트 `CLAUDE.md` 「Git 정책」).
   🔴 **main 커밋을 정리한 뒤에만 보낸다**(유저 확정 2026-09-06). 워커가 리베이스하는 순간 그 밑의
   main 커밋은 **굳는다** — 다시 쓰면 여덟 브랜치가 `--onto` 리베이스를 해야 한다(그냥
   `rebase main` 은 옛 main 커밋을 자기 것으로 알고 다시 얹으려다 충돌한다). 그래서 순서는
   ① main 에 커밋 자유롭게 → ② 회차 끝에 같은 유형·작업을 묶는다 → ③ **그 다음** rebase 요청.
   실측 09-06: 메시지 올 때마다 로그를 커밋하고 바로 요청을 보내 로그 커밋 셋이 따로 굳었다.
   ⚠ **main 을 다시 쓴 뒤의 요청은 `git rebase --onto main <옛 base>` 다** — 옛 base 는 관리자가
   다시 쓰기 **전에** `git merge-base <옛 main> <브랜치>` 로 세션마다 재서 찍어 준다. 검증은
   **개수가 아니라 내용**이다 — `git log --oneline main..HEAD` 에 자기 게임 커밋만 남았는가.
   개수는 **줄어드는 게 정상**이다(옛 main 커밋을 자기 것으로 세고 있었다 — 09-06 sfc 12→10 ·
   pce 28→24). 「전과 같은 수」로 보내면 워커가 손실로 오해해 되돌린다.
   ⚠ **요청에 이 한 줄을 같이 보낸다**(2026-09-07) — `grep -c '^|||||||' docs/reference/our-findings.md`.
   **커밋된 충돌 마커 잔해**가 있으면 `merge.conflictstyle=diff3` 탓에 git 이 자기 마커와 헷갈려
   `error: could not parse conflict hunks` 로 선다(우회: `git -c merge.conflictstyle=merge rebase main`).
   실측 09-07: 여덟 트리 중 둘에 있었고, **리베이스를 미룰수록 그 커밋이 뒤로 밀려 충돌 회차가 는다.**
   🔴 **머지가 도는 동안에는 리베이스 요청을 보내지 않는다**(유저 확정 2026-09-07).
   순서가 이것이다 — **① 각 세션의 묶음 머지가 끝난다 → ② 유저가 확인한다 → ③ 히스토리를
   정리한다 → ④ 그제서야 리베이스 요청.** 앞당기면 헛일이 된다: 브랜치가 얹히는 순간 그 밑
   main 은 굳는데, **정리는 아직 안 끝났다.** 실측 09-07 — main 의 docs 아홉을 넷으로 묶은
   뒤에도 ss-ed1+2 의 히스토리 정리(153 → 18)가 대기 중이라, 미리 얹은 브랜치는 그 정리를
   못 받는다. **묶음 머지 기간에는 main 이 계속 움직인다고 보고, 리베이스는 그 기간이 닫힌 뒤에.**
   ⚠ **꼭 필요할 때만 요청한다**(유저 확정 2026-09-06). 「뒤 N」≠0 자체는 신호가 아니다 — 그
   게임이 **실제로 읽는 공용**(shared 코드 · scripts · 정본 데이터 · 그 게임이 따를 규칙)이
   바뀌었을 때만 보낸다. 관리자 로그·남의 게임 문서·README 따위는 이유가 안 된다. 받아 갈
   것이 없는 리베이스는 워커 토큰만 쓰고 main 커밋을 굳힌다.

🔴 **워크트리는 만지지 않는다.** 파일을 고치면 아홉째 워커가 되어 그 브랜치에서 충돌한다.
워커의 판단을 대신하지도 않는다 — 규칙이 이미 있으면 **그 자리를 찍어 주는 것**까지다
(09-06 실측: pc98 의 「붙임 지명」 물음은 `naming.md` 층 규칙이 이미 답이었다).

## ED1 이식판은 같은 단계로 같이 간다

🔴 **머지 전에 관리자가 근거 캡처를 직접 연다**(유저 지적 2026-09-07). 조건 ⑶ 은 「캡처가
있다」가 아니라 **「그 캡처가 그 칸을 뒷받침한다」**이다. 파일 존재만 확인하고 머지한 실측이 있고,
**그 화면은 관리자가 앞서 직접 보고 「치우쳤다」고 판단했던 것**인데 세션이 「원판과 같다」고 하자
자기 눈으로 본 것을 보고로 덮어썼다. ⇒ **결함이 한 번이라도 보고된 칸은 반드시 열어 본다.**
⚠ **세션 보고가 관리자의 관측을 이기지 못한다.** 어긋나면 **어느 쪽이 틀렸는지 가르기 전엔 안 닫는다.**

🔴 **머지할 때마다 루트 `README.md` 를 같이 고친다**(마스터 지시 2026-10-05). 「패치 현황」 표와
저장소 구조가 대상이다. 상태가 바뀐 게임의 칸과 갱신 날짜를 고치고, 머지 뒤 docs 커밋으로 붙인다.
배포 페이지의 `patcher/site/site.json` 도 함께 맞춘다. 실측: README 는 PS1 이 배포된 날에도
「리버싱 진행 중」이었고, 게임은 셋만 적혀 있었으며, 이미 버린 번역 방침을 적고 있었다.
진행 계획 문서(ROADMAP.md)는 같은 이유로 걷었다. 현황은 README, 세부는 게임별 상태 문서에 둔다.

시스템 메뉴 · 전투 · 고유명사를 이미 지나 **인게임 QA 단계**에 있다(마스터 2026-09-15).

💡 **이건 예외를 여는 게 아니라 원래 자리다.** 라운드 눈금(① 시스템 메뉴 ② 시스템 메시지

⚠ **관리자가 이걸 몰라 하루에 두 번 틀렸다**(2026-09-15). 위 「ED1 은 같은 단계로 같이 간다」를

마스터께 여쭸다. ⇒ **닫힘은 여덟이 아니라 일곱으로 센다.**

[`ed1-phases.md`](ed1-phases.md) — PS1 ED1 이 밟은 순서를 P0~P7 로 굳혔다. 상태 문서 「한 줄 요약」의
`단계: Pn/7` 을 대시보드가 표에 싣는다. 판정 대기는 `[P3]` 처럼 단계를 머리에 달아 단계별로 묶어 올린다.

## 규약

- **세션 이름 = 워크트리 폴더 이름.** `/rename <게임>`. `+` 도 된다(`ps1-ed3+4`). 관리자는 `manager`.
  이름 하나로 세션 목록과 워크트리 목록이 짝지어진다 — 메시지 수신자도 이 이름이다.
- 🔴 **호칭은 「마스터」다**(지시 2026-09-08). 대화·문서·커밋 메시지 전부.
  ⚠ **이미 적힌 「유저 확정 …」 은 그대로 둔다** — 그날의 판정 **기록**이라 되쓰면 이력이
  흔들린다. **새로 쓰는 글만** 바꾸고, 그 자리를 다른 일로 손볼 때 같이 고친다.
  한꺼번에 치환하지 않는다.
- **마스터 판정 대기는 상태 문서의 `## 마스터 판정 대기` 절에**(옛 이름 `## 유저 판정 대기`). 워커가 못 정하는 것만 둔다.
  `dashboard.sh` 가 이 절 이름은 정확히 잡고, 다른 절(「열려 있는 물음」 등)은 느슨하게 잡는다.
  닫히면 그 절에서 뺀다 — 결정은 `policy.md` 결정 대장으로 옮긴다.
- **이미지는 메시지에 실리지 않는다**(평문만). 스크린샷은 **`.local/inbox/<게임>/`** 에 떨어뜨리고
  「pce 에 넣었다」고만 하면 관리자가 **절대경로**를 찍어 넘긴다(워크트리엔 `.local` 이 없다).
  클립보드 붙여넣기는 디스크에 없어 못 넘긴다.
- **기종 간 발견은 관리자가 검증하고 뿌린다.** 워커 하나의 발견(예: Condensed 한글 전폭 8px)은
  관리자가 공용 자료로 **재확인한 뒤** 해당될 만한 세션에 「참고용, 판단은 네 몫」으로 보낸다.
  틀린 발견을 여덟에 뿌리면 여덟이 흔들린다.
- **메시지 첫 줄은 그 자체로 한 문장.** 받는 쪽 사람은 첫 줄만 미리 본다.
  출처를 머리에 단다 — `[유저 지시, 관리자 중계]` · `[관리자 중계, <세션> 발견 · 참고용]` · `[관리자]`.

## 🔴 관리자의 값은 라우팅이 아니라 **교차 검출**이다 (2026-09-08 실측)

한 라운드를 돌아 보니 관리자가 **맞은 것과 틀린 것이 갈렸다.**

    맞은 것   여덟을 나란히 놓아야 보이는 것
              · UI 라벨이 `그외`/`그 외`/`기타` 셋으로 갈린 것 — 아무도 몰랐다
              · **게이트가 다 초록인데 화면이 틀리는 부류가 하루에 넷**이라는 것
              · 선행 레포 하나가 **두 트랙을 동시에** 살린 것
    틀린 것   **전달**
              · `強さ` 를 평면으로 돌려 취소 메시지를 다시 보냈다
              · 커밋 정리에서 **기각된 안을 해법으로** 적었다(세션이 잡았다)
              · 「히스토리 정리」에 **범위·docs 를 안 적어** 둘이 똑같이 반쪽을 했다
              · 메시지가 엇갈려 세이브·ROM 이 이미 왔는데 또 청했다

⇒ **라우팅은 세션이 문서를 읽으면 되는 일이고, 교차 검출은 아무도 못 하는 일이다.**

**그래서 셋을 지킨다:**
1. 🔴 **정본은 데이터로, 방침은 커밋으로.** 메시지로 방침을 돌리면 틀렸을 때 취소 메시지가
   또 나간다. 데이터로 올리면(오늘 `shared/glossary` 의 `ui` 범주처럼) 세션이 리베이스하며
   **저절로 받고 게이트가 잰다.** 메시지는 **알림**이지 **정본**이 아니다.
2. **뿌리기 전에 「이게 트랙마다 다를 수 있나」를 먼저 묻는다.** `強さ` 는 자리마다 다른 말이라
   평면으로 뿌리면 **여덟이 같이 틀린다.** ⚠ 「기종 간 발견은 관리자가 검증하고 뿌린다」의
   구체다 — 검증이 「사실인가」만이 아니라 **「모두에게 같은가」**까지다.
3. **지시에는 범위와 예외를 적는다.** 「히스토리 정리해라」는 **브랜치 전체인지 이번 회차분인지**,
   **docs 를 포함하는지**를 안 적으면 세션은 「방금 한 것」만 묶는다 — 둘이 똑같이 그랬다.

💡 **서브에이전트는 워커를 대체하지 않는다**(마스터와 확인 2026-09-08). 세션이 며칠치 기억을
들고 있는 것이 자산이다 — 오늘 값을 낸 순간이 다 거기서 나왔다(「이 가설을 버렸는데 그 근거가
틀렸다」·하루에 셋을 스스로 뒤집기·「닫힌 것」과 「뒤집힌 것」 구분). ⇒ **전수 검색·이분처럼
경계가 분명하고 값으로 검산되는 일**은 **워커 안에서** 에이전트로 돌린다.

## 🔴 관리자가 틀리는 꼴 일곱 (라운드 ⑥ 실측 2026-09-13 — 한 회차에 다 나왔다)

위 절이 「관리자의 값이 어디 있나」라면 이건 **「관리자가 어디서 손해를 내나」**다.
한 워커·한 회차에서 나온 것이라 **다음 회차에 그대로 되풀이될 것**만 적는다.

1. 🔴 **다음 할 일을 내 기억에서 읽었다.** 「다음은 셋」이라고 줬는데 **셋 다 이미 끝나
   커밋까지** 돼 있었다. 세 번 그랬다. 원인은 잊은 게 아니라 **출처**다 — 나는 **내가 보낸
   메시지 목록**을 상태로 읽었고, 그건 「내가 시킨 것」이지 **「무엇이 됐나」가 아니다.**
   ⇒ 할 일을 주기 전에 **`git -C <워크트리> log --oneline main..HEAD`** 를 본다. 한 줄이고
   내 기억보다 싸고 정확하다. **그리고 QA 표에 항목마다 커밋 해시를 달게 한다** — 그러면
   누구도 기억에 의존하지 않는다(「완료 이력은 커밋 히스토리다」의 실무판이다).
2. 🔴 **없는 신고를 근거로 남의 일을 게이트했다.** 캡처만 있고 **글로 적힌 신고가 한 줄도
   없는 항목**에 내가 원인 가설을 붙였고, 그게 **창 31개 일괄 변경 + 다른 세션의 재현 조사 +
   또 다른 항목의 대기**를 막았다. 실제로는 **아무것도 안 짤려 있었다.**
   ⇒ **캡처만 있고 글이 없는 것은 항목이 아니다.** 번호를 붙이는 순간 **한 줄이라도 글을
   적는다** — 그게 관리자 몫이다. 그리고 **내 가설에 번호를 주지 않는다.**
3. 🔴 **「메시지 금지」를 보내는 방향에만 걸고 올리는 방향엔 안 걸었다.** 「지금 굴리는 하나
   외엔 메시지 금지」를 워커에게만 적용하고, **마스터에게 올리는 보고**엔 안 걸어 여덟 트리의
   판정 대기를 한꺼번에 올렸다 — 지적을 받았다.
   ⇒ 아끼는 것이 토큰이 아니라 **마스터의 주의**라면 방향과 무관하게 걸린다.
   **수집은 파일에 쌓고, 올리는 것은 지금 굴리는 것만.** 나머지는 **라운드 개시 때** 한 번에.
4. 🔴 **수치를 여덟 번 헐겁게 냈고 원인이 하나였다.** 방향도 늘 같았다 — **처음이 크고
   나중이 작다**(125→109 · 209→134 · 78→25→1 …). 값으로 잡은 원인:
   **`grep -c` 는 줄을 세고, 이 레포의 정본은 한 블록이 여러 줄**이다(판단 근거를 `note` 에
   적는 관행이 있다) ⇒ **주석이 많은 축일수록 더 부푼다** = **이미 많이 들여다본 자리에서
   더 크게 틀린다.** 최악의 편향이다.
   ⇒ **블록 수는 파싱해서 센다.** `grep -c` 는 「있나 없나」에만.
   ⚠ 그리고 나는 **같은 메시지에 「분모 134」와 「합 209」를 같이 써 보냈고 그 불일치를 못
   봤다.** ⇒ **수치를 두 형태로 적었으면 합을 맞춰 본다** — 안 맞으면 둘 중 하나는 틀렸고,
   **그 자체가 신호다.** 받는 쪽도 되물으라고 전한다.
5. ⚠ **판정을 겹쳐 청했다.** 「정본과 실사용이 갈렸다」를 마스터 판정으로 올리려 했는데
   **코드 주석에 이유가 있었다**(칸 바이트 예산). 「…의」로 끝나는 문안도 원문 부호를 보니
   답이 하나였다. ⇒ **판정은 값이 없을 때 청한다.** 값이 있으면 **값으로 닫고 한 줄만 알린다.**
   ⚠ 뒤집힌 형태도 있다 — 세션이 **「측정만 하고 판정은 다음 회차」 원칙을 어기고 반영까지**
   했는데 **그대로 두는 게 맞았다**(근거가 원문의 종결어미라 갈릴 여지가 없었다).
   ⇒ 가르는 물음은 **「원문을 읽으면 답이 하나인가」**다. 하나면 반영, 둘 이상이면 대기.
6. 🔴 **한 회차에 「문장이 결론과 반대로 적힌 것」이 셋 나왔다** — 내 것 하나, 세션 것 둘.
   「짤린다」(짤린 적 없다) · 「게이트에 사각지대」(게이트가 빌드를 실패시켰다) ·
   「패턴이 안 걸린다」(걸렸다 — 뜻한 건 「패턴 문제가 아니다」였다).
   **셋 다 값은 맞고 문장만 뒤집혔는데, 다음 사람이 읽는 것은 문장이다.**
   ⇒ **결론을 한 줄로 적었으면 값과 부호가 맞나 되읽는다.** 그리고 **틀린 한 줄은 발견한
   그 자리에서 고친다** — 「다음에 만질 때」로 미루지 않는다. 읽히는 동안 계속 손해이고,
   고치는 값은 5분이다. ⚠ 특히 **마스터가 직접 읽는 파일**(QA 표)에서는 더 그렇다.

7. 🔴 **한 사례에서 규칙을 지어내 다른 자리에 옮겼다 — 하루에 셋.** 관리자는 여러 세션을
   보니 패턴이 보인다고 **착각하기 쉽다.** 셋 다 「한 곳에서 통한 것」을 검증 없이 옮긴 것이다:
   - **PS1 전용 기계를 새턴 트랙에** — 저작권 조치로 `align_map` 포인터 + `subs_at` 을
     그대로 중계했는데, 그 트랙엔 **그 파일이 아예 없다**(스키마가 달라 조치는 **재번역**이었다).
     세션이 잡았다.
   - **원인 바이트로 좁힘** — 아침에 같은 바이트(`0xFF`)로 한 건을 닫았기에 저녁 건도 그것으로
     몰아갔다. 전수로 세니 **10건 중 2건**이고 나머지 8은 다른 바이트였다. **세션이 넓게
     고쳐서 살았다.**
   - **유저 환경 사실을 에뮬 환경에 적용** — 「나는 카드 2 안 쓴다」는 **유저의 다른
     에뮬레이터** 얘기였는데 우리 쪽 설정에 그대로 적용해 **되던 배치를 깨뜨렸다.**
     그리고 그 뒤 「두 카드가 같아서 막힌다」는 **가설을 지어내 되돌리기까지** 했다 —
     실제 원인은 **그 화면이 16초 걸린다**는 것이었다.
   ⇒ **규칙을 옮기기 전에 「이 자리에서도 참인가」를 값으로 묻는다.** 위 절의 2번
   (「뿌리기 전에 트랙마다 다를 수 있나를 묻는다」)의 재판인데, **그때는 용어였고 이번엔
   기계·원인·환경**이었다. 넓은 것일수록 옮기고 싶어진다.

💡 일곱을 관통하는 한 줄 — **관리자는 값을 만들지 않고 옮긴다.** 그래서 관리자의 실수는
**틀린 값이 아니라 틀린 한 줄·없는 항목·낡은 목록**의 꼴로 나오고, **남의 며칠을 정한다.**

## 🔴 리베이스를 부른 뒤에는 main 을 **되쓰지 않는다** (2026-09-08 실측 — 관리자 실수)

라운드 마감 뒤 여덟에 「`rebase main` 해라」를 돌리고 **그 사이에 docs 커밋을 두 번
`--amend`** 했다(`8bfab8dc` → `ad2100e7` → `a2f45521`). 세션마다 리베이스 시각이 달라
**여덟이 서로 다른 죽은 커밋 위에 떴다** — 일곱은 `ad2100e7`, 하나는 `8bfab8dc`.
⇒ 리베이스를 한 번 더 돌려야 했고, 그때는 **`rebase main` 이 아니라 `--onto`** 여야 한다
(그냥 `rebase main` 하면 죽은 docs 커밋을 새것 위에 다시 얹어 충돌하거나 두 벌이 된다).

    BAD=$(git log --reverse --format=%H main..HEAD | head -1)   # 죽은 main 커밋이 범위 맨 아래
    git rebase --onto main $BAD

⚠ **이 레포가 이미 경고하던 자리다**(`CLAUDE.md` 「미루지 않는다 — 늘 맞춰 둔다」의
「main 은 되쓰기도 잦다」). **그 문서를 쓰면서 밟았다.**

**⇒ 규율 둘:**
1. **리베이스를 부르기 전에 main 을 확정한다.** 부른 뒤에 고칠 것이 생기면 **`--amend` 가
   아니라 새 커밋**으로 얹는다 — 그러면 세션들은 `rebase main` 한 번이면 되고 죽은
   커밋이 안 생긴다.
2. **그래도 되썼으면 「몇 시에 리베이스했나」가 아니라 값으로 잰다** —
   `git log --reverse main..<브랜치> | head -1` 이 **죽은 main 커밋이면** `--onto` 다.
   세션마다 다를 수 있으니 **브랜치별로** 본다.

⚠ **1번이 절대는 아니다.** 「비슷한 작업은 한 커밋」(`CLAUDE.md`)이 이길 때가 있다 — 실제로
마스터가 이 규율 커밋을 **앞의 라운드 docs 커밋에 합치라고** 판정했다(2026-09-08). 둘 다 같은
라운드의 문서라 트렁크에 두 줄로 남을 이유가 없다. ⇒ **되쓰지 말라가 아니라, 되쓸 거면
값을 싸게 만들라**가 규율의 뜻이다. 싸게 만드는 법이 바로 아래다.

### 부른 뒤에 되쓸 수밖에 없으면 — **좌표를 같이 보낸다**

「리베이스 다시 해라」만 보내면 받는 쪽은 `rebase main` 을 쓰고 **죽은 커밋을 다시 얹는다.**
반대로 **`--onto <죽은커밋>` 과 「네 범위 맨 아래에 그게 딱 하나」**를 같이 보내면, 받는 쪽은
**값 확인 한 번과 명령 한 줄**로 끝난다(여덟 다 그렇게 3분에 끝냈다 — sfc-ed1 · ss-ed1+2).
⚠ 좌표는 **브랜치마다 다를 수 있다** — 그 창에서 **먼저 리베이스한 세션**은 더 옛 커밋 위에
있다(실측: ps1-ed1+2 만 `8bfab8dc`, 나머지 일곱은 `ad2100e7`). ⇒ 하나의 좌표를 여덟에
똑같이 돌리면 **먼저 움직인 쪽이 어긋난다.** 부르는 쪽이 브랜치별로 재서 준다(ps1-ed1+2).
💡 더 나은 형태는 **목표를 주는 것**이다 — 「`rebase main` 해라」가 아니라 **「`54474727` 위로
얹어라」**. 그러면 main 이 그 사이 움직여도 받는 쪽이 **`--onto` 가 필요한지 스스로 안다**
(제 tip 의 부모가 그 sha 가 아니면 죽은 커밋이 낀 것이다 — md-ed1).

### 값으로 판정한다 — 넷 (여덟 세션 실측 2026-09-08)

🔴 **`rebase main` 은 죽은 커밋을 다시 얹으면서 충돌 없이 조용히 성공한다.** 「충돌이 나면
알겠지」로 판단하면 늦는다 — 오늘 나온 축 「지금 통과한다가 안전하다가 아니다」의 git 판이다.

| 물음 | 값 | 왜 |
| ---- | -- | -- |
| `--onto` 가 필요한가 | `git log --oneline main..HEAD` 에 **내 것 아닌 게 보이나** | 충돌은 신호가 아니다 (sfc-ed1) |
| 떨궈도 되나 | **그 커밋이 건드린 파일로 좁힌** `--numstat` 의 **삭제가 0** 인가 | `CLAUDE.md` 「머지는 한 방향뿐이다」 2번의 그 규율. ⚠ 잣대도 범위도 틀리기 쉽다 — 아래 |
| 내 작업이 안 흔들렸나 | `git rev-parse HEAD:games/<게임>` 이 **전후 같은가** | **커밋 수만 세면 내 것이 딸려 나가도 맞을 수 있다** (ss-ed3) |
| 푸시로 무엇이 버려지나 | 버려지는 것들의 **patch-id 대조** | `--force-with-lease` 는 「origin 이 그대로인가」만 보고 **무엇이 버려지는가는 안 보여 준다** (ps1-ed3+4) |

⚠ **양방향 `git log` 만으로는 겁먹거나 대충 넘긴다** — 리베이스하면 해시가 다 달라 「origin
에만 있는 것」이 **통째로** 뜬다(pce-ed1 은 5줄 전부였다). 목록 옆에 **내용**을 같이 본다 —
`git diff <origin> <HEAD> -- games/<게임>` 이 비면 「내 작업이 안 없어진다」가 한 줄로 증명된다.
**해시가 아니라 내용이라 리베이스에 안 흔들린다.**

💡 넷을 관통하는 한 물음은 **「내 범위에 내 것 아닌 게 있나」**다 — 머지 전엔 **남의 게임이
섞였나**, 리베이스 전엔 **main 것이 섞였나**. 방향만 반대고 명령은 같다 (ps1-ed3+4).

#### 🔴 「흡수됐나」를 재는 잣대 셋 중 둘이 **가짜 빨간불**을 낸다 (sfc·ss-ed1+2·ps1-ed3+4 실측)

| 잣대 | 판정 |
| ---- | ---- |
| **줄 단위 `git grep`** | ❌ `-` 로 시작하는 줄을 git 이 **옵션으로 먹고** usage 를 뱉는다 → 「main 에 없다」로 찍히는데 **실제로는 있다.** 마크다운은 목록이 `-` 라 **거의 항상 난다** (sfc-ed1) |
| **제목 대조** | ❌ **squash 앞에서 거짓 경보** — 없어진 게 아니라 **제목만 합쳐진 것**이다 (ps1-ed3+4) |
| **`git diff --stat`** | ❌ **삭제가 섞여도 한 줄로 보인다**(`50 ++++----`). 여럿이 이걸로 확인했고 **그땐 우연히 삭제가 0 이라 맞았다** (ss-ed1+2) |
| **`git diff --numstat`** | ✅ 추가·삭제가 **숫자 둘로 갈린다.** 둘째 칸이 0 이면 상위집합이다 |

#### 🔴 그리고 `--numstat` 도 **범위를 안 좁히면 못 쓴다** (ps1-ed1+2·ps1-ed3+4 실측)

`git diff --numstat <떨굴것> main` 은 **레포 전체**를 본다. main 이 그 사이에 다른 게임·공용을
고쳤으면 **삭제가 당연히 0 이 아니고**, 그건 내 커밋 얘기가 전혀 아니다.
⇒ **그 커밋이 건드린 파일로 좁힌다**:

    git diff --numstat <떨굴것> main -- $(git show --name-only --format= <떨굴것>)

🔑 **이 게이지는 ✅ 만 말할 수 있고 ❌ 는 못 말한다.**
**삭제 0** 이면 「main 이 내 것을 포함한다」가 증명된다 — 떨궈도 된다.
**삭제 ≠ 0** 은 **빨간불이 아니다.** 물음이 실은 **둘**이기 때문이다 (ps1-ed3+4):

| 물음 | 삭제가 뜻하는 것 |
| ---- | ---------------- |
| **main 이 앞으로 갔나** | main 이 그 파일을 **더 고쳤다.** 삭제가 나는 게 정상이다 |
| **내 커밋이 흡수됐나** | 이건 `--numstat` 이 답할 수 없다 — **patch-id 대조**다 |

⇒ 삭제가 뜨면 **줄을 읽는다**(이게 판정이다):

    git diff <떨굴것> main -- <그 파일> | grep '^-' | grep -v '^---'

없어진 줄이 **내가 쓴 것**이면 손대지 말고 올린다. **main 이 자기 것을 고친 것**이면 떨군다.

⚠ 이 절의 첫 판(2026-09-08 오전)에 **줄 대조**를 적었다가 그날 오후에 sfc 가 잡았다.
🔑 **「지금 통과한다가 안전하다가 아니다」의 반대편은 「지금 실패한다가 위험하다가 아니다」**다 —
**잣대가 틀리면 가짜 빨간불도 난다.** sfc 는 하루에 양쪽을 다 봤다.

#### 굳은 절차 여섯 (ss-ed3, 세 번 돌려 보고)

    ① 좌표 확인   git diff --numstat <떨굴 base> main -- $(git show --name-only --format= <떨굴 base>)
                                                           ← 「이미 들어갔나」가 한 줄로 (삭제 0)
    ② 전 트리     before=$(git rev-parse HEAD:games/<게임>)
    ③ 얹기        git rebase --onto main <떨굴 base>
    ④ 후 트리     같은지 대조                            ← 커밋 수로는 못 보는 것
    ⑤ 되돌릴 곳   git branch -f backup/<이름>-pre-force<N> origin/game/<이름>
    ⑥ 올리기      git push --force-with-lease

세 번 다 ④ 가 통과해 **게이트를 안 돌렸다** — 리베이스 한 번에 빌드 5분+게이트를 아낀다.
🔴 **④ 는 「내 게임 트리가 안 변했다」만 말한다.** `shared/`·`scripts/` 가 바뀌어 들어오면
**조판이 흔들리므로 게이트를 돌려야 한다.** 안 적으면 다음 사람이 ④ 만 믿고 **코드 변경까지
건너뛴다**(ss-ed3).
💡 커밋 목록 대신 **내용**을 보는 짝도 같이 쓴다 — 리베이스하면 해시가 다 달라
「origin 에만 있는 것」이 **통째로** 뜬다(pce-ed1 은 6줄 전부). `git diff <origin> <HEAD> --
games/<게임>` 이 비면 「내 작업이 안 없어진다」가 한 줄로 증명된다.

#### 🔑 좌표의 경계 — **「어디로」는 주고, 「버려도 되나」는 받는 쪽이 잰다** (md-ed1)

좌표는 그 확인을 **없애는 게 아니라 값싸게** 만든다. 실측(md-ed1): 좌표가 없을 땐 판단이
셋(⑴ main tip ⑵ `--is-ancestor` 로 죽은 커밋 판별 ⑶ 범위 맨 아래 찾기)이었고, 좌표를 받으니
**「그 둘이 정말 흡수됐나」 하나**로 줄었다. 🔴 **그 하나는 남긴다** — `CLAUDE.md` 2번이
「손으로 풀면 남의 작업을 조용히 되돌린다」고 경고하는 자리가 거기다.

⇒ 실측으로 이 구조에선 `--onto` 가 계속 싸다 — pc98-ed1 한 트리에서 **세 번이 다 무충돌·게임
파일 무변경**. 게임 브랜치가 `docs/`·`games/<게임>/` 만 건드리고 main 이 `docs/` 만 얹는 한 그렇다.

### ⚠ 중계는 규칙을 **다시 쓰지 말고 짚는다** (pc98-ed1 지적)

이 지시를 여덟에 돌리며 규율 둘(`--onto` · 「흡수됐나부터 값으로」)을 **처음부터 설명**했는데,
그 둘은 **`CLAUDE.md` 「머지는 한 방향뿐이다」 2번에 이미 있었다.** 다시 쓰면 받는 쪽은
**그게 문서에 있는 줄을 모른다** — 다음에 관리자가 없으면 같은 판단이 안 선다.
⇒ 중계문에 **정본 줄을 짚는다**. 💡 앞 절 「중계는 알림이고 권한은 문서로 온다」의 짝이다 —
그건 **권한**, 이건 **지식**.

### ⚠ 워커 푸시가 **아직 안 올라간 main 의 객체를 먼저 올린다** (ss-ed3)

브랜치가 origin 에 없는 `main` 커밋 위에 얹혀 있으면, 브랜치를 푸시할 때 **그 커밋들의 객체가
함께 올라간다.** ref 는 안 건드리니 무해하고, 마스터가 main 을 밀면 맞아떨어진다.

## 커밋 (유저 확정 2026-09-06)

**커밋은 자유롭게, 묶은 뒤에 rebase 요청, 푸시는 유저.** main 도 같다 — 관리자가 main 의
주인이다. ⚠ main 은 묶는 시점이 **푸시 전이 아니라 rebase 요청 전**이다 — 게임 브랜치가
얹히면 그 밑은 못 다시 쓴다(위 4번).
유형별로 가른다(`feat`/`docs`/`fix`). 푸시 전에 **인접한 같은 유형·같은 작업**을 하나로 묶어
히스토리를 깔끔하게 한다. ⚠ 경계 둘은 그대로다 — **이미 `origin` 에 올라간 것**과
**게임 브랜치가 그 위에 얹힌 것**은 다시 쓰지 않는다(여덟 브랜치를 강제 리베이스시킨다).
main 을 묶을 수 있는 구간은 「아직 어느 게임 브랜치도 rebase 로 받아 가지 않은 꼬리」다:

    for b in $(git branch --format='%(refname:short)' | grep ^game/); do
      echo "$b $(git merge-base main $b | cut -c1-8)"; done      # 가장 앞선 merge-base 뒤로만 묶는다

🔴 **`docs` 커밋은 라운드당 하나다 — 회차 중에는 커밋하지 않는다**(유저 지시 2026-09-07).

    회차 중   문서는 고치되 **커밋하지 않는다**(작업 트리에 둔다)
    머지 전   `git stash` → 머지 → `git stash pop`
    라운드 끝 그때 한 번 커밋한다

⚠ **커밋해 두면 머지 사이사이에 흩어진다** — 09-07 실측: 열여섯이 머지 넷 사이에 끼어
`git log --first-parent` 가 「무엇이 닫혔나」로 안 읽혔고, 묶으려니 **머지를 통째로 다시 쌓아야**
했다(브랜치를 다시 머지하면 ①·⑤ 가 한 머지로 합쳐지는 부작용까지 딸려 왔다).
⚠ **안 커밋한 채로 머지하면 머지가 선다** — `error: Your local changes ... would be overwritten`.
그래서 **stash 가 짝**이다. 이것도 그날 실제로 밟았다.
🔒 작업 트리에 오래 두는 게 불안하면 **스크래치패드에 `git diff > 백업.patch`** 를 떠 둔다 —
stash 는 충돌 없이 pop 되는 게 보통이지만, 잃으면 그날 회차의 규율이 통째로 날아간다.

💡 **아래는 그 앞 판(회차마다 묶기)이었고, 지금은 위 규칙이 정본이다.**
🔴 **main 의 `docs` 는 매번 커밋하지 않는다 — 쌓아 뒀다 한꺼번에**(유저 지시 2026-09-07).
회차 중에 세션이 규율을 하나 낼 때마다 커밋하면 **main 이 그 하나하나로 채워진다**(실측 09-07:
하루에 docs 커밋 열여섯). 문서는 고치되 **커밋은 회차 끝에 한 번**, 메시지에 무엇들이 들어갔는지
목록으로 적는다. ⚠ 그래야 `git log --first-parent main` 이 **「무엇이 닫혔나」**로 읽힌다 —
규율 하나하나는 그 커밋 본문에서 읽으면 된다.

**푸시 — `main` 은 마스터, 게임 브랜치는 그 세션**(마스터 확정 2026-09-08).
⚠ 관리자는 `main` 을 **밀지 않는다** — 묶어 두고 마스터가 민다.
🔴 **그리고 이 규칙은 관리자가 중계로 못 푼다.** 실측 2026-09-08: 마스터 지시를 중계했더니
**세 세션이 다 거절했다** — 「내가 확인할 수 있는 건 「관리자가 그렇게 전했다」까지고,
원격 되쓰기는 되돌리기 어려운 쪽이다. **규칙을 세운 쪽이 마스터라 풀어 주는 것도 마스터여야
한다**」(ps1-ed1+2). **그 판단이 옳다.**
⇒ 원격 경계를 여는 지시는 **마스터가 직접** 말하거나, **문서에 박혀** 세션이 리베이스로 받는다.
중계는 **알림**이지 **권한**이 아니다.
🔑 **다만 「알림」이 없으면 문서도 안 읽힌다**(md-ed1 2026-09-08). 세션이 공용 규칙 변경을
스스로 알아채는 길은 **리베이스뿐**이고, 리베이스는 관리자가 부를 때 돈다.
⇒ **역할이 이렇게 갈린다 — 중계는 「바뀌었다」를 알리고, 문서는 「무엇인지」와 「권한」을
준다.** 관리자가 「어디를 보라」까지 짚어 주면 세션의 판단 근거가 **「누가 말했나」에서
「어디에 적혀 있나」로** 옮겨 간다. 실측: 같은 지시를 메시지로 세 번 보냈을 때 셋 다
멈췄고, 문서에 박고 줄 번호까지 짚어 주자 셋 다 스스로 넘었다(조건도 문서에 있어 그대로
밟았다).

## 회차 절차

1. `sh scripts/dashboard.sh --brief` → 표. 「뒤」≠0 은 **관찰**이지 요청 사유가 아니다(위 4번).
   더티가 오래면 물어본다.
2. 게임별 상세(`dashboard.sh <게임>`)에서 「유저 판정 대기」를 모은다. **규칙이 이미 있는 물음은
   관리자가 닫는다**(자리를 찍어 답한다). 남은 것만 유저에게.
3. 워커가 보낸 메시지를 처리한다 — 유저에게 올릴 것 · 다른 세션에 뿌릴 것 · main 에서 고칠 것.
4. `check-updates.sh` 로 외부 의존물을 본다. 새 버전은 유저 판단.
5. [`manager-log.md`](manager-log.md) 에 회차를 적는다 — 보낸 것 · 받은 것 · 판정 대기 · main 변경.
   로그는 **회차에 한 번** 커밋한다(메시지마다 커밋하지 않는다).
6. main 커밋을 묶는다 → 그 게임이 읽는 공용이 바뀐 세션에만 rebase 요청. 순서가 바뀌면 안 된다.
