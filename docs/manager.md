# 관리자 세션 — 규약 (유저 확정 2026-09-06)

게임 워크트리마다 세션이 하나씩 여덟이 돈다. 사람이 탭을 넘나들며 상태를 모을 수 없어
**관리자 세션 하나**를 main 본 트리에 둔다. 회차 기록은 [`manager-log.md`](manager-log.md).

## 관리자가 하는 일 넷

1. **전 작업을 꿰뚫는다.** 세션 시작 시 여덟 상태 문서(`games/<게임>/docs/*status*.md`)를 다
   읽고, 회차마다 `sh scripts/dashboard.sh` 로 갱신한다. 세션의 busy/idle 은 세션 목록으로 겹친다.
2. **브릿지.** 유저 지시를 해당 세션에 세션 간 메시지로 전달하고, 워커가 올린
   「유저 판정 대기」를 모아 유저에게 한 목록으로 올린다. 답이 오면 다시 뿌린다.
3. **main 관리.** 공용(`shared/`·`scripts/`·`docs/`) 손질, `sh scripts/check-updates.sh` 로
   emucap·스킬·패치 템플릿 갱신 확인. 워커가 낸 공용 문제(문서 오류·정본 불일치)를 main 에서 고친다.
4. **rebase 요청.** main 에 커밋이 쌓이면(dashboard 「뒤 N」≠0) 각 세션에 `git rebase main` 을
   요청한다. 더티면 먼저 커밋하라고 같이 보낸다. 되머지는 아니다(루트 `CLAUDE.md` 「Git 정책」).
   🔴 **main 커밋을 정리한 뒤에만 보낸다**(유저 확정 2026-09-06). 워커가 리베이스하는 순간 그 밑의
   main 커밋은 **굳는다** — 다시 쓰면 여덟 브랜치가 `--onto` 리베이스를 해야 한다(그냥
   `rebase main` 은 옛 main 커밋을 자기 것으로 알고 다시 얹으려다 충돌한다). 그래서 순서는
   ① main 에 커밋 자유롭게 → ② 회차 끝에 같은 유형·작업을 묶는다 → ③ **그 다음** rebase 요청.
   실측 09-06: 메시지 올 때마다 로그를 커밋하고 바로 요청을 보내 로그 커밋 셋이 따로 굳었다.
   ⚠ **꼭 필요할 때만 요청한다**(유저 확정 2026-09-06). 「뒤 N」≠0 자체는 신호가 아니다 — 그
   게임이 **실제로 읽는 공용**(shared 코드 · scripts · 정본 데이터 · 그 게임이 따를 규칙)이
   바뀌었을 때만 보낸다. 관리자 로그·남의 게임 문서·README 따위는 이유가 안 된다. 받아 갈
   것이 없는 리베이스는 워커 토큰만 쓰고 main 커밋을 굳힌다.

🔴 **워크트리는 만지지 않는다.** 파일을 고치면 아홉째 워커가 되어 그 브랜치에서 충돌한다.
워커의 판단을 대신하지도 않는다 — 규칙이 이미 있으면 **그 자리를 찍어 주는 것**까지다
(09-06 실측: pc98 의 「붙임 지명」 물음은 `naming.md` 층 규칙이 이미 답이었다).

## 규약

- **세션 이름 = 워크트리 폴더 이름.** `/rename <게임>`. `+` 도 된다(`ps1-ed3+4`). 관리자는 `manager`.
  이름 하나로 세션 목록과 워크트리 목록이 짝지어진다 — 메시지 수신자도 이 이름이다.
- **유저 판정 대기는 상태 문서의 `## 유저 판정 대기` 절에.** 워커가 못 정하는 것만 둔다.
  `dashboard.sh` 가 이 절 이름은 정확히 잡고, 다른 절(「열려 있는 물음」 등)은 느슨하게 잡는다.
  닫히면 그 절에서 뺀다 — 결정은 `policy.md` 결정 대장으로 옮긴다.
- **이미지는 메시지에 실리지 않는다**(평문만). 스크린샷은 **`.local/inbox/<게임>/`** 에 떨어뜨리고
  「pce 에 넣었다」고만 하면 관리자가 **절대경로**를 찍어 넘긴다(워크트리엔 `.local` 이 없다).
  클립보드 붙여넣기는 디스크에 없어 못 넘긴다.
- **기종 간 발견은 관리자가 검증하고 뿌린다.** 워커 하나의 발견(예: Condensed 한글 전폭 8px)은
  관리자가 공용 자료로 **재확인한 뒤** 해당될 만한 세션에 「참고용, 판단은 네 몫」으로 보낸다.
  틀린 발견을 여덟에 뿌리면 여덟이 흔들린다.
- **메시지 첫 줄은 그 자체로 한 문장.** 받는 쪽 사람은 첫 줄만 미리 본다.
  출처를 머리에 단다 — `[유저 지시, 관리자 중계]` · `[관리자 중계, <세션> 발견 · 참고용]` · `[관리자]`.

## 커밋 (유저 확정 2026-09-06)

**커밋은 자유롭게, 묶은 뒤에 rebase 요청, 푸시는 유저.** main 도 같다 — 관리자가 main 의
주인이다. ⚠ main 은 묶는 시점이 **푸시 전이 아니라 rebase 요청 전**이다 — 게임 브랜치가
얹히면 그 밑은 못 다시 쓴다(위 4번).
유형별로 가른다(`feat`/`docs`/`fix`). 푸시 전에 **인접한 같은 유형·같은 작업**을 하나로 묶어
히스토리를 깔끔하게 한다. ⚠ 경계 둘은 그대로다 — **이미 `origin` 에 올라간 것**과
**게임 브랜치가 그 위에 얹힌 것**은 다시 쓰지 않는다(여덟 브랜치를 강제 리베이스시킨다).
main 을 묶을 수 있는 구간은 「아직 어느 게임 브랜치도 rebase 로 받아 가지 않은 꼬리」다:

    for b in $(git branch --format='%(refname:short)' | grep ^game/); do
      echo "$b $(git merge-base main $b | cut -c1-8)"; done      # 가장 앞선 merge-base 뒤로만 묶는다

푸시는 언제나 유저가 한다.

## 회차 절차

1. `sh scripts/dashboard.sh --brief` → 표. 「뒤」≠0 은 **관찰**이지 요청 사유가 아니다(위 4번).
   더티가 오래면 물어본다.
2. 게임별 상세(`dashboard.sh <게임>`)에서 「유저 판정 대기」를 모은다. **규칙이 이미 있는 물음은
   관리자가 닫는다**(자리를 찍어 답한다). 남은 것만 유저에게.
3. 워커가 보낸 메시지를 처리한다 — 유저에게 올릴 것 · 다른 세션에 뿌릴 것 · main 에서 고칠 것.
4. `check-updates.sh` 로 외부 의존물을 본다. 새 버전은 유저 판단.
5. [`manager-log.md`](manager-log.md) 에 회차를 적는다 — 보낸 것 · 받은 것 · 판정 대기 · main 변경.
   로그는 **회차에 한 번** 커밋한다(메시지마다 커밋하지 않는다).
6. main 커밋을 묶는다 → 그 게임이 읽는 공용이 바뀐 세션에만 rebase 요청. 순서가 바뀌면 안 된다.
