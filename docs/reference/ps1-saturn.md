# PS1 · 세가새턴 기법

PS1(PlayStation 1)과 세가새턴(SS) 한글화 작업에 쓰는 실전 기법 레퍼런스. 폰트 탐색(NO$PSX 디버거 / 루아 스크립트), 팔레트 추출, CD 이미지 섹터 구조, mkpsxiso 빌드, 1bpp→4bpp 폰트 변환 루틴과 고유번호 테이블까지 정리한다. PS1은 현재 작업 타깃(영웅전설)이라 특히 상세히 보존했다.

> 출처: hansicgu 카페

## NO$PSX의 디버거로 폰트를 찾는 방법 (#32114)

- 원문: https://cafe.naver.com/f-e/cafes/16259867/articles/32114
- 도구: NO$PSX 디버거 2.2, HxD, 크리스탈 타일2(CrystalTile2), Notepad++
- 테스트 타이틀: THE ADVENTURE OF PUPPET PRINCESS (마알왕국의 인형공주, NTSC-J)

게임에서 실제 출력되는 글자를 기준으로, VRAM에 그려진 폰트를 역추적해 원본 이미지(ISO/BIN) 내 위치까지 찾아가는 절차다. 압축되지 않은 폰트라는 전제.

### 1) VRAM에서 글자 찾기

1. 폰트가 화면에 보이는 순간, **디버거 창을 활성화(아무 곳이나 클릭)** 해서 에뮬레이션을 멈춘다. (화면 창이 아니라 디버거 창을 눌러야 pause 됨)
2. 디버거 상단 `Window` 메뉴 → **VRAM Viewer**를 연다.
3. `3D/RE` 창으로 넘어가 오른쪽 **트리 구조**에서 폰트 그림이 그려진 노드를 찾는다. 각 글자(예: は, じ)가 트리 항목으로 잡힌다.

### 2) 트리 노드의 폭·높이 값 해석

트리 노드 아래에는 램에 기록될 때의 값들이 나오는데, 마지막 4바이트가 글자 크기다.

- `は` → `0x000C000C` (높이 12, 너비 12)
- `じ` → `0x000C0009` (높이 12, 너비 9 — 실제로 じ가 더 좁음)

즉 마지막 4바이트 = `00 0C 00 0C` 형태의 (height, width). 이 값을 게임이 어디서 가져오는지가 추적 목표.

### 3) MIPS 트레이스 로그 준비

`00 0C 00 0C`가 들어오는 레지스터 전체에 브레이크를 거는 건 비효율적이라, 로그 기능으로 접근한다.

1. 상단 `Options` → `Other` 페이지 → **TTY Debug Message Limit**를 `Overwrite log after 100MB`(또는 `Stop logging after 100MB`)로 설정.
2. `Window` → **TTY Debug Window**를 띄운다.
3. TTY Debug Window 상단 `Enable` → **Log MIPS cpu tracelog** 체크. MIPS 명령 로그가 매우 많이·빠르게 쌓인다(에뮬이 느려질 정도).

로그가 너무 느리므로, 목표 구간 직전 상태를 **스냅샷(강제저장)** 해둔다(예: 메뉴 뜨기 직전). 그 뒤 tracelog를 켠 상태로 스냅샷을 로드하고 바로 디버거 창을 활성화하면, 로그가 쌓인 채로 pause 된다. 에뮬 활성화↔pause를 반복하며 원하는 글자가 뜨는 순간을 잡는다. TTY Debug Window의 **Copy**로 로그를 클립보드에 복사해 Notepad++에 붙인다(수백만 줄 규모).

### 4) 로그에서 크기 값의 출처 역추적

트리 노드 아래 데이터 예시(ほ 기준):

```
CPU.PC:    80014CB0
DMA.Start: 000478CC
DMA.Link:  0004E3B4
---
64808080
008E0085
7910C000
000C000C
```

크기 값 바로 위 4바이트(`7910C000`)를 로그에서 검색 → 여러 곳(3곳)에서 잡힘. 각 히트 5줄 아래에 `r3=000C000C`를 기록하는 동일 프로그램 주소가 보인다.

```
80019648 ACE20010 mov  [r7+10h],r2   ;[8004E3C4], r2=7910C000
8001964C 9562000A movh r2,[r11+0Ah]  ;[1F80000A]
80019650 95630008 movh r3,[r11+8h]   ;[1F800008]
80019654 00021400 shl  r2,10h        ;r2=0000000C
80019658 00621825 or   r3,r2         ;r3=0000000C, r2=000C0000
8001965C ACE30014 mov  [r7+14h],r3   ;[8004E3C8], r3=000C000C
```

`0x8001965C`가 r3(=000C000C)를 쓴다. 그 r3는 `0x1F800008`·`0x1F80000A`에서 온 값을 or 한 것. 즉 이 두 주소에 언제 0x0C가 들어가는지 다시 위로(역순) 검색한다.

```
80033B60 A6270008 movh [r17+8h],r7   ;[1F800008], r7=0000000C
80033B64 A628000A movh [r17+0Ah],r8  ;[1F80000A], r8=0000000C
80033B68 92060006 movb r6,[r16+6h]   ;[800DCF3E]
80033B6C 0C00654A call 80019528h
```

r7·r8은 `0x800DCF58`에서 가져온다. 데이터 윈도우로 `0x800DCF58`을 보면 실제로 `0x0C 0x0C` 값이 들어있다(ほ). 다음 글자 じ는 `0x800DD3A0`에 `0x09 0x0C`.

### 5) 폰트 데이터를 원본 이미지에서 찾기

램에 올라온 폰트가 압축이 아니라면 원본 ISO/BIN에서 그대로 검색된다. 그런데 위 크기 값만으로는 원본에서 안 잡힌다 → **폰트 픽셀 데이터를 써 넣는 구간**을 찾아야 한다.

1. 데이터 윈도우에서 `0x800DCF58`(ほ)·`0x800DD3A0`(じ) 위에 우클릭 → `Break/Watch Window` → **Define Breakpoint** → `[800DCF58]!?` 형태로 **읽기/쓰기 시 멈춤** 브레이크포인트를 건다(두 주소 모두).
2. TTY Debug Window `Flush`로 로그를 비우고, 스냅샷을 로드해 다시 재생하면 로그가 훨씬 짧게(예: 1134줄) 남는다.
3. 마지막 몇 줄에 폰트 픽셀을 쓰는 명령이 잡힌다.

```
800336F4 90820000 movb r2,[r4]      ;[80079356]
800336F8 24850002 add  r5,r4,2h     ;r4=80079356
800336FC A2020020 movb [r16+20h],r2 ;[800DCF58], r2=0000000B
```

`0x800336F4`가 r4(=`0x80079356`) 위치에서 픽셀 값(0x0B)을 읽어온다. 그 주소를 데이터 윈도우로 보면 `80 80 80 8F...` 같은 값이 나오는데, 이런 그라데이션 패턴은 "감"으로 폰트 그림일 가능성이 크다.

4. 이 픽셀 바이트열을 원본 이미지(ISO/BIN)에서 검색 → 잡히면 압축이 아님이 확정. **크리스탈 타일2**로 그 오프셋을 열고 너비·높이를 맞추면 は 등 실제 폰트가 보인다.
   - 글자 사이 노이즈가 끼는 건 PSX 매체(섹터 구조)의 특성 — 원문에서는 상세 생략(디버거 무관 주제).
   - 파일을 추출해서 보면 노이즈 없는 온전한 폰트를 얻을 수 있다.

### 요지

- 만약 원본에서 검색이 **안 되면 압축된 것**이므로, 로그를 거슬러 올라가 압축 해제 직전(압축 원본) 구간까지 추적해야 원본 데이터를 찾는다(원문에서는 압축 케이스는 다음 기회로 유보).
- 이 로그 분석으로 전체 폰트 로딩 구조를 파악하면, 폰트가 부족할 때 프로그램을 수정할 근거가 된다. 단 PSX는 램이 매우 작아 하드웨어적으로 확장이 불가능할 수도 있다.
- 세부 화면은 원문 스크린샷 참조([IMG] 다수).

## [PSX1] 루아 스크립트를 이용한 폰트 및 이미지 찾기 (#32428)

- 원문(카페): https://cafe.naver.com/f-e/cafes/16259867/articles/32428
- 외부 블로그(본체): https://sunlightface.github.io/psx1/루아-스크립트를-이용한-폰트-및-이미지-찾기/
- 도구: PCSX-Redux 에뮬레이터(루아 스크립트 지원)

카페는 마크다운을 지원하지 않아 본문은 위 블로그 링크로 대체된 강좌다. 카페 본문에서 파악되는 요지만 정리(상세 절차·코드는 블로그 참조):

- PCSX-Redux의 **루아 스크립트**로 폰트/이미지를 찾는다.
- 핵심 근거: PS1 하드웨어 구조상 **VRAM에는 DMA를 통해 데이터가 전송**되므로, DMA 전송을 관찰하면 대부분의 게임에서 폰트/텍스처 위치를 잡을 수 있다(모든 게임에 100% 적용되진 않을 수 있음).
- 타일(tile) 방식이 아니라 **텍스처(texture) 방식**으로 이미지를 다루는 게임에 특히 유효(댓글: 타일 방식만 다뤄온 사람에게 도움).

블로그 저자가 예고한 후속 강좌 주제(요지):

1. REST API + 미지원 기능은 루아 스크립트를 **IPC 브릿지**로 이용해 MCP를 구축하는 방법.
2. xref + 동적 호출(callback) 분석으로 미사용 BIOS/SDK 라이브러리 함수를 제거하고 그 자리를 **code cave**로 활용하는 법.
3. **heap tracker**를 만들어 자주 쓰는 크기·래핑 함수를 분석 → 구식 malloc을 최적화해 메모리 단편화를 제거, static buffer로 만들어 남는 공간을 확보하고 **폰트를 확장**하는 방법.

## PS1 팔레트 추출 방법 (#31100)

- 원문: https://cafe.naver.com/f-e/cafes/16259867/articles/31100
- 도구: NO$PSX(https://problemkaputt.de/psx.htm), 크리스탈 타일2
- 원 출처(영문): [Tutorial] How to find PSX palettes — https://www.vg-resource.com/thread-41343.html

그림 파일에 팔레트가 안 보일 때(그래픽과 팔레트가 분리 저장된 경우), VRAM에서 팔레트를 찾아 추출하는 절차.

1. NO$PSX로 게임을 실행하고, 팔레트를 찾고 싶은 그래픽이 화면에 뜨는 지점까지 진행한다.
2. 디버거 → `Window` 탭 → **VRAM/GPU Viewer**를 연다.
3. 우측 항목 ①을 클릭하고, 방향키로 이동해 ②에 찾는 그래픽이 뜰 때까지 스크롤한다.
4. ③ 정보 창에서 **코드 3번째 줄의 4자리**가 팔레트 오프셋이다(예시: `7D80`).
5. `Options` → `Emulation Setup`에서 **SAV/SNA File Format을 Raw로 변경**.
6. `File` → **Write snapshot**으로 상태를 저장(SNA 파일 생성).
7. 크리스탈 타일2로 그 SNA 파일을 연다.
8. 앞서 찾은 팔레트 오프셋을 **×0x20 한 뒤 +0x289070** 한 주소로 이동한다. (예: `7D80` → 실제 SNA 내 팔레트 주소)
9. 해당 위치에 팔레트가 나온다. 주소 시작 부분에서 우클릭 → `DATA` → **팔레트 변환** → 팔레트 **내보내기**.
10. 대상 그래픽 파일을 열어 팔레트 **가져오기** → 정상 색으로 표시됨.

> `×0x20`은 VRAM 오프셋(16bit word 단위)을 바이트 주소로 환산하는 계수, `+0x289070`은 Raw SNA 파일 내 VRAM 영역의 시작 오프셋으로 보인다(원문은 상수만 제시). 세부 화면은 원문 스크린샷 참조.

## 플레이스테이션 디컴파일/컴파일 툴 mkpsxiso (#31986)

- 원문: https://cafe.naver.com/f-e/cafes/16259867/articles/31986
- 도구: mkpsxiso — https://github.com/Lameguy64/mkpsxiso

PS1 게임 이미지를 디컴파일(추출)·컴파일(재빌드)하는 툴 소개. PlayStation homebrew 개발용으로 작성된 ISO 디스크 이미지 메이커다. 상세 사용법은 깃허브 저장소 참조.

일반적인 mkpsxiso 흐름(도구 규약 기준):

- **dumpsxiso**(동봉 도구)로 기존 BIN/CUE를 풀면, 디스크 내 파일들이 폴더로 추출되고 원본 레이아웃을 기술한 **XML(`.xml`)** 파일이 함께 생성된다.
- 추출된 파일을 수정(폰트/텍스트 등 교체)한다.
- **mkpsxiso**에 그 XML을 넘겨 BIN/CUE를 다시 빌드한다. XML에 파일 배치·LBA·오디오 트랙 정보가 담겨 있어 섹터 구조를 재구성한다.
- CDmage처럼 "기존 파일 크기 이내"라는 제약 없이 레이아웃을 다시 계산하므로, 파일 확장·재배치에 유리하다.

> 정확한 커맨드·XML 스키마는 저장소 README가 정본. 본 항목은 카페 원문에 링크만 있고 상세는 없음.

## SS(새턴)과 PS1(플스1) 이미지 파일 구조에 관해서 (#30166)

- 원문: https://cafe.naver.com/f-e/cafes/16259867/articles/30166
- 참고: https://byuu.net/compact-discs/structure (원출처 소멸), https://psx-spx.consoledev.net/cdromdrive/#cdrom-sector-encoding
- 도구: CDmage, 헥스에디터

SS/PS1 BIN 이미지가 왜 헥스에디터 직접 추출과 CDmage 추출이 다른지 — 즉 데이터가 순수 데이터가 아니라 **섹터(2352바이트) 단위**로 부가정보와 함께 기록되기 때문이라는 구조 해설.

### CD 기본

- CD-ROM은 약 333,000개의 섹터로 구성. 오디오 CD는 75섹터 = 1초.
- 데이터 CD(옐로북)는 각 섹터 = **2352바이트**. 이 중 실제 데이터는 **2048바이트(0x800)**.
- 2352바이트 내역(옐로북 Mode 1): 동기화 12 + 실제데이터 2048 + 섹터시작식별 등 + EDC 4 + 예약 8 + RSPC 에러정정 276. ECC 276 = P-패리티 172 + Q-패리티 104.

### 섹터 포맷 (실제 바이트 레이아웃)

**SS (Mode 1):**

```
동기화(12) + 섹터주소(3) + Mode번호(1) + 실제데이터(2048) + EDC(4) + 예약(8) + ECC(276) = 2352
```

**PS1 (Mode 2 / Form 1):**

```
동기화(12) + 섹터주소(3) + Mode번호(1) + 서브헤더(4) + 서브헤더복사(4) + 실제데이터(2048) + EDC(4) + ECC(276) = 2352
```

- 두 경우 모두 파일 데이터는 0x800(2048)씩 쪼개져 섹터마다 들어가고, 섹터당 2352바이트(=0x930) 단위로 기록된다. 어떤 파일이 이미지 어디에 있는지도 섹터 단위로 기록됨.
- PS1은 예약 8바이트 자리에 대신 서브헤더 4 + 서브헤더 복사 4가 들어가는 게 SS와의 차이.

### 헥스에디터로 본 첫 섹터

파일 맨 앞에 나오는 헥스:

```
SS : 00FFFFFF FFFFFFFF FFFFFF00 00020001
PS : 00FFFFFF FFFFFFFF FFFFFF00 00020002 00000800 00000800
```

그 뒤에 실제 데이터 0x800(2048)바이트가 이어진다.

- 앞 12바이트 `00 FFFFFF FFFFFFFF FFFFFF 00` = **동기화 코드**(모든 섹터 동일).
- 다음 섹터주소(3) + 모드(1):
  - SS `00020001` → 00분:02초:00섹터, 모드 01
  - PS `00020002` → 00분:02초:00섹터, 모드 02
  - PS는 이어서 서브헤더 `00000800 00000800`.
- 첫 섹터주소가 150(=2초×75)부터 시작. 오디오 CD의 트랙 앞 2초 침묵 관행이 그대로 적용됨.
- 주소 3바이트 = 분:초:섹터. 섹터 0~~74, 초 0~~59로 순환. `00:02:74` 다음은 `00:03:00`, `00:59:74` 다음은 `01:00:00`.

### 섹터주소 ↔ LBA 관계

- TOC(이미지 앞쪽, 파일이름·위치·크기 기록)에는 파일 위치가 **LBA = 섹터번호 − 150**으로 저장된다.
- 파일의 이미지 내 실제 바이트 주소 = `(섹터번호 − 150) × 0x930` = `LBA × 0x930`.
- 예: 00.000 파일 LBA 129 → `129 × 0x930 = 0x0004A130`이 실제 주소. 시작 섹터번호는 129 + 150 = 279. 그 주소로 가면 동기화 코드 `...FFFFFF00 00035401`(=00:03:54, 모드1 = 3×75+54 = 279)로 일치.
- CDmage는 최종 섹터를 파일에 기록된 값이 아니라 **cue의 트랙 시작점 + 롬파일 크기로 역산**해 표시한다(끝에 더미 2섹터=4704바이트 추가하면 최종 섹터가 정확히 +2 증가함을 실험으로 확인).

### 확장 가능성

- CDmage는 롬/파일 확장 미지원(새 파일이 TOC 기록 크기보다 크면 삽입 불가).
- PS 롬 확장 지원 툴: **PSX-MODE2-EN** — https://www.romhacking.net/utilities/1417/ (Mode2 파일 치환, 메가 단위로 커져도 치환 후 실행 확인. 오디오트랙·cue는 미갱신 → 데이터 트랙만 있는 게임에 유용).
- **TOC_Changer**나 TOC 직접 수정으로 파일당 0~2KB 제한 확장 가능(기존 빈 공간 활용). 게임이 TOC 외 별도 크기 기록을 두면 그것도 모두 수정해야 함(게임마다 다름).
- 직접 롬 확장 실험: PS 롬은 **EDC(4) + ECC(276)를 00으로 채우고** 동기화 코드만 작성해 2352바이트 단위로 확장 후 파일 삽입 → **에뮬에서는 구동 확인**(실기는 EDC/ECC 때문에 안 될 수 있음). SS도 같은 방식 시도 가능성. 동기화 코드는 데이터 2048바이트당 1개 필요하므로 프로그램/엑셀로 자동 생성 권장.

## psx1 브레이브 사가1 폰트 및 고유번호 테이블 (#31968)

- 원문: https://cafe.naver.com/f-e/cafes/16259867/articles/31968
- 대상: 브레이브 사가1 (PS1)
- 도구: 디스어셈블러(IDA 계열 추정), 폰트 변환 코드
- 첨부: `16x16_1bpp패킹 변환 16x12_4bpp.txt`, `브레이브사가 폰트1 tbl.txt` (원문 첨부파일 다운로드 링크)

### 폰트 저장·변환 구조

- 폰트는 **1bpp로 패킹**되어 저장. `SYSDATA.BIN`의 **0xD000**에 **16×16 1bpp**(타일당 32바이트)로 존재. 아래로 더 내려가면 중복 문자(더미이거나 계산용 배치 추정)도 있음.
- 게임은 이를 런타임에 **16×12 4bpp**로 변환해서 사용.
- 실행파일 안에 SJIS 폰트 테이블도 있음(댓글).

### 1bpp → 4bpp 변환 루틴 (MIPS)

`SYSDATA.BIN` 등 다른 롬에도 같은 구조가 있을 수 있어 서브루틴을 보존. 16×16 1bpp(32바이트) 블록을 개수만큼 4bpp로 변환/복구 가능.

루틴 구조(주소는 원 글의 브레이브 사가1 실행파일 기준): 폰트 기준 포인터를 읽어 `글자 번호 × 32` 를 더한 1bpp 원본에서
워드를 하나씩 꺼내, 상위 비트부터(`srl 31`) 한 비트씩 4bpp 니블로 늘려 `sw` 로 쓴다 — 안쪽 8회(비트) × 4회(워드당 출력) × 6회(줄 묶음).
원 글의 IDA 목록은 링크로 본다(원문 코드 보관: `_inventory/code/hansicgu-31968-brave-saga-1bpp4bpp.md`, 로컬 전용).

동작 요약: 1bpp 각 비트(MSB부터 `srl 31`로 추출)를 4bpp 니블로 확장. 안쪽 루프 8회(한 워드의 상위 비트들)×4회×6회 구조로 16×16 타일을 처리. 이 루틴을 참고해 오프라인 변환/복구 코드를 짤 수 있다.

### 고유번호(문자 코드) 테이블

커스텀 고유번호 테이블을 쓰므로 OCR 노가다로 매핑을 만들어야 함(원문 tbl 첨부).

- **1바이트 고유번호:** `00`~`FA`
- **2바이트 고유번호:** 상위 바이트가 `FB`~`FF`일 때 2바이트로 해석. 해당 글리프 폰트 오프셋 계산식:

  ```
  base_addr + ( ((0x100 - 상위1바이트) << 8) + 하위1바이트 ) * 0x60   (16x12 4bpp)
  또는 ... * 0x20                                                   (16x16 1bpp)
  ```

  (타일당 크기: 16×12 4bpp = 0x60=96바이트, 16×16 1bpp = 0x20=32바이트)

- 상위 바이트별 블록:

  ```
  FF: (0x100-FF)<<8 = 0x100 → 0x100*0x60 + 하위    // FF00 ~ FFFF
  FE: (0x100-FE)<<8 = 0x200 → 0x200*0x60 + 하위    // FE00 ~ FEFF
  FD: 0x300 → 0x300*0x60 + 하위                    // FD00 ~ FDFF
  FC: 0x400 → 0x400*0x60 + 하위                    // FC00 ~ FCFF
  FB: 0x500 → 0x500*0x60 + 하위                    // FB00 ~ FB86
  ```

  마지막은 `FB86`까지(댓글로 확인). `F3`~`F6`은 미사용(타일에서도 빈 공간).

- **제어 문자 코드:**

  ```
  0xFA  상태 변경 (보통 종료)
  0xF9  줄바꿈
  0xF8  입력 대기
  0xF7  지연(delay)
  ```

- 대사 위치는 대부분 **`EVENTGRP.bin`**에 존재. 텍스트 포인터 구조는 추가 디버깅 필요(원문·댓글 기준 미해결).

## PS-EXE 에서 「빈 자리」를 고르는 법 — 0런은 빈 자리가 아니다 (우리 발견 2026-08-27)

문자열이 원래 칸보다 길어 못 넣을 때, 흔한 해법은 **빈 자리에 옮기고 참조를 돌리는 것**이다.
PS1 실행파일에서 그 「빈 자리」를 잘못 고르면 **오프닝 뒤 검은 화면**으로 죽는다. 실제로 물렸다.

### 헤더가 알려 주는 것과 안 알려 주는 것

`PS-X EXE` 헤더(선두 0x800B):

| 오프셋          | 뜻                                                                       |
| --------------- | ------------------------------------------------------------------------ |
| `0x10`          | 시작 PC                                                                  |
| `0x14`          | `gp0` — ⚠ **0 인 빌드가 흔하다**(그러면 `$gp` 는 코드가 런타임에 세운다) |
| `0x18` / `0x1C` | text 로드 주소 / 크기 (**파일 0x800 부터가 text**)                       |
| `0x20` / `0x24` | data 주소 / 크기                                                         |
| `0x28` / `0x2C` | **bss 주소 / 크기**                                                      |
| `0x30`          | 초기 SP                                                                  |

🔴 **`bss` 가 `0x0 +0x0` 인 빌드가 많다**(실측: 『영웅전설 1+2』 PS1 의 `ED.EXE`·`ED2.EXE` 둘 다).
그러면 **0 으로 초기화된 전역이 TEXT 안에 그대로 실려 있다.** 즉 **파일에서 0 이라고 안 쓰는
자리가 아니다** — 링커가 0 으로 채워 둔 **전역 변수**일 수 있고, 거기에 문자열을 쓰면
프로그램이 제 변수를 밟는다.

### `$gp` 창이 위험지대다

MIPS 는 전역을 **`$gp` 상대**로 읽는다(`lw $v0, offset($gp)`, 오프셋 ±32KB). 그래서:

- `$gp` 를 세우는 자리를 찾는다 — `lui $gp, hi` + `addiu $gp, $gp, lo` 를 디스어셈블로 찾는다
  (헤더 `gp0` 가 0 이면 이 방법뿐이다).
- **`[$gp−32KB, $gp+32KB]` 안의 0런은 전역 변수 구역으로 의심한다.**

🔴 **역설이 하나 있다.** 참조를 돌릴 때 `addiu` 하위 16비트만 고치고 `lui` 를 안 건드리려면
새 주소가 **같은 창** 안이어야 하는데, **그 창이 바로 `$gp` 위험지대**다. 창 밖으로 나가려면
`lui` 까지 고쳐야 하고, 그러면 그 `lui` 를 **다른 `addiu` 와 공유**하는지 먼저 봐야 한다.

### 그래서 검증은 이렇게 한다

1. **`$gp` 창 밖인가** — 위 방법으로 `$gp` 를 구해 확인한다. (오늘 실패는 이 한 줄이 없어서다)
2. **`lui` 없는 접근이 있나** — GP 상대 접근은 `lui` 가 없어 **포인터 스캔에 안 보인다.**
   베이스 레지스터가 `$gp`(r28)이고 오프셋이 대상 범위인 명령을 따로 센다.
3. **알려진 블롭 내부가 아닌가** — 사운드 뱅크(VAB)·포인터 표 등. `docs/patcher-checklist.md`
   「0 으로 차 있다고 빈 공간이 아니다」 항목과 같은 검사다.
4. **원문을 지우지 않는다** — 참조만 돌리고 원문 바이트는 제자리에 둔다. 못 본 경로가 그
   자리를 읽어도 **원문이 나올 뿐 안 깨진다.**
   ⚠ 단 이건 **읽는 쪽**만 지킨다 — **쓰는 쪽**(남의 변수 자리에 쓰는 것)은 못 막는다.
   오늘 사고가 정확히 그것이었다.

### 표를 통째로 옮기는 건 더 위험하다

같은 게임에서 224B 이름 표를 통째로 재packing 했다가 **맵 배경이 통째로 검게** 나갔다.
그 표가 **`$gp` 기준점 위**에 앉아 있었고(`$gp = 표−8`), 표 안에 `sh`/`lh` 로 읽고 쓰는
**변수**까지 섞여 있었다. 이름 25개가 전부 `lui`/`addiu` 로 참조돼 「참조 0건 0」 이었는데도
그랬다 — **「참조가 다 있으니 옮겨도 된다」가 여기서 깨진다.**
