# PSP · 휴대기기(GB/GBC/GBA/NDS) 기법

PSP와 휴대용 콘솔(게임보이/컬러/어드밴스, 닌텐도 DS) 한글화에서 쓰이는 기법을 카페 강좌 원문에서 정리한 레퍼런스다. PSP는 이 프로젝트의 로드맵 타깃이며, GB·GBC·GBA·NDS 항목은 플랫폼을 넘어 전이 가능한 범용 기법(VRAM 타일 적재, 포인터 규칙, 압축 스트림 탐색, 언팩/리팩 환경, 기드라 분석 흐름) 위주로 담았다. 각 항목은 원문 링크·도구·구체 절차를 보존한다.

### PSP 내장폰트 게임 롬내 폰트추가 (EBOOT 수정X) (#30420)

- 원문: https://cafe.naver.com/f-e/cafes/16259867/articles/30420
- 도구: UMDGEN, PPSSPP(콘솔로그·역어셈블리), Ghidra + allegrex 플러그인

PSP 펌웨어(내장) 폰트를 쓰는 게임을, EBOOT를 손대지 않고 디스크(UMD) 안의 커스텀 폰트를 불러오게 우회하는 두 가지 방법.

**방법 A — 호출 뺏어오기(플러그인 삽입) 타입**
- 첨부(USRDIR.7z)의 `hansicgu.prx`(중국의 오래된 `fontfuck` 플러그인 기반)와 `jpn0.pgf`(일본어폰트+한글이 추가된 일명 "몬헌폰트") 두 파일을 `PSP_GAME\USRDIR` 내부에 넣는다.
- 이 두 파일이 USRDIR에 있으면 내장폰트 대신 해당 `jpn0.pgf`를 가져온다. UMDGEN으로 삽입.
- 검증: PPSSPP 콘솔로그에서 `font/zh_gb.pgf`를 가져오려 한 흔적을 확인하고, 디버그 → 역어셈블리 → 하단 Modules에 `fontfuck` 모듈이 존재하는지 확인.
- 한계(댓글 검증): PPSSPP에서는 잘 되지만 실기(PSP 실기)에서는 prx 유무와 무관하게 이 단순 복붙 방식이 동작하지 않는 사례가 보고됨. 실기용은 피스워커 한패처럼 `fontfuck`을 원래 있던 `libfont.prx`(fontlib) 파일로 대체하는 형태가 필요할 수 있음.

**방법 B — 원본 모듈에서 폰트 지시 위치를 돌려버리기(재서명, 신규)**
- kirk 코드가 해독되어 서명 관련 부분이 해결되었기에, 원본 모듈이 폰트를 가리키는 위치 자체를 수정한 뒤 재서명하여 사용 가능.
- Ghidra + allegrex 플러그인으로 `libfont.prx`를 수정(MIPS 문서 참고).
- 첨부(hansicgu.7z): `jpg0.pgf`는 `PSP_GAME\USRDIR`에 넣고, 수정된 `libfont.prx`는 기존 `libfont.prx`를 대체해서 넣는다.
- 내장폰트 게임인데 `libfont.prx`가 없으면, 암호화를 풀었을 때 다른 이름이거나 다른 모듈에 함께 로드되는 경우가 있음. `sceFont_Library`를 찾은 다음 `~SCE`부터 바이너리째로 넣는 방식(추정).
- 실기에서 정상 전환 확인.

**추가 팁 — 인코딩별 한글 삽입**
- 유니코드를 쓰는 게임은 한글을 바로 출력 가능.
- Shift-JIS를 쓰는 게임은 타 콘솔처럼 테이블 작업이 필요: 한자 영역 내 `亜`부터의 영역에 한글을 추가하는 테이블화 작업. 이미지(폰트) 작업은 위 폰트로 이미 되어 있으니 테이블만 만들면 됨.
- 높은 확률로 디스크 내에 `jis2ucs.bin` 파일이 포함되어 있음. 기존 한자 영역 부분 대신 한글을 넣고 1:1 매칭 테이블을 만든 뒤 그 테이블로 번역을 진행.

심화편(참고): https://cafe.naver.com/hansicgu/30454 — PSP 내장폰트 전환 PRX 분석 및 과정 심화.

### PSP 테일즈 오브 판타지아 — top.prx 내 하드코딩 파일 추출 (#29122)

- 원문: https://cafe.naver.com/f-e/cafes/16259867/articles/29122
- 도구: Python 스크립트 + comptoe 라이브러리(https://github.com/lifebottle/comptoe)

게임 실행 모듈(`top.prx`) 안에 하드코딩(별도 파일 아님)으로 박혀 있는 압축 리소스를, 압축 스트림 시그니처를 브루트포스로 스캔해 찾아 추출하는 기법.

**압축 스트림 헤더 포맷(9바이트)**
- 압축형식: 1바이트 — `1` = LZSS, `3` = LZSS+RLE
- 압축된 크기: 4바이트 (little-endian)
- 원래 크기: 4바이트 (little-endian)

**스캔 절차(SearchPRX)**
- 파일 처음부터 offset을 1씩 증가시키며(스트림 크기만큼 점프하지 않는 단순·비효율 방식) 각 위치의 첫 바이트가 `1` 또는 `3`인지 검사.
- 그 뒤 4+4바이트를 압축크기/원본크기로 읽어 후보 필터링: 압축크기 < 원본크기, 압축률 100배 이내(`압축크기*100 > 원본크기`), 압축크기 > 0, 1MB(1000000) 미만, 파일크기 미만.
- 후보를 `comptoe.Decode`로 압축해제 시도. 해제 결과 길이가 원본크기 ±4 범위에 들면 유효로 간주해 덤프.
- TIM(그래픽) 여부를 판별해 확장자/파일명 분류(`isTimData`). TOP에서는 약 400개 파일이 추출되며, 그 안에 요청된 Font1의 다른 버전, TIM 그래픽, 1비트 그래픽(512바이트, 카드 그림 등)이 포함됨. 폰트가 아니라 그래픽으로 한글화해야 하는 파일들이 섞여 있음.

**LZSS+RLE 개념(댓글 정리)**
- 이중압축이 아니라 LZSS와 RLE를 "동시에 쓰되 규칙이 서로 겹치지 않게" 혼합한 형태. 트라이에이스(TOP) 계열 실사례로 확인됨.
- comptoe의 `PrepareVersion`에서 version 1은 `F=0x12`, version 3은 `F=0x11`로 윈도우 파라미터가 갈리고, Decode에서 RLE를 항상 사용(version 3)/조건부 사용(version 1)의 차이가 핵심. 해외 TOP 작업자들이 정의한 용어가 그대로 쓰여 혼란이 있었던 것.
- 주의(댓글): 일부 기술명(예: `リンゴ乱舞`)은 `top.prx`에서 검색되지 않아, 별도로 압축된 채 박혀 있을 수 있음. 14×14 폰트로 렌더되는 텍스트라도 이런 압축 데이터에 숨어 있을 수 있음.

### 기드라로 vita eboot.bin 분석 (#31607)

- 원문: https://cafe.naver.com/f-e/cafes/16259867/articles/31607
- 도구: Ghidra(최신), VitaLoaderRedux-1.08, vita3k 에뮬레이터
- 대상: PS Vita eboot.bin. 실행 모듈을 기드라로 여는 흐름 자체는 PSP 등 다른 플랫폼 실행파일 분석에도 전이 가능.

Vita 게임의 실행 영역(`eboot.bin`)은 한글화에 필수 분석 대상. 요즘 vita3k에서 구동되는 `eboot.bin`은 인크립트(암호화) 상태로, 디크립트본보다 용량이 작고 열어도 대사·UI 문자열이 보이지 않음.

**1) eboot.elf 확보(디크립트)**
- vita3k 실행 → 설정 → 설정 → debug에서 **ELF dumping** 활성화.
- 게임 실행(예: 패치·DLC 모두 적용한 상태). 실행과 동시에 vita3k가 `eboot.bin`을 해독해 `eboot.elf`를 생성.
- 결과물은 vita3k 설치 폴더에 새로 생기는 `elfdumps` 폴더 안에 `eboot.elf`와 함께 `libc`, `libfios2`, `libSceF2`, `libpvf` 등 라이브러리 elf가 같이 나옴.

**2) 기드라에 로더 설치**
- VitaLoaderRedux-1.08 압축해제 → `dist` 안의 압축파일이 실제 익스텐션.
- 기드라 File → Install Extensions → `+`(Add extension) → 해당 파일 선택 후 설치, 기드라 재시작.

**3) 분석**
- 기드라 batch import로 정리된 elf 파일들을 모두 불러온 뒤 `eboot.elf`를 더블클릭해 오토 분석.
- 첫 착수점: 좌측 중앙 Symbol Tree의 filter에 `start`를 검색해 최초 실행 함수를 찾는다.

### GBC VRAM에 원하는 타일을 올려보기 (#24193)

- 원문: https://cafe.naver.com/f-e/cafes/16259867/articles/24193
- 도구: GB 에뮬레이터 디버거(액세스/on-write 브레이크포인트, BG map·VRAM viewer), 헥스 에디터

폰트 확장이 아니라, "원하는 VRAM 위치에 원하는 타일을, 필요한 순간에 강제로 그려넣는" 범용 기법(예시는 드퀘몬2 순정 일판 롬). 원본 타일 로딩 루틴에 훅을 걸어 자체 코드를 덧붙이는 방식.

**1) 새 타일 준비**
- 롬의 빈 공간에 올릴 이미지를 GB 2BPP로 그림(예: 8글자 = 80바이트).
- 배치 주소 예 `3CC000` → 참조 오프셋 `(3CC000 mod 4000) + 4000 = 4000`, 뱅크 번호 `3CC000 / 4000 = F3`.

**2) 타일이 올라가는 순간 포착**
- 인게임에서 대상 타일이 VRAM `8A40`부터 그려짐을 확인. 정확도를 위해 다음 타일 주소 `8A50`을 기준으로 사용.
- 디버거 액세스 브레이크포인트에 `8A50`을 **on write**로 추가 후 리셋 → VRAM에 타일을 쓰는 코드에서 멈춤.
- 그 루틴에서 `ret`를 검색해 리턴 지점에 BP를 걸고 F9로 진행, BP 해제 후 F7로 한 줄 실행하면 호출자(예: `0C59`)로 빠져나옴 → 여기가 타일 로딩을 유발하는 지점.

**3) 훅 코드 삽입(빈 공간 CALL)**
- 호출자의 원래 로딩 호출을 빈 공간(예 `3F60`) CALL로 교체. `3F60`에서:
  - 먼저 원래 로딩 루틴(`0C59`) 콜(할 일 다 하고 오게 함).
  - `push`로 레지스터 보존.
  - `bc` = 새 타일 크기(80바이트), `de` = 새 타일 주소, `hl` = 써 넣을 VRAM 시작 위치(`つ` 위치부터).
  - 실제 복사 루틴(`3FA0`) 호출 후 `pop`으로 복원, `ret`로 아무 일 없던 듯 복귀.
- 복사 루틴 `3FA0`:
  - `DI`(인터럽트 비활성).
  - 현재 참조 뱅크 저장(이 게임은 모든 뱅크의 0 위치에 뱅크 번호를 매겨 둠 — 게임마다 다를 수 있음).
  - 새 타일의 `F3` 뱅크로 전환.
  - **VRAM에 쓰기 가능한 상태인지 검사**(이 검사가 없으면 쓸 수 없는 타이밍에 write되어 깨진 글자가 올라감 — 핵심 함정).
  - `de`(새 타일) → `hl`(VRAM)로 복사하며 `bc`를 1씩 감소, `bc`==0이면 종료.
  - 저장해둔 뱅크 번호를 `pop`해 원복, `EI`로 인터럽트 활성 후 리턴.

**4) 인게임에도 유지시키기**
- 인게임 진입 시 다시 `8A50` on-write가 걸리며 원본이 일본어 타일을 또 그림(다른 호출자, 예 `0CE5`). 위와 동일하게 `0CE5`의 호출을 빈 공간 CALL로 바꾸고, `0CE5` 실행 후 `3FA0`을 실행하는 같은 양식으로 처리.
- 그 결과 새 타일이 유지되며 기존 메뉴 텍스트가 깨질 수 있는데, BG map에서 타일 넘버를 확인해 헥스 에디터로 해당 타일 배열 데이터를 찾아, VRAM viewer의 새 타일 번호로 재배열해 화면을 맞춤.
- 이 방식으로 한 번에 여러 군데 타일도 수정 가능. 필요한 만큼 필요한 순간에 원하는 타일을 그려넣을 수 있음.

### GBC 타이틀 로고 수정하기 (#31046)

- 원문: https://cafe.naver.com/f-e/cafes/16259867/articles/31046
- 도구: GB 에뮬레이터(BGB 등)의 VRAM 덤프·VRAM viewer, 헥스 에디터
- 대상: GBC 타이틀 로고(BG 타일 + 팔레트 + OAM 스프라이트 조합). 예시는 드퀘몬.

타이틀 화면 로고를 깔끔하게 바꾸려면 BG 타일뿐 아니라 팔레트와 OAM(스프라이트)까지 함께 손봐야 함.

**절차**
- 타이틀 화면을 띄운 상태에서 **BG 타일 VRAM 덤프**(`$8800 ~ $9800`)를 떠서 입맛에 맞게 수정.
- 수정한 타일을 롬의 빈 공간에 붙여넣음. 패턴(순서)을 맞춰 넣으면 map 재정렬이 불필요하고, 안 맞추면 map을 다시 정렬하는 수고가 필요.
- **OAM에 쓰인 스프라이트 타일 덤프**(`$8000 ~ $8100`)도 수정. 이 게임은 OAM 데이터를 WRAM 어딘가에 박아두었다가 한 번에 `$FE00`에 적용하는 구조 → 그 지점을 찾아 OAM 데이터의 포인터와 데이터를 수정하면 필요한 타일로 잡티(팔레트가 튀는 부분) 제거 가능.
- `$9800`부터 팔레트를 적용하는 부분을 찾아 팔레트도 입맛대로 수정.
- 타일 교체 + 팔레트 교체 + OAM 수정을 모두 마치면 완성. (5년 전 무식하게 타일만 건드린 결과물 대비, 팔레트·OAM까지 손봐야 깔끔한 결과가 나옴.)

## GBA

### GBA 한글화 기초 지식 (#27717)

- 원문: https://cafe.naver.com/f-e/cafes/16259867/articles/27717
- 도구: GBA 에뮬레이터 디버거(브레이크포인트), 헥스 에디터

메모리 맵·포인터 규칙·압축(lz77) 브레이크 트릭 등 GBA 한글화 착수에 필요한 기초.

**메모리 맵 / 포인터 규칙**
- 게임팩 ROM(Read-only) 영역 최대 32MB. ROM 주소 범위: `08000000 ~ 09FFFFFF`.
- 포인터는 보통 4의 배수 주소에 존재. 데이터 값은 보통 little-endian.
- ROM이 대개 16MB를 넘지 않아, 절대 포인터를 찾을 땐 `3, 7, B, F`로 끝나는 주소의 값이 `08`이 됨. 즉 포인터는 주소 끝자리가 `0, 4, 8, C`인 위치부터 시작하는 4바이트 값. (32MB일 때 16MB 초과분 포인터는 `09`로 시작.)
- 일부 예외 제외하고 절대 포인터는 `08000000 ~ 09FFFFFF`를 가리킴. (예외로 `0A000000 ~ 0DFFFFFF`를 가리킬 수 있으나, `0A~0B`, `0C~0D` 구간의 값 자체는 `08~09`와 동일 = 미러.)

**포인터 계산 예시**
- 파일 오프셋 `0x0E6F24`의 대사 `かつやくのあと` → 메모리 주소 `0x080E6F24` → little-endian `[24 6F 0E 08]`. 이 4바이트가 기록된 곳이 포인터 위치(`0x0E6F14`).
- `0x0E6F34`의 `はじめから` → 포인터 값 `[34 6F 0E 08]`, 포인터 위치 `0x0E6F0C`.

**CPU / 화면 영역**
- CPU: ARM7TDMI. 보통 THUMB 명령어(2바이트) 사용(ARM 명령어는 4바이트). 편하게 계산 가능한 레지스터는 `r0, r1, r2, r3`.
- ROM의 모든 내용은 명령어 아니면 데이터.
- 화면을 결정하는 영역: `05000000-050003FF`(BG/OBJ Palette RAM), `06000000-06017FFF`(VRAM), `07000000-070003FF`(OAM). 이 영역에 쓸 땐 보통 `swi #0x0b`(CPU Set), `swi #0x0c`(CPU Fast Set)를 사용.

**lz77 압축 이미지 위치 잡기(브레이크 트릭)**
- HEX 값 `[11 DF 70 47]`(명령어 `swi 0x11` / `bx lr`)을 찾아 브레이크를 걸면 lz77 압축 해제 직전에 멈춤 → 이때 `r0` 값이 lz77 압축 이미지 위치.
- 예: `r0 = 0x086ada44`이면 ROM 파일 상 `0x6ada44`에 lz77 압축 그래픽이 존재.

## NDS

### NDS 한글패치 작업 공간 구축(unpack/repack, 배너 한글화) (#32283)

- 원문: https://cafe.naver.com/f-e/cafes/16259867/articles/32283
- 도구: NDSWorkSpace(첨부, ndstool 기반 `.bat`), CrystalTile2, NDS_Banner_Editor(첨부), MelonDS/실기(확인). 댓글 추천: TinkeDSi(https://github.com/R-YaTian/TinkeDSi).

NDS 롬을 손쉽게 언팩/리팩하는 환경을 갖추고, 메타데이터(게임 코드 + 한국어 배너)를 한글화하는 절차. 예시는 제노사가.

**작업 공간(unpack/repack)**
- 첨부 NDSWorkSpace.zip을 폴더째 풀고 같은 경로에 대상 롬을 `originROM.nds`로 배치(다른 이름이면 `unpackNDS.bat`/`repackNDS.bat` 안의 `-x originROM.nds`를 수정).
- `unpackNDS.bat` 실행 → nds 내부 파일들이 쏟아져 나옴. 한글화는 주로 `DATA` 폴더 안 파일을 편집.
- `repackNDS.bat` 실행 → 원본 형태로 리빌드(첨부는 결과물 이름이 `Xenosaga12_rebuilded.nds`로 나오므로 `.bat`를 notepad++ 등으로 열어 출력 파일명 수정).

**메타데이터 한글화 — (1) 게임 코드**
- `header.bin`을 헥스 에디터(인코딩 ANSI)로 열어 게임 코드의 지역 문자(예 U/J)를 `K`로 수정(예 `AXSJ → AXSK`).
- `repackNDS.bat`으로 ROM 리빌드.
- 리빌드된 ROM을 CrystalTile2로 열어 도구 → 파일 시스템 정보 → 편집 → **CRC 체크** 누르고 저장(액세스 날짜조차 안 바뀌고 알아서 저장됨).
- CRC가 수정된 롬을 CrystalTile2로 언팩해 바뀐 `header.bin`을 꺼냄. (보통 NDSWorkSpace를 하나 복사해 그쪽에서 꺼내 원래 작업 폴더로 가져옴.)

**메타데이터 한글화 — (2) 배너(한국어 배너)**
- 정식 발매작은 갖춘 데이터로, 게임 정보를 읽을 때 한글로 뜨게 하는 부분. 인터넷의 유사 툴 대부분은 한국어 배너를 지원하지 않으나 첨부 NDS_Banner_Editor는 지원.
- NDS_Banner_Editor 실행 → `banner.bin` 열기 → Korean 항목에 한글 게임명·개발사 입력.
- 우하단 **Version은 반드시 `0x0003 - Korean DS`로 설정**.
- 저장해 `banner.bin` 갱신 후 `repackNDS.bat`으로 리빌드. 한국어 배너 표시는 MelonDS 또는 실기로 확인.
