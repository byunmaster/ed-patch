# 콘솔·일반 작업후기

PS1·PS2·세가새턴·PSP·PC엔진 및 언리얼 엔진 등 다양한 플랫폼의 한글화 작업후기·구현기를 정리한 레퍼런스다. 자막 시스템을 저사양 하드웨어에서 어떻게 구현했는지, 내장폰트를 우회하는 절차, 폰트 데이터의 위치를 찾는 방법, 대사가 씹히는 원인과 해결, 디스크·EXE 분석에서 알아낸 구조와 주소를 재현 가능한 형태로 요약했다. 각 항목은 카페 원문 본문과 댓글의 알짜 정보만 반영했으며, 이미지로만 설명된 부분은 텍스트로 확인 가능한 범위만 옮겼다.

## PS1·PS2

### PS1 발키리 프로파일 실메리아 필수 분석 (#32823)

- 원문: https://cafe.naver.com/f-e/cafes/16259867/articles/32823
- 도구: 자체 언패커(리소스 구조 자동 구축)

기법·발견:

- 실메리아는 디스크 이미지를 그냥 열어보면 리소스가 보이지 않는다. 리소스에 몇 겹의 암호화가 적용되어 있어, 텍스트만 추출하는 수준을 넘어 온전한 언패킹이 필요하다.
- 단순 추출이 아니라 리소스 구조 자체를 분석해 자동으로 재구축하는 방식으로 접근했다. 이 과정을 거치면 텍스트 패키지 내부의 글립(폰트 글자 이미지)을 추출·출력할 수 있다.
- 결론: 실메리아는 한글화가 기술적으로 가능(핵가능)하다는 수준까지 분석 완료. 남은 것은 자질구레한 의미 분석 정도이며 필수 구조 분석은 끝났다. (작성자는 실제 한글화 착수 의사는 없음 — 번역·이미지 작업 부담 때문.)
- 참고: 발키리 프로파일 1편은 이미 별도로 한글화가 진행되어 제보가 잦아든 상태.

  리버싱해 **한글 전각 · 공백 반각**을 구현했다. (우리 `krwrap` 의 반각 부호 0.5슬롯과 같은 계열)

  글자를 하나씩 맞춰 고쳤다. 다른 폰트로 바꾸면 깨지는 자리가 또 생겨서 갈무리를 기준으로 삼음.
- 작은따옴표가 **어퍼스트로피일 때와 인용부호일 때 모양이 달라 보여** 여러 번 고쳤다.
- **문화 참조는 옮기지 않고 바꿨다** — 일본 옛 방송·유명인 개그는 직역하면 한국어로 아무
  재미가 없어서 같은 분위기의 한국 표현으로 갈았다. 음차로 남긴 이름은 영문판 현지화를 참고.

### PS1 건퍼레이드 마치 독음 패치 시도 [해결] (#32298)

- 원문: https://cafe.naver.com/f-e/cafes/16259867/articles/32298
- 도구: HxD, BMS(폰트 압축/분해 도구), 구글드라이브 공유 분해 프로그램

기법·발견:

- 폰트 교체 절차: 수정한 폰트 데이터를 HxD에서 Ctrl+A로 전체 복사 → 원본 FONT.BIN에서 Ctrl+G로 주소 입력창을 열고 오프셋 `72`로 이동 → 붙여넣기 후 저장. 이때 기존 파일과 크기가 다르다는 경고(용량이 작거나 큼)가 떠도 계속 진행한다.
- 최초 실패 원인: 원래 한자가 놓이는 위치가 아닌 엉뚱한 위치에 한글 독음 테이블을 그대로 박아 넣어서 게임에서 텍스트가 출력되지 않았다(음악만 흐름).
- 조언에 따른 올바른 접근: 독음 폰트가 아니라 **SJIS 형태(축약형 shift-jis 테이블)**를 기준으로 폰트 작업을 다시 해야 한다. 폰트가 출력되는 구조 자체를 SJIS 코드포인트에 맞춰야 게임 루틴이 글자를 찾는다.
- 어느 글자가 어느 SJIS 코드에 대응하는지 찾는 실전 팁: 게임에 나오는 특정 한자(예: `亞`)를 아무 한글로 바꿔 넣고, 화면에 출력되는 문자열(예: `１９４５年`)을 텍스트 형태로 검색해 그 자리를 `亞亞亞亞亞`로 교체해 보면, 어느 코드가 화면 어디에 찍히는지 감을 잡을 수 있다.
- 해결: 실제 막힘의 직접 원인은 **붙여넣기 실수**(1번 원본 파일에 3번 파일을 잘못 붙여넣음)였다. 첨부 파일을 올바로 조합해 테스트하니 한글 출력이 정상 동작.
- 추가 발견: 대사 텍스트는 `EVDATA.BIN` 파일에 들어 있으나, 제어코드와 오프셋 구조는 한눈에 파악되지 않는다.

### PS2 령(제로) 제로3 자막 시스템 구현 (#31273)

- 원문: https://cafe.naver.com/f-e/cafes/16259867/articles/31273
- 도구: 코드 후킹, GS/DMA 직접 제어, PCSX2(검증), 실기(PS2 9만번대)

기법·발견:

- 제로3(제로 ~~문신의 소리~~)는 판본별로 자막 처리가 다르다. 베이스인 **일어판은 컷신 대사에 자막이 없고**, 북미판(영어 음성)도 자막이 없다. **유럽판만 별도 자막 시스템이 구현**되어 있다. 흥미롭게도 일어판 코드에도 (사용되지 않을 뿐) 이 자막 시스템 코드가 일부 남아 있다.
- 선택: 유럽판으로 베이스를 바꾸는 대신 **일어판에 자막 시스템을 직접 구현**. 이유는 (1) 유럽판에도 자막이 없는 요소(전투 중 원령 대사 등)까지 자막을 넣을 수 있고 — 이는 옵션 ON/OFF 제공, (2) 영상·음성 이식 없이 패치 용량을 1GB 급에서 수 KB로 줄일 수 있기 때문.
- 폰트: 별도 폰트를 넣지 않고 **VRAM에 상주하는 원본 시스템 폰트를 그대로 재사용**하되 크기만 축소해서 자막 글자로 씀.
- 구현 방식:
  1. **프레임 버퍼 스왑 직후의 코드를 후킹**하여 매 프레임 원하는 코드(자막 그리기)를 실행.
  2. **음성·영상 파일을 읽는 파일 로드 루틴도 후킹**해, 특정 파일이 읽히는 시점을 캐치 → 어떤 컷신/음성이 재생되는지 식별.
  3. 그 시점에 대응하는 **자막 데이터를 파싱**해 텍스처를 생성.
  4. **GS(그래픽 신시사이저)에 그리기 위한 태그들을 DMA로 전송**해 자막 텍스처를 화면에 합성.
- 남은 과제: 출력 도중 일시정지(메뉴 열기 등) 처리, 특정 상황에서 알파 블렌딩 텍스처가 제대로 출력되지 않는 문제. PCSX2는 에뮬레이션 부정확성 때문에 실기 테스트가 필수라고 판단.

### 윙키소프트의 슈퍼로봇대전 폰트 정리 (#32497)

- 원문: https://cafe.naver.com/f-e/cafes/16259867/articles/32497
- 도구: 헥스 에디터(폰트 뷰어로 폰트 크기 지정하여 확인)

기법·발견:

- 윙키소프트 슈퍼로봇대전 PS1 시리즈들의 폰트 파일 구조를 비교해 TBL(코드↔글자 테이블) 공유 가능성을 정리:
  - **2차**: `SLPS_024.06`
  - **3차**: `SLPS_025.30`
  - 2차·3차·EX는 **오프셋 시작점만 다를 뿐 한자 배열(순서)이 동일**. → TBL이 100% 같진 않아도 한자 순서만 맞추면 서로 이식·공유 가능.
  - **F / F 완결편**: 2-3-EX와 유사하게 시작하지만 뒤쪽이 조금 달라짐(공백 크기가 다르고, 큰 줄기는 같으나 중간중간 차이). F와 F 완결편끼리는 동일.
  - **4차**: 폰트가 `STAYDAT.BIN`에 들어 있고 한자 순서가 달라짐. 폰트를 볼 때 **8x16 크기로 지정**해야 제대로 보임(신 슈퍼도 동일).
  - **신 슈퍼 / 4차**: 8x16을 쓰며 배열이 완전히 달라 다른 게임들과 공유 불가.
- 결론: 2차 작업 시 3차·EX까지 세트로 재사용 가능, F·F 완결편은 부분적으로 도움, 4차·신 슈퍼는 새로 작업.
- 컴플리트 박스셋: 폰트 파일 하나로 3개 게임을 관리. 로봇 사전·전투 메시지는 3개 게임이 공유하고 시나리오 대사만 게임별로 별도.
- 댓글 보강(SFC 4차 참고): SFC판 4차는 **8x16 폰트가 1바이트 코드(00~EF), 12x16 폰트가 2바이트 코드(F0 00 ~ F5 FF)** 할당. SFC를 PS1으로 거의 그대로 이식했으므로 코드 체계가 크게 다르지 않을 것으로 추정 → SFC 대사의 PS1 이식 가능성 시사.

### PSP EXIT — 내장폰트 우회 (#31581)

- 원문: https://cafe.naver.com/f-e/cafes/16259867/articles/31581
- 도구: UMDGen, 010 Editor, PPSSPP(해독 EBOOT 덤프), 그미래님의 `libfont.prx`, 몬헌 `jpn0.pgf`

기법(재현 절차) — PSP 자체(시스템) 폰트를 쓰는 게임에 원하는 폰트를 넣기 위한 내장폰트 우회:

1. 원본 ISO를 UMDGen으로 불러온다.
2. `File > FILE LIST > EXPORT`로 **원본의 LBA 값을 파일로 저장**(나중에 그대로 IMPORT해서 파일 배치를 복원하기 위함).
3. `PSP_GAME/USRDIR/module/libfont.prx`를 **그미래님 배포 `libfont.prx`로 교체**(내장폰트 우회 커스텀 라이브러리). "교체하시겠습니까"에 YES.
4. `File > FILE LIST > IMPORT`로 앞서 저장한 LBA 값을 다시 불러온다.
5. `PSP_GAME/USRDIR`에 **몬헌용 `jpn0.pgf` 폰트 파일**을 넣는다.
6. 다시 `File > FILE LIST > IMPORT`로 LBA 값을 불러온다. → **LBA IMPORT는 총 2회**(libfont.prx 저장 시 1회, jpn0.pgf 저장 시 1회). 안 하면 에러.
7. 다른 이름으로 ISO 저장.
8. PPSSPP: `설정 > 개발자도구 > 게임 부팅 시 해독된 EBOOT.BIN 덤프` 체크.
9. PPSSPP로 게임을 1회 실행 → 덤프 생성 확인 후 종료.
10. `memstick/psp/system/dump`에 생성된 해독 .BIN을 `EBOOT.BIN`으로 이름 변경.
11. 덤프한 EBOOT.BIN을 010 Editor로 연다.
12. 010 Editor에서 **유니코드**를 선택하고 `亜 = 0x9C4E`를 찾는다.
13. `亜`부터 시작해 **일본어 한자 세트 2350자를 순서대로 붙여넣는다**(EBOOT 내부 한자 테이블을 원하는 글립 매핑으로 덮어씀).
14. UMDGen으로 7번의 ISO를 다시 불러오고 `EXPORT`로 LBA 값을 새로 저장.
15. 수정한 `EBOOT.BIN`을 `PSP_GAME/SYSDIR`에 덮어쓰기.
16. `IMPORT`로 방금 저장한 LBA 값 복원 후 새 ISO로 저장.

주의·보강:

- EXIT의 경우 **EXPORT ↔ IMPORT를 매 단계 계속 해줘야** 하며, 안 하면 실기 실행 시 블루스크린. EXIT 1편·2편 작업법 동일.
- 댓글 보강: **FBA 처리는 게임에 따라 선택 사항**이다. 원래는 "원본 저장 → 파일 교체 → 원본 불러오기 1회"면 충분하고, EXIT가 까다로워서 여러 번 반복한 것. FBA를 안 해도 되는 게임이 많다.
- 댓글 보강: 우회 후 ISO 용량이 700MB→4GB로 폭증하거나 실기에서 한글이 깨지면 절차 중 무언가 잘못된 것(정상 절차에서는 용량이 그렇게 늘지 않음).

### 악마성 드라큘라 피의윤회 자막 시스템 구현 (#31144, PC엔진)

- 원문: https://cafe.naver.com/f-e/cafes/16259867/articles/31144
- 도구: 디버거(스프라이트 출력 루틴 역추적), 자체 스크립트 인터프리터

기법·발견:

- **하드웨어 제약**: PC엔진은 배경 레이어가 1개뿐이라 자막을 배경으로 깔 수 없다. 자막은 **스프라이트로 띄워야** 하는데, 스프라이트는 **번호(순서)에 따라 레이어 우선순위가 결정**되어, 원래 화면 스프라이트보다 자막을 앞에 배치하기가 까다롭다.
- 해결: 코나미의 스프라이트 출력 방식을 디버깅으로 파악해 **스프라이트 출력 순서를 변경**, 기존 스프라이트 앞에 새 자막 스프라이트를 띄우는 데 성공.
- **자막을 하드코딩 대신 스크립트 방식으로 구현**(영상 컷신이 많고 인게임에도 대사 치는 몹이 있어서). 1바이트 명령어 기반 인터프리터 설계:
  - `F1`: 대사 온/오프
  - `F2`: 대기(인자 2바이트, 시간)
  - `F3`: 스프라이트를 할당할 VRAM 위치(2바이트)
  - `F4`: 위치(4바이트, Y·X 좌표)
  - `F5`: 팔레트 속성(2바이트, 캐릭터별 폰트 색상 변경 가능)
  - `F6`: 1bpp 그래픽 로딩(5바이트)
  - `F7`: 문자셋 뱅크(1바이트)
  - `F8`: 스크립트 주소 이동 및 초기화(1바이트)
  - `FF`: 제어 종료
- 스크립트 예시 동작: `F7 73`(문자 로딩 뱅크 73번 사용) → `F3 00 03`(스프라이트 그래픽이 로딩된 VRAM 0000 위치 설정) → `F6 00 C0 00 60 08`(Card RAM 73번 뱅크의 `$C000`에서 VRAM `$6000`으로 0x08 만큼 스프라이트 그래픽 생성·로딩) → `F4 FF 00 70 00`(자막 위치 Y:00FF X:0070) → `F1 01`(자막 표시) → `F2 90 00`(0x0090 대기) → `F1 00`(자막 끄기). 여러 대사를 이 패턴 반복으로 처리.
- 타이밍은 아직 사이클 속도 계산기를 만들지 않아 수동으로 맞춰 놓았고, 작업 속도를 위해 시간 계산기 제작이 후속 과제.
- 교훈: PC엔진 같은 저사양기에서 VRAM/카드 RAM 뱅크·스프라이트 슬롯을 아껴 쓰지 않으면 화면 깨짐 등 문제가 생기므로, 한정된 코드·메모리를 최대한 긁어써야 한다.
- 이전 작업(#31097): 오프닝 텍스트와 프롤로그 데스의 PCM 음성을 한국어로 적용. BIOS 폰트를 쓰는 게임이지만 CD 빌트인으로 로딩해 출력.

### 언리얼 엔진 게임 폰트 위치 찾기 (#30757, UE5)

- 원문: https://cafe.naver.com/f-e/cafes/16259867/articles/30757
- 도구: FModel(pak 뷰어), 언리얼팩(UnrealPak.exe, 공식 SDK 동봉), 리팩 배치(pack-v11.cmd 류)

기법(폰트 위치 추적 절차) — 예제: Chained Together:

1. FModel로 pak을 열어 `Widgets/Font(s)` 폴더를 찾는다. 폰트 이름으로 후보를 추린다:
   - 이름에 "이모지"가 붙은 폰트는 제외.
   - NotoSans 계열은 다국어 폰트라 `VariableFont`=유럽, `JP`=일본어, `SC`=중국어로 갈리므로 대표 폰트 후보에서 제외.
   - 남은 대표 폰트(예: `bordonaro`) 후보를 다른 폰트로 교체해 테스트.
2. 교체 후 인게임 일부에서 한글이 나오지만, **설정 화면 등 곳곳에서 한글이 공란**으로 남는다. → 찾은 폰트가 전부가 아님을 의미.
3. **핵심 기법**: `Fonts` 폴더만 보지 말고, 해당 위젯의 `.uasset`(예: `MainMenu_W.uasset`)을 FModel로 열어 내부에서 `font`를 검색한다. `ObjectPath` 항목에 **실제 참조되는 폰트 경로**가 드러난다. 이 예제에서는:
   - `ChainedTogether/Plugins/V_WidgetEssentials/Content/Fonts/Lato-Regular_Font.0` (플러그인 폴더)
   - `Engine/Content/EngineFonts/RobotoTiny.0` (엔진 폴더)
     → 폰트가 `Content` 폴더에만 있는 게 아니라 **플러그인 폴더와 엔진 폴더에 분산**되어 있었다. 이 둘을 모두 교체하면 한글이 정상 표시.

- 교훈: 게임 파일이 전부 `Content` 안에만 있다고 가정하지 말 것. 위젯 uasset의 `ObjectPath`가 실제 참조 폰트를 가리키는 정본이다.
- 리팩 보강(댓글): 엔진 폴더·게임 폴더로 나뉜 자산은 리팩 시 하나로 합쳐도 되고 각각 2개로 나눠 패킹해도 된다. UnrealPak 배치는 `대상경로 소스경로` 쌍을 여러 줄로 나열해 여러 폴더를 함께 묶을 수 있다(WRC 예시처럼 en-us/폰트 등 각 매핑을 줄마다 기재).

### 완성형 폰트를 이용한 자판(한글 IME) 입력 시스템 구현 (#32139)

- 원문: https://cafe.naver.com/f-e/cafes/16259867/articles/32139
- 도구: 커스텀 조합 로직(ASM 훅), 이진 탐색 테이블

기법·발견 — 게임 내 이름 입력 등에서 초성·중성·종성을 조합해 완성형 한글을 실시간으로 만드는 IME 구현:

- **완성형 인덱스 공식**: `(초성순서 × 21 × 28) + (중성순서 × 28) + 종성순서`. 예: "간"(ㄱ+ㅏ+ㄴ) → `(0×21×28)+(0×28)+4 = 4`, "나"(ㄴ+ㅏ) → `(2×21×28)+(0×28)+0 = 1176`. 이 값은 11,172자 완성형 테이블의 인덱스.
- **공간 최적화**: 11,172 × 2바이트 = 22,344바이트 전체 테이블은 과함. 대신 **실제 게임 폰트에 존재하는 글자만** 추린 축약 테이블 2개를 두고 이진 탐색으로 찾는다:
  1. 초성·중성·종성 상태를 담는 **3바이트 구조체(ImeState)** — cho/jung/jong.
  2. **정렬된 조합키 값 테이블**(위 공식으로 인코딩된 값들이 오름차순).
  3. 테이블 (2)의 각 인덱스에 대응하는 **폰트 고유번호(글립 코드) 테이블**.
- 조합키 계산 시 **0 베이스 보정**: 초성·중성은 -1, 종성은 0이 "받침 없음"이므로 -1 하지 않음. 예: ㄴ(cho=2)+ㅏ(jung=1)+없음(jong=0) → `(2-1)×588 + (1-1)×28 + 0 = 588`. (588 = 21×28) → 이진 탐색으로 588의 인덱스 i를 찾고 → 고유번호테이블[i] = `0x845A`("나") → 목적지 주소에 저장.
- **입력 알고리즘 규칙**:
  - 초성/중성 입력: 항상 **교체**(이전 값 덮어씀). 짝이 없으면 자모 단독 표시, 짝이 있으면 완성형 갱신. 어느 경우든 **같은 슬롯에서 교체 표시, 커서(pos) 증가 없음**.
  - 종성 입력: **초성·중성이 둘 다 있을 때만** 받는다. cho=0 또는 jung=0이면 무시하고 리턴(pos 증가 없음). 유효하면 교체 저장 후 완성형 갱신.
  - 완료키(확정): 슬롯이 비었으면 기본 문자(공백 등)로 채우고, ImeState를 0으로 초기화, **pos를 1 증가**(최대 길이 내).
  - 초/중/종/완료 범위 밖 문자: ImeState 초기화 후 입력 문자를 슬롯에 그대로 저장, pos는 이 루틴에서 건드리지 않음.
- **삭제 처리(패드 B / Back)**: 원본 루틴은 커서를 -1 하며 삭제하는데, 한글은 확정 전에도 같은 슬롯을 계속 갱신하므로 충돌. 그래서 훅으로 가로챔:
  - **조합 중 삭제**: 원본의 커서 감소를 실행하지 않고, **현재 슬롯만 0으로 지우고**(완성형 1글자 통째 삭제) ImeState 초기화 후 즉시 리턴 → 커서는 그 자리에 유지.
  - **조합이 끝난(확정) 상태의 삭제**: 훅이 개입하지 않고 원본대로 커서 -1 + 이전 글자 삭제.
- 요약: 초/중/종은 "같은 슬롯 교체, pos 유지", 완료키는 "ImeState 초기화 + pos+1", 삭제는 조합 중이면 "현재 슬롯만 삭제·커서 유지" 조합 후면 "원본대로 커서 -1".

### 베어너클3 — 줄바꿈은 화면마다 다른 계약이다 (#34314)

- 원문: https://cafe.naver.com/f-e/cafes/16259867/articles/34314
- 2026-08. 작업 시간 배분: 로고 30%(실패) · 테스트·검수 50% · 줄바꿈 10% · 텍스트 10%

텍스트 치환 자체는 금방 끝났고 **시간을 다 먹은 건 줄바꿈과 검수**였다.

- 좌측 정렬이 안 되고 **단어 중간에서 줄이 끊겼다.** 「규칙을 찾아 일괄 수정」은 몇 번을 해도
  안 됐다 — 화면마다 규칙이 달랐기 때문이다.
- 🔴 녹색 CRT 화면은 **13×4 = 52셀을 고정으로 소비하는 특수 구조**였고, 신문 화면·후반부
  특수 화면은 **또 다른 행 크기와 출력 규칙**을 썼다.
- ⇒ **출력 루틴을 찾아도 「보기 좋게」는 자동으로 안 된다.** 화면 종류별로 계약을 따로 세운다.
- 로고(그래픽) 한글화는 토큰의 대부분을 먹고 실패했다. **그래픽 한글화의 비용을 미리 재고**
  들어갈 것.
