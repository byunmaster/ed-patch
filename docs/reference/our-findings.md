# 우리 프로젝트 발견 (Our Findings)

이 프로젝트(eiyuu-densetsu-kr)에서 **직접 발견·검증한 재사용 기법**을 축적하는 살아있는 문서.
같은 폴더의 다른 문서들이 한식구 카페·외부 블로그 등 **커뮤니티 자료**라면, 이 문서는 **우리 실전 발견**이다.

## 축적 규칙

작업 중 새 해결책·기법을 확인하면:

1. **관련 플랫폼 문서에 이미 그 주제가 있으면** 거기(`ps1-saturn.md` 등)에 보강한다.
2. **없으면 여기**에 아래 템플릿으로 추가한다.
3. 확정(검증)된 것만. 추정은 "가설"로 명시.

```
### 제목 (플랫폼)

- 근거/위치: 커밋·파일:라인·태스크·메모리
```

## PS1 — 영웅전설 (ED1 / ED2)

- 근거/위치: 프로젝트 메모리 `ed1-opening-font`.
- 일반화: BIOS 폰트를 쓰는 PS1 타이틀 전반의 공통 이슈.
- 날짜: 2026-07(기록) — 재확인 권장.

### 시스템 텍스트 정렬 ASM — 정렬값 = 바이트수 × 3 (PS1)

- 날짜: 2026-07(기록) — 재확인 권장.

### UI 버튼/스프라이트 텍스트 한글화 — 원본 보존 + 획만 페인트 (PS1, 범용)

- 상황: 타이틀/메뉴의 그래픽 버튼(8bpp TIM 스프라이트)에 일본어가 박혀 있음. 원본 버튼의
  프레임·베벨·radius·선택/비선택 상태색·위치·크기를 **그대로 두고 텍스트만** 한글로 바꾸고 싶다.
  버튼을 새로 그리면(이미지 에셋 합성·절차적 재작도) 엔진 blit 특성 때문에 위치·크기·테두리가
  상태별로 어긋나 계속 반려됨.
- 해결(검증·확정 순서):
  1. **엔진 blit 캘리브레이션 먼저**: 각 스프라이트 셀에 색띠+눈금(5/10px)을 심어 디스크에 쓰고
     화면 실측 → 엔진이 셀을 **1:1(무스케일)로 고정 슬롯에 blit**함을 확인(눈금 10px→화면 10px).
     즉 **TIM 좌표 = 화면 좌표**. 이걸 알아야 텍스트 위치·크기를 추측 없이 잡는다.
     (추측으로 재작도하면 셀마다 크기·오프셋이 달라 무한 반복됨 — 반드시 실측.)
  2. **원본 버튼 보존 + 일본어 획만 페인트**: 어두운 획 검출(행 p75·p25 중간 임계 + dilation) →
     **검출된 획 픽셀만** 버튼 내부색(획 아닌 픽셀의 채널별 p40=바탕색)으로 칠한다. ⚠ inpaint
     (최근접)는 가장자리 획을 **버튼 밖 맵색으로 당겨와 테두리를 오염**시킴 → 폐기. "내부색으로만
     페인트"는 외부색을 절대 안 써서 오염이 원천 불가.
  3. **테두리 inset 마스크**: fill 영역 바깥 (가로,세로) N px(=버튼 프레임/베벨)는 절대 안 칠해
     테두리를 상태 무관 100% 원본으로 보존. 세로 베벨이 두꺼우면 세로 inset을 크게. 라운드 코너는
     rounded_rectangle 마스크로 맵 삼각형(radius) 보존.
  4. **그라디언트 버튼(금색 알약 등)**: 단색 채움은 그라디언트를 flat하게 뭉갬 → **행별로 그 행의
     밝은 픽셀(상위~32%) median**으로 채움. 획 사이로 비치는 배경색을 잡아 빽빽한 행도 처리하며
     세로 그라디언트 유지.
  5. **한글은 fill과 분리 합성**: 획 지운 뒤 별도 스프라이트로 버튼 중앙(cx·cy 실측)에 얹고, 좌우
     미세보정은 dx로(fill 영역과 무관). 일본어가 한글보다 넓으면 fill rect를 일본어 실측폭까지 확장.
- 근거/위치: `games/ps1-ed1+2/tools/patch_gfx_title.py`(`overwrite_text`·`render_coll_buttons`·
  `render_buttons`), `docs/devlog.md`(전체 시행착오 이력).
- 일반화: **TIM/스프라이트 UI를 쓰는 레트로 게임 전반**에 적용. 핵심 재사용 패턴 = ①엔진 blit
  캘리브레이션(추측 금지) ②원본 보존·획만 페인트(외부색 안 씀) ③테두리 inset ④그라디언트는 행별.
- 날짜: 2026-07-16.

## 문안 파생 체계(textmap) — 저작권 있는 문장을 리포에 안 담는 구조

- 문제: 패치 도구에 번역 테이블을 임베드하면 팔콤 일문 원문·정발(만트라) 번역문이
  리포·git 히스토리에 남는다. 리포 공개 시 저작권·커뮤니티 리스크.
- 구조(3계층): `originals/`(소장 원본, gitignore) → `textmap/*.json`(커밋 — 정발 문안은
  **(파일·오프셋·길이) 포인터**로만, 우리가 쓴 번역만 원문 수록) → 빌드 시
  `tools/derive_text.py`가 원본에서 문장을 추출·검증(sha1 가드)해 테이블 재구성.
- JP 원문 키는 sha1 해시 — 소비 코드는 디스크에서 스캔한 JP를 해싱해 조회하므로
  일문이 리포 어디에도 없다. 단어 수준 명칭·라벨은 저작권 대상이 아니라 코드 유지.
- 임베드형 테이블을 이 구조로 옮길 땐 `tools/gen_textmap.py`: 테이블을 ast로 읽어 DOS
  코퍼스 역검색(원문 그대로/조판 역변형/미발견=우리 번역)으로 분류 → textmap 생성 →
  파생 라운드트립 == 원 테이블 assert → 소비부를 로더로 치환 → **빌드 바이트 동일** 확인.
- 위치: `games/ps1-ed1+2/tools/derive_text.py`·`gen_textmap.py`·`textmap/`.
- 일반화: 정발판이 존재하는 모든 한글패치에 그대로 재사용(차기 게임 골격).
- 날짜: 2026-07-13.

## ⚠ 텍스트 재삽입의 "구조 계약" — 블록을 재조립하면 소프트락이 난다 (PS1, 일반)

**한 줄 규칙: 엔진은 블록의 텍스트가 아니라 구조(세그먼트 수·제어코드·위치)를 계약으로 읽는다.
번역문만 맞추고 구조를 바꾸면, 증상은 "오타"가 아니라 소프트락·이벤트 정지로 나온다.**

- 상황: ED1 1장 "몬스터 침공 → 마을 탈출 → 월드맵" 진입에서 대사창이 열린 채 진행 불가.
  깨진 미세 글자 + `▽`는 뜨는데 ◯/✕ 무효, **음악은 계속**(오디오 IRQ는 독립이라 프리징 아님).
  침실 이벤트에선 주인공이 이동을 못 함. 초기부터 있었고 여러 세션을 태운 난제.
- 원인(확정): **창 수(=`%c` 세그먼트 수) 계약 위반의 "과잉읽기"**. 엔진은 블록당 세그먼트를
  **원본 개수만큼** 읽는다. KR 재조립본이 원본보다 **적게** 만들면 종단을 못 만나 **뒤 데이터까지
  읽어** 깨진 글자를 뿌리며 무한 대기 → 씬 상태머신이 특정 state에서 stall.
  - **부족 = 소프트락(치명), 초과 = 꼬리 창 잘림(문장 일부 미표시, 표시 손실).**
  - 실측: 전 씬 1339블록 중 창 수 일치 59.6%, 부족 23, 초과 518.
- 해결: 재조립본의 `%c` 수가 원본보다 적으면 **그 블록은 번역 제외(원본 유지)**.
  (`tools/reinsert_kr_pilot.py` `reflow_run`의 `window_deficit`). 근본 해결은 "정확히 원본 N개로
  packing"이며, 그래야 부족 회복 + 초과의 꼬리잘림까지 동시 해소된다.
- 함께 규명된 별건: **참조되지 않는 데이터는 절대 이동시키지 말 것.** 재배치기가 갱신하는 건
  코드의 `lui+addiu/ori` 포인터뿐인데, `lui+lw`로만 읽히거나 **아무 포인터도 없는 값 테이블**
  (여기선 2바이트 엔트리 49개짜리 테이블)은 앵커 탐지(포인터처럼 생긴 워드만 스캔)에도 안 걸려
  대사 패킹에 밀린다 → 절대/상대 접근이 stale. 규칙: **"갱신 가능한 포인터로 참조되지도, 번역되지도
  않는 블록은 이동 금지(핀 고정)"** — 비용 번역 4/947, 위험 이동 0.
- 근거/위치: `games/ps1-ed1+2/tools/reinsert_kr_pilot.py`,
  `games/ps1-ed1+2/docs/status.md`(QA 메모 "1장 탈출→월드맵 먹통").
- 날짜: 2026-07-22.
- **추가 확정(2026-07-23): 계약은 `%c` 수만이 아니라 `%s`/`%d` 수까지다.** 1장 밤 습격 이벤트
  정지(대사 ▽에서 입력 무효·음악 지속)의 원인이 **JP 블록의 인라인 화자 `%c%s%c`를 조판기가
  첫 화자 리터럴로 치환하며 `%s`를 떨어뜨린 것**으로 실증됐다(전 씬 56블록, `%c` 수는 전부
  일치했는데도 정지). 서식 지정자는 엔진의 인자 소비 스텝이라 수가 줄면 씬 이벤트가 어긋난다.
  가드: `reflow_run`의 `fmt_drop`(재조립본의 `%s`/`%d`가 원본보다 적으면 번역 제외) — 유저
  재검증으로 정지 해소 확인. 근본 해결은 `%s` 바이트 방출 + 인라인 화자 헤더 보존.
- **최종 확증(2026-07-24): 대사 블록은 sprintf 포맷 문자열이고, `%c` 하나 = 인자 1바이트를
  버퍼에 주입하는 escape다.** 콜사이트 디스어셈블(ED1SCN1 eid 20, `jal sprintf(0x800CC740)`,
  인자열 `2·이름ptr·1·0x83·0x5C·8·…`)로 실증. 창 전환(8)·색 on/off(2/1/3)·페이지 대기까지 전부
  "인자로 넘긴 제어 바이트가 버퍼에 박히고 렌더러(제어코드 1~~14 점프테이블)가 해석"하는
  구조다. 그러므로 **창 수 계약의 실체 = 재조립본의 `%c`/`%s`/`%d` 개수·순서가 콜사이트
  인자열과 정렬되는 것**(개수가 어긋나면 뒤 인자가 전부 밀린다 = 색 깨짐~~소프트락 스펙트럼).
  - **0x5C 이스케이프 관용**: 둘째 바이트가 0x5C('\\')인 SJIS 글자(ソ 등)는 팔콤 툴체인이
    문자열에 못 쓰고 `%c%c`+인자(0x83, 0x5C)로 주입한다(C 소스 이스케이프 충돌). 번역하려면
    쌍을 실제 글자로 치환한 정본으로 조판 후 쌍을 **같은 전이 구간 안**(창 꼬리)에 복원해
    인자 순서를 보존하고, 콜사이트 즉치를 0x20(공백)으로 패치해 비가시화한다
    (`reinsert_kr_pilot.py` inject_pairs + SCN_ARG_PATCHES, 해당 블록이 번역될 때만 적용).
  - **다중 화자·색 블록의 채움 규칙**: 창=화자·색 단위이므로 본문을 균형 분배하면 안 되고
    (엉뚱한 화자 창에 대사가 들어간다 — 실측), **정발 페이지 수 == 창 수일 때 1:1 배정**만
    허용한다. 부호 전용 창(침묵 ・・・)은 원문 통과, 인라인 명칭({spk}아이템{/spk})은 독립
    창으로 전개. 근거가 없으면 채우지 말고 원문 유지가 정답.
- **⭐ 계약은 구조만이 아니다 — "위치"가 계약인 구간이 있다(2026-08-03 실측).** 구조
  (`%c`·`%s`·`%d` 개수)가 **전부 일치**하는데도, 블록이 **줄어들어 뒤가 당겨지는 것**만으로
  이벤트가 깨졌다. ED1 크루즈 아론 취침→아침 기상에서 자동이동 목적지가 어긋나고(침대 대신
  침대 옆) 축소량이 커지면 진행 차단(책상 위 고정)까지 갔다.
  - **증상이 축소량에 단조 반응한다** — 이게 구조 위반과 갈리는 지문이다. 이분 실측:
    −12B 정상 / −20B·−24B 목적지 어긋남 / −32B 락. 구조 위반이면 이런 계단이 안 나온다.
  - 원인은 그 자유 구간 **안**에 앵커·미참조 핀 어느 쪽으로도 안 잡히는 절대참조 대상이
    있다는 것. `unref` 판정은 **번역된 블록이면 참조가 없어도 이동을 허용**하므로 구멍이 남는다
    (구간 밖 2B 값 테이블은 이미 핀 고정돼 있었다 — 같은 사건의 2026-07-22 규명분).
  - **해법: 구간 단위 원본 길이 고정**(`reinsert_kr_pilot.FIXED_RUNS`). 짧으면 00패딩이라
    구간 내 모든 블록이 제자리다. ⚠ **한 블록만 고정하면 소용없다** — 앞 블록이 줄면 같이
    당겨진다. 반드시 자유 구간(앵커 사이) 통째로.
  - **회수 손실은 0이었다** — 고정 때문에 `size`로 퇴출된 블록은 기존 **확장 영역 이주**
    2단계가 받아준다(원본 자리엔 JP 바이트가 남고 참조만 새 주소로 → 위치 계약도 유지).
  - 진단은 `PILOT_EXCLUDE_EIDS` 이분 4판이면 갈렸다. **정적 계측으로 회귀를 부정하려 들지
    말 것** — "블록이 다 참조=O이고 합계가 줄기만 한다"는 사실이었지만 무죄의 근거가 아니었다.

### ⭐ 정렬·배정은 매 라운드 "다시 계산"된다 — 확정분은 계산에서 빼내라 (일반)

- 상황: 인게임에서 통과했던 대사가 다음 라운드에 **조용히 딴 대사로 바뀐다.** 하루 종일
  "고칠수록 꼬인다"가 반복됐다(2026-08-03).
- 원인은 셋인데 전부 같은 뿌리다 — **결과물이 소스가 아니라 매번 재계산되는 파생물**이다.
  1. `align_semantic`(LaBSE)·`assign_pages`(Hungarian)는 **전역 최적**이라 후보 풀이 바뀌면
     _이미 잘 맞던 짝까지_ 다른 블록에게 넘어간다. 문턱을 낮추면(0.75→0.62) 특히 심하다.
  2. `align_jp_kr` 를 인자 없이 돌리면 **의미정렬 정본을 구조 신호 초안으로 통째 덮어쓴다.**
     초안은 같은 화자의 변형 대사를 swap 하므로 시점이 안 맞는 대사가 나온다.
  3. 정렬 산출물은 `work/`(gitignore)라 **머신을 안 따라간다.** 다른 PC 에서 이어받아
     복구하면 2번을 밟기 쉽다(실제 사고 경로).
- 해결(두 겹):
  - **확정 락** `tools/lock_lines.py` — 인게임 통과분의 **문안 해시(sha1-10)** 를 커밋되는
    `locked_lines.json` 에 못 박고, 빌드가 대조해 **달라지면 실패**시킨다. 조용한 회귀가
    구조적으로 불가능해진다. ⚠ 문안 자체는 저장하지 않는다(저작권) — textmap 과 같은 관용.
    ⚠ 락 검증을 로더 안에 두면 **복구 도구까지 잠긴다** — 관리 도구 전용 우회
    (`LOCK_BYPASS=1`)를 반드시 함께 둘 것(실측 교착).
  - **정본 보호** — `align_semantic` 이 출력에 `generator` 표식을 남기고, `align_jp_kr` 는
    그 표식이 있으면 덮어쓰기를 거부한다(`--force` 로만 강제).
- 일반화: **자동 정렬·자동 배정을 쓰는 모든 번역 파이프라인**에 해당한다. "사람이 확인한
  것"과 "기계가 매번 다시 푸는 것"을 반드시 분리하라.
- 날짜: 2026-08-03.

#### 후속 — 파생물의 신선도는 "존재"가 아니라 "시각"으로 판단한다 (2026-08-03(3))

락을 걸어둔 채 머신을 옮겼더니(회사→집) 같은 사고가 **한 번 더** 났고, 이번엔 락이 잡았다.

- 증상: 빌드가 **확정 락 위반 24건**으로 실패. 해시가 서로 **맞바뀐 쌍**이었다
  (`jp1261: A→B` 와 `jp1116: B→A`) — 새 문안이 생긴 게 아니라 **짝이 순열로 재배치**된 것.
- **첫 진단은 틀렸다.** "집 파생물이 4일 묵어서"라고 보고 전 체인(extract → align_semantic)을
  다시 돌렸는데 **똑같은 24건이 해시까지 동일하게** 재현됐다. 묵은 게 원인이 아니었다.
- 진짜 원인: **원문에 완전 중복 블록이 있어 배정이 "정확한 동점"이 된다.** 루디아 병사
  여럿이 **글자까지 똑같은 JP 대사**를 하고, 정발도 같은 대사를 여러 번 조금씩 다르게
  옮겨놨다. 동일 텍스트 → 동일 임베딩 → 총점이 같은 배정이 둘 이상 → 승자는 부동소수
  잡음·순회 순서가 정한다. **머신이 바뀌면 갈린다.**
  - 실측(ED1SCN1): 락 좌표와 다른 배정 **117건**, 그중 JP 원문 완전 중복이 **65건**,
    실제로 문안까지 달라진 건 **24건**. 나머지는 좌표만 다르고 화면 글자는 같다.
  - **점수 문턱으로는 못 막는다** — 동점이라 양쪽 다 높다(0.97 / 0.94).
  - ⚠ 진단할 때 **"어느 쪽이 옳은가"를 먼저 묻지 말 것.** 중복 대사끼리의 교환이라
    대개 **양쪽 다 옳다**. 문제는 오역이 아니라 **재현 불가**다.
- 그래서 **재계산으로는 복원이 불가능하다.** 검증만 하는 락은 이때 **빌드를 세워 놓고
  앞으로 못 나가게** 만든다. 좌표(`src`)는 이미 락에 들어 있었으므로 **되씌우는 것이 답**이다.
- ⚠ **머신을 옮긴 직후 `--freeze` 를 돌리면 안 된다.** freeze 는 "현재 계산값을 정답으로
  승인"하는 도구라, 어긋난 상태에서 돌리면 **락이 잡아야 할 드리프트를 조용히 덮는다**.
  실제로 덮었다가 diff 에서 출처 테이블(`ED1/C_001 #10` → `ED1/C_009 #4`)이 갈린 걸 보고
  되돌렸다. **순서는 빌드 먼저 → 락이 판정 → 필요하면 재생성**이고, freeze 는 인게임 QA
  직후에만 쓴다.
- **진짜 해결 = 비결정적 단계를 빌드 밖으로 뺀다.** 코드는 같은 입력에 같은 산출물을 내야
  한다는 게 기본인데, 빌드 경로 한복판에 임베딩+전역최적화가 있었던 것 자체가 설계 결함이다.
  1. **배정을 파생물에서 소스로 올린다** — `align_map.json`(커밋)에 `{씬: {jp_eid: {table,
entry_id, speaker}}}`. 좌표는 포인터, speaker 는 단어 라벨이라 **문장은 안 담긴다**
     (textmap 이 "정발 포인터 + sha"만 담는 것과 같은 관용 — 저작권 노출 0).
  2. **정본이 있으면 빌드는 정렬 파일을 안 읽는다.** 정렬 산출물을 **전부 지우고 빌드해도
     바이트 동일한 이미지**가 나오는 것으로 검증했다(sha1 일치). 새 머신에 torch·LaBSE 를
     안 깔아도 빌드가 돈다.
  3. 정렬기는 **제안 생성기**로 강등 — 의도적으로 돌려 `--diff` 로 검토하고 `--update` 로만
     정본에 반영한다. 컴파일러가 소스를 읽지 추론을 하지 않는 것과 같은 배치다.
- 과도기 장치로 `reinsert_kr_pilot.apply_lock_src`(락 좌표 되씌우기)도 함께 뒀다 — 정본이 없는
  씬에서 쓴다. ⚠ 되씌우면 원래 그 좌표를 쓰던 락 밖 블록이 남아 **같은 대사가 두 번** 나갈 수
  있다 — 좌표 충돌 시 락 밖 쪽을 떨어뜨리는 가드를 반드시 함께 둘 것.
- 교훈이 둘이다.
  1. **"기준선을 저장한다"면 판정만 하지 말고 복원까지 할 수 있어야 한다.** 판정만 하는
     기준선은 환경이 갈린 순간 **작업을 멈추게 하는 장치**가 된다. 락에 좌표를 이미 적어
     두고도 안 쓰고 있었던 게 정확히 그 상태였다(독스트링은 재적용을 약속하고 있었는데
     구현이 검증까지만 와 있었다 — **문서와 코드가 어긋난 걸 사고가 드러냈다**).
  2. **"검증기를 갱신기로 쓰지 말 것."** 기준선을 만드는 명령(`--freeze`)과 확인하는
     명령(빌드)은 절대 같은 자리에서 돌리지 않는다. 어긋났을 때 freeze 를 먼저 누르면
     드리프트가 정답으로 승격된다.
- ⚠ **반올림·타이브레이크로 때우려 하지 말 것.** `sim` 을 `round(4)` 해서 잡음을 지우는 안도
  있었지만, 그건 "부동소수 오차가 이 정도 안쪽"이라는 **검증 불가능한 가정**에 기댄다.
  비결정적 단계를 빌드에서 빼면 가정 자체가 필요 없다.
- 일반화(다음 게임에서도 그대로):
  - **ML·전역최적화 산출물을 빌드 의존물로 두지 마라.** 임베딩·헝가리안·LLM 출력은 부동소수와
    라이브러리 버전에 의존해서 "재현 가능한 산출물"이 아니다. **제안 생성(비결정적, 사람이
    검토) / 빌드(결정적, 소스만 읽음)** 를 반드시 가른다.
  - **입력에 중복이 있으면 최적화는 반드시 동점을 만든다.** 레트로 게임 대사는 NPC 여럿이
    같은 말을 하는 게 흔해서 이 조건이 **기본값**이다.
  - 저작권 때문에 문안을 커밋 못 하는 프로젝트라도 **좌표(포인터)는 커밋할 수 있다** —
    재현성과 저작권은 상충하지 않는다.

### HUD 지명 접미(입구·부근·방위) — 좌표로 고르고, 지명 슬롯은 널종단이다 (PS1 ED1)

- 구조: HUD 는 `[지명] + [접미]` 를 이어 그린다. 접미 테이블은 ED.EXE `0xF9074`
  (`入口`·`付近`·`北`·`南`·`東`·`西`). **정발 DOS 도 같은 구조**(ED1MAIN.EXE 0x27945).
- **접미는 인덱스가 아니라 좌표로 고른다**(2026-08-04 정정 — 전엔 "맵마다 인덱스가 박혀 있다"고
  적었는데 틀렸다). 조립 루틴 RAM `0x800856BC` 는 48개 맵 등록좌표(`0x800DDDD0`, 4B stride)와
  **플레이어 월드 좌표**를 재서 — **정확히 일치 → `入口` · ±8 → `付近` · 그 밖 → 방위**.
  마을·던전 **안**에서는 월드 좌표가 그 타일에 고정돼 늘 "정확히 일치"라, 실내에서도
  `네리아 항구 입구` 로 뜬다. 이게 원판 사양이다.
- ⚠ **"실내에서만 접미를 없애기"는 이 루틴 안에서 불가능하다**(2026-08-04 실패 실측).
  월드맵에서 **마을 타일에 올라선 상태**도 좌표가 똑같이 "정확히 일치"라 루틴이 둘을 못 가른다.
  `入口` 분기의 복사 루프(`0x80085A48 slti $v1,$v0,4` → imm 0)를 죽여 봤더니 실내는 해결됐지만
  **월드맵의 `입구`까지 사라졌다.** 가르려면 "실내인가"를 아는 런타임 플래그가 필요하고,
  호출처 6곳(전부 `j 0x800856BC`, `a0=0x80166650`)이 화면별로 갈리므로 **그 자리에서** 갈라야
  한다. 후보 전역 `0x80108B2C`(2와 비교)·`0x80108AD5`(6과 비교)는 정적으로 확정 못 했다 —
  **에뮬 RAM 대조가 필요**하다.
  **일반화: 화면마다 달라야 하는 동작을 공용 조립 루틴 안에서 가르려 하지 말고, 호출처를 센다.**
- **함정 ①: 지명은 짝수 바이트여야 한다.** 반각 공백(1B)이 끼어 **홀수**가 되면 실내 HUD 에서
  글자가 깨지고 앞 문자열의 꼬리가 비친다. 원본 지명 48개가 **전부 짝수**(SJIS 2B/글자)라
  원작에선 생길 수 없던 상황이다. 상세 기제는 아래 ⚠⚠.
- 함정 ②: 한계는 **지명 단독이 아니라 `지명+접미` 합계**다(14B). 지명만 재면 여유가 있어
  보이지만 `베르가 광산`(11B)+`입구`(4B)=15B 로 이미 빠듯하고, 공백을 넣으면 17B 가 되어
  뒷글자가 잘린다.
- ⚠ **함정 ③ — 그 14B 는 렌더 폭이 아니라 "테이블 슬롯 크기"다**(2026-08-04 정정).
  지명 테이블은 `0xBE690` 부터 **stride 14B 고정 48슬롯**(`patch_sys_ui.PLACES_STRIDE`).
  그래서 **폰트 폭을 줄여도 해결되지 않는다** — 처음엔 우리도 렌더 폭 문제로 알고 폰트 축소를
  선행 과제로 적어 뒀는데, 그 오진이 문서 두 곳에 퍼졌다.
  **일반화: "글자가 잘린다"를 만나면 렌더러를 보기 전에 저장 슬롯부터 재라.**
- ✅ **결말 — 조립 코드를 읽고 나니 stride 확장도 필요 없었다**(2026-08-04, 디스어셈블).
  조립 루틴은 RAM `0x800856C0`. 플레이어 좌표로 가장 가까운 맵을 고른 뒤
  **① 지명을 널 만날 때까지 바이트 복사 → ② 접미를 이어 붙임 → ③ 널** 로 한 버퍼를 만든다.
  - ①이 **널종단**이므로 슬롯 14B 의 실제 가용은 **13B + 널**이고, 우리 최장 지명은 11B 다 —
    **2B 가 남는다.** stride 를 넓힐 이유가 없었다(= 함정 ③의 처방도 과잉이었다).
  - ②는 **ED.EXE 접미표(`0xF9074`)를 스택으로 먼저 복사**하는데 그 **복사 바이트 수가 명령에
    박혀 있다**(`入口`·`付近` 4B = `lwl/lwr` 한 쌍, 방위 2B = `lb`×2). 표를 늘려도 안 읽는다 —
    **접미 쪽에 공백을 넣으려면 ASM 을 고쳐야 한다.** (주소는 자동으로 따라간다 —
    `patch_items` 가 이 표를 촘촘히 재packing 하면서 참조 immediate 를 같이 고친다.)
  - 그래서 공백은 **지명 슬롯 꼬리**에 넣었다(반각 1B). 데이터만 바뀌고, 접미가 없는 자리에선
    꼬리 공백이라 화면상 무해하다.
  - 전각으로 넣었다가 지명 내부 간격과 안 맞아 반각으로 되돌렸다(유저 확정).
    ⚠ 이 꼬리 공백은 **슬롯 꼬리**라 아래 짝수 규칙과 무관하다(지명 자체는 짝수를 지킨다).
- ⚠⚠ **실내 HUD 는 다른 경로이고, 지명이 홀수 바이트면 깨진다**(2026-08-04, 원본 디스크 대조로

### 재삽입 전 체크리스트 (다음 게임에서도 그대로)

1. **세그먼트 수 보존** — 원본의 창/페이지 구분자 개수를 세고, 재조립본이 **부족하지 않게**.
   부족은 소프트락이므로 최소한 "부족이면 제외" 가드를 넣는다.
2. **포맷 지정자 보존** — 원본의 `%s`·`%d`(런타임 이름·수치 주입)를 임의로 리터럴로 바꾸거나
   빼면 엔진의 인자 소비가 어긋난다. 인라인 화자 헤더(`%c%s%c`)도 구조의 일부다.
3. **인라인 제어코드 보존** — 텍스트에 섞인 저바이트 코드는 장식이 아니라 흐름 제어일 수 있다.
   일괄 공백 치환 전에 각 코드의 의미를 확인.
4. **비대사 데이터 식별** — 텍스트 영역이 전부 대사는 아니다. 값 테이블·이름 문자열·스크립트
   조각이 "블록"으로 오분류된다. **번역 대상이 아닌 건 움직이지 않는 게 기본값.**
5. **참조 유형 전수 확인** — `addiu/ori`뿐 아니라 `lw` 참조, 그리고 **무참조** 데이터가 있는지.
   무참조 = 절대주소로 읽힌다는 뜻이므로 이동 금지.
6. **구조가 다 맞는데 깨지면 위치를 의심** — 증상이 축소량에 단조 반응하면 그 구간은
   원본 길이 고정으로 돌린다(위 "위치가 계약인 구간" 절).

### 소프트락 디버깅 절차 (재사용)

프리징(=CPU 정지)과 소프트락(=루프는 도는데 진행 불가)은 다르다. **음악이 나오면 소프트락**이고,
아래 순서가 가장 빠르다. 라이브 RAM에서 "깨진 블록 찾기"부터 하면 토끼굴에 빠진다(실패 경험).

⚠ **0. 먼저 CPU 상태를 읽는다 — "소프트락"이 사실은 크래시일 수 있다**(2026-08-09 실측).
음악이 계속 나오고 커서만 멎어도, `CAU`(ExcCode)·`EPC`·`BadVAddr` 를 보면 **예외**인 경우가 있다.
PSX 는 미처리 예외에서 BIOS `A0(0x40) SystemErrorUnresolvedException` 무한 루프로 들어가는데,
그 루프가 "게임이 도는 것"처럼 보인다. ED1 실측: `ExcCode 4`(AdEL) · `EPC = BadVAddr =
0x9420C50A`(정렬도 아님) = **스크립트가 쓰레기 주소로 점프**. 증상 이름에 속으면 대기 주체를
찾느라 아래 3~4번을 헛돈다. `get_state` 한 번이면 갈린다.
⚠ 예외 벡터가 `SR.BEV=1` 이면 **ROM**(0xBFC00180)이라 RAM 브레이크포인트가 안 걸린다.
⚠ **명령 단위 트레이스를 켜고 프레임을 돌리지 말 것** — 에뮬레이터가 응답 불능이 된다.
브레이크포인트로 세운 **뒤에** 트레이스를 본다.

1. **먹통 상태를 세이브스테이트로 확보** — 재현 비용이 크므로 반드시 저장. 이후 분석은 이걸 로드.
2. **PC를 읽는다** — 대개 저수준 vsync 대기 루프(어떤 대기든 여기 머문다). 여기서 멈추지 말 것.
3. **스택의 리턴주소로 콜체인을 거슬러 올라가** 진짜 대기 주체를 찾는다.
4. **상태머신을 찾는다** — 점프테이블로 분기하는 스텝 함수와 그 **상태 변수**를 특정하고,
   프레임을 돌려도 값이 안 변하면 "어느 상태에서 stall"인지 확정된다.
   (ED1 실측: 실행기 `0x800B50C0`, 상태변수 `0x80108A68`, 점프테이블 `0x8001C08C`, state 5 고착.)
5. **differential 빌드로 원인 계층을 이분한다** — 이게 코드 추적보다 훨씬 빠르다.
   패처별 on/off 플래그를 상시 갖춰둘 것: 재삽입만 OFF / 재배치만 OFF(제자리 고정) / 병합만 OFF /
   원본 라운드트립. ED1에선 `PILOT_TEXT_IDENTITY`·`PILOT_FIXED`·`PILOT_NOSPLICE`·`PILOT_IDENTITY`.
   "대사 재삽입만 끈 빌드가 정상" → 범인이 대사 재삽입으로 즉시 확정됐다.
6. **원본 vs 재조립본을 구조로 비교** — 텍스트가 아니라 **제어코드 시퀀스**를 나란히 찍어 본다.
   무엇을 잃었는지가 바로 보인다(여기선 `%c` 개수와 `%s`).
   ⚠ 비교는 **빌드가 실제로 쓴 바이트**로 한다(재조립 후보가 아니라). 재배치 매핑을 가로채
   원본↔최종을 블록별로 대조하면 "부족 0건"을 **증명**할 수 있고, 그래야 이 계층을 지운다.

⚠ **순서를 뒤집는 게 낫다 — 5번을 먼저 한다.** 2026-08-09 에 정적 배제(구조 계약·치환 오염·
트레이스)를 셋이나 돌고 나서 `PILOT_FIXED` 한 번으로 답이 나왔다. **먼저 이분하고, 그다음에
좁힌다.** 계층이 정해지면 정적 조사는 훨씬 짧아진다.

### ASM 훅·테이블을 실을 "빈 공간"은 파일이 0인 것만으로 고르면 안 된다 (PS1, 일반)

- 상황: 실행 파일(ED.EXE) 데이터 세그먼트의 0런에 훅 스텁·룩업 테이블을 실었더니 인게임에서
  즉시 크래시. 훅 로직을 아무리 고쳐도(워크 주소 고정·스캔 상한 추가) 재현됐다.
- 해결: 그 구간(ED1 `0x801059A0` 부근)은 **파일에선 0이지만 런타임 워크램**이었다 — 게임이
  거기에 데이터를 써서 우리 명령어를 덮었다. **코드/데이터 배치 후보는 3중 검증을 통과한 것만
  쓴다**: ①원본·현빌드 파일에서 0 ②디스어셈블에서 그 구간을 가리키는 포인터/절대 접근 0건
  ③**필드·전투 등 실플레이 세이브스테이트 RAM 덤프에서 0 유지**. ③이 없으면 "0런"은
  "아직 안 쓰인 버퍼"와 구별되지 않는다. 배치 시 대상 구간 0 assert를 코드에 남겨 타 패치와의
  충돌도 함께 막는다(대사 도너 풀과 겸용이면 도너 목록에서 예약 제외).
- 부수 교훈: MIPS `j`로 훅을 걸 때 **1워드만 교체하면 다음 명령이 지연 슬롯으로 선실행**되고
  복귀 후 또 실행된다. load라면 무해하지만 계약이 모호하니 **2워드(j+nop) 교체 + 원명령 2개를
  스텁 말미에서 재현**하는 편이 안전하다. 그리고 훅 지점이 **다른 j의 재진입 타겟**일 수 있으므로
  (ED1 `0x800B2054` ← `0x800B1ED4`) 두 진입 경로 모두 no-op 스텁으로 먼저 A/B할 것.
- 근거/위치: `games/ps1-ed1+2/tools/patch_josa_hook.py`, `docs/devlog.md`(07-20 크래시 /
  07-27 원인 규명·재설계), 도너 3중 검증은 구 HANDOFF 07-26(git 이력).
- 일반화: 오버레이·상주 실행 파일을 쓰는 모든 플랫폼에 그대로 적용. 특히 콘솔은 BSS/힙이 파일
  이미지에 0으로 남으므로 "파일 0 = 미사용"이 자주 틀린다.
- 날짜: 2026-07-27
- **⛔ 반례로 갱신(2026-07-29) — 위 3중 검증을 통과하고도 깨졌다. 4번째 기준이 필요하다.**
  ED1에서 그 기준을 통과한 0런 16곳에 대사를 실었더니 **효과음이 깨졌다**(메뉴 확인음 소실,
  창 열림·로딩에서 "삐"). 정체는 **ED.EXE에 박힌 `pBAV`(PS1 VAB) 사운드 뱅크 16개의 내부
  무음 ADPCM 패딩**이었다. 왜 3중 검증이 통과했나 — **뱅크는 CPU가 주소로 읽는 게 아니라
  통째로 SPU RAM에 전송된다.** 그래서 ①파일에서 0이고 ②lui 참조가 0건이며(개별 주소로
  안 읽으니까) ③게임이 **쓰지** 않으니 런타임 덤프도 계속 0이다. 기존 검증은 전부
  "게임이 여기에 **쓰는가**"만 봤고 **"게임이 여기를 통째로 **읽어 가는가**"는 못 봤다.**
  - **④ 새 기준: 알려진 자료구조 매직을 스캔해 그 블롭 내부가 아님을 확인**한다.
    최소한 `pBAV`(VAB) · `SEQp`(SEQ) · `\x10\x00\x00\x00`(TIM) · 폰트/비트맵 영역.
    실행 파일에 사운드 뱅크·이미지가 통째로 임베드되는 건 콘솔에서 매우 흔하다.
  - **정밀화(같은 날 후속): 블롭 전체가 금지구역인 건 아니다 — 위험한 건 "재생되는 부분"이다.**
    VAB는 `[헤더: 프로그램 128슬롯·톤·VAG 오프셋 테이블 — 미사용분이 전부 0]` + `[파형(ADPCM)]`
    구조다. 실제로 소리를 깬 건 **파형의 첫 ADPCM 블록**을 덮었을 때뿐이었다(각 VAG의 첫 16B가
    무음이라 0런 스캐너가 파형 시작을 삼켰다). 헤더의 미사용 0 패딩은 덮어도 무해했다.
    ⇒ 배치 한계는 **런 크기가 아니라 "파형 시작 직전"**으로 잡고 코드에 assert로 박아둘 것
    (ED1: `JOSA_SAFE`/`DATA_SAFE` = 508B, 런 크기 524B를 쓰면 8B가 파형을 침범했다).
    파형 시작 = `VAB시작 + 32 + 128*16 + 512*nprog + 512`.
    ED1의 조사 훅은 이 계산 덕에 **재배치 없이** 지연 슬롯 3곳을 채워 12B 줄이는 것만으로
    해소됐다(516→504B). 검증은 "빌드본의 전 VAB 파형이 원본과 바이트 동일"로 확인.
  - **놓친 조기 신호**: 후보 0런들의 크기가 죄다 **524~528B로 비슷**했다. 우연한 빈틈이
    그렇게 균일할 리 없다 — "레코드마다 같은 자리에 있는 **구조적 패딩**"이라는 뜻이었다.
    **0런 크기가 규칙적이면 그건 빈 공간이 아니라 자료구조다.**
  - **증상 감별**: 이 오염은 크래시가 아니라 **"기능 하나가 조용히 이상해짐"**으로 나온다
    (효과음 하나 소실, 다른 하나는 노이즈). 그림이 안 깨지고 진행도 되므로 텍스트 QA만
    해서는 절대 안 잡힌다 — **소리를 켜고 QA할 것.**
  - **원인 추적이 빨랐던 이유 = 커밋 이분**(유저 제안). 후보 커밋을 빌드해 실기로 좁히면
    (여기선 4회) 정적 추적보다 훨씬 빠르다. 계층 스위치(`PILOT_NODONOR` 등)와 조합해
    "커밋으로 좁히고 → 스위치로 단독 확정"이 정석. 확정 후 **수정 빌드가 진단 빌드와
    바이트 동일**한지 확인하면 회귀 없이 고쳤음이 증명된다.
  - 근거/위치: `games/ps1-ed1+2/tools/reinsert_kr_pilot.py`(`DONOR_RUNS` 폐기 주석·
    `PILOT_NODONOR`), `patch_josa_hook.py`(`PLACE_*_RAM` 잔여 리스크 주석).

### 조판 훅은 "누가 폭을 계산하나"가 아니라 "누가 먼저 호출되나"로 고른다 (PS1, 일반)

- 상황: 런타임 조립 문장의 조사 병기(`을(를)`)를 렌더 직전에 줄이는 훅을 달았는데, 조사는
  제대로 나오는데 **줄이 이상한 데서 끊겼다**("…사 / 용했다"). 폭 계산이 아직 3슬롯짜리 병기로
  이뤄진 탓인데, 처음엔 "그리는 루틴"(ED1 `0x800AD3A8`)을 원인으로 지목하고 그 인자를 라이브로
  들여다볼 세션을 잡아뒀다.
- 해결: 라이브 대신 **전수 `jal` 스캔으로 콜그래프를 그렸다**(4바이트씩 훑어 `op==3`인 워드의
  타깃을 모아 호출자·피호출자 목록화 — 몇 초). 그러자 파이프라인이 드러났다:
  `strcpy` → `0x800ACE18`(자동 개행 삽입, 글자단위) → `0x800B1E58`(`0x0A`로만 분할 → 워크버퍼)
  → `0x800AD3A8`(그리기). **개행은 조립보다 먼저 결정**되므로 워크버퍼 단계 훅은 구조적으로
  늦고, 지목했던 루틴의 인자도 원문이 아니라 이미 잘린 워크슬롯이었다 — **확인하려던 질문
  자체가 성립하지 않았다**. 훅을 `0x800ACE18` **호출 앞**으로 옮기니(=`jal` 타깃 1워드 교체 +
  스텁 끝에서 `j 원래대상` 꼬리호출) 폭 계산이 최종 글자수와 일치해 문제가 사라졌다.
- 부수 기법: 훅 대상이 **호출자 전용 스택 사본**이고 변환이 **항상 짧아지며** 뒤 단계가 `strlen`을
  다시 재는 자리라면, 문자열 제자리 수정은 오버플로·길이 불일치 없이 안전하다. 이 세 조건을
  먼저 확인할 것. 그리고 `jal` 타깃 교체는 j-훅과 달리 **원명령 재현·지연 슬롯 처리가 필요 없다**
  (지연 슬롯이 원래 `nop`이면 특히) — 가능하면 j-훅보다 이쪽.
- 부수 기법 2: 손조립 MIPS는 **파이썬 시뮬만 맞고 인코딩이 틀려도 테스트가 통과**한다.
  쓰는 명령만 구현한 **미니 인터프리터(~80줄, 지연 슬롯 포함)로 어셈블된 바이트를 실제 실행**해
  시뮬과 바이트 비교하면 그 구멍이 막힌다. 빌드 후 **디스크에서 다시 꺼낸 바이트**로 한 번 더
  돌리면 배치·정렬까지 함께 검증된다.
- 근거/위치: `games/ps1-ed1+2/tools/patch_josa_hook.py`(`assemble_prewrap_stub`, `_emulate`,
  `_selftest`), `docs/devlog.md`(07-28 절).
- **그리고 훅을 안 거는 선택지를 먼저 볼 것**: 런타임 이름(`%s`) 뒤에 조사가 오지 않게
  **어순·문안을 설계**하면 훅 자체가 필요 없다. ED1 도구점이 그렇게 처리했다 — 살 때는 이름 뒤에
  서술을 바로 붙이고(`…이군요`), 팔 때는 조사를 **고정 명사**에 붙인다(`… 값은 %d Gold가…` —
  받침 있는 '값'에 조사가 고정되어 아이템명과 무관). 훅이 안 닿는 렌더러(직접 그리기·상점 등)엔
  이게 유일하게 확실한 해법이고, 닿는 곳에서도 더 싸다. **훅이 생겼다고 되돌리지 말 것.**

  단계"가 다른 게 기본이라, 훅 자리는 콜그래프를 먼저 그리고 고른다.

## ⚠ 화면의 이름이 어디서 오는지는 한 곳이 아니다 (번역 일반)

같은 "이름이 틀렸다" 증상인데 고칠 데가 셋이었다(2026-08-02, ED1 실측). 증상만 보고
한 곳을 고치면 "고쳤는데 그대로"가 반복된다 — **먼저 경로를 판정**한다.

1. **원문 테이블의 리터럴** — 블록 안에 이름이 글자로 박혀 있다. 재삽입이 바꾼다.
2. **화자 매핑표** — 블록은 `%c이름%c` 골격만 주고 우리가 대응표로 채운다(`_tpl_name`).
3. **런타임 주입 `%s`** — 엔진이 캐릭터명 테이블에서 읽어 넣는다. 블록엔 이름이 아예 없다.
   이 경우 대사 파이프라인을 아무리 고쳐도 안 바뀐다 — 실행파일의 이름 테이블을 고쳐야 한다.

4. **씬 오버레이가 들고 있는 이름 사본** — 3번과 겉모습이 같다(블록엔 `%s` 뿐). 다만 소스가
   실행파일이 아니라 **그 씬 파일 안의 널종단 이름 문자열**이다. ED1 은 이벤트마다 사본을
   따로 둔다(구엔의 탑 사일레스는 `ロー`판·`ゲイル`판이 각자 사본을 갖는다).

판정법: **JP 원문 블록의 바이트를 본다.** `%s`(0x25 0x73)가 있으면 3·4번이다.
⚠ 3번은 **세이브에 복사되는 값**일 수 있다(ED1은 새 게임 시 1회 복사) — 그러면 기존
세이브에서는 영원히 옛 이름이 나온다. 패치가 맞는지는 **새 게임으로** 확인한다.
⚠ HUD 이름이 맞는데 대사 이름이 틀리면 2·3·4번을 의심한다(HUD가 픽셀 패치인 경우가 있다).

⚠ **4번은 블록 목록에 안 보일 수 있다.** 사본이 포인터 테이블 **바로 뒤**에 붙으면 블록
분할이 테이블 blob 에 통째로 삼켜서, 대사 파이프라인의 어느 도구에도 안 잡힌다(ED1SCN2
`@0x10D84` 의 `ゲイル` — 4,542B blob 의 꼬리 6바이트였다, 2026-08-09). 전 씬을 **바이트로**
훑어야 나온다 — "이름 + 널" 이면서 블록 시작이 아닌 자리.

⚠ **같은 이벤트의 사본마다 경로가 다를 수 있다.** ED1 구엔의 탑 사일레스 석판은 SCN2 안에
**세 벌**로 복제돼 있는데 둘은 4번(옆 리터럴), 하나는 3번(레코드)이었다. 그래서 한 자리에서
고쳐 놓고 "닫았다" 하면 다른 자리에서 그대로 나온다 — **재현 자리가 같은지부터 맞춘다**
(유저 스샷의 **NPC 스프라이트 하나**가 다른 맵이라는 단서였다. 화면 글자만 보면 놓친다).

⚠ **경로 판정은 정적 추적보다 런타임 전수 검색이 싸다.** 위 건은 디스어셈블로 호출부·
소스까지 다 짚고도 답이 틀렸다(3번으로 결론냈는데 4번이었다). RAM 2MB 에서 그 이름의
바이트열을 세면 30초다 — **화면에 있는 글자는 RAM 어딘가에 반드시 있다.** 후보가 몇 곳인지
먼저 세고, 그다음에 누가 그걸 읽는지 좁힌다.

## ⚠ 섹터를 고쳐 쓸 땐 EDC만이 아니라 ECC(P/Q)도 재계산하라 (CD 기반 콘솔, 일반)

**한 줄 규칙: Mode2 Form1 섹터의 유저 데이터를 바꾸면 EDC와 **ECC 패리티 둘 다** 다시 만들어야
한다. EDC만 고친 이미지는 에뮬에서 멀쩡히 돌아가지만 실기에서 조용히 깨질 수 있다.**

- 왜 에뮬로는 안 잡히나: mednafen·DuckStation 등은 읽기 시 ECC 정정을 하지 않고 그냥 넘긴다.
  반면 **실기 CD 컨트롤러는 하드웨어 Reed-Solomon 정정을 수행**하므로, 스테일 패리티가
  멀쩡한 유저 데이터를 "정정"해 오히려 손상시킬 수 있다. 즉 **전 QA를 에뮬로 통과해도
  실기 배포에서 터지는 계열**이라, 사고 나기 전에 도구 쪽에서 막아두는 게 맞다.
- 사양(2352B raw 섹터): 0~~11 sync · 12~~15 헤더 · 16~~23 서브헤더 · 24~~2071 유저데이터(2048) ·
  **2072~~2075 EDC**(16~~2071의 2056B 대상) · **2076~~2247 P 패리티** · \**2248~~2351 Q 패리티**.
- ECC 계산: GF(2^8) 생성다항식 `0x11D`(ecm/cdrdao 표준 f/b 룩업 테이블).
  대상은 12~~2075의 2064B이고 **Mode2는 헤더(12~~15)를 0으로 채운 상태로 계산**한다(Mode1은 그대로).
  P = `(major 86, minor 24, major_mult 2, minor_inc 86)`, Q = `(52, 43, 86, 88)`.
- **구현 검증법(강력 권장)**: 새로 짠 ECC로 **원본 이미지의 Form1 섹터**들의 P/Q를 지우고
  재계산해 저장값과 바이트 비교한다. 전부 일치하면 구현이 맞다(우리: 62/62 일치).
  그다음 빌드본의 **변경 섹터 전수**로 EDC·ECC를 재검증한다(우리: 780섹터 불일치 0).
- Form2(서브헤더 `sec[18] & 0x20`) 섹터는 EDC/ECC 구조가 달라 대상에서 제외한다.
- 비용: 순수 파이썬으로도 섹터당 ~4.3k 루프라 780섹터에 수 초. 도구에 상시 넣어둘 만하다.
- 구현: `games/ps1-ed1+2/tools/common.py` `ecc_update()` (`write_user_data`가 EDC 뒤에 호출).

## 원판 자체의 코드 버그로 "번역했는데 안 나오는 대사"가 생긴다 (PS1, 일반)

**한 줄 규칙: 번역·포인터가 다 맞는데 특정 대사가 화면에 안 나오면, 그 대사를 만드는
콜사이트에 exec BP를 걸어라. 원판 코드가 fall-through로 자기 메시지를 덮어쓰는 경우가 있다.**

- 상황(ED1 크루즈 마을): NPC 두 명이 **같은 대사**만 하고, 다른 대사 블록은 번역됐는데도
  화면에 안 나왔다. 정발(DOS)에는 그 대사가 나온다 → "우리 재삽입이 뭔가 망가뜨렸다"로 보였다.
- 정적 확인으로는 멀쩡했다: 두 문자열이 원본·빌드본에 **각각 1회씩만** 존재, 코드 참조도
  각자 제 위치를 가리킴, NPC→메시지 연결은 ID 기반이라 재삽입이 못 건드림.
- **BP 트레이스가 결정타**: 두 블록의 sprintf 콜사이트에 exec BP(멈추지 않는 로그 모드)를 걸고
  말을 걸었더니 **한 번의 대화에서 두 콜사이트가 연속 히트**했다. 디스어셈블해 보니 앞 케이스에
  종료 점프가 없어 뒤 케이스로 흘러들어가고, 두 `sprintf`가 **같은 버퍼**를 써서 뒤가 앞을
  덮어쓰고 있었다 — **원판 코드의 fall-through 버그**.
- 우리 무관함 입증법: **원본과 빌드본의 같은 구간을 디스어셈블해 나란히 비교**한다.
  포인터 즉치만 다르고 나머지가 동일하면 그 동작은 원판 것이다.
- 복구는 대개 **몇 워드 제자리 패치**로 끝난다(스텁 불필요): 문제 케이스가 자기 sprintf를 버리고
  **공용 꼬리로 점프**하게 하고, 부족한 인자는 점프의 **지연 슬롯**에서 채운다.
  ⚠ 패치 전 반드시 **그 주소로 들어오는 j/jal·점프테이블 워드가 없는지 전 오버레이 스캔**.
- 검증: 패치 후 같은 지점에서 BP 로그가 **한 콜사이트만 히트**로 바뀌는지 본다.
- 판단: 원판에 없던 동작을 추가하는 것이므로 **유저 승인 필요**. "정발에 있는 건 다 이식"
  방침이면 복구가 맞다.
- 날짜: 2026-07-30. 근거: `games/ps1-ed1+2/docs/status.md`(jp287 항목),
  `reinsert_kr_pilot.SCN_ARG_PATCHES`.

#### ✅ generation binding — 축소판으로 세웠다

```
GenerationMemberManifest { generation_id, glyph_plan: FileDigest, inputs[], outputs[] }
→ verifier: member.generation_id ≠ glyph.generation_id 면 실패
```

producer 마다 **정확한 glyph-plan digest** 를 남기고, 결합기는 _"이미 만들어진 임의 파일을
사후에 같은 세대라고 선언하지 않는다."_ 계획이 바뀌면 그걸 소비한 산출물이 전부 낡는데, 하나만
다시 굽고 나머지가 옛 세대를 쓰면 **인덱스가 어긋나 글자가 뒤바뀐다** — 조용히 틀린다.

⚠ **처음엔 「우리도 위험하다」고 적었는데 근거가 틀렸다.** `patcher/subset_font.py` 를 게임 폰트
생성기로 오인했는데 그건 **웹 패처 페이지의 CSS 폰트**다. 실제 경로를 따라가 보니:

```
hangul_map.SYLLABLES = ksx1001_syllables()      ← 계획: 완성형 2,350음절, 코드순
   ├─→ hangul_font.font_block()                 → ED.EXE 폰트 블록
   ├─→ SYL_INDEX                                → 본문 인코딩(글자 → 슬롯)
   └─→ patch_josa_hook                          → 조사 테이블(같은 차례)
```

**계획이 파일이 아니라 순수 함수**라 한 실행 안에서는 소비자끼리 어긋날 수 없다. 저쪽이
manifest 로 결박해야 했던 건 계획이 **파일 산출물**이라 낡은 걸 물 수 있어서다.

**그래도 두 길이 남아 세웠다** — ① 코드가 바뀌면 낡은 이미지에 새 계획으로 덧쓸 수 있다
(A/B·단독 실행) ② 계획을 고치면서 소비자 일부만 다시 굽는다.

| 장치                          | 무엇                                                   |
| ----------------------------- | ------------------------------------------------------ |
| `hangul_map.PLAN_SHA1`        | 계획 지문. **import 시점 assert** — 고치면 즉시 죽는다 |
| `hangul_font.font_block()`    | 폰트 블록을 **한 곳에서만** 만든다(재삽입·PoC 가 공유) |
| `build.check_font_generation` | 빌드 끝에 **이미지의 폰트 ↔ 지금 계획** 대조           |

둘 다 재현 검증했다 — 계획을 한 글자 바꾸면 지문이 어긋나고, 이미지 폰트를 1바이트 뒤집으면
`build.py` 가 세운다. 전량 manifest 는 여전히 YAGNI(소비자가 셋이고 전부 한 실행 안에 있다).

#### ✅ 자유 공간 판정 — 문제는 디스어셈블러가 아니었다

> _"A raw byte hit is not code evidence"_ — 바이트가 맞았다고 코드가 아니다.

우리 사고(2026-07-29, 효과음 파괴)를 다시 보니 **재귀 디스어셈블로도 못 잡는 부류**였다.
VAB 뱅크는 CPU 가 주소로 읽는 게 아니라 **통째로 SPU RAM 에 전송**된다 — 코드 도달성 분석에
안 걸린다. 그때 정한 새 기준은 _"자료구조 매직을 스캔해 알려진 블롭 내부가 아님을 먼저 확인"_
이었는데, **그 절차가 주석에만 있었다.** 안전 한계(`JOSA_SAFE`·`DATA_SAFE`)는 손으로 한 번
계산해 박은 매직 넘버였다.

주석의 레시피를 코드로 돌려 보니 두 상수를 **정확히 재현**했다 → `tools/vab.py` 로 옮기고
`patch_josa_hook.verify_safe_bounds` 가 매 빌드에 대조한다.

```
pBAV 뱅크 16개 · @0x0BEBB8 progs=1 → 파형 시작 0x0BF7D8 (= JOSA_SAFE)
기록된 금지 런 14개 중 파형 침범으로 확인 14 · 아닌 것 0
```

⚠ **교훈은 「디스어셈블러를 만들자」가 아니다** — _산문으로 적은 재검증 절차는 아무도 안 돌린다._

#### ✅ 인자 순서도 계약이다 (`fmt_order`)

mcpads `validate_translations` 의 _"소비자별 제어 토큰 **순서** 변경 차단"_ 을 보고 확인했더니
우리 게이트가 `%s`·`%d` 를 **개수만 따로** 세고 있었다. 엔진은 인자열을 스트림 순서로 소비하므로
`%s…%d` → `%d…%s` 면 **이름 자리에 수치**가 들어간다. 실측 섞인 블록 63개, 어긋난 건 0 —
사고는 없었지만 체인 순서를 뒤집는 배정 하나면 열린다. `fmt_order` 게이트를 넣었다.
⚠ `%c` 는 뺐다 — 꼬리 잘림 자리에서 종단을 더 내는 게 허용이라 순서 비교가 오탐이 된다.

⚠ **EDC/ECC 는 우리가 이미 갖고 있다**(`common.ecc_update`) — 새턴 `disc/edc_ecc.rs` 를 보고
확인했다. 뒤진 게 아니라 같은 결론에 따로 도달한 자리다.

## ⚠ 「정발에 짝이 없다」는 증명이 아니라 매처의 한계다 (번역 이식 일반)

- **상황**: 「대응 문안이 원본 로컬라이즈판에 없다」는 판정이 **여덟 번 틀렸다**(2026-08-09~11).
  전부 이웃이 무는 표만 보고 낸 결론이었다. 전투 문구에서만 네 번 연속 틀렸는데 원인이
  매번 달랐다 — 다른 파일에 있었다(SINDLL → MONDLL → ED1MAIN) · 같은 파일 안에서 낱말이
  갈려 있었다 · 인덱서 버그.
- **해결**: 「없다」고 적기 전에 **어간 한 낱말로 전 코퍼스를 훑는다**(`tools/find_text.py`).
  뜻으로 검색하면 못 찾는다. 찾은 자리가 **실제로 쓰이는지**(무는 블록이 있는지)와
  **시점 사본**을 나란히 본다(`--siblings`) — 사본마다 부호·표기가 다르다.
- **일반화**: 매처가 못 찾았다는 건 그 이상을 뜻하지 않는다. 부정 판정은 **전수 검색으로만**

- **날짜**: 2026-08-11

## ⚠ 유사도로 문안을 일괄 채택하려면 가드가 먼저다 (번역 이식 일반)

- **상황**: 원본 로컬라이즈판 문안을 유사도 0.70 으로 일괄 채택했다가 **조용히 망가진 것들**이
  나왔다. 유사도는 글자를 보지 뜻을 안 본다.

  | 증상                  | 무슨 일이 났나                           |
  | --------------------- | ---------------------------------------- |
  | 조사 중복             | 조사가 이미 있는 자리에 또 붙었다        |
  | 이름 접미 파괴        | 몬스터 개체 접미(`…C`)가 `…AC` 로 뭉갰다 |
  | 조사 소실 · 내용 손실 | 조각 경계를 잘못 잡아 앞뒤가 잘렸다      |
  | 제어바이트 유입       | 조각에 붙은 제어코드가 문안으로 들어갔다 |

- **해결**: 가드 다섯(**서식 · 이름 · 조사 · 이름표 · 손실**)을 반영 **전에** 건다. 조각
  구분자는 **0x20 미만 전부**로 잡는다(하나씩 열거하면 계속 샌다). 꼬리 말줄임·선두 조사·
  이스케이프는 조각에서 뗀다. ⚠ **선두 조사를 떼는 게 컸다** — 로컬라이즈판은 이름을 인자로
  주입하고 조사를 조각 앞에 두는데(`는 소멸했다`) 이식 대상에선 조사가 우리 몫이라, 떼고 나니
  그 자리들이 깨끗이 맞았다. 유사도는 높은데 뜻이 틀린 자리는 **부정 목록**으로 못 박는다
  (우리: `battle_deny.json` — ⚠ 사유는 우리 말로만 적는다, 원문을 적으면 저작권 규칙 위반).
- **⚠ 검증은 인게임이 아니라 파생값 전수 검산으로 한다.** 전투 문구는 **그 몬스터를 만나야**
  보여서 인게임 전수 확인이 불가능하다. 반영 때마다 옛 문안 ↔ 새 문안을 전량 대조하는 편이
  실제로 위 증상을 전부 잡아냈다.
- **날짜**: 2026-08-09 ~ 08-11

## ⚠ 「이상한 접두가 붙었다」는 대개 **한 바이트 밀림**이다 (SJIS·EUC 계열 일반)

가변폭 인코딩에서 앞 레코드의 꼬리 바이트 하나가 문자열 앞에 붙으면 **2바이트 짝이 통째로
밀려** 전혀 다른 글자로 읽힌다 — `ff` + `ギュード` 가 `сMュード` 로 읽혔다(PS1 ED2 몬스터
이름표 실측 2026-08-14).

증상이 「앞에 쓰레기가 붙었다」로 보이기 때문에 **접두를 잘라내는 쪽으로 가면 첫 글자를 같이
잃는다**(실제로 `ギ` 를 잃었다). 고치는 자리는 잘라내기가 아니라 **디코드**다 — 앞에서 한
바이트씩 떼며 다시 읽고, 가장 그럴듯한 해석을 고른다.

⚠ **첫 성공을 받으면 안 된다.** 밀린 해석도 「디코드 성공」이라 통과한다. 후보를 점수로
고른다 — 실측에서는 「끝자리 빼고 ASCII 가 섞이지 않은 쪽」 + 「덜 떼어낸 쪽」이 정답이었다.

이걸 고치자 세 이름이 한꺼번에 풀렸고, 「정발에만 있고 원판엔 없다」던 항목이 **원판에도
있었다**. 매칭이 안 되는 이유가 매칭 로직이 아니라 **디코드**에 있을 수 있다.

## emucap — `read_memory` 는 오프셋, `set_breakpoint` 는 논리 주소 (2026-08-16, PS1)

같은 서버의 두 API 가 **주소 체계를 다르게 받는다.**

- `read_memory(memory_type="ram", address=…)` — **오프셋**(0 ~ 2MB). RAM 0x80010000 은
  `address=0x10000`. 논리 주소를 주면 `bad_params` 로 죽는다.
- `set_breakpoint(memory_type="ram", start=…)` — **논리 CPU 주소**. RAM 0x80080000 은
  `start=0x80080000`. 오프셋을 주면 **에러 없이 조용히 아무것도 안 잡는다.**

⚠ **음성 결과가 조용히 거짓이 된다.** 오프셋으로 BP 를 걸면 「쓰기 0건」이 나오는데 그건
「안 쓴다」가 아니라 「안 봤다」다 — 자유 RAM 판정을 그걸로 내릴 뻔했다. **대조군을 먼저
걸어라**: 반드시 쓰이는 구간(예: 게임 워크램)에 같은 방식으로 걸어 이벤트가 나오는지
확인한 뒤에야 음성 결과를 믿는다.

## ⚠ 폰트를 갈아끼웠으면 「로마자니까 안 깨진다」가 틀린다 (2026-08-16, PS1·일반)

한자 슬롯 2,350칸을 한글로 덮고 렌더 폰트를 우리 것으로 리다이렉트하면, **그 렌더러가
그리는 2바이트 코드는 전부** 우리 폰트에서 글리프를 꺼낸다 — 한자든 가나든 **전각
로마자든** 상관없다. 슬롯 범위(0x889F~) 밖이라 안전하다고 판단한 자리가 실제로는 깨졌다:

- `ＧＭＦ`(개발사) → 화면엔 「일자인」
- `ＣＲＥＤＩＴＳ`(스태프롤 머리말) → 일곱 글자 잡소리

**진단이 두 번 틀렸다.** ① 「슬롯 코드 범위에 안 드니 안 깨진다」로 판정했다 — 범위가
아니라 **렌더 경로**를 봐야 했다. ② 원본 이미지를 읽고 「남은 원문 0」이라 결론냈다 —
빌드 산출물을 봐야 했다.

**게이트로 만드는 법.** 사문 테이블까지 훑으면 죽은 사본이 걸려 못 쓴다. 그래서
**이번 회차에 우리가 실제로 갱신한 포인터 자리**에서 표 구간을 유도하고, 그 표가
가리키는 문자열에 **우리 슬롯 밖 2바이트 코드**가 하나라도 있으면 빌드를 죽인다
(`patch_opening_font.patch_game`). 인게임 캡처 없이 잡힌다.

**곁가지 — 폰트 예산이 곧 어휘 예산이다.** 새 글리프 하나가 최대 32B고 압축 폰트는
안전 0런(4,203B)에 들어가야 한다. END1 은 내레이션이 59줄이라 여유가 26B뿐이었다 —
`SAL Laboratory` 를 그대로 못 쓰고 **이미 있는 음절로만** 문안을 골랐다(`살 연구소`).

## ⚠ emucap — `tap` 으로 프레임을 넘기면 브레이크포인트가 안 잡힌다 (2026-08-16, 일반)

BP 를 걸고 `tap`(입력 + 프레임 진행)으로 게임을 몰면 **이벤트가 하나도 안 쌓인다.**
같은 BP 가 `resume` 자유 실행에서는 정상으로 운다 — 실측: 예외 벡터(0x80000080)에
건 대조군이 `tap` 구간에서 0건, 자유 실행 12초에 **974건**.

그래서 화면을 보며 `tap` 으로 진행하다 「훅이 한 번도 안 돈다」는 음성 결과를 얻으면
**그건 측정이 죽은 것**이지 코드가 안 도는 게 아니다. 진행은 `input_control`
`pulse_while_running`(입력만 넣고 실행은 계속) 으로 하고, 관측은 자유 실행에서 한다.

⚠ **대조군이 너무 뜨거우면 조용한 BP 가 묻힌다.** 예외 벡터는 초당 수백 번 울려
큐를 넘긴다(4,096건 + **1,095건 유실**). 대조군으로 기구를 확인했으면 **떼고** 다시 잰다.

이 레포의 「대조군을 먼저 걸어라」(emucap 오프셋/논리주소 절)와 짝이다 — 그때는 주소
단위가 틀려서, 이번엔 실행 방식이 틀려서 같은 함정에 빠졌다.

## ⚠ emucap mednafen — read/write 워치포인트는 침묵한다, exec 만 신뢰 (2026-08-17, 일반)

이 어댑터 빌드(db58b40@mednafen-1.32.1)에서 **데이터 워치포인트(read/write)가 한 번도
울지 않았다.** sprintf 가 확실히 쓰는 버퍼(전투 로그 조립 버퍼)에 write BP 를 걸어도,
확실히 읽히는 파일 적재 구역에 read BP 를 걸어도 0건 — 물리(0x000F1718)·가상(0x800F1718)
표기 둘 다 시도했다. 같은 자리의 **exec BP 는 정상**으로 운다.

그래서 「누가 이 메모리를 읽나/쓰나」는 이 어댑터로는 못 잡는다. 대신:

- **읽는 쪽**: 소비 코드(그리기·조립 루틴)에 exec BP → 레지스터에서 소스 주소를 얻는다.
- **쓰는 쪽**: 정적으로 그 주소의 lui/addiu 상수를 전수 검색해 후보를 좁힌 뒤 exec BP.
- pause 없는 exec BP 는 히트마다 **레지스터 전체가 이벤트로 쌓인다** — 뜨거운 자리는
  이걸로 원샷 수집이 싸다(`poll_events` + `output_path`).

⚠ 곁들여: **주소 오산을 의심하라.** ED2MON 적재 주소를 0x149640 으로 잘못 계산해 놓고
「BP 가 안 잡히니 DMA 인가」로 반나절을 돌았다 — 실제로는 0x14A000 이었다. find_pattern
매치값을 hex 로 다시 확인하는 30초가 가설 하나를 통째로 아낀다.

## 일본어 유무 판정은 SJIS 런이 아니라 「어절 마커」로 (2026-08-18, 기종 정찰 일반)

SJIS 2바이트 런 정규식은 **랜덤 바이트에 속는다** — 포인터·압축 데이터가 한자로 디코드돼
"유효 일본어"로 잡힌다. PS1 ED3 씬 아카이브에서 런 404건이 잡혔는데 **전부 노이즈**였다
(慓·灸щ給щ 류). 이걸 믿으면 "생 텍스트가 있다"는 오진으로 착수 판단이 뒤집힌다.

- **판정은 실제 어절의 바이트열 카운트로**: です·ます·ました·という·こと·ない·して 를
  인코딩 후보(SJIS·EUC-JP·ISO-2022·UTF-16LE)별로 인코드해 `bytes.count()`. 마커 0 =
  커스텀 테이블 or 압축, 수백~수천 = 생 텍스트. 오탐이 사실상 없다.
- 문자열을 걸러야 할 때도 **가나 2자 이상 + 가나 비율**을 요구하면 랜덤 한자를 배제한다
  (한자만으로 된 짧은 런은 신뢰 불가).
- 부분문자열 재사용률은 **하한선**이다 — 같은 대상을 블록 축자 대조로 재면 90.8%→99.2%
  (새턴 ED1+2 실측). 비교엔 쓰되 절대값으로 읽지 말 것.

## HDI 는 배포물이 아니라 「설치 결과물」일 수 있다 — FAT 타임스탬프로 판별 (2026-08-18, PC-98 일반)

`pc98-ed2` 의 .hdi 를 열어 보니 **누군가 2018-07-29 에 MS-DOS 3.30 가상 하드를 만들어
게임을 설치한 것**이었다. 판별은 FAT 디렉터리 엔트리의 날짜가 해 준다 — 층이 갈린다:

| 층        | 날짜               | 예                                          |
| --------- | ------------------ | ------------------------------------------- |
| OS        | 1991-11-08         | IO.SYS · COMMAND.COM                        |
| 게임 원본 | 1992-06-20 ~ 07-03 | PROG.BZH · SCENA/* (원본 날짜로 복사됨)     |
| 설치 흔적 | 2018-07-29         | CONFIG.SYS · 전 디렉터리 · CFG · **세이브** |

- ⚠ 함정: 설치기가 **게임 데이터를 다시 쓰기도 한다** — `TEXT.BZH` 만 2018 날짜였다.
  "원본 날짜인 파일 = 원본"은 성립하지만 역은 파일별로 의심해야 한다.
- 설치본은 **원본 지문·패치 대상 부적격**(재설치마다 다른 이미지 = 비결정), 단
  **내용 대조용으로는 유효** — 다른 판과 바이트 대조로 자산의 무결성을 검증할 수 있다
  (만트라 ED2 와 301파일 동일 실측). 정본이 필요하면 배포 플로피(.d88)를 구한다.

## HxC MFM / KryoFlux 보존 덤프는 직접 디코드해서 쓴다 (2026-08-18, 레트로PC 일반)

FM-TOWNS 소장분이 `.mfm`(HxC) + `.raw`(KryoFlux 플럭스)로 왔다 — 에뮬레이터가 바로 먹는
이미지가 아니다. 변환기를 찾기 전에 **직접 디코드가 백 줄이면 된다**:

1. `HXCMFM` 헤더 → 트랙 수·면수·트랙 오프셋 테이블 (`<HBHHBI` @7, 엔트리 `<HBII`).
2. 트랙 비트스트림에서 **A1 싱크(0x4489, 클럭 결손)** 16비트 패턴을 검색.
3. `A1 A1 A1 FE` = ID 필드(C/H/R/N + CRC), `A1 A1 A1 FB` = 데이터 필드.
   MFM 디코드는 홀수 비트만 취하면 된다. **CRC16-CCITT(0xFFFF) 로 섹터를 검증**해
   통과분만 채택 — 조용한 비트 오류가 못 들어온다.
4. C/H/R 순으로 이어붙이면 플랫 이미지. (FM-TOWNS ED1+2: 1024B×8섹터×2면 2HD)

- **빈 트랙 12~14개는 정상**이다 — 80트랙 매체를 84실린더로 넉넉히 뜬 보존 덤프의 여백.
  결번 의심 전에 (전체 트랙 − 빈 트랙) × 면수가 매체 규격과 맞는지 본다.
- 디스크당 **한 트랙만 섹터 수·크기가 다른 것**(12~13섹터 혼합)도 보존 덤프의 특징 —
  프로텍트/라벨 트랙이다. 데이터 영역이 아니면 무시해도 된다.
- `.raw`(플럭스) 쪽은 **보존 마스터**로만 둔다 — MFM 이 CRC 전량 통과라면 쓸 일이 없고,
  용량만 수십 배다.
